# 8.1 故障排查：六个坏掉的工程

> **这一节你会做出**：拿到一个"代码每行都像对的"的坏工程，能用时钟、引脚、模式、数据四步，把毛病定位到一个具体的地方，并写出修复。
> **前置**：[[3.2_调试与排错]]，第 4 到 7 章　｜　**预计**：阅读 + 动手 90 分钟

> [!tip] 跳读自测：这一节你可能不用读
> 先回答下面几个问题（写下来，别只在心里答）。**全部答对**就直接跳到 [[8.2_ADC采集]]；有一题拿不准，就从头读。
> 1. 四步排查法的四步分别是什么？每一步各自在问什么？
> 2. 读代码找问题：下面的程序里 LED 的软件定时器永远不到点，`g_ms` 一直是 0。但你在调试器里看到 `htim6` 的计数器 `CNT` 一直在变。问题最可能在哪？
>    ```c
>    /* main() 里 */
>    HAL_TIM_Base_Start_IT(&htim6);
>    /* 回调也写对了：if (htim->Instance == TIM6) { g_ms++; } */
>    ```
> 3. 串口助手和程序里的波特率都是 115200，收到的却是乱码，而且 LED 的闪烁周期也不对。你先查四步里的哪一步？查什么？
> 4. ISR 里 `ticks++`，主循环里 `n = ticks; ticks = 0;`。这两行有什么问题？给一种修法。
>
> > [!success]- 答案，以及跳过后要带走的东西
> > 1. 时钟（这个外设有时钟吗？系统时钟是不是你以为的值？），引脚（对的引脚配成了对的功能吗？），模式（外设模式、极性、中断开关是不是你想的？），数据（送进去、读出来的值对吗？中间被谁改过？）。
> > 2. 中断没有放行。定时器自己在走，说明时钟和外设都没问题；`g_ms` 不变，说明中断没有进到回调。去 CubeMX 的 NVIC 页勾选 TIM6 的全局中断。
> > 3. 第一步，时钟。串口和 `HAL_Delay` 的时间都由时钟算出来，两个同时不对，多半是软件以为的时钟频率和真实不符（比如 `HSE_VALUE` 与晶振不一致）。用调试器看 `SystemCoreClock`。
> > 4. 读和清零之间，ISR 可能插进来加一，那一次计数就丢了。修法：只让 ISR 写 `ticks`，主循环自己记"上次的值"，用差值；或者把读和清零包在一个很短的关中断临界区里。
> >
> > **带走清单**：
> > - 排查顺序：时钟 → 引脚 → 模式 → 数据。每次只改一处，改完验证一次。
> > - 本节「速查表」：现象对应先查什么，打印出来贴在桌边。
> > - 代码：本节「开机自检」里的 `diag.h` 和 `diag.c`（提供 `boot_report()`，把软件认为的各路时钟打印出来），分别放进 `User/Inc` 和 `User/Src`，CMake 会自动收进构建，新增文件后重新配置一次（见 2.2）。依赖 3.1 的 `log.h`。在 `main.c` 里 `#include "diag.h"`，开机调用一次即可。

## 先看一个怪现象

半夜两点，灯不亮。你把灯泡检查了三遍，灯丝是好的。最后发现，是楼下的总闸没推上去。

单片机的故障大多长这样：你盯着的那一行代码没错，错在代码之外。你反复读 `HAL_GPIO_WritePin`，它当然对，可它写进去的那个外设根本没通电。

这一节有六个坏掉的工程。每一个都先给你症状和关键代码，你先猜问题出在哪一步，再翻开答案核对。有了前面七章的积累，你已经见过其中大部分零件，现在是让它们坏一次的时候。

## 怎么用这一节

排查就像查一间房子的灯：先看总闸推上去没有，再看线接到哪个插座，再看开关拨在哪一档，最后才看通过去的电对不对。这四步在单片机里有真名，就是你在 3.2 里学过的 **时钟 → 引脚 → 模式 → 数据**：

| 步骤 | 它在问什么 | 常用的查法 |
|---|---|---|
| ① 时钟 | 这个外设通电了吗？系统时钟是你以为的值吗？ | CubeMX 时钟树；调试器看 `SystemCoreClock`；寄存器视图里看外设时钟使能位 |
| ② 引脚 | 对的引脚，配成了对的功能吗？板子上真接到这个引脚了吗？ | 对照原理图；CubeMX 引脚图；示波器或万用表量波形 |
| ③ 模式 | 外设的工作模式、方向、极性、中断开关，是你想要的吗？ | 逐个字段读初始化代码；调试器看 `huartx`、`htimx` 里的字段 |
| ④ 数据 | 送进去的、读出来的值对吗？中途被谁改过？ | `LOG()` 打印；断点看变量 |

每个案子的节奏一样：

1. 先读**案情**，把你的第一怀疑写下来。
2. 展开**破案**，看证据怎么找、问题出在哪、怎么修。
3. 如果你的怀疑和答案不一样，回头想想是哪一条线索被你漏掉了。

## 动手做

### 案子 1：总闸没推上去

**案情**：你把 LED 搬到 PE5（4.2），这次不用 CubeMX 生成的 `MX_GPIO_Init`，自己手写一个。编译没有警告，下载成功，LED 不亮，万用表量 PE5，始终没有出现高电平。

```c
void led_init_bad(void)
{
    GPIO_InitTypeDef g = {0};
    g.Pin   = GPIO_PIN_5;
    g.Mode  = GPIO_MODE_OUTPUT_PP;
    g.Pull  = GPIO_NOPULL;
    g.Speed = GPIO_SPEED_FREQ_LOW;
    HAL_GPIO_Init(GPIOE, &g);                          /* 此时 GPIOE 没有时钟 */
    HAL_GPIO_WritePin(GPIOE, GPIO_PIN_5, GPIO_PIN_SET);
}
```

> [!question] 先猜一猜
> 代码里该有的步骤好像都有：配置模式，写高电平。嫌疑最大的是四步里的哪一步？你会用什么办法证明？

> [!success]- 破案
> 第一步，**时钟**。外设没有时钟的时候，写进它寄存器的值不会生效，`HAL_GPIO_Init` 也不会检查，所以不报错、不警告，一切像是成功了。
>
> **证据**：在 `HAL_GPIO_Init` 之后加一个断点，打开 Cortex-Debug 的外设面板（CORTEX PERIPHERALS，内容来自 `launch.json` 里 `svdFile` 指向的 SVD 文件，见 3.2），看 GPIOE 的 MODER，PE5 对应的两位应该是 01（输出），你会看到还是 00。再看 RCC 的 AHB1ENR，GPIOE 对应的使能位是 0。外设时钟关闭时寄存器写入无效，具体行为以参考手册为准。这两个位置怎么找，见[[【原理】寄存器与内存映射|寄存器与内存映射]]。
>
> **修复**：在配置之前开时钟。
>
> ```c
> void led_init_ok(void)
> {
>     GPIO_InitTypeDef g = {0};
>     __HAL_RCC_GPIOE_CLK_ENABLE();                      /* 第一步：时钟 */
>     g.Pin   = GPIO_PIN_5;
>     g.Mode  = GPIO_MODE_OUTPUT_PP;
>     g.Pull  = GPIO_NOPULL;
>     g.Speed = GPIO_SPEED_FREQ_LOW;
>     HAL_GPIO_Init(GPIOE, &g);
>     HAL_GPIO_WritePin(GPIOE, GPIO_PIN_5, GPIO_PIN_SET);
> }
> ```
>
> 用 CubeMX 生成的初始化不会犯这个错，它会替你写 `__HAL_RCC_GPIOE_CLK_ENABLE()`。手写、移植、改引脚的时候才要自己记住。

### 案子 2：线接错了插座

**案情**：你手写了串口 1 的引脚初始化，把它放到 PA9、PA10。程序在跑（LED 在闪），可串口助手一片空白，一个字节也没有。

```c
void uart1_pins_bad(void)
{
    GPIO_InitTypeDef g = {0};
    __HAL_RCC_GPIOA_CLK_ENABLE();
    g.Pin   = GPIO_PIN_9 | GPIO_PIN_10;
    g.Mode  = GPIO_MODE_AF_PP;
    g.Pull  = GPIO_PULLUP;
    g.Speed = GPIO_SPEED_FREQ_VERY_HIGH;
    /* g.Alternate 没填，保持 0 */
    HAL_GPIO_Init(GPIOA, &g);
}
```

> [!question] 先猜一猜
> LED 在闪，说明程序没跑飞，时钟也大概没问题。你接下来查哪一步？看到什么现象就能确认？

> [!success]- 破案
> 第二步，**引脚**。`GPIO_MODE_AF_PP` 只是说"这个引脚交给某个外设去驱动"，具体交给谁，要靠 `Alternate` 字段指明。它没填，保持初始化时的 0，也就是系统复用功能，不是 USART1。串口外设本身工作正常，只是它的 TX 信号没有连到这个引脚上。
>
> **证据**：用逻辑分析仪或示波器量 PA9，应该看到发数据时的跳变，实际一直是高电平。或者在 CORTEX PERIPHERALS 里看 GPIOA 的 AFRH，PA9 对应的 4 位应该是 7（USART1 在 F4 上的复用编号），实际是 0。复用到底怎么选中外设，见[[【原理】引脚复用机制|引脚复用机制]]。
>
> **修复**：补上 `Alternate`。
>
> ```c
> void uart1_pins_ok(void)
> {
>     GPIO_InitTypeDef g = {0};
>     __HAL_RCC_GPIOA_CLK_ENABLE();
>     g.Pin       = GPIO_PIN_9 | GPIO_PIN_10;
>     g.Mode      = GPIO_MODE_AF_PP;
>     g.Pull      = GPIO_PULLUP;
>     g.Speed     = GPIO_SPEED_FREQ_VERY_HIGH;
>     g.Alternate = GPIO_AF7_USART1;
>     HAL_GPIO_Init(GPIOA, &g);
> }
> ```
>
> 用 CubeMX 的人，对应的坑是：改了引脚，忘了重新生成代码，或者忽略了 4.2 里讲的复用冲突提示。看一眼引脚图里这个引脚上标的功能名是不是 `USART1_TX`，比读代码快。

### 案子 3：开关拨反了

**案情**：按键低电平有效，内部上拉（4.1）。你照着 4.1 的结构自己写了一份 `key.c`，下载之后，什么都没按，蜂鸣器自己"嘀"了一声；你把按键按下去，没动静；手一松，又"嘀"了一声。

```c
static uint8_t key_is_down(const key_obj_t *k)
{
    return HAL_GPIO_ReadPin(k->port, k->pin) == GPIO_PIN_SET;
}
```

> [!question] 先猜一猜
> 按键有反应，只是"按下"和"松开"对调了。这条现象说明前两步（时钟、引脚）怎么样？问题在后两步的哪里？

> [!success]- 破案
> 现象本身就是线索：按键有反应，只是反了，说明时钟和引脚都通了，问题在**模式**里的极性，也可以说是**数据**的解读。松开时上拉把引脚拉高，读到 `GPIO_PIN_SET`，函数却把它当成"按下"；所以上电 20 ms 后状态机就确认了一次"按下"，真按下去反而被当成"松开"，手一松又确认一次。
>
> **证据**：在主循环里打印 `HAL_GPIO_ReadPin` 的值，松开时是 1，按下时是 0。再对照原理图，确认按键是接地的。
>
> **修复**：4.1 把"极性"集中在 `key_is_down` 这一个函数里，所以只改这一处：
>
> ```c
> static uint8_t key_is_down(const key_obj_t *k)
> {
>     return HAL_GPIO_ReadPin(k->port, k->pin) == GPIO_PIN_RESET;
> }
> ```
>
> 这就是"极性只在一处"的好处：不用满工程找哪里写反了。LED 也是一样：你以为高电平亮，板子是低电平亮，灯就一直亮，写 1 反而灭。先读原理图，再决定是 `SET` 还是 `RESET`。

### 案子 4：电压不对

**案情**：你从一份能跑的例程里，把 `SystemClock_Config` 整个复制到自己的工程里，PLL 参数是对的。板子焊的是 8 MHz 晶振。下载之后，串口助手收到的全是乱码，波特率两边都是 115200。你还发现 `HAL_Delay(500)` 的 LED 闪烁周期明显比 0.5 秒长。

```c
/* stm32f4xx_hal_conf.h，没有改过 */
#if !defined (HSE_VALUE)
  #define HSE_VALUE    25000000U   /* 模板里的默认值 */
#endif
```

> [!question] 先猜一猜
> 串口和延时同时出问题。这两件事有什么共同的源头？你会先查四步里的哪一步，用什么办法看？

> [!success]- 破案
> 第一步，**时钟**，但这次不是"没开"，而是"软件以为的频率和真实的不一样"。PLL 寄存器写的是对的，芯片真的跑在 168 MHz；但 HAL 在计算 `SystemCoreClock` 时，用的是 `HSE_VALUE` 这个常量。晶振实际是 8 MHz，常量却写着 25 MHz，算出来的 `SystemCoreClock` 就是 168 MHz × 25 ÷ 8 = 525 MHz。
>
> 之后所有依赖它的东西都跟着错：SysTick 以为 1 ms 要数 525000 下，实际只有 168 MHz，每一"毫秒"变成了 3.125 ms，`HAL_Delay(500)` 要等约 1.56 秒；串口波特率分频是按 525 MHz 推算的，实际波特率只有约 36864（按此推算，以你的实测为准）。
>
> **证据**：用 Debug 构建，断点停住，在 WATCH 面板里看变量 `SystemCoreClock`。F407 的最高主频是 168 MHz，看到 525000000 立刻知道不对。串口乱码时 LOG 读不出来，所以这一步要靠调试器，不要靠打印。
>
> **修复**：让 `HSE_VALUE` 和实物一致：
>
> ```c
> #define HSE_VALUE    8000000U   /* 以你板子上晶振的标称频率为准 */
> ```
>
> 在 CubeMX 里，这个值来自时钟树页面里 HSE 的输入频率。建议用 CubeMX 生成，不要手工拼凑。时钟树怎么看，放在[[【原理】时钟树|时钟树]]。

### 案子 5：两个人抢着改同一本账

**案情**：ISR 每 1 ms 给计数器加一，主循环每隔一会儿把它"取走并清零"，累加到总数里。你让它跑了很久，发现总数总是比 `HAL_GetTick()` 小一点，而且越跑差得越多。每次单步调试都看不出毛病。

```c
void tim_isr_bad(void)          /* 假设每 1 ms 进一次 */
{
    ticks_bad++;
}

uint32_t take_ticks_bad(void)
{
    uint32_t n = ticks_bad;     /* 读 */
    ticks_bad = 0;              /* 清零：读和清零之间，ISR 可能插进来加了一 */
    return n;
}
```

注意：这里的 `ticks_bad` 是文件级的 `static` 变量，这是为了讲竞态的最小复现；真实代码按 5.4 的对象写法，计数放进对象里。

验证用的代码，把"主循环累计取走的数"和 HAL 自己的毫秒计数放在一起比：

```c
void report_ticks(void)
{
    static uint32_t total = 0;
    total += take_ticks_bad();                       /* 换成 take_ticks_ok() 再比一次 */
    LOG(LOG_INFO, "total=%lu hal_tick=%lu\r\n",
        (unsigned long)total, (unsigned long)HAL_GetTick());
}
```

> [!question] 先猜一猜
> 变量已经是 `volatile`，5.1 的规矩你遵守了。为什么还是丢计数？

> [!success]- 破案
> 这是第四步，**数据**。`volatile` 保证每次真的去读写内存，却不保证"读，再清零"这两步之间没有人插进来。中断可以在任意两条指令之间打断主循环：主循环刚把 `ticks` 读走，还没来得及清零，ISR 又加了一，随后清零把这一次抹掉了。这就是读改写冲突，原理见[[【原理】读改写与原子性|读改写与原子性]]。
>
> **证据**：这类毛病很难靠断点和单步抓住，因为那个缝只有几条指令那么窄，只是偶尔才被撞上。要靠统计：长时间运行，累计总数始终少于 `HAL_GetTick()`，而且差距在缓慢增大。
>
> **修复**，两种：
>
> 修法一，**单写者**：只有 ISR 写 `ticks`，主循环只读，自己记"上次的值"，用差值。从此没有人需要"清零"。
>
> ```c
> void tim_isr_ok(void)
> {
>     ticks_ok++;
> }
>
> uint32_t take_ticks_ok(void)
> {
>     static uint32_t last = 0;   /* 只有主循环用它 */
>     uint32_t now = ticks_ok;
>     uint32_t n = now - last;    /* 无符号相减，回绕也对 */
>     last = now;
>     return n;
> }
> ```
>
> 修法二，**关中断临界区**：把读和清零包进一个很短的关中断区间，并且保存、恢复原来的 PRIMASK，这样在已经关着中断的地方调用也不会误开。
>
> ```c
> uint32_t take_ticks_cs(void)
> {
>     uint32_t primask = __get_PRIMASK();
>     __disable_irq();
>     uint32_t n = ticks_bad;
>     ticks_bad = 0;
>     __set_PRIMASK(primask);
>     return n;
> }
> ```
>
> 优先选修法一，不需要关中断，也不会拖慢其他中断。多种安全做法的比较在 5.4。

### 案子 6：门铃没接线

**案情**：你按 5.2 的步骤配好了 TIM6，代码也抄了一遍，可 LED 的软件定时器从来不到点，`g_ms` 一直是 0。

```c
void tick_start(void)
{
    if (HAL_TIM_Base_Start_IT(&htim6) != HAL_OK) {
        Error_Handler();
    }
}

void HAL_TIM_PeriodElapsedCallback(TIM_HandleTypeDef *htim)
{
    if (htim->Instance == TIM6) {
        g_ms++;
    }
}

void tim6_probe(void)
{
    LOG(LOG_INFO, "tim6 cnt=%lu g_ms=%lu\r\n",
        (unsigned long)__HAL_TIM_GET_COUNTER(&htim6), (unsigned long)g_ms);
}
```

> [!question] 先猜一猜
> 启动函数、回调函数看上去都对。`tim6_probe()` 打印出来是 `tim6 cnt=37210 g_ms=0`（数字是示意），而且每次 `cnt` 都不同。结合这一点，故障在哪里？

> [!success]- 破案
> 定时器计数器 `cnt` 在变，说明时钟、定时器本身都没问题，毛病出在**中断路径**。一次中断要过三道门，缺一道都不会进到你的回调：
>
> | 第几道门 | 谁负责 | 怎么查 |
> |---|---|---|
> | ① 外设发出请求 | 外设里的中断使能位 | 启动用的是 `HAL_TIM_Base_Start_IT`，不是不带 `_IT` 的 `HAL_TIM_Base_Start` |
> | ② 中断控制器放行 | NVIC 里这条中断线的使能 | CubeMX 的 NVIC 页，勾选 TIM6 的全局中断（F407 上叫 TIM6 and DAC global interrupt） |
> | ③ 回调函数被找到 | 函数名与 HAL 头文件一字不差 | 拼写、大小写、参数 |
>
> 本案的原因是第②道门：NVIC 没有勾。第①道门你已经走过（用的是 `_IT`），第③道门的名字也没错。
>
> **证据**：除了 `cnt` 在变，最直接的办法是回 CubeMX 看 NVIC 页有没有勾；也可以在 CORTEX PERIPHERALS 里展开 NVIC，看这条中断对应的使能位（待核对面板里的叫法）。
>
> **修复**：在 CubeMX 里勾选，重新生成。不需要改任何一行代码。NVIC 在这里做了什么，见[[【原理】中断与NVIC|中断与 NVIC]]。

## 刚才发生了什么

六个案子，换成一张表，你会发现它们落在四步里：

| 案子 | 症状 | 卡在哪一步 | 一句话判据 | 对应章节 |
|---|---|---|---|---|
| 1 总闸 | 引脚毫无反应，不报错 | ① 时钟 | 外设没时钟，写进去的值留不下 | 2.2、4.2 |
| 2 插座 | 程序在跑，外设没输出 | ② 引脚 | 引脚没有复用给外设（Alternate） | 3.1、4.2 |
| 3 开关 | 现象整个反了 | ③ 模式 / ④ 数据 | 极性与实物不符 | 4.1 |
| 4 电压 | 串口乱码，延时不准 | ① 时钟 | 软件以为的频率与真实不符 | 2.2、3.1、5.2 |
| 5 抢账 | 偶发丢数据，难复现 | ④ 数据 | 读改写之间被中断插进来 | 5.1、5.4 |
| 6 门铃 | 定时器在走，回调不来 | ③ 模式 | 中断三道门缺一道 | 5.1、5.2 |

回头看，这六个案子有三个共同点。

**第一，毛病都在代码"之外"或"之间"**。没有一个是语法错误，没有一个会让编译器报警。所以靠读代码很难看出来，要靠证据：一次电压测量、一行 `LOG()`、调试器里的一个变量。

**第二，现象本身是线索**。案子 3 里"按键有反应，只是反了"，已经排除了前两步；案子 6 里"计数器在变"，已经排除了时钟。每多一条现象，嫌疑范围就缩小一圈。

**第三，每次只改一处**。改一处，验证一次。同时改三处，好了你也不知道是哪一处起了作用。

### 速查表

| 现象 | 先查什么 |
|---|---|
| 完全没反应，不报错 | 外设时钟开了吗？引脚功能配了吗（GPIO 还是复用）？共地了吗？ |
| 程序在跑，外设没输出 | 引脚复用（Alternate）对不对？示波器上有没有波形？ |
| 现象整个反过来 | 极性：按键高有效还是低有效？LED 高亮还是低亮？ |
| 串口乱码 | 先查时钟（`SystemCoreClock`、`HSE_VALUE`），再查波特率、TX/RX 有没有接反 |
| 定时器在走，回调不来 | 中断三道门：外设使能 `_IT`、NVIC 勾选、回调名字 |
| 偶尔丢数据、偶尔出错、难复现 | 共享变量：谁写、谁读、有没有"读完再改"的缝 |
| Debug 能跑、Release 就不对（或反过来） | 缺 `volatile`（5.1）；未定义行为；栈不够。Release 没有调试信息（`-g0`），先用 Debug 复现再查 |

### 开机自检

案子 4 和案子 1 都是时钟的事，而"软件以为的时钟"是最容易用一行日志验证的东西。建议每个工程都在开机时打印一次：

```c
/* User/Inc/diag.h */
#ifndef DIAG_H
#define DIAG_H

/* 开机自检：把软件认为的各路时钟打印出来，和 CubeMX 时钟树对一遍 */
void boot_report(void);

#endif /* DIAG_H */
```

```c
/* User/Src/diag.c */
#include "diag.h"
#include "main.h"
#include "log.h"

void boot_report(void)
{
    LOG(LOG_INFO, "sysclk=%lu hclk=%lu pclk1=%lu pclk2=%lu\r\n",
        (unsigned long)HAL_RCC_GetSysClockFreq(),
        (unsigned long)HAL_RCC_GetHCLKFreq(),
        (unsigned long)HAL_RCC_GetPCLK1Freq(),
        (unsigned long)HAL_RCC_GetPCLK2Freq());
}
```

这两个文件放进 `User/Inc` 和 `User/Src` 后，**重新配置一次 CMake**，顶层 `CMakeLists.txt` 里的 GLOB 就会把 `diag.c` 收进构建（见 2.2）。

在 `main.c` 的 `USER CODE BEGIN Includes` 区加 `#include "diag.h"`，在 `USER CODE BEGIN 2` 区，`log_init(&huart1)` 之后调用 `boot_report();`。你应该看到的数字和你的 CubeMX 时钟树完全一致，比如 CPU 168 MHz 的配置下，`sysclk` 和 `hclk` 是 168000000（以你的时钟树为准）。不一致，就先别看别的。

如果串口本身就是乱码（案子 4 的情况），这行日志读不出来，这时回到调试器看变量。

回到开头那盏不亮的灯。现在你知道了：先去推总闸，再看线，再看开关，最后才看电。盯着灯泡看三遍，不是认真，是顺序错了。

## 记住这几条

1. 出问题先按**时钟 → 引脚 → 模式 → 数据**走一遍，不要先怀疑编译器或芯片。
2. 每次只改一处，改完立刻验证。
3. 用最便宜的证据：一次 LED 翻转、一行 `LOG()`、一次电压测量、调试器里的一个变量。
4. 时钟是第一步，也最容易被忽视。工程开机时打印一次各路时钟，和时钟树对一遍。
5. 极性（高有效还是低有效）只在一个函数里说一次，别散落在各处。
6. 中断与主循环共享的数据，"读完再清零"是缝。优先用单写者，必要时才关中断。
7. 中断要过三道门：外设使能中断，NVIC 放行，回调名字与 HAL 头文件一字不差。

## 练习

1. 在自己的工程里故意制造案子 1、2、6 中的两个（比如删掉时钟使能、不勾 NVIC），然后装作不知道，按四步把它们找出来。最好找个朋友帮你制造。（复现）
2. 在你的工程里加上 `diag.h` / `diag.c` 和 `boot_report()`，把你板子"正常时"的各路时钟记在 README 里。以后遇到莫名其妙的时序问题，先看这一行。（改造）
3. 下面这段代码，TIM6 已经启动，NVIC 也勾了，`g_ms` 却不走，而且编译不报任何警告。为什么？先写下预测，再核对。（预测）
   ```c
   void HAL_TIM_PeriodElapsedCallBack(TIM_HandleTypeDef *htim)
   {
       if (htim->Instance == TIM6) {
           g_ms++;
       }
   }
   ```

> [!success]- 提示与答案方向
> 1. 记录你每一步看了什么、排除了什么，这就是你的排查日志。
> 2. 数字以你的时钟树为准。
> 3. 函数名里的 `Callback` 被写成了 `CallBack`，大小写不一致。HAL 里那个叫 `HAL_TIM_PeriodElapsedCallback` 的弱函数还在，没被覆盖；你写的是一个全新的、没人会调用的函数，编译和链接都正常。这是中断第③道门。函数名与参数以 HAL 头文件为准。
