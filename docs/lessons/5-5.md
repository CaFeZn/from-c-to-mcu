# 5.5 定时精度

> **这一节你会做出**：给板子装一把以 CPU 周期计时的"秒表"，分清 1 ms 节拍"不准"的三种原因，并能按症状选对工具和对策。
> **前置**：[[5.2_定时器与节拍]]、[[5.4_中断与主循环共享数据]]　｜　**预计**：阅读 + 动手 60 分钟

> [!tip] 跳读自测：这一节你可能不用读
> 先回答下面四个问题（写下来，别只在心里答）。**全部答对**就直接跳到 [[6.1_串口命令行]]；有一题拿不准，就从头读。
> 1. 下面的主循环，想让 `do_work()` 每 100 ms 执行一次，`do_work()` 本身要花约 5 ms。实际的执行周期是 100 ms 吗？该怎么改？
>    ```c
>    while (1) {
>        do_work();
>        HAL_Delay(100);
>    }
>    ```
> 2. `HAL_Delay(1)` 实际会等多久？
> 3. 一个 1 ms 节拍"长期偏快或偏慢"，另一个"平均是准的，但偶尔晚到"，各是哪一类问题？各自最先该查什么？
> 4. 在同一块板上，用 `DWT->CYCCNT` 去量 `g_ms` 节拍的间隔，能不能发现晶振本身偏了 1%？
>
> > [!success]- 答案，以及跳过后要带走的东西
> > 1. 不是。周期是"活 + 等待"，约 105 ms 以上，而且 `HAL_Delay` 本身还会多等不到 1 ms。改成按绝对时间到点：`soft_due(&t, 100u)`（5.2）。
> > 2. 在 1 ms 到 2 ms 之间。`HAL_Delay(n)` 会多等一个节拍，保证"至少"等够。
> > 3. 前者是时基本身的频率误差，先查时钟源和 CubeMX 里的晶振频率；后者是中断延迟造成的抖动，先查有没有长的中断或临界区。
> > 4. 不能。CPU 和定时器来自同一棵时钟树，一起偏，比值不变。要用外部的参照（示波器、逻辑分析仪、PC 的时钟）。
> >
> > **带走清单**：
> > - `timing.h` / `timing.c`：`dwt_init()`、`dwt_cycles()`、`dwt_to_us()` 是通用的周期秒表；`interval_t`（统计某个事件的间隔，每个事件建一个实例）和 `audit_t`（对账）是两个小对象。放 `User/Inc/timing.h` 和 `User/Src/timing.c`，后文需要量耗时时可以直接用。探针 `probe.h` / `probe.c` 只是实验，不用带走。
> > - 选时钟源的结论：要精度用外部晶振（HSE），并保证 CubeMX 里填的晶振频率与板上一致。
> > - 约定：统计这类带状态的东西，做成 `struct` 加以对象指针为首参的函数，不用全局变量。周期任务用绝对时间（`soft_due`），不要用"干活 + `HAL_Delay`"；关中断期间和中断里都不要调 `HAL_Delay`。
> > - 放在 `User/Inc`、`User/Src` 下的文件，CMake 会自动收进来；新增文件后重新配置一次（见 2.2）。
> > - 本节依赖 5.4 的 `User/Inc/critical.h`。

## 先看一个怪现象

5.2 里那台墙上的节拍器，号称一拍一毫秒。可乐队合奏乱掉，至少有三种办法：

节拍器自己走快了或走慢了；节拍器很准，但某个乐手总是晚半拍才听到；有人被叫去干别的事，漏听了好几拍。

对应到板子上，节拍器是**定时器的时钟**，乐手听到是**中断响应**，漏听的是**丢拍**。三种症状看上去都是"1 ms 不准"，查法和修法完全不同。

> [!question] 先猜一猜
> 假设 `g_ms` 数到 3,600,000，也就是号称过了一小时。拿手机秒表对比，差多少？分两种板子：
> ① 用外部晶振（常见精度是 ±20 ppm，也就是百万分之二十，具体以你的晶振规格书为准）
> ② 用芯片内部的 RC 振荡器（常温下大约 ±1%，随温度电压会更大，以数据手册为准（待核对））
> A. 都不到 1 秒　B. ① 不到 1 秒，② 几十秒　C. 都是几十秒　D. 都是几分钟

> [!success]- 揭晓
> 选 B。算一下：3600 s × 20 ppm = 3600 × 0.00002 = 0.072 s，约 72 ms，肉眼看不出。3600 s × 1% = 36 s，你对着秒表就能看出来。
> 同样是"1 ms 节拍"，换一种时钟源，误差差了几百倍。本节的头一件事，就是学会判断你的 1 ms 属于哪一种。

## 动手做

### 第一步：给板子装一把秒表

CPU 每走一个时钟周期，内核里有一个计数器就加一。如果能读它，就拿到一把分辨率为"一个 CPU 周期"的秒表：168 MHz 下，一个周期不到 6 ns。

它的真名叫 **DWT 的周期计数器**（寄存器名 `DWT->CYCCNT`）。用之前要先打开，代码很短：

新建 `User/Inc/timing.h`：

```c
#ifndef TIMING_H
#define TIMING_H

#include "main.h"

/* 打开 DWT 周期计数器。放在 main() 的 USER CODE BEGIN 2，越早越好 */
void dwt_init(void);

/* 读当前周期数。32 位，会回绕；两次读数无符号相减，就是中间经过的周期数 */
static inline uint32_t dwt_cycles(void)
{
    return DWT->CYCCNT;
}

/* 周期数换成微秒。用的是 SystemCoreClock，所以它必须是对的 */
uint32_t dwt_to_us(uint32_t cycles);

#endif /* TIMING_H */
```

新建 `User/Src/timing.c`：

```c
#include "timing.h"
#include "critical.h"    /* 5.4 的临界区 */
#include "log.h"             /* 3.1 的日志层。g_ms 来自 main.h（5.2） */

void dwt_init(void)
{
    /* 第一步：打开跟踪功能的总开关，DWT 才有电 */
    CoreDebug->DEMCR |= CoreDebug_DEMCR_TRCENA_Msk;
    /* 第二步：计数器清零 */
    DWT->CYCCNT = 0U;
    /* 第三步：打开周期计数器 */
    DWT->CTRL |= DWT_CTRL_CYCCNTENA_Msk;
}

uint32_t dwt_to_us(uint32_t cycles)
{
    /* 先升到 64 位再乘，否则 cycles * 1000000 很容易溢出 32 位 */
    return (uint32_t)(((uint64_t)cycles * 1000000ULL) / SystemCoreClock);
}

/* 周期数换成毫秒，给下面的演示用 */
static uint32_t cycles_to_ms(uint32_t cycles)
{
    return cycles / (SystemCoreClock / 1000U);
}
```

在 `main()` 的 `USER CODE BEGIN 2` 里，`log_init` 之后加一行 `dwt_init();`，再验证一下它真的在走：

```c
uint32_t c0 = dwt_cycles();
HAL_GPIO_TogglePin(LED_GPIO_Port, LED_Pin);
uint32_t c1 = dwt_cycles();
LOG(LOG_INFO, "toggle took %lu cycles\r\n", (unsigned long)(c1 - c0));
```

你应该看到 `took` 后面是个很小的数，但不是 0。如果是 0，说明计数器没打开，回头检查 `dwt_init()` 有没有被调到。

几件要留心的事：

- 这个计数器是 **32 位**的，会回绕。168 MHz 下 2^32 个周期约 25.6 秒，所以一次最多量约 25 秒。两次读数用**无符号减法**，回绕一次也是对的。
- 初始化写在你自己的代码里，别指望别人替你打开。F4 上不需要额外解锁，别的内核可能要（见分支）。
- 量的是**编译出来的代码**。换 CMake 的构建类型，Debug（`-O0 -g3`）和 Release（`-Os`）量到的数字会不一样（切换方法见 2.2），所以测耗时要在最终要用的构建类型下测。
- 周期换微秒用 `SystemCoreClock`，所以它得是对的。后面第六步会回头讲它什么时候不对。

### 第二步：HAL_Delay(1) 到底等多久

> [!question] 先猜一猜
> 连续调用 `HAL_Delay(1)` 五次，每次实际等待多久？
> A. 恰好 1000 µs　B. 0 到 1000 µs 之间　C. 1000 到 2000 µs 之间　D. 每次都在 2000 µs 附近

在 `timing.h` 的 `#endif` 之前加一行：

```c
void demo_hal_delay_1ms(void);   /* HAL_Delay(1) 到底等多久 */
```

在 `timing.c` 末尾追加：

```c
/* HAL_Delay(1) 到底等多久？连续量五次 */
void demo_hal_delay_1ms(void)
{
    for (int i = 0; i < 5; i++) {
        uint32_t c0 = DWT->CYCCNT;
        HAL_Delay(1U);
        uint32_t us = dwt_to_us(DWT->CYCCNT - c0);
        LOG(LOG_INFO, "HAL_Delay(1) took %lu us\r\n", (unsigned long)us);
    }
}
```

`main()` 里调用 `demo_hal_delay_1ms();`。你应该看到五行 `HAL_Delay(1) took ... us`，数字都落在 1000 到 2000 之间；因为每次返回时都刚过一个节拍边界，下一次又从边界附近出发，连续调用时多半都接近 2000。这是按规则推演的预期，板子上以你实际看到的为准。

> [!success]- 揭晓
> 选 C（连续调用时通常像 D）。HAL 里 `HAL_Delay` 的核心是这样的（你的 HAL 版本可能略有不同）：
> ```c
> wait += (uint32_t)(uwTickFreq);                 /* 多等一个节拍 */
> while ((HAL_GetTick() - tickstart) < wait) { }
> ```
> 为什么要多等一个节拍？调用 `HAL_Delay` 的时刻，落在两次节拍之间的哪个位置是随机的。如果不加这一个，最坏情况下它会比你要求的少等将近一个节拍。多加一个，换来的是"保证不会少"，代价是"最多多等一个节拍"。
> 所以 `HAL_Delay(n)` 的含义是：至少 n 毫秒，最多约 n + 1 毫秒。

### 第三步：周期任务，干活 + HAL_Delay 为什么会越拖越慢

在 `timing.h` 的 `#endif` 之前再加一行：

```c
void demo_period(void);          /* 周期任务的两种写法 */
```

在 `timing.c` 末尾追加：

```c
/* 假装每一轮要干 5 ms 的活 */
static void fake_work(void)
{
    HAL_Delay(5U);
}

/* 周期任务的两种写法，各跑 10 轮。目标：每轮 100 ms，总共 1000 ms */
void demo_period(void)
{
    /* 写法 A：干完活再 HAL_Delay(100)。每轮 = 活 + 等待 */
    uint32_t c0 = DWT->CYCCNT;
    for (int i = 0; i < 10; i++) {
        fake_work();
        HAL_Delay(100U);
    }
    uint32_t a_ms = cycles_to_ms(DWT->CYCCNT - c0);

    /* 写法 B：先定好每一轮的"绝对截止时刻"，活干多久都不影响下一轮的起点。
     * 这就是 5.2 里 soft_due() 的内核，这里展开写，是为了放进一个函数里量总时间 */
    c0 = DWT->CYCCNT;
    uint32_t next = g_ms + 100U;
    for (int i = 0; i < 10; i++) {
        fake_work();
        while ((int32_t)(g_ms - next) < 0) {
            /* 等到截止时刻。写成有符号差值，g_ms 回绕时也对 */
        }
        next += 100U;
    }
    uint32_t b_ms = cycles_to_ms(DWT->CYCCNT - c0);

    LOG(LOG_INFO, "[period] A=%lu ms, B=%lu ms (target 1000)\r\n",
        (unsigned long)a_ms, (unsigned long)b_ms);
}
```

> [!question] 先猜一猜
> 写法 A 每轮"干活 5 ms，再等 100 ms"；写法 B 每轮按绝对时刻到点。各跑 10 轮，目标都是 1000 ms。A 和 B 各会量到多少？

`main()` 里调用 `demo_period();`。你应该看到：

```
[period] A=10xx ms, B=100x ms (target 1000)
```

B 紧贴 1000，A 比 1000 大不少。A 的数字能推出来：它的"活"是 `HAL_Delay(5)`，实际约 6 ms，等待是 `HAL_Delay(100)`，实际约 101 ms，每轮约 107 ms，10 轮约 1070 ms。数字取决于第二步的规则，以你实际量到的为准。

> [!success]- 揭晓
> A 的毛病不在 `HAL_Delay` 不准，而在写法：每一轮的长度是"活 + 等待"，活干多久，周期就多长，误差还会一轮一轮累积。B 的写法是先定好每一轮的绝对截止时刻，活早点晚点完成，下一轮的起点不动。
> B 就是 5.2 里 `soft_due()` 的内核。实际写代码时直接用 `soft_due(&t, 100u)`，不需要手写。

### 第四步：量一量节拍的间隔

现在量 `g_ms` 这个 1 ms 节拍，相邻两次中断之间到底隔了多少个 CPU 周期。

这里换一种写法。统计要记住的东西不少：上一次的时刻、最短、最长、次数。如果写成一堆全局变量加几个函数，下次想给按键中断也统计一遍，就得把整套再抄一份。所以把它们装进一个 `struct`，操作都写成"第一个参数是这个 struct 的指针"的函数。这样的组合，叫**对象**；HAL 里的 `UART_HandleTypeDef huart1` 和 `HAL_UART_Transmit(&huart1, ...)` 就是同一个套路，你早就在用了。

在 `timing.h` 的 `#endif` 之前加上：

```c
/* 间隔统计对象：记录某个事件相邻两次发生之间隔了多少个 CPU 周期。
 * 状态全在对象里，同一份代码可以给 TIM6、按键中断、串口各建一个实例。 */
typedef struct {
    volatile uint32_t last;      /* 上一次事件的周期计数，只有 interval_mark 写 */
    volatile uint32_t min;
    volatile uint32_t max;
    volatile uint32_t n;
    volatile uint32_t primed;    /* 第一次只记时刻，不算间隔 */
} interval_t;

void interval_init(interval_t *iv);
void interval_mark(interval_t *iv);                 /* 只在中断里调用：事件发生了 */
void interval_report(interval_t *iv, const char *name, uint32_t ideal_cycles);
                                                    /* 主循环里调用：报告并清零重新统计 */
```

在 `timing.c` 末尾追加。注意这里有两个写者（ISR 记，主循环清零），所以用了 5.4 的临界区：

```c
/* ---------- 间隔统计 ---------- */

void interval_init(interval_t *iv)
{
    iv->last = 0U;
    iv->min = 0xFFFFFFFFUL;
    iv->max = 0U;
    iv->n = 0U;
    iv->primed = 0U;
}

void interval_mark(interval_t *iv)
{
    uint32_t now = DWT->CYCCNT;

    if (iv->primed != 0U) {
        uint32_t d = now - iv->last;      /* 无符号相减，回绕也对 */
        if (d < iv->min) {
            iv->min = d;
        }
        if (d > iv->max) {
            iv->max = d;
        }
        iv->n++;
    }
    iv->primed = 1U;
    iv->last = now;
}

void interval_report(interval_t *iv, const char *name, uint32_t ideal_cycles)
{
    /* 主循环既要读又要清零，ISR 也在写：有两个写者，所以用 5.4 的临界区 */
    uint32_t primask = irq_save();
    uint32_t mn = iv->min;
    uint32_t mx = iv->max;
    uint32_t n = iv->n;
    iv->min = 0xFFFFFFFFUL;
    iv->max = 0U;
    iv->n = 0U;
    irq_restore(primask);

    if (n == 0U) {
        LOG(LOG_WARN, "[%s] no sample\r\n", name);
        return;
    }
    LOG(LOG_INFO, "[%s] n=%lu min=%lu max=%lu cycles, ideal=%lu\r\n",
        name, (unsigned long)n, (unsigned long)mn, (unsigned long)mx,
        (unsigned long)ideal_cycles);
}
```

对象的实例放在 `main.c` 里，包含头文件，定义两个实例：

```c
/* USER CODE BEGIN Includes */
#include "log.h"        /* 3.1 */
#include "timing.h"
#include "probe.h"
/* USER CODE END Includes */
```

```c
/* USER CODE BEGIN PV */
static interval_t tick_iv;     /* 节拍间隔统计对象 */
static audit_t audit;          /* 对账对象 */
/* USER CODE END PV */
```

回调里加一行，把对象交给它：

```c
/* USER CODE BEGIN 4 */
void HAL_TIM_PeriodElapsedCallback(TIM_HandleTypeDef *htim)
{
    if (htim->Instance == TIM6) {
        g_ms++;                  /* 5.2 已有 */
        interval_mark(&tick_iv); /* 本节新增：节拍来了，记一笔 */
    }
}
/* USER CODE END 4 */
```

`main()` 里记得先 `interval_init(&tick_iv)`，再开定时器中断，主循环里每 2 秒调用一次 `interval_report(&tick_iv, "tick", SystemCoreClock / 1000U)`（完整的用户代码在第六步后一并给出）。你应该看到：

```
[tick] n=2000 min=xxxxxx max=xxxxxx cycles, ideal=168000
```

`ideal` 是理想间隔：`SystemCoreClock` 除以 1000。`n` 约 2000，`min` 和 `max` 紧紧围绕 `ideal`，只差很小的数。为什么还会差一点？定时器每拍是硬件数出来的，很准；但 CPU 进入中断的时刻会因为正在执行的指令、其他中断而有几个周期的出入。这就是**抖动**。

> [!failure] 猜想：min 和 max 一样大，说明节拍完美，没有任何问题
> 再看一眼：这把秒表和定时器是同一棵时钟树上的两条枝。如果整棵树都快了 1%，定时器每一拍还是"84,000 个定时器时钟"，CPU 周期也同比例变短，`min` 和 `max` 看上去照样围绕 `ideal`。这把秒表量得出"晃"，量不出"快慢"。后面第六步回来处理。

### 第五步：故意拉长临界区

5.4 说过，关中断期间中断进不来。现在拉长一次，亲眼看看后果。

新建 `User/Inc/probe.h`：

```c
#ifndef PROBE_H
#define PROBE_H

void probe_long_critical_section(void);

#endif /* PROBE_H */
```

新建 `User/Src/probe.c`：

```c
#include "main.h"
#include "critical.h"
#include "probe.h"

/* 故意关中断 3 ms，当作"一个写得太长的临界区" */
void probe_long_critical_section(void)
{
    uint32_t cycles_per_us = SystemCoreClock / 1000000U;
    uint32_t wait = 3000U * cycles_per_us;

    uint32_t primask = irq_save();
    uint32_t start = DWT->CYCCNT;
    while ((DWT->CYCCNT - start) < wait) {
        /* 空等。这期间所有中断都被挡在门外 */
    }
    irq_restore(primask);
}
```

再加上"对账"：用 CPU 周期折算出真实过去了多少毫秒，和 `g_ms` 数出来的对比。它也是一个小对象。在 `timing.h` 的 `#endif` 之前加上：

```c
/* 对账对象：记下开始时刻的 CPU 周期数和 g_ms，之后对比两者折算出的时间 */
typedef struct {
    uint32_t cyc0;
    uint32_t ms0;
} audit_t;

void audit_start(audit_t *a);
void audit_report(const audit_t *a);    /* 窗口要小于 25 秒 */
```

在 `timing.c` 末尾追加：

```c
/* ---------- 对账：g_ms 有没有丢拍 ---------- */

void audit_start(audit_t *a)
{
    /* 两个读数要取自同一时刻 */
    uint32_t primask = irq_save();
    a->cyc0 = DWT->CYCCNT;
    a->ms0 = g_ms;
    irq_restore(primask);
}

void audit_report(const audit_t *a)
{
    uint32_t primask = irq_save();
    uint32_t cyc = DWT->CYCCNT;
    uint32_t ms = g_ms;
    irq_restore(primask);

    uint32_t real_ms = cycles_to_ms(cyc - a->cyc0);
    uint32_t tick_ms = ms - a->ms0;
    LOG(LOG_INFO, "[audit] by_cycles=%lu ms, by_g_ms=%lu ms, lag=%ld ms\r\n",
        (unsigned long)real_ms, (unsigned long)tick_ms,
        (long)real_ms - (long)tick_ms);
}
```

> [!question] 先猜一猜
> 如果每 2 秒做一次 3 ms 的关中断，`[tick]` 那行的 `max` 和 `min` 会怎样？`[audit]` 那行的 `lag` 会怎样？
> 提示：3 ms 里，本来应该有 3 次节拍中断。

> [!success]- 揭晓
> `max` 会涨到约 3 个 `ideal`，因为那一次中断被推迟了 3 ms 才进来。`min` 会变得很小，因为 3 ms 结束后，被挡住的那一次中断一进来，下一拍马上又到了。
> 更要紧的是 `lag` 会一次次涨。被挡住的 3 次更新，只留下一个"有一次更新"的挂起标记，中断一次也只进来一次，`g_ms` 只加了一下，丢了约 2 到 3 拍。每个 2 秒窗口里做一次，`lag` 就多约 2 到 3 毫秒。这是推演的预期，以你实际看到的为准。
> 这个现象有名字：抖动不累积，**丢拍**会累积。

完整的用户代码在下一步给出。

### 第六步：量不出的那一半

前面所有办法，都是拿 CPU 周期当尺子，量的是同一棵时钟树上长出来的东西。树整体快慢，它量不出。要量快慢，需要一个**外部的参照**。三种常用办法，从粗到细：

- **手机秒表**：让串口每行都带 `g_ms`，对着秒表看一段时间。误差 1% 的话，10 分钟差约 6 秒，肉眼能看出；20 ppm 的差别，用秒表看不出来。
- **PC 的时间戳**：串口助手给每行加上 PC 的时间，跑得足够久再对比。精度受串口延迟影响，适合看出分钟级的偏差。
- **逻辑分析仪或示波器**：让一个引脚由 `soft_due` 每 500 ms 翻转一次，量它的周期。仪器自己的时钟比板子的准，这是最直接的办法。

确定偏了之后，处理的顺序是：

1. **先查 CubeMX 里填的晶振频率**。时钟树页面里 HSE 的输入频率，必须等于板上晶振外壳或原理图上标的数。填错了，PLL 算出来的所有频率都按同一个比例错：`SystemCoreClock` 是错的，上面的秒表折算是错的，串口波特率也是错的（115200 变成乱码，多半是这个原因）。这与 [[【原理】时钟树|时钟树]] 里的 PLL 公式有关。
2. 再看**用的是哪个时钟源**：

| 需求 | 选 |
|---|---|
| LED、按键、日志时间戳这类一般用途 | 外部晶振 HSE，经 PLL 倍频 |
| 不在乎精度，想省掉晶振 | 内部 RC（HSI），接受 ±1% 级别的误差（以数据手册为准） |
| 长时间走时（小时、天），或要掉电后继续走 | RTC 配 32.768 kHz 晶振（LSE） |
| 串口、CAN 这类通信 | 外部晶振。通信对时钟容差有要求，CAN 比串口更严，7.x 里再说 |

最后把前面所有的用户代码拼起来。`main()` 里：

```c
/* USER CODE BEGIN 2 */
uint32_t t_report;
uint32_t t_pin;
log_init(&huart1);                 /* 3.1：已经加过就不要重复 */
dwt_init();                        /* 本节新增：先开秒表 */
interval_init(&tick_iv);           /* 先把对象初始化好，再开中断 */
HAL_TIM_Base_Start_IT(&htim6);     /* 5.2：已经写过就不要重复 */

demo_hal_delay_1ms();
demo_period();

audit_start(&audit);               /* 从这一刻开始对账 */
t_report = g_ms;
t_pin = g_ms;
/* USER CODE END 2 */
```

```c
/* USER CODE BEGIN 3 */
if (soft_due(&t_report, 2000u)) {  /* 每 2 秒一次 */
    interval_report(&tick_iv, "tick", SystemCoreClock / 1000U);
    audit_report(&audit);          /* g_ms 有没有落后 */
    probe_long_critical_section(); /* 第五步才加这一行 */
}
if (soft_due(&t_pin, 500u)) {      /* 第六步：用软件定时器翻转一个引脚，拿去量 */
    HAL_GPIO_TogglePin(LED_GPIO_Port, LED_Pin);
}
/* USER CODE END 3 */
```

按 5.2 的契约，`g_ms` 在 `main.h` 里声明，`soft_due()` 在 `main.c` 的 `USER CODE 0` 区，这里直接用。

> [!note] 5.2 留下的问题：g_ms 和 HAL_GetTick() 什么时候不一致
> 它们由两个不同的中断推进（TIM6 和 SysTick）。像第五步那样关中断，两个都停。但如果拖住 CPU 的是一个优先级介于两者之间的长中断，一个会照常走，一个丢拍，两者就分家了。所以遇到时间对不上时，别先怀疑哪个"不准"，先看是谁被挡住了。

## 刚才发生了什么

三种"1 ms 不准"，现在有了真名：

| 症状 | 比喻 | 真名 | 常见原因 | 怎么查 | 怎么办 |
|---|---|---|---|---|---|
| 长期偏快或偏慢，比例固定 | 节拍器自己走快了 | **频率误差** | HSI；晶振精度；CubeMX 晶振频率填错 | 外部参照（秒表、逻辑分析仪） | 换 HSE；核对时钟树；长期走时用 RTC |
| 平均准，偶尔晚到，不累积 | 乐手晚半拍听到 | **抖动**（来自中断延迟） | 被别的中断或临界区拖后 | `interval_report()` 看 min/max | 缩短 ISR 和临界区；调整优先级 |
| 越跑越慢，不规则 | 漏听了几拍 | **丢拍** | 中断被挡的时间超过一个节拍，几次合成一次 | `audit_report()` 对账 | 同上；需要精确时长时，别数中断次数，读一个自由运行的计数器做差 |

最后一格值得多说一句。`g_ms` 是靠"数中断次数"累加出来的，丢一次就少一拍，而且永远补不回来。一个自由运行的硬件计数器（比如本节的 `DWT->CYCCNT`）不依赖中断，读两次相减，得到的是真实经过的时间。精度要求高的计时，用后者。

还有第四类，不属于硬件：**用法**。`HAL_Delay` 多等一个节拍，"活 + 等待"会累积周期，这些不是时钟的错，是写法的错。

最后，`HAL_Delay` 和 `HAL_GetTick()` 靠 [[【原理】SysTick与HAL时基|SysTick]] 中断推进。中断被关了，或者你身处一个优先级不低于 SysTick 的中断里，时间不走，`HAL_Delay` 就永远等不到，程序卡死。这是 5.4 练习 3 的答案的另一半。

## 记住这几条

1. 先判类型再动手：长期偏快慢，查时钟源；偶尔晃，查中断延迟；越跑越慢且不规则，查丢拍。
2. `HAL_Delay(n)` 实际在 n 到 n + 1 毫秒之间，且期间 CPU 原地等待。它不是精确延时，也不要在中断里或关中断时调用。
3. 周期任务一律按绝对时间到点（`soft_due`），不要写成"干活 + `HAL_Delay`"。
4. 要精度就用外部晶振，并保证 CubeMX 里填的晶振频率与板上一致；长期走时用 RTC 加 32.768 kHz 晶振。
5. 用 `DWT->CYCCNT` 量耗时：先 `dwt_init()`，差值用无符号减法，单次最多量约 25 秒（168 MHz）。
6. 同一棵时钟树量同一棵时钟树，量不出整体快慢，需要外部参照。
7. 需要精确时长，别靠数中断次数，读自由运行的计数器做差。

## 练习

1. **复现**：把 `probe_long_critical_section()` 里的 3000 改成 500，再改成 1500，各跑一次。`max` 和 `lag` 各怎样变化？
2. **改造**：再建一个 `interval_t` 实例，用在按键中断上：`HAL_GPIO_EXTI_Callback` 里调用 `interval_mark()`，主循环里报告。按几下，看两次中断之间的最短间隔。不需要改 `timing.c` 的任何一行。
3. **预测**：假设 CPU 为 168 MHz，下面这段读到的 `d` 大约是多少个周期？折合多少秒？先写下预测再试。
   ```c
   uint32_t t0 = dwt_cycles();
   HAL_Delay(30000U);
   uint32_t d = dwt_cycles() - t0;
   ```

> [!success]- 提示与答案方向
> 1. 500 µs：不到一个节拍，最多一次中断被推迟，不会合并，`max` 变大，`lag` 基本不涨。1500 µs：中间可能夹着一个或两个节拍边界，两个时就合成一次，`lag` 开始涨。临界区短过一个节拍，只造成抖动；长过，才开始丢拍。
> 2. 新增 `static interval_t key_iv;`，`interval_init(&key_iv)` 一次，回调里 `interval_mark(&key_iv)`，主循环里 `interval_report(&key_iv, "key", 0U)`。同一份代码，两个实例，各记各的。如果按一次键，`min` 却特别小，说明一次按下触发了多次中断，那是按键抖动（4.1）。
> 3. 30 秒是 30 × 168,000,000 = 5,040,000,000 个周期，超过 2^32 = 4,294,967,296，回绕一次，`d` 约 745,032,704 个周期（再加上 `HAL_Delay` 多等的不到 1 ms），折合约 4.4 秒。量的东西超过 25.6 秒，结果就是错的，而且错得看不出来。

回到开头：节拍器快慢、乐手晚听、漏听。现在遇到"我的 1 ms 不准"，你不用猜了。先看是哪一种：用外部参照看快慢，用 min/max 看抖动，用对账看丢拍。每一种，都有对应的下一步。
