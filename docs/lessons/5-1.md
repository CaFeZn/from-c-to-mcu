# 5.1 中断入门

> **这一节你会做出**：用按键中断翻转 LED；亲手撞见"优化一开，程序就卡死"，并说清为什么加一个 `volatile` 就能救。
> **前置**：[[4.1_GPIO点灯按键蜂鸣器]]、[[3.2_调试与排错]]　｜　**预计**：阅读 + 动手 60 分钟

> [!tip] 跳读自测：这一节你可能不用读
> 先回答下面几个问题（写下来，别只在心里答）。**全部答对**就直接跳到 [[5.2_定时器与节拍]]；有一题拿不准，就从头读。
> 1. 读代码找问题：下面的程序在 Debug 构建（`-O0 -g3`）下按键后能继续往下走，在 Release 构建（`-Os -g0`）下却卡死。原因是什么？怎么改？
>    ```c
>    static uint8_t done = 0;
>    void HAL_GPIO_EXTI_Callback(uint16_t GPIO_Pin) { (void)GPIO_Pin; done = 1; }
>    /* main 里：*/
>    while (done == 0) { }
>    ```
> 2. 能不能在 `HAL_GPIO_EXTI_Callback` 里调用 `HAL_Delay(20)` 做消抖？为什么？
> 3. 下降沿触发的按键中断，一次干脆的按压，回调一定只被调用一次吗？
> 4. `volatile` 保证了什么，没有保证什么？
>
> > [!success]- 答案，以及跳过后要带走的东西
> > 1. 编译器在代码里看不到有人修改 `done`（回调是硬件触发的，不是哪行 C 代码调用的），就把读取挪到循环外，只读一次。改成 `static volatile uint8_t done`。
> > 2. 不能。`HAL_Delay` 要等 SysTick 让计数前进，ISR 里如果优先级不比 SysTick 高，计数不走，会永远等下去。ISR 本身也该尽可能短。
> > 3. 不一定。按键抖动会产生多个下降沿，回调可能被调用多次，所以中断版也要消抖。
> > 4. 保证每次访问都真的读写内存，不会被优化掉或合并。没有保证"一步完成"（原子性），多个变量一起读写也没有保证，这是 5.4 的内容。
> >
> > **带走清单**：
> > - CubeMX 配置：按键引脚设为 EXTI，下降沿触发，上拉，在 NVIC 页勾选对应中断。
> > - 套路：**flag + volatile 模式**，ISR（回调）里只置标志，主循环里检测并处理。模板见本节 [[#flag + volatile 模式]]，5.2 起会反复用到。
> > - 回调写法：重写 `void HAL_GPIO_EXTI_Callback(uint16_t GPIO_Pin)`，先判断 `GPIO_Pin`；不要自己清中断标志。
> > - ISR 规矩：短、不阻塞、不调 `HAL_Delay`、不输出日志。
> > - 构建类型：Debug 是 `-O0 -g3`，Release 是 `-Os -g0`（定义在工具链文件里，见 2.2）。同一份代码在两者之间表现不同时，先怀疑缺 `volatile`。Release 没有调试信息，调试器按变量名看不到变量，需要时在 `CMakeLists.txt` 里临时追加 `-g3`（做法见本节「第三步」）。

## 先看一个怪现象

等人来访，有两种办法。第一种，每隔一分钟跑到门口看一眼。第二种，装个门铃，平时干自己的事，铃响了再去。

门铃显然好。可是，这个剧组里还有一位导演，他只看剧本，不看现场。剧本里没有一句台词写着"门铃响了"，于是他自作主张：门口那张便条，看一遍就够了，不用每次都去。

结果门铃响了一百次，屋里的人始终没有动。

先从第一种办法的毛病说起。

> [!question] 先猜一猜
> 下面这段代码让 LED 每秒翻转一次，翻转之后检查一次按键，按下就切换蜂鸣器。你在 LED 翻转的间隙里**点一下按键**（按下到松开约十分之一秒），蜂鸣器会响吗？
>
> ```c
> /* USER CODE BEGIN 3 */
> HAL_GPIO_TogglePin(LED_GPIO_Port, LED_Pin);
> HAL_Delay(1000);                       /* 睡 1 秒，期间谁也不看 */
> if (HAL_GPIO_ReadPin(KEY_GPIO_Port, KEY_Pin) == GPIO_PIN_RESET) {
>     HAL_GPIO_TogglePin(BUZZER_GPIO_Port, BUZZER_Pin);
> }
> /* USER CODE END 3 */
> ```

> [!success]- 揭晓
> 大多数时候不会。主循环一圈要睡一秒，只有睡醒后读按键的那一瞬间，才有机会看到"按着"。你的手指一按一松，只占一秒里的十分之一，十次里大概有九次会错过。这就是 4.1 里说的轮询的代价：它只在自己想看的时候看。
> 解决办法就是门铃：让按键自己来喊 CPU，不管 CPU 当时在干什么。

### 第一步：在 CubeMX 里配外部中断

1. 在 Pinout 视图里，把按键引脚从 GPIO_Input 改成 `GPIO_EXTI0`（后面的数字是这个引脚的编号，PA0 对应 0，PA1 对应 1，以此类推，以你的引脚为准）。
2. 在 GPIO 配置页，把 GPIO mode 设成 External Interrupt Mode with Falling edge trigger detection（下降沿触发）。按键按下是从高变低，正好是下降沿。Pull 保持 Pull-up。
3. 在 NVIC 配置页，勾选这个引脚对应的 EXTI line 中断（比如 EXTI line0 interrupt）。
4. 重新生成代码。

有两个小规矩，现在知道，以后少踩坑：

- **同一个编号只有一条中断线**。PA0 和 PB0 的编号都是 0，它们共用 EXTI0，同一时刻只能有一个用作外部中断。
- 编号 5 到 9、10 到 15 的引脚是**几个引脚共用一个中断入口**。进了入口之后，要靠回调函数的参数判断是哪个引脚。

生成之后，打开 `stm32f4xx_it.c`，你会找到 CubeMX 替你写好的这个函数。按 PA0 举例：

```c
void EXTI0_IRQHandler(void)
{
  /* USER CODE BEGIN EXTI0_IRQn 0 */

  /* USER CODE END EXTI0_IRQn 0 */
  HAL_GPIO_EXTI_IRQHandler(KEY_Pin);
  /* USER CODE BEGIN EXTI0_IRQn 1 */

  /* USER CODE END EXTI0_IRQn 1 */
}
```

这个函数的名字是固定的，由芯片的启动文件决定，不要改。它里面调用的 `HAL_GPIO_EXTI_IRQHandler` 会先替你把"中断已处理"的标记清掉，再调用一个叫 `HAL_GPIO_EXTI_Callback` 的函数。这个函数在 HAL 里是一个"空壳"，等着你来重写。

### 第二步：写最简单的版本，等一次按键

第一版故意写得最朴素：回调里把一个标志置 1，主程序在开机后等这个标志。**注意，先不加 volatile。** 这是故意的。

```c
/* USER CODE BEGIN Includes */
#include "log.h"
/* USER CODE END Includes */

/* USER CODE BEGIN PV */
static uint8_t key_flag = 0;
/* USER CODE END PV */

/* USER CODE BEGIN 4 */
void HAL_GPIO_EXTI_Callback(uint16_t GPIO_Pin)
{
    if (GPIO_Pin == KEY_Pin) {
        key_flag = 1;
    }
}
/* USER CODE END 4 */

/* main() 里，MX_..._Init 之后、while (1) 之前 */
/* USER CODE BEGIN 2 */
LOG(LOG_INFO, "waiting for key...\r\n");
while (key_flag == 0) {
    /* 空等 */
}
LOG(LOG_INFO, "key pressed\r\n");
/* USER CODE END 2 */
```

先用 **Debug** 构建类型：在 VS Code 的 CMake Tools 里选 Debug 的 preset，或者命令行 `cmake --preset debug`（preset 的名字以 CubeMX 实际生成的为准）。它给编译器的选项是 `-O0 -g3`：不优化，带完整调试信息。这两组选项写在工具链文件 `cmake/gcc-arm-none-eabi.cmake` 里（见 2.2）。

构建，下载，打开串口助手。

> [!example] 你应该看到什么
> 串口先出现 `waiting for key...`。按一下按键，再出现 `key pressed`。

一切正常。现在是这一节的重头戏。

### 第三步：切到 Release

> [!question] 先猜一猜
> 代码一个字都不改，只把构建类型从 Debug 切到 **Release**（编译选项变成 `-Os -g0`，优化体积），重新构建、下载。按键以后会怎样？
> A. 和以前一样　B. 串口停在 waiting，永远不出 key pressed　C. 编译就报错

先在心里选好，然后动手试。

> [!success]- 揭晓
> 按我们对这段代码的分析，答案是 B。你应该看到：串口停在 `waiting for key...`，无论按多少次键，都没有 `key pressed`。
> 同一份代码，同一块板子，同一个按键，只因为构建类型不同，行为变了。不同的编译器版本表现可能不一样，如果你的没有卡住，看本节的练习 1。

遇到"无优化能跑、优化就不行"的程序，千万别马上怀疑硬件。我们做个排查，用 3.2 里学过的调试器。

先解决一个小麻烦。Release 的 `-g0` 表示不带调试信息，调试器里按名字看不到 `key_flag`。临时在顶层 `CMakeLists.txt` 的末尾加一行，让 Release 也带上：

```cmake
# 临时实验：让 Release 也带调试信息。用完删掉
target_compile_options(${CMAKE_PROJECT_NAME} PRIVATE -g3)
```

保存后重新配置、构建。这一行排在 Release 自带的 `-g0` 后面，后面的生效。我在本机用 CubeCLT 里的 CMake 3.28.1 和 arm-none-eabi-gcc 12.3.1 试过：不加这一行，目标文件里没有调试信息；加了就有。

> [!failure] 猜想 1：中断根本没有触发
> 如果中断没触发，`key_flag` 应该一直是 0。在 VS Code 调试界面的 WATCH 面板里看 `key_flag`，按键之后你应该看到它是 **1**。划掉：中断触发了，回调也跑了。

> [!failure] 猜想 2：按键或接线有问题
> 同一块板子，Debug 构建下一切正常。划掉。

> [!question] 那么问题在哪？
> 变量已经变成 1 了，可程序没有往下走。再用调试器暂停程序，看它停在哪里。你应该看到：它停在等待循环里，而且不管你怎么让它继续运行，都出不来。
> 既然内存里的值是 1，循环又在读这个值，它为什么看不见？

我们不猜，直接看编译器干了什么。下面这段汇编，是我用 CubeCLT 里的 CMake 3.28.1 和 arm-none-eabi-gcc 12.3.1，分别按 Debug 和 Release 构建**同一份**等待代码，再用 `arm-none-eabi-objdump -d` 反汇编得到的，只截取等待那一部分（你的编译器版本不同，指令会有差别）：

> [!example] Debug 与 Release 的区别（我这台机器上的结果）
> **Debug（`-O0 -g3`）**：
> ```
>  e:  ldr   r3, [pc, #24]    @ 取 key_flag 的地址
> 10:  ldrb  r3, [r3, #0]     @ 读 key_flag 的值
> 12:  cmp   r3, #0
> 14:  beq.n e                @ 是 0 就回到 e，重新取地址、重新读
> ```
> **Release（`-Os -g0`）**：
> ```
>  a:  ldr   r3, [pc, #24]    @ 取 key_flag 的地址
>  c:  ldrb  r3, [r3, #0]     @ 只读这一次
>  e:  cbnz  r3, 12           @ 非 0 就往下走
> 10:  b.n   10               @ 是 0 就在这里原地跳自己，永远
> ```
> 读不懂汇编没关系，看结构：Debug 的循环**每圈都回去重新读内存**；Release 的循环**只在循环前读了一次**，之后只是原地打转。
> 我另外用 gcc 的 -O0、-Og、-O1、-O2、-Os 逐个编译过：-O0 和 -Og 每圈重读，-O1、-O2、-Os 只读一次（-O3 没有试）。两个构建类型只覆盖了 -O0 和 -Os，想亲眼看 -O2，见练习 1。

所以真相是：**编译器把读取挪到了循环外面**。它的推理很合理：循环里没有任何一行代码修改 `key_flag`，那它的值在循环期间就不会变，读一次就够。这不是编译器的 bug。你选的 Debug 或 Release，背后就是在对工具链里的编译器（这里是 arm-none-eabi-gcc，在电脑上编译、给 ARM 单片机用的[[【原理】交叉编译与工具链|交叉编译器]]）说"优化到什么程度"：Debug 传 `-O0 -g3`，Release 传 `-Os -g0`。优化越狠，它越敢做这类"我觉得没必要"的改动。

### 第四步：探针，什么能救它，什么只是碰巧

**探针 A**：在等待循环里加一句 `HAL_Delay(1);`，保持 Release，再试。

我在 Release 构建下反汇编检查过，这样改以后，编译器在每次 `HAL_Delay` 之后会重新读 `key_flag`，程序能正常响应。

那是不是说明问题解决了？不是。这个改动能"救"它，仅仅因为编译器看到一次它没法看透的函数调用，不敢断定变量没变，于是被迫重新读。这是**碰巧**，不是保证。编译器看得越透（比如换版本、开更激进的跨文件优化），这个碰巧越容易失效。

**探针 B**：去掉探针 A，给变量加上 `volatile`：

```c
static volatile uint8_t key_flag = 0;
```

保持 Release，再试。我反汇编检查过，加了 `volatile` 以后，Release 构建下的等待循环每圈都重新读内存，按键就能正常响应。

`volatile` 的意思是告诉编译器：这个变量**可能在你看不见的地方被改动**，所以每次用它，都必须真的去内存里读，每次写它，都必须真的写进去，不许省。

### 第五步：把按键真正做成产品

等待版只能用一次。真正的用法是：中断里只做最少的事，主循环有空时再处理。同时，别忘了按键会抖。

> [!question] 先猜一猜
> 用下降沿触发的中断，你**干脆地按一次**，回调函数会被调用几次？

> [!success]- 揭晓
> 可能不止一次。按键按下的那几毫秒里，电平会抖，每一次从高掉到低，都是一个下降沿，都会触发一次中断。具体几次和你的按键有关，有的按键很干净，你需要多按几次才能撞上。
> 4.1 里你用主循环轮询加状态机消抖。中断版有一个更省事的思路：**ISR 只负责记下"有边沿来过"和"什么时候来的"，主循环等这段时间安静了，再回头读一次引脚确认。**

这样做还有个好处：松开按键时的抖动也可能产生下降沿，主循环确认时发现引脚已经是高电平，就会把它丢掉。

完整代码（用户代码放在对应的 `USER CODE` 区）：

```c
/* USER CODE BEGIN PV */
#define KEY_QUIET_MS  20U                  /* 最后一次边沿之后，安静多久才确认 */

static volatile uint8_t  key_edge = 0;     /* ISR 置 1，主循环清 0 */
static volatile uint32_t key_edge_tick = 0;/* 最近一次边沿的时刻（ms） */
static volatile uint32_t isr_count = 0;    /* 观察用：进了几次中断 */
/* USER CODE END PV */

/* USER CODE BEGIN 4 */
void HAL_GPIO_EXTI_Callback(uint16_t GPIO_Pin)
{
    if (GPIO_Pin == KEY_Pin) {             /* 多个引脚共用同一个回调，先认人 */
        key_edge_tick = HAL_GetTick();     /* 只读一个计数器，不会阻塞 */
        key_edge = 1;
        isr_count++;
    }
}
/* USER CODE END 4 */

/* main() 的 while (1) 里 */
    /* USER CODE BEGIN 3 */
    if (key_edge && (HAL_GetTick() - key_edge_tick >= KEY_QUIET_MS)) {
        key_edge = 0;
        if (HAL_GPIO_ReadPin(KEY_GPIO_Port, KEY_Pin) == GPIO_PIN_RESET) {
            HAL_GPIO_TogglePin(LED_GPIO_Port, LED_Pin);
            LOG(LOG_INFO, "key down, isr_count=%lu\r\n", (unsigned long)isr_count);
        }
    }
    /* USER CODE END 3 */
```

`isr_count` 是为了观察而加的。每次按键，串口会打印一行，两行之间 `isr_count` 的差值，就是这一次按压里进了几次中断。

> [!example] 你应该看到什么
> 每按一次，LED 翻转一次，串口一行，且只有一行。`isr_count` 每次增加的数大于等于 1，抖动明显的按键会出现大于 1。长按不放不会重复触发。松开时 LED 不动。

这里 `key_edge` 和 `key_edge_tick` 两个变量是配合使用的，在极少数情况下，主循环读到的可能是"一半新一半旧"。这个小隐患先放着，5.4 会专门讲怎么堵。

## 刚才发生了什么

先给整条路径起名：

```mermaid
flowchart LR
    A[按键按下] --> B[EXTI 检测到边沿]
    B --> C[NVIC 通知 CPU]
    C --> D[CPU 暂停主循环，跳去 EXTI0_IRQHandler]
    D --> E[HAL 调用你的回调]
    E --> F[回调置标志]
    F --> G[回到被打断的地方继续]
    G --> H[主循环发现标志，去处理]
```

回到开头的门铃，对应关系是这样的：

| 开头的说法 | 真名 |
|---|---|
| 门铃响 | **中断请求**。硬件在没有任何代码调用的情况下，要求 CPU 停下手头的事 |
| 去门口按铃的人 | **外部中断**（EXTI），这里是按键的下降沿 |
| 跑去应门的管家 | **中断服务函数**（ISR）。你的回调就在它里面被调用 |
| 门口的便条 | **标志变量**，`key_flag` 和 `key_edge` |
| 屋里干活的主人 | **主循环** |
| 只看剧本的导演 | **编译器** |
| 谁来协调谁先应门 | [[【原理】中断与NVIC\|NVIC]]（嵌套向量中断控制器），负责排队和优先级 |

现在回答"为什么 Release 会卡死"。从编译器的视角看，整个程序里，**没有任何一行代码调用** `HAL_GPIO_EXTI_Callback`。调用它的是 `EXTI0_IRQHandler`，而调用后者的，是硬件，不是某行 C 代码。所以编译器看不到"有人在背后改 `key_flag`"，它只看见主循环在读一个谁也不改的变量，于是把读取提到循环外。

`volatile` 就是你对导演的一句补充说明：这个变量有人在场外改，每次都得真去看。编译器怎么做出这些优化，`volatile` 到底禁止了什么，在 [[【原理】volatile与编译器优化|volatile 与编译器优化]] 里讲。

还有一点要记清：`volatile` 只保证"每次都真读真写"，**不保证一步完成**。如果主循环和 ISR 都要改同一个变量，或者要一起读好几个变量，光有 `volatile` 不够，这是 5.4 的内容。

### flag + volatile 模式

这一节的核心套路，后面的定时器、串口都会反复用到，值得单独记下。它只有三块：

```c
/* 1. 共享变量：中断里写、主循环里读，必须 volatile */
static volatile uint8_t flag = 0;

/* 2. 中断一侧：只置标志，立刻返回 */
void HAL_GPIO_EXTI_Callback(uint16_t GPIO_Pin)
{
    if (GPIO_Pin == KEY_Pin) {
        flag = 1;
    }
}

/* 3. 主循环一侧：有空时检测标志，先清再处理 */
if (flag) {
    flag = 0;
    /* 真正的处理放在这里：翻转 LED、打印日志…… */
}
```

只要共享的是一个"有没有发生"的标志，这个模式就够用。如果共享的是计数、时间戳这类会被两边同时改的值，或者要一次读好几个相关变量，就要看 5.4。

## 记住这几条

1. 中断里改、主循环里读的变量，**一律加 `volatile`**。这不是优化选项，是正确性要求。
2. ISR 里只做**最少的事**：置标志、记时刻、计个数。真正的处理交给主循环。
3. ISR 里**不输出、不调用 `HAL_Delay`、不等待任何东西**。`HAL_Delay` 靠 SysTick 让计数前进，ISR 里如果优先级不比 SysTick 高，计数就不会走，你会在里面永远等下去。输出日志也一样放到主循环里。
4. 回调里先判断 `GPIO_Pin`，再做事。不要自己清中断标志，HAL 已经替你清了。
5. 按键的边沿会抖，中断版同样要消抖。
6. 遇到"变量变了，程序却没动"，先用调试器看变量，判断问题在 ISR 一侧还是主循环一侧；然后试试在 Debug 和 Release 之间切换，看现象会不会跟着变。

## 练习

1. 用第二步的等待代码，在顶层 `CMakeLists.txt` 末尾临时追加不同的优化选项，各试一次，记下哪些会卡死。比如试 -O2：（复现）
   ```cmake
   # 临时实验：在 Release 之上追加 -O2（再换成 -O1 试一次）。用完删掉
   target_compile_options(${CMAKE_PROJECT_NAME} PRIVATE -O2 -g3)
   ```
   这一行排在 Release 自带的 `-Os -g0` 后面，gcc 以最后出现的优化选项为准（我在本机看过 CMake 生成的编译命令里的顺序）。改完保存，重新配置、构建。
2. 再接一个按键 KEY2，用另一条 EXTI 线，共用同一个回调，按下 KEY2 翻转蜂鸣器。回调里要怎么区分两个键？（改造）
3. 如果在回调里加一句 `HAL_Delay(50)` 来"消抖"，你预测会发生什么？先写下预测，再试。（预测）

> [!success]- 提示与答案方向
> 1. 按我们的编译结果，-O1、-O2、-Os 会卡，-O0、-Og 不会。以你的编译器为准。做完实验，把追加的那一行删掉，别带进正式工程。
> 2. 用 `GPIO_Pin == KEY_Pin` 和 `GPIO_Pin == KEY2_Pin` 分别判断，各用一个标志。注意两个键的引脚编号不能相同，否则共用一条线。
> 3. 在 CubeMX 默认的优先级配置下，通常会卡死：`HAL_Delay` 要等 SysTick 让计数前进，而你正在一个不比 SysTick 优先级低的 ISR 里，SysTick 打断不了你。就算没卡死，也违背了"ISR 要短"。优先级数值以你的工程为准，CubeMX 的默认值请自行核对（待核对）。
