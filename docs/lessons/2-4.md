# 2.4 程序是怎么跑起来的

> **这一节你会做出**：看懂 CubeMX 工程的目录和 `main.c` 的骨架，知道自己的代码该写在哪、哪里会被覆盖；亲手量出变量放在哪个段；弄明白"回调"为什么没人调用它却会被执行。
> **前置**：[[2.2_开发环境与第一次点灯]]　｜　**预计**：阅读 + 动手 50 分钟

> [!tip] 跳读自测：这一节你可能不用读
> 先回答下面四个问题（写下来，别只在心里答）。**全部答对**就直接跳到 [[3.1_串口与日志]]；有一题拿不准，就从头读。
> 1. 下面的 `main` 烧进板子后，灯会闪吗？为什么？
>
>    ```c
>    int main(void)
>    {
>      /* USER CODE BEGIN 1 */
>      HAL_Delay(100);
>      /* USER CODE END 1 */
>
>      HAL_Init();
>      SystemClock_Config();
>      MX_GPIO_Init();
>      while (1)
>      {
>        HAL_GPIO_TogglePin(LED_GPIO_Port, LED_Pin);
>        HAL_Delay(500);
>      }
>    }
>    ```
>
> 2. 在 `USER CODE` 区之外手写了一行代码，之后回 CubeMX 改了点设置、重新生成代码，这一行会怎样？你在 `Core/Src` 里新建的 `.c` 文件，会被 CubeMX 维护的源文件清单自动收进构建吗？
> 3. 我想在按键中断里做事，写了一个函数 `void HAL_GPIO_EXTI_Callbak(uint16_t GPIO_Pin)`（少了个 c）。编译能通过吗？它会被调用吗？
> 4. 下面两个全局变量，初值 `5` 存在哪里？它们各自主要占用 `size` 输出的哪一列（`text` / `data` / `bss`）？构建结尾打印的 FLASH 用量和 RAM 用量，各由 `size` 的哪几列相加得到？
>
>    ```c
>    int a = 5;
>    int b;
>    ```
>
> > [!success]- 答案，以及跳过后要带走的东西
> > 1. 不会闪，程序永远停在第一行。`HAL_Delay` 靠 SysTick 每毫秒计一次数，而 SysTick 是 `HAL_Init()` 里才启动的。在它之前调用，计数永远不动，等待永远不结束。
> > 2. 那一行被删掉：CubeMX 重新生成时，只保留 `USER CODE BEGIN / END` 之间的内容，其余按模板重写。新建的 `.c` 也不会被收进来：清单 `cmake/stm32cubemx/CMakeLists.txt` 由 CubeMX 维护，只认它自己生成的文件。自己的文件放 `User/Src`，靠顶层 `CMakeLists.txt` 里的 GLOB 收进来（见 2.2）。
> > 3. 能通过，加了 `-Wall -Wextra` 也没有警告（我用 arm-none-eabi-gcc 12.3 试过）；但不会被调用。HAL 调的是 `HAL_GPIO_EXTI_Callback`，你拼错了名字，它就成了一个没人认识的新函数，HAL 里那个空的弱函数照常执行。
> > 4. `a` 的初值 5 存在 **Flash** 里，启动时被搬到 RAM；它主要占 `data`。`b` 没有初值，只占 `bss`，启动时被清零。对本节展示的简单布局，可用 `text + data` 估算 Flash 内容、`data + bss` 估算静态 RAM；实际各存储区占用还要看链接脚本与 map，不能一概等同链接器的区域报告。
> >
> > **带走清单**：①常用的 `USER CODE` 区和用途（见第三步的表），后面所有章节都按这个位置放代码：全局变量放 `PV` 区，你自己的函数放 `USER CODE 0` 区或 `USER CODE 4` 区，一次性的启动代码放 `USER CODE 2`，主循环里的放 `USER CODE 3`，需要被多个文件看到的 `extern` 声明放 `main.h` 的 `USER CODE BEGIN EC` 区；②回调靠重写 HAL 的弱函数，名字必须与 HAL 头文件一致；③`size` 按节属性汇总，`--print-memory-usage` 按链接脚本区域统计；本例的简单相加是估算，不是所有工程通用的等式；④启动文件由 `cmake/stm32cubemx/CMakeLists.txt` 带进构建，链接脚本由工具链文件里的 `-T` 指定，你自己的文件放 `User/`（见 2.2）。

## 先看一个怪现象

你写的 `main` 函数，从来没有被任何一行代码调用过。可是每一次上电，它都准时开始跑。

这像一家店：早上没有人对店长喊"开门"，门自己开了。因为在店长上班之前，已经有人把地扫了、货摆上了、灯开了。这一节我们就是去看看那位"提前到岗的人"，以及店开门之后，店里的规矩。

本节的比喻就是**开店**：上电后先有人打扫（启动代码），再开业筹备（初始化），然后营业（主循环），门铃一响，店员放下手头的事去应门（中断与回调）。

> [!question] 先猜一猜
> `main` 是被谁调用的？
> A. 你写的某个函数　B. 编译器在编译时自动加了一行调用　C. CPU 复位后先跑的一段启动代码　D. 下载器
> 选一个，第一步之后揭晓。

## 动手做

### 第一步：看工程目录

打开你在 2.2 里生成的 CMake 工程（加上第八步建的 `User/`），目录大致是这样：

```
Led/
├─ CMakeLists.txt                 顶层构建入口（CubeMX 只生成一次，之后归你改）
├─ CMakePresets.json              预设：debug、release 等
├─ cmake/
│  ├─ gcc-arm-none-eabi.cmake     工具链文件：编译器、编译选项，还有 -T 链接脚本
│  └─ stm32cubemx/
│     └─ CMakeLists.txt           CubeMX 维护的源文件、头文件清单，重新生成会改写
├─ Core/
│  ├─ Inc/  main.h  stm32f4xx_hal_conf.h  stm32f4xx_it.h
│  └─ Src/  main.c  stm32f4xx_it.c  stm32f4xx_hal_msp.c  system_stm32f4xx.c
│           syscalls.c  sysmem.c   （C 库要用的底层桩，GCC 工程里才有）
├─ Drivers/
│  ├─ CMSIS/                      内核和芯片的头文件（寄存器名都在这里）
│  └─ STM32F4xx_HAL_Driver/       HAL 库本体
├─ User/
│  ├─ Inc/                        你自己的 .h
│  └─ Src/                        你自己的 .c
├─ startup_stm32f407xx.s          启动文件
├─ STM32F407XX_FLASH.ld           链接脚本（文件名随芯片和版本略有不同）
├─ Led.ioc                        CubeMX 的工程文件：你在界面上的所有选择都存在这里
└─ build/debug/                   构建产物：Led.elf、Led.hex、Led.bin、Led.map 等
```

| 位置 | 它是什么 | 你要不要改 |
|---|---|---|
| `Core/Src/main.c` | 入口和骨架 | 只改 `USER CODE` 区之间 |
| `Core/Inc/main.h` | CubeMX 生成的引脚宏 | 只在 `USER CODE` 区加声明 |
| `Core/Src/stm32f4xx_it.c` | 中断入口，如 `SysTick_Handler` | 只在 `USER CODE` 区加代码 |
| `stm32f4xx_hal_conf.h`、`stm32f4xx_hal_msp.c` | HAL 配置、底层初始化 | 不手改，回 CubeMX 改 |
| `Drivers/` | 库 | 不改 |
| `User/` | 你的代码 | 随便写，靠顶层 `CMakeLists.txt` 的三行收进来 |
| `cmake/stm32cubemx/CMakeLists.txt` | CubeMX 的源文件清单 | 不手改 |
| 顶层 `CMakeLists.txt` | 构建入口 | 在用户部分加自己的东西 |
| 启动文件、链接脚本 | 启动代码、内存布局 | 现在不改 |
| `.ioc` | CubeMX 工程 | 用 CubeMX 打开改，不手编辑 |

这里有两个文件，是 1.1 里那条流程的老朋友：**启动文件**（汇编写的，负责把环境收拾好再调用 `main`）和**链接脚本**（告诉链接器 Flash 和 RAM 各从哪里开始、各多大、各段放哪）。它们是怎么被带进 CMake 构建的？

- **启动文件**列在 `cmake/stm32cubemx/CMakeLists.txt` 的源文件清单里，和 `main.c` 排在一起。顶层有 `enable_language(C ASM)`，所以 CMake 把 `.s` 文件也交给 `arm-none-eabi-gcc` 去汇编。
- **链接脚本**不在源文件清单里，它是链接时的一个选项：工具链文件里有一行 `-T "${CMAKE_SOURCE_DIR}/STM32F407XX_FLASH.ld"`，`-T` 的意思就是"别用默认布局，按这个脚本摆"。脚本开头定义了三块存储区，和构建结尾那张 `Memory region` 表的三行一一对应：

```
MEMORY
{
RAM (xrw)      : ORIGIN = 0x20000000, LENGTH = 128K
CCMRAM (xrw)      : ORIGIN = 0x10000000, LENGTH = 64K
FLASH (rx)      : ORIGIN = 0x8000000, LENGTH = 1024K
}
```

它们的细节放在[[【原理】启动流程与链接脚本|启动流程与链接脚本]]里，这一节只量它们的效果。

> [!success]- 揭晓：先猜一猜的答案
> 选 C。上电或复位后，CPU 先去 Flash 起始处取两样东西：栈顶地址和复位入口 `Reset_Handler`，然后执行启动文件里的这段启动代码，它做完准备工作，最后才调用 `main`。你的 `main` 是被它调用的，这就是开店前那位打扫的人。第六步我们会亲眼看到这两样东西。

### 第二步：读 `main()` 的骨架

打开 `main.c`，除掉注释，`main()` 的骨架只有四段：

```c
int main(void)
{
  /* USER CODE BEGIN 1 */

  /* USER CODE END 1 */

  HAL_Init();                 /* ① 通电试灯：Flash 缓存、中断分组、启动 SysTick */

  /* USER CODE BEGIN Init */

  /* USER CODE END Init */

  SystemClock_Config();       /* ② 定营业时间：晶振起振，PLL 拉到 168 MHz */

  /* USER CODE BEGIN SysInit */

  /* USER CODE END SysInit */

  MX_GPIO_Init();             /* ③ 摆设备：每个你在 CubeMX 里勾选的外设，一个 MX_xxx_Init */

  /* USER CODE BEGIN 2 */

  /* USER CODE END 2 */

  /* USER CODE BEGIN WHILE */
  while (1)                   /* ④ 营业：永远循环 */
  {
    /* USER CODE END WHILE */

    /* USER CODE BEGIN 3 */

  }
  /* USER CODE END 3 */
}
```

这个顺序是固定的：**HAL_Init → SystemClock_Config → MX_*_Init → while(1)**。以后你在 CubeMX 里每多勾一个外设（串口、定时器、CAN），这里就多一行 `MX_xxx_Init`，顺序不用你管。

注意第 ① 步 `HAL_Init()` 里做的一件事：启动 SysTick，每 1 ms 触发一次中断。2.2 里 `HAL_Delay` 数的"毫秒"，就来自这里。

### 第三步：`USER CODE` 规则

先做一个小实验，再解释规则。

> [!question] 先猜一猜
> 在 `MX_GPIO_Init();` 的下一行（不在任何 `USER CODE` 之间）写一行 `HAL_GPIO_WritePin(LED_GPIO_Port, LED_Pin, GPIO_PIN_SET);`。然后回 CubeMX，随便改一处（比如给另一个引脚加个标签），重新 GENERATE CODE。再看 `main.c`，你那一行还在吗？

> [!success]- 揭晓
> 不在了。CubeMX 每次生成，都会按模板把整个文件重写一遍，只有 `USER CODE BEGIN xxx` 和 `USER CODE END xxx` 之间的内容会被原样保留。这就是"区"的意义：**装修队（CubeMX）的地盘随时会被刷新，留给店主的便签栏才会保留。**

常用的区和用途如下：

| 区 | 所在位置 | 放什么 |
|---|---|---|
| `Includes` | 文件头 | `#include` 你自己的头文件 |
| `PD` / `PM` | 宏定义处 | 常量和宏 |
| `PV` | 全局变量处 | 你的全局变量的**定义** |
| `PFP` | 函数原型处 | 你自己函数的声明 |
| `USER CODE 0` | `main` 之前 | 你的小工具函数 |
| `USER CODE 1` | `HAL_Init` 之前 | 极早期的代码，几乎不用 |
| `USER CODE 2` | 外设初始化之后、循环之前 | 只执行一次的启动代码，如启动定时器 |
| `USER CODE 3` | 主循环里 | 反复执行的代码 |
| `USER CODE 4` | `main.c` 文件末尾 | 回调函数和你的其他函数 |
| `main.h` 的 `EC` | 头文件里 | 需要多个文件共用的 `extern` 声明 |

区只管 CubeMX 生成的文件。代码一多，就放进 `User/Src` 和 `User/Inc`（见 2.2 第八步），`main.c` 里只留几行调用，回调函数也可以写在自己的 `.c` 文件里。

第二个实验，针对第 ① 步。

> [!question] 先猜一猜
> 在 `USER CODE BEGIN 1` 里放一行 `HAL_Delay(100);`，下载运行。灯会怎么样？

> [!success]- 揭晓
> 灯不再闪，程序停在了那一行。按 HAL 源码推断（这条我没有上板验证，你可以自己试）：`HAL_Delay` 的做法是不停地比较"现在的毫秒数"和"开始时的毫秒数"，而毫秒数靠 SysTick 每 1 ms 加一，SysTick 在 `HAL_Init()` 里才启动。在 `HAL_Init` 之前调用，毫秒数永远是 0，条件永远不满足，就卡在那里。[[【原理】SysTick与HAL时基|SysTick 与 HAL_Delay]] 里有完整的来龙去脉。
>
> 规矩：**依赖 SysTick 的函数，不要放在 `HAL_Init()` 之前。**

### 第四步：回调，没人调用却被执行

CubeMX 工程里有一类函数，你从来没调用过，它们却在合适的时机被执行，叫**回调**（callback）。比如按键中断来了，HAL 怎么知道该去跑你的代码？

> [!question] 先猜一猜
> 你从来没有向 HAL "登记"过任何东西，只是写了一个函数。你觉得 HAL 凭什么能找到并调用它？

答案藏在 HAL 的源码里。打开 `stm32f4xx_hal_gpio.c`，搜索 `HAL_GPIO_EXTI_Callback`：

```c
__weak void HAL_GPIO_EXTI_Callback(uint16_t GPIO_Pin)
{
  /* Prevent unused argument(s) compilation warning */
  UNUSED(GPIO_Pin);
  /* NOTE: This function Should not be modified, when the callback is needed,
           the HAL_GPIO_EXTI_Callback could be implemented in the user file
   */
}
```

HAL 自己先写了一个**什么也不做**的同名函数，前面加了 `__weak`（弱）。意思是"这是个默认版本，如果别处有同名的正式版本，用正式的"。你在 `USER CODE 4` 区里写一个同名函数，链接器就会选你的：

```c
/* USER CODE BEGIN 4 */
/* 重写 HAL 的弱函数：函数名和参数必须和 HAL 头文件里的声明完全一致 */
void HAL_GPIO_EXTI_Callback(uint16_t GPIO_Pin)
{
  if (GPIO_Pin == KEY_Pin)                          /* 是不是按键那个引脚触发的 */
  {
    HAL_GPIO_TogglePin(LED_GPIO_Port, LED_Pin);     /* 回调在中断里跑：短小，不调用 HAL_Delay */
  }
}
/* USER CODE END 4 */
```

现在你的工程里还没有按键，所以这段先读不用抄，5.1 会真正配出来。整条调用链是这样的：

```
引脚上出现电平变化
  → 向量表里对应的中断入口（stm32f4xx_it.c 里的 EXTIx_IRQHandler）
    → HAL_GPIO_EXTI_IRQHandler（HAL 里的处理函数）
      → HAL_GPIO_EXTI_Callback（弱函数；你重写了，就跑你的）
```

你可以用工具亲眼验证"弱"和"强"。构建一次，对 HAL 的 `stm32f4xx_hal_gpio.c` 编出来的目标文件执行（它在构建目录里，我这里的路径是 `build/debug/cmake/stm32cubemx/CMakeFiles/STM32_Drivers.dir/__/__/Drivers/STM32F4xx_HAL_Driver/Src/stm32f4xx_hal_gpio.c.obj`）：

```
arm-none-eabi-nm 上面那个 .obj 文件的路径
```

> [!example] 我在电脑上的结果（你的地址会不同）
> - 构建目录里 HAL 自带的目标文件：`W HAL_GPIO_EXTI_Callback`（`W` 是 weak，弱符号）
> - 下面几条，是我把 HAL 的 gpio 文件和一个单独写的函数分别编译成目标文件、再合并得到的：
> - 你写对名字的目标文件：`T HAL_GPIO_EXTI_Callback`（`T` 是正常定义）
> - 两个合并后：只剩一个 `T`，就是你的
> - 你把名字拼错成 `HAL_GPIO_EXTI_Callbak` 再合并：弱的 `W HAL_GPIO_EXTI_Callback` 和你的 `T HAL_GPIO_EXTI_Callbak` **并存**，没有任何报错，HAL 调用的依然是那个空函数
> - 如果你写了两个同名的正式函数：链接器报 `multiple definition`

所以回调有两条规矩：**名字和参数以 HAL 头文件为准，拼错了编译器不会提醒你**；**本节的 GPIO 中断回调在 ISR 里执行，要短小、不能阻塞、不要调用 `HAL_Delay`**。不是所有 HAL 回调都处于中断，例如 `MspInit` 通常由初始化路径同步调用；应沿具体调用点确认上下文。

### 第五步：量一量变量住在哪

2.2 里你已经看到构建结尾有两段输出，现在来读懂它们。第一段是链接器自己打印的（工具链文件里的 `-Wl,--print-memory-usage`），按存储区报告用了多少；第二段是 `arm-none-eabi-size` 的结果（顶层 `CMakeLists.txt` 里的 `print_section_sizes` 在构建完成后调用它），按"段"报告大小：

```
Memory region         Used Size  Region Size  %age Used
             RAM:        1584 B       128 KB      1.21%
          CCMRAM:          0 GB        64 KB      0.00%
           FLASH:        6008 B         1 MB      0.57%
   text	   data	    bss	    dec	    hex	filename
   5996	     12	   1572	   7580	   1d9c	Led.elf
```

三个段名先记一下，一句话各一个：

- **`.text`**：代码，和只读的常量（输出里的 `text` 一列包含它们）。
- **`.data`**：有初值的全局和静态变量。初值存在 Flash 里，启动时被搬进 RAM。
- **`.bss`**：没有初值的全局和静态变量。启动时清零，不占 Flash。

**这份示例输出**恰好能对上：5996 + 12 = 6008，12 + 1572 = 1584。但 `size` 按 ELF 节属性分类，链接器按 `MEMORY` 区域和布局统计；对齐空隙、多个 RAM 区、加载地址与运行地址、预留堆栈区都会影响结果，不能当成恒等式。

`bss` 汇总也不只等于你写下的未初始化变量：某些链接脚本把预留堆栈输出节标成不占文件字节的可分配节，`size` 会把它计入这一类。检查你工程的 `_Min_Heap_Size`、`_Min_Stack_Size` 和 map 文件，而不是假设所有 CubeMX 工程使用固定值。进一步见[可执行文件格式](/notes/executable-formats)和[启动流程与链接脚本](/notes/startup-linker-script)。

做个实验。在 `PV` 区加一个数组，并在主循环里用到它（没人用的变量，链接器可能把它丢掉）：

```c
/* USER CODE BEGIN PV */
volatile int g_arr[100];    /* volatile 先照写，5.1 解释 */
/* USER CODE END PV */
```

主循环里 `blink_step();` 下面加一行 `g_arr[0]++;`，构建，看输出。然后把定义改成 `volatile int g_arr[100] = {1};`，再构建一次。

> [!example] 我在电脑上量到的结果（2.2 第八步之后的工程，Debug 构建；你的绝对数字不同，增减应该相同）
>
> | 版本 | text | data | bss | FLASH 用量 | RAM 用量 |
> |---|---|---|---|---|---|
> | 2.2 第八步之后的工程 | 5996 | 12 | 1572 | 6008 | 1584 |
> | 加 `volatile int g_arr[100]`（用到） | 6016 | 12 | 1972 | 6028 | 1984 |
> | 加 `volatile int g_arr[100] = {1}`（用到） | 6016 | 412 | 1572 | 6428 | 1984 |
>
> 没有初值：`bss` 多了 400（100 个 4 字节整数），Flash 只多了 20，那是循环里新加那一行的代码。有初值：`data` 多了 400，`bss` 回到原来的数，Flash 一下多了 420：400 字节是数组的初值，要存在 Flash 里等着启动时搬进 RAM。两种写法 RAM 都多了 400。

于是 `int a = 5;` 里的 5 存在 Flash 里，是启动代码在 `main` 之前把它搬进 RAM 的。这就是为什么 1.4 里的全局变量，在单片机上一上电就带着正确的初值。

再回到 2.1 自测里那行 `int g_table[100000];`。把它加进 `PV` 区并在循环里用到，构建，你会看到链接器报错。我这里的结果是（你的数字会不同）：

```
section `.bss' will not fit in region `RAM'
region `RAM' overflowed by 270512 bytes
```

这就是 `MEMORY` 里那块 128 KB 的 `RAM` 装不下 400,000 字节。查看 `Memory region` 那几行，是遇到"RAM 不够"时的第一站。

### 第六步：看看 CPU 最先读的两个数

这一步是选做。用任意十六进制查看器打开编译出的 `Led.bin` 看前 8 个字节，比如 PowerShell 里执行 `Format-Hex build/debug/Led.bin` 看第一行，或者 Git Bash 里执行 `od -A x -t x1 -N 8 build/debug/Led.bin`。

> [!example] 我编译的最小工程里，前 8 个字节是（你的可能不同）
> `00 00 02 20  69 16 00 08`
>
> 每 4 个字节是一个数，低字节在前（小端，[[【拓展】字节序之争|字节序之争]]里有故事）：
> - 第一个数 `0x20020000`：栈顶地址，正好是 128 KB 那块 RAM 的结尾
> - 第二个数 `0x08001669`：复位后要执行的第一段代码的地址，就是启动文件里的 `Reset_Handler`（最低位的 1 是处理器模式的标记，实际地址是 `0x08001668`；用 `arm-none-eabi-nm` 能在 `.elf` 里查到 `Reset_Handler` 就在这个地址）

这就是"CPU 复位后先读的两样东西"。你的程序一上电，就是从这里开始的。

## 刚才发生了什么

把整件事从头串一遍：上电或复位后，CPU 到 Flash 起始处读出栈顶地址和复位入口，跳进启动文件里的 `Reset_Handler`。我读了本机示例工程里的启动文件，它按这个顺序做事：

1. 设置栈指针。
2. 调用 `SystemInit`，做最基本的系统初始化。此时时钟还是芯片内部的 RC 振荡器，不是 168 MHz。
3. 把 `.data` 的初值从 Flash 搬到 RAM。
4. 把 `.bss` 清零。
5. 调用 C 库的初始化（`__libc_init_array`）。
6. 调用 `main`。

然后才是你熟悉的那段：`HAL_Init` → `SystemClock_Config` → `MX_*_Init` → `while(1)`。所以 `main` 之前，有人先跑了；这就是"没人调用 `main` 它却会运行"的答案。

再看 HAL 里一个更重要的结构。2.2 的 `HAL_GPIO_TogglePin(LED_GPIO_Port, LED_Pin)` 把"哪个端口、哪个引脚"作为参数传进去。后面第 3 章起你会反复写 `HAL_UART_Transmit(&huart1, 数据, 长度, 超时)`，这里的 `huart1` 值得多看一眼。它的类型 `UART_HandleTypeDef` 是一个 `struct`：寄存器基地址（`Instance`）、波特率等配置（`Init`）、收发缓冲区的指针和计数、当前状态……一个串口的全部数据都装在里面，所有操作函数都把它的指针放在第一个参数。这正是 1.6、1.7 学过的东西：**`struct` 加上以它的指针为第一个参数的函数，就是"对象"**。`huart1` 是对象，`HAL_UART_Transmit` 是它的方法，板上有两个串口，就有 `huart1`、`huart2` 两个对象，状态各管各的，互不干扰。

回调也一样。默认的"重写弱函数"方式，是同一类的所有对象共用一个回调，函数的参数里带着 `huart`，让你分辨是哪个对象触发的。HAL 还有另一种方式：在 `stm32f4xx_hal_conf.h` 里把 `USE_HAL_UART_REGISTER_CALLBACKS` 设为 1（默认是 0），这个 `struct` 里就会多出 `TxCpltCallback` 这样的**函数指针成员**，你把函数登记进对象里，不同的对象可以挂不同的行为。这就是 1.7 的函数指针。后面你自己写驱动，也要用同样的写法，把状态放进对象里，不要散落成一堆全局变量，这个思路放在[[【原理】C语言里的面向对象|C 语言里的面向对象]]里展开。

## 记住这几条

1. **自己的代码只写在 `USER CODE` 区之间。** 区外的内容，在重新生成时会被覆盖。想改配置，回 CubeMX 改再生成。
2. **初始化顺序固定：HAL_Init → SystemClock_Config → MX_*_Init → 你的代码。** 依赖 SysTick 的函数（如 `HAL_Delay`）不要放在 `HAL_Init` 之前。
3. **回调靠重写 HAL 的 `__weak` 函数。** 名字和参数以 HAL 头文件为准，拼错了编译器不报错，也不会被调用。
4. **本节的中断回调短小、不阻塞、不调用 `HAL_Delay`。** 回调只是调用方式，不等于 ISR；初始化等同步回调的执行上下文要另查。
5. **常见布局中，可写的非零初始化全局变量进 `.data`；零初始化或未显式初始化的静态存储期对象常进 `.bss`。** `const`、链接器裁剪和自定义节可能改变落点；用 map 核实，别把 `text/data/bss` 的相加当成所有区域的精确用量。
6. **`main` 之前有启动代码先跑过**：设栈、搬 `.data`、清 `.bss`、再调 `main`。
7. **`huart1` 这样的句柄就是对象。** 写自己的模块时也用 `struct` + 以指针为首参的函数，状态放对象里。

## 练习

1. 照第五步做一遍实验，把自己量到的三行数字填进表里。（复现）
2. 把 2.2 的闪灯改成：上电先快闪 3 下，然后进入每 500 ms 翻转一次的慢闪。快闪该放在哪个 `USER CODE` 区？按复位键，你会看到什么？（改造）
3. 在 `USER CODE 4` 区写一个 `HAL_TIM_PeriodElapsedCallback`，但没有在 CubeMX 里配任何定时器中断。这个函数会被调用吗？先写下预测。（预测）

> [!success]- 提示与答案方向
> 1. 绝对数字以你自己的为准，增减量和上表一致。
> 2. 放 `USER CODE BEGIN 2`，只执行一次：
>
>    ```c
>      /* USER CODE BEGIN 2 */
>      for (int i = 0; i < 6; i++)          /* 翻转 6 次 = 闪 3 下，灯回到初始状态 */
>      {
>        HAL_GPIO_TogglePin(LED_GPIO_Port, LED_Pin);
>        HAL_Delay(100);
>      }
>      /* USER CODE END 2 */
>    ```
>
>    每次按复位键，都会重新走一遍 `main`，所以快闪 3 下会再出现一次。
> 3. 不会。回调是被中断触发的，没有定时器中断，就没有人去调用它。弱函数只是给"来了就有人接"准备的，不会自己跑起来。
