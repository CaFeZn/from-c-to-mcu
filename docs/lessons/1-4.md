# 1.4 函数与作用域

> **这一节你会做出**：先亲身感受一次"同一段代码复制粘贴三份，改一处漏两处"的痛，再用函数把它解决，并学会"封装"这个词；会写带参数、带返回值的函数；分清局部变量、全局变量和 `static` 局部变量各自活多久；亲手让递归下潜，找到它的极限，并知道为什么单片机上基本不用递归。
> **前置**：[[1.2_变量运算与控制流]]　｜　**预计**：阅读 + 动手 50 分钟

> [!tip] 跳读自测：这一节你可能不用读
> 先回答下面四个问题（写下来，别只在心里答）。**全部答对**就直接跳到 [[1.5_数组与指针]]；有一题拿不准，就从头读。
> 1. 下面函数连续调用三次，返回值依次是什么？把 `static` 去掉呢？
>    `int next(void) { static int n = 10; n++; return n; }`
> 2. `void f(int x) { x = 5; }`，调用 `f(a)` 之后，调用者的 `a` 会变吗？
> 3. 同一段处理逻辑被复制粘贴到了三个地方，之后要改规则，最大的风险是什么？用函数怎么解决？什么叫"封装"？
> 4. 局部变量没赋初值就读，会读到什么？没赋初值的全局变量呢？为什么在单片机上基本不写递归？
>
> > [!success]- 答案，以及跳过后要带走的东西
> > 1. 11、12、13。去掉 `static` 后每次都是 11，因为 `n` 每次调用都重新建、重新赋值。
> > 2. 不会。参数是复印件，函数里改的是副本。
> > 3. 风险是改了一处、漏了另外几处，而且编译器不会提醒。办法是把这段逻辑只写一遍，打包成函数，别处调用，要改只改一处。封装就是把一件事做完整、打包起来，对外只留名字、参数、返回值。
> > 4. 局部变量读到的值没有保证（可能是上一个函数留下的旧数据）；全局变量和 `static` 变量自动是 0。递归每深一层就在栈上占一块，而单片机的栈只有几 KB，层数一深就会溢出；没有操作系统兜底，常常是悄悄改坏别的数据。
> >
> > **带走清单**：本节没有后文要引用的代码或配置，带走的是思路和约定：重复出现的逻辑打包成函数（封装：对外只留名字、参数、返回值），后面所有章节都这样写；全局变量加 `g_` 前缀（5.2 的 `g_ms` 就是这样命名）；要让函数"记住上一次"就用 `static` 局部变量；函数参数是复印件（1.5 的 `swap` 要用）；板上不写递归、不在函数里放大数组。本节的例子都放在 `c-lab` 的 `src/` 下，用 `add_demo` 登记，不用保留；另外记住构建类型可以切换：Debug 不做优化，Release 做优化，同一份代码的实验结果可能不同。

## 先看一个怪现象

你写完了三路温度传感器的处理。每一路都是同样的几行：读数低于 0 就按 0 算，高于量程上限就按上限算。第一路写了一分钟，第二、第三路你复制粘贴，改个变量名，十秒钟搞定。

两周后，硬件升级，量程上限从 100 改成了 120。你打开代码，改了第一路，然后去喝水了。又过了三个月，没有人记得这件事。

```c
#include <stdio.h>

int main(void) {
    int t1 = 150, t2 = 150, t3 = 150;   /* 三路温度传感器，都读到了 150 */

    /* 第 1 路：低于 0 按 0 算，高于量程上限按上限算 */
    if (t1 < 0) {
        t1 = 0;
    }
    if (t1 > 120) {
        t1 = 120;
    }
    printf("t1 = %d\n", t1);

    /* 第 2 路：同样的处理，复制粘贴过来的 */
    if (t2 < 0) {
        t2 = 0;
    }
    if (t2 > 100) {
        t2 = 100;
    }
    printf("t2 = %d\n", t2);

    /* 第 3 路：再粘贴一遍 */
    if (t3 < 0) {
        t3 = 0;
    }
    if (t3 > 100) {
        t3 = 100;
    }
    printf("t3 = %d\n", t3);

    return 0;
}
```

> [!success]- 揭晓
> 输出是：
>
> ```

> t2 = 100
> t3 = 100
> ```
>
> 只有第一路是 120，另外两路还是旧的 100。编译器一声不吭，因为每一段单独看都没有错。错在"同一件事被抄了三份，改的时候只改了一份"。
>
> 想亲手跑一遍：存成 `src/clamp_paste.c`，在 `CMakeLists.txt` 末尾加一行 `add_demo(clamp_paste)`，构建并运行。

这个毛病不挑人。抄 3 份就有 3 处要同步，抄 30 份呢？问题不在于你粗心，而在于**同一件事，在程序里不该出现第二遍**。

## 动手做

### 第一步：把重复的事打包成函数

办法是：这件事**只写一遍**，给它起个名字，别处要用，就叫这个名字。这就是**函数**。

可以把函数想成一间小办公室：你把材料（参数）递进去，它做完事，把结果（返回值）递出来。你不用管它里面怎么做。

```c
#include <stdio.h>

/* 把 x 限制在 [lo, hi] 之内，返回限制后的值 */
int clamp(int x, int lo, int hi) {
    if (x < lo) {
        return lo;
    }
    if (x > hi) {
        return hi;
    }
    return x;
}

/* 温度的量程只写在这一处：以后要改，只改这里 */
int clamp_temp(int x) {
    return clamp(x, 0, 120);
}

int main(void) {
    int t1 = 150, t2 = 150, t3 = 150;   /* 三路温度传感器，都读到了 150 */

    printf("t1 = %d\n", clamp_temp(t1));
    printf("t2 = %d\n", clamp_temp(t2));
    printf("t3 = %d\n", clamp_temp(t3));
    return 0;
}
```

本教程第 1 章的例子都放在同一个 CMake 工程 `c-lab` 里（建法见本章开头）。每个例子的跑法一样：保存为 `src/clamp_fixed.c`，在 `CMakeLists.txt` 末尾加一行 `add_demo(clamp_fixed)`，然后三步：配置、构建、运行。

```
cmake -S . -B build -G Ninja      # 配置（第一次需要；之后改了 CMakeLists.txt，构建时会自动重新配置）
cmake --build build               # 构建
./build/clamp_fixed               # 运行（Windows 命令提示符里写 build\clamp_fixed.exe）
```

在 VS Code 里，对应 CMake Tools 底部状态栏的 Configure、Build 和运行▶。`c-lab` 的 `CMakeLists.txt` 里已经加了 `-Wall -Wextra`，所以编译器会多说话，警告会直接显示在构建输出里。

工程所在的路径请保持纯英文、不带空格：CubeCLT 自带的 CMake 3.28.1，在路径含中文时配置阶段会崩溃。

你应该看到：

```
t1 = 120
t2 = 120
t3 = 120
```

三路都是 120。现在量程只写在 `clamp_temp` 里。

**试一试**：把 `clamp_temp` 里的 120 改成 150，重新构建并运行。三路一起变了，没有谁会被漏掉。

这种做法有名字了，叫**封装**：把一件事做完整、打包起来，对外只留下三样东西，**名字**（`clamp_temp`）、**参数**（`int x`）、**返回值**（`int`）。用的人不必知道里面怎么做，也碰不到里面；写的人想改里面（比如换量程，将来改成查表），只要名字、参数、返回值不变，调用的人一行都不用动。

再留意一下结构：`clamp_temp` 里又调用了 `clamp`。`clamp` 管"把一个数夹在上下限之间"这件通用的事，`clamp_temp` 管"温度的量程是多少"这件专门的事。各管一件，各自好改。

### 第二步：参数与返回值，以及一个小陷阱

函数的声明由四样东西组成：返回值的类型、名字、参数列表、函数体。下面这个程序有两个函数：`max2` 收两个参数、返回一个值；`try_change` 想在函数里改调用者的变量，看看行不行。

```c
#include <stdio.h>

/* 两个参数，一个返回值 */
int max2(int a, int b) {
    return (a > b) ? a : b;
}

/* 想在函数里把调用者的变量改成 99，看看行不行 */
void try_change(int x) {
    x = 99;
    printf("in try_change: x = %d\n", x);
}

int main(void) {
    printf("max2(3, 8)   = %d\n", max2(3, 8));
    printf("max2(-5, -9) = %d\n", max2(-5, -9));

    int v = 1;
    try_change(v);
    printf("in main: v = %d\n", v);
    return 0;
}
```

保存为 `src/params.c`，在 `CMakeLists.txt` 末尾加一行 `add_demo(params)`，构建并运行。

你应该看到：

```
max2(3, 8)   = 8
max2(-5, -9) = -5
in try_change: x = 99
in main: v = 1
```

最后两行值得停一下。`try_change` 在里面把 `x` 改成了 99，回到 `main`，`v` 还是 1。

> [!question] 先猜一猜
> 为什么函数里改了，外面没变？
> 提示：想想"把材料递进办公室"这个动作，递进去的是原件，还是复印件？

> [!success]- 揭晓
> 递进去的是**复印件**。调用 `try_change(v)` 时，`v` 的值被复制了一份，交给参数 `x`。函数里改的是复印件，原件纹丝不动。这叫**按值传递**。
> 下一节你会看到：想让函数改到原件，得把原件的"地址"递进去。

**探针一**：把 `max2` 整个函数挪到 `main` 的下面，再构建。会看到：

```
warning: implicit declaration of function 'max2' [-Wimplicit-function-declaration]
```

C 编译器从上往下读，读到 `main` 里的 `max2(...)` 时，还不知道它是什么。解决办法是在 `main` 前面补一行声明：`int max2(int a, int b);`。声明只告诉编译器"有这么个函数，长这样"，函数体可以晚点再写。这行声明，其实就是封装对外露出的那三样东西：名字、参数、返回值。

### 第三步：三个计数器，三种寿命

函数里的变量，活多久，谁能看见？先看一个小怪事。下面三个函数，每个里面都有一个"计数器"，都是 `n++` 然后打印。主函数把它们各调用三次。

```c
#include <stdio.h>

int g_count = 0;                 /* 全局：整个程序共用 */

void count_local(void) {
    int n = 0;                   /* 局部：每次进函数重新建一个 */
    n++;
    printf("local  n = %d\n", n);
}

void count_global(void) {
    g_count++;
    printf("global g_count = %d\n", g_count);
}

void count_static(void) {
    static int n = 0;            /* static 局部：只初始化一次，函数返回后还活着 */
    n++;
    printf("static n = %d\n", n);
}

int main(void) {
    for (int i = 0; i < 3; i++) {
        count_local();
        count_global();
        count_static();
        printf("--\n");
    }
    return 0;
}
```

> [!question] 先猜一猜
> 第三轮（最后一次循环）里，三行分别打印什么？
> `local`、`global`、`static` 这三个数，是三个 1，还是三个 3，还是别的？先写下你的答案，再往下翻。

> [!success]- 揭晓
> 运行方式就在下面，输出是：
>
> ```
> local  n = 1
> global g_count = 1
> static n = 1
> --
> local  n = 1
> global g_count = 2
> static n = 2
> --
> local  n = 1
> global g_count = 3
> static n = 3
> --
> ```
>
> 局部的那个永远是 1。全局和 `static` 的会一路涨到 3。三个看起来一模一样的计数器，行为完全不同。

把上面那段代码保存为 `src/scope_counters.c`，加一行 `add_demo(scope_counters)`，构建并运行 `./build/scope_counters`，核对你的猜测。

三个计数器，对应三种变量。给它们各配一个比喻：

- **局部变量**是办公室里的草稿纸：进门领一张新的，出门收走。每次进来，都是一张白纸。
- **全局变量**是走廊里的公告栏：谁路过都能看，谁路过都能改，一直挂在那里。
- **`static` 局部变量**是锁在这间办公室抽屉里的笔记本：只有这间办公室能翻，但门关上以后，笔记本还在。下次进来，接着上次写。

比喻之后是真名：草稿纸是**局部变量**（它的寿命叫**自动存储期**），公告栏是**全局变量**，笔记本是**`static` 局部变量**（后两者的寿命叫**静态存储期**，整个程序运行期间都活着）。

**探针二**：笔记本真的只有这间办公室能翻吗？把 `main` 改成直接打印 `count_static` 里的 `n`：

```c
#include <stdio.h>

void count_static(void) {
    static int n = 0;
    n++;
}

int main(void) {
    count_static();
    printf("%d\n", n);
    return 0;
}
```

构建会报：

```
error: 'n' undeclared (first use in this function)
```

`static` 让变量**活得久**，但没有让它**被看见**。能不能看见，由它写在哪一对大括号里决定，这叫**作用域**。想让别的函数也能读写它，只有两条路：把它拿到函数外面变全局，或者让函数把值返回出来。

**探针三**：给公告栏加一个访客。在 `count_local` 里也加一句 `g_count = 100;`，重新构建并运行。三轮打印出来都是 101，计数再也涨不起来（我这里验证过）。公告栏的问题就在这里：谁都能改，出了错，你得翻遍整个程序找是谁改的。

### 第四步：局部变量去哪了

函数返回以后，那张草稿纸去哪了？这是本节的核心问题。我们让两个毫不相干的函数各开一个局部变量，打印它们的地址：

```c
#include <stdio.h>

/* 两个毫不相干的函数，各有一个局部变量，打印它们的地址 */
void first(void) {
    int a = 1;
    printf("first : &a = %p\n", (void *)&a);
}

void second(void) {
    int b = 2;
    printf("second: &b = %p\n", (void *)&b);
}

int main(void) {
    first();
    second();
    first();
    return 0;
}
```

保存为 `src/scope_addr.c`，在 `CMakeLists.txt` 末尾加一行 `add_demo(scope_addr)`，构建并运行。先猜，再运行。

> [!question] 先猜一猜
> `first`、`second`、`first` 三次打印的地址，是三个不同的，还是有相同的？

> [!success]- 揭晓
> 我这台机器上是这样的（地址每台机器不同，但"是否相同"的结论应该一致）：
>
> ```
> first : &a = 0061ff0c
> second: &b = 0061ff0c
> first : &a = 0061ff0c
> ```
>
> 三个全是同一个地址。草稿纸收走以后，桌面上那块地方没有消失，只是被下一个来的人接着用了。

所以答案是：局部变量没有"去"哪，它占的那块地方被**归还**了，下一个函数会借走同一块。这块地方所在的区域叫**[[【原理】栈与函数调用|栈]]**。

这带来一个后果。如果新来的人没把纸擦干净就直接读，会读到什么？

```c
#include <stdio.h>

int g_zero;                      /* 全局变量没写初值：自动是 0 */

/* 上一个客人在草稿纸上写了 42，走的时候没擦 */
void leave_note(void) {
    int x = 42;
    printf("leave_note: x = %d\n", x);
}

/* 这个函数的局部变量没赋初值，会看到什么？ */
void read_note(void) {
    int y;
    printf("read_note : y = %d\n", y);
}

int main(void) {
    static int s_zero;           /* static 局部也一样，默认 0 */
    printf("g_zero = %d, s_zero = %d\n", g_zero, s_zero);
    leave_note();
    read_note();
    return 0;
}
```

保存为 `src/scope_uninit.c`，在 `CMakeLists.txt` 末尾加一行 `add_demo(scope_uninit)`，构建并运行。先猜，再运行。

> [!question] 先猜一猜
> `read_note` 里的 `y` 没赋过值。它会打印什么？全局和 `static` 的那两个呢？

> [!success]- 揭晓
> 先把 `build` 目录配置成 Debug（不做优化）：`cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Debug`，构建并运行。我的输出是：
>
> ```
> g_zero = 0, s_zero = 0
> leave_note: x = 42
> read_note : y = 42
> ```
>
> 没赋值的 `y` 读到了 42，正是上一个函数留下的数。全局变量和 `static` 变量没赋初值，会被自动清零；局部变量不会。

**探针四**：再配置一个 Release 构建目录（gcc 下 CMake 的 Release 会加 `-O3 -DNDEBUG`，这是我在本机生成的 `build.ninja` 里查到的），构建并运行同一份代码：

```
cmake -S . -B build-release -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build-release
./build-release/scope_uninit
```

我这里 `y` 变成了：

```
g_zero = 0, s_zero = 0
leave_note: x = 42
read_note : y = 0
```

结果跟着优化等级变了。没赋初值的局部变量，读出来的值是**没有保证的**。注意，两次构建 gcc 都给了警告 `'y' is used uninitialized`。`-Wall` 就是用来拦这种事的，别忽略它。

### 第五步：套娃（递归）

还记得办公室的比喻吗？每遇到一个子问题，你就在桌上铺一张新草稿纸，算完了，把这张纸撕掉。桌子只有那么大。如果每个子问题里又套着子问题，纸越铺越多，终于有一刻，桌上放不下了。

程序里真有这么一张桌子，它放不下的时候，程序会直接倒下。那个著名的程序员问答网站叫 Stack Overflow，名字就取自这种倒下的方式（待核对）。

函数可以调用自己，这叫**递归**。每套一层，桌上就多一张草稿纸。先写一个经典例子，阶乘：

```c
#include <stdio.h>

/* n 的阶乘。用 unsigned long long，因为阶乘长得很快。 */
unsigned long long fact(int n) {
    if (n <= 1) {
        return 1;
    }
    return (unsigned long long)n * fact(n - 1);
}

int main(void) {
    for (int n = 1; n <= 5; n++) {
        printf("%d! = %llu\n", n, fact(n));
    }
    printf("20! = %llu\n", fact(20));
    printf("21! = %llu\n", fact(21));
    return 0;
}
```

保存为 `src/fact.c`，在 `CMakeLists.txt` 末尾加一行 `add_demo(fact)`，构建并运行。

```
1! = 1
2! = 2
3! = 6
4! = 24
5! = 120
20! = 2432902008176640000
21! = 14197454024290336768
```

20 的阶乘 2432902008176640000 是对的。21 的阶乘打出来的数不对，这是 1.2 里的老朋友：`unsigned long long` 装不下了，回绕。这个错和递归深度无关，别混了。

现在看看"桌子"是怎么被占用的。下面这个程序每下潜一层，就打印一次那一层局部变量的地址。它**只下潜 4 层就停**，不会真的把桌子摆满：

```c
#include <stdio.h>
#include <stdint.h>

static uintptr_t g_prev = 0;     /* 上一层局部变量的地址 */

/* 每进一层，就多摆一张草稿纸。
   这里只下潜 max 层，打印每层局部变量的地址，不会真的把桌子摆满。 */
void dive(int depth, int max) {
    int marker = depth;          /* 本层的一个局部变量 */
    uintptr_t here = (uintptr_t)&marker;

    if (depth == 0) {
        printf("depth %d: %p\n", depth, (void *)&marker);
    } else {
        printf("depth %d: %p  (lower than previous by %lu bytes)\n",
               depth, (void *)&marker, (unsigned long)(g_prev - here));
    }
    g_prev = here;

    if (depth < max) {
        dive(depth + 1, max);
    }
}

int main(void) {
    dive(0, 4);
    return 0;
}
```

保存为 `src/stack_dive.c`，在 `CMakeLists.txt` 末尾加一行 `add_demo(stack_dive)`，构建并运行。

```
depth 0: 0061fef8
depth 1: 0061fec8  (lower than previous by 48 bytes)
depth 2: 0061fe98  (lower than previous by 48 bytes)
depth 3: 0061fe68  (lower than previous by 48 bytes)
depth 4: 0061fe38  (lower than previous by 48 bytes)
```

每深一层，地址就低一截，我这里每层占 48 字节（这是我的机器和编译选项下的结果，你的数字会不同）。地址往低处长，是栈的习惯，这一点留给分支去讲。

那么桌子到底多大？下面这个程序从命令行读一个深度 `n`，递归地算 1 加到 `n`。你一档一档往上加，自己找极限：

```c
#include <stdio.h>
#include <stdlib.h>

/* 递归求 1 + 2 + ... + n。每一层都要等下一层的结果，所以所有层都得留在栈上。 */
long long sum_to(long long n) {
    if (n == 0) {
        return 0;                /* 终止条件：没有它，递归永远不会停 */
    }
    return n + sum_to(n - 1);
}

int main(int argc, char *argv[]) {
    long long n = 10;
    if (argc > 1) {
        n = atoll(argv[1]);       /* 从命令行读深度，方便一档一档往上加 */
    }
    printf("sum_to(%lld) = %lld\n", n, sum_to(n));
    return 0;
}
```

保存为 `src/stack_sum.c`，加一行 `add_demo(stack_sum)`。用不做优化的 Debug 构建目录 `build`，避免编译器自作主张。构建后一档一档往上加：

```
./build/stack_sum 1000
./build/stack_sum 10000
./build/stack_sum 40000
./build/stack_sum 50000
./build/stack_sum 1000000
```

> [!example] 我这台机器上的结果（Windows，MinGW gcc 6.3.0；你的数字会不同）
> - `1000`、`10000`、`40000` 都正常，`1000` 的输出是 `sum_to(1000) = 500500`
> - `50000` 开始，程序什么都没打印就消失了。在 PowerShell 里查退出码，是 `0xC00000FD`（Windows 对栈溢出的标记）
> - 也就是说，在我这里极限在 40000 到 50000 层之间

这样"崩"是安全的：操作系统只会终止这一个程序，电脑不会卡死。在 Linux 上你会看到 `Segmentation fault`（段错误）。

**探针五**：同样的代码，用上面配置的 Release 目录构建，再试 `./build-release/stack_sum 1000000`。我这里它居然算出来了：`sum_to(1000000) = 500000500000`。编译器看穿了这个递归，把它改写成了循环，桌子根本没被占用。但这是优化的"好心"，不是语言保证的，换个写法或换个编译选项，它就可能不改。**不要靠它**。

## 刚才发生了什么

三种变量，放在一张表里：

| 种类 | 比喻 | 真名 | 活多久 | 没赋初值 | 谁能看见 |
|---|---|---|---|---|---|
| 草稿纸 | 进门领、出门收 | 局部变量（自动存储期） | 函数一次调用期间 | **不确定**（可能是旧数据） | 它所在的大括号里 |
| 公告栏 | 走廊里挂着 | 全局变量（静态存储期） | 整个程序运行期间 | 0 | 整个文件（及其他文件） |
| 笔记本 | 锁在抽屉里 | `static` 局部变量（静态存储期） | 整个程序运行期间 | 0 | 只有它所在的大括号里 |

全局变量和 `static` 变量没赋初值时是 0，这件事不是魔法：程序真正开始跑 `main` 之前，有一段启动代码先把它们清零。在电脑上由系统和库代替你做，在单片机上这段代码就是工程里的启动文件（2.4 会看到）。想知道变量具体放在内存的哪一块，见 [[【原理】启动流程与链接脚本|启动流程与链接脚本]]。

还有一种常见情况：内层变量和外层变量同名，内层的会**遮住**外层的。练习三会让你撞上它。

"草稿纸怎么铺、怎么收"的机制，每次调用在栈上占的那一块叫**栈帧**。函数一调用，系统就在栈顶划一块给它放参数和局部变量；一返回，这块就还回去。这就是为什么第四步里的地址会重复，也是递归能"套娃"的原因：每一层有自己的一块。细节放在分支里。

最后回到开头。三段复制粘贴的代码，错在同一件事出现了三份。现在你知道怎么办了：打包成函数，量程只写一处，这就是封装。至于第三步那三个计数器：`local` 每次进门领新纸，所以永远是 1；`global` 在公告栏上，谁加都累积；`static` 在抽屉里，只有自己翻，但也一直累积。

**到单片机上会怎样**：栈同样放在 RAM 里，但 RAM 以 KB 计。CubeMX 生成的链接脚本里，默认栈大小我印象中只有 0x400，也就是 1 KB（待核对，以你工程里的链接脚本为准）。在 PC 上能下潜四万层的递归，在板子上可能几十层就越界了。这就是为什么板上代码里基本见不到递归，也不会在函数里开一个很大的局部数组。

## 记住这几条

1. **同一件事不要写第二遍**。重复出现的逻辑，打包成函数（封装）：调用的人只依赖名字、参数、返回值，要改，只改一处。
2. **局部变量用之前一定先赋初值**。读没赋过值的局部变量，结果没有保证，还会随着优化等级变。
3. **想让函数"记住上一次"，用 `static` 局部变量**，不要为此新开一个全局变量。它活得久，又不会被别的函数乱改。
4. **全局变量能少用就少用**，用了就加 `g_` 前缀，一眼认出它。全局变量是谁都能改的公告栏，出了错很难找人。
5. **函数的参数是复印件**。想让函数改到外面的变量，得传地址（下一节）。
6. **递归必须有终止条件，并且要估算最大深度**。在单片机上，默认不写递归；也不要在函数里放大数组当局部变量。
7. **别返回局部变量的地址**。函数一返回，那块地方就归还了，下一节会专门撞一次。

## 练习

1. 在你的机器上，用 Debug 构建找出 `sum_to` 崩溃的深度范围，再换 Release 构建看看还崩不崩，记下你的结论。（复现）
2. 写一个函数 `int next_id(void)`，每调用一次返回 1、2、3……，不许用全局变量。（改造）
3. 先写下预测，再运行。下面程序的四行输出分别是什么？（预测）

```c
#include <stdio.h>

int total = 10;

/* 参数也叫 total，会把全局的 total 遮住 */
int step(int total) {
    total += 1;
    return total;
}

int bump(void) {
    static int calls = 0;
    calls += 2;
    total += calls;
    return total;
}

int main(void) {
    printf("%d\n", step(total));
    printf("%d\n", total);
    printf("%d\n", bump());
    printf("%d\n", bump());
    return 0;
}
```

保存为 `src/scope_predict.c`，在 `CMakeLists.txt` 末尾加一行 `add_demo(scope_predict)`，构建并运行。

> [!success]- 提示与答案方向
> 1. 数字因机器而异。Release 下大概率不崩，因为递归被改写成了循环；但这不是保证。
> 2. 答案如下（保存为 `src/next_id.c`，加一行 `add_demo(next_id)`），输出 `id = 1`、`id = 2`、`id = 3`：
>
> ```c
> #include <stdio.h>
>
> /* 每调用一次返回下一个编号：1, 2, 3 ... */
> int next_id(void) {
>     static int id = 0;           /* 只初始化一次，函数返回后仍然活着 */
>     id++;
>     return id;
> }
>
> int main(void) {
>     for (int i = 0; i < 3; i++) {
>         printf("id = %d\n", next_id());
>     }
>     return 0;
> }
> ```
>
> 3. 输出依次是 `11`、`10`、`12`、`16`。
>    - 第一行：`step` 的参数 `total` 遮住了全局的 `total`，里面加一改的是复印件，返回 11。
>    - 第二行：全局的 `total` 没被动过，还是 10。
>    - 第三行：`bump` 第一次调用，`calls` 变成 2，全局 `total` 变成 12。
>    - 第四行：第二次调用，`calls` 记得上次的 2，变成 4，`total` 变成 16。
