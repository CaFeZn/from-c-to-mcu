# 1.8 程序变大了：拆文件，让 CMake 管起来

> **这一节你会做出**：把 1.7 的命令表拆成 `main.c` / `util.c` / `util.h` 三个文件，用自己的 `CMakeLists.txt` 编成一个程序；亲手踩一遍宏的坑、头文件重复包含、重复定义、漏链接一个文件；用 CMake 的开关切换一套跟踪输出；最后学会让头文件只露出接口、把内部藏起来。
> **前置**：[[1.4_函数与作用域]]　[[1.7_函数指针与回调]]，以及 `c-lab` 工程的三步（配置、构建、运行）　｜　**预计**：阅读 + 动手 70 分钟

> [!tip]- 已经做过多文件工程：跳读自测
> 先回答下面几个问题（写下来，别只在心里答）。**全部答对**就直接跳到 [[1.9_小项目_命令解析器]]；有一题拿不准，就从头读。
> 1. 下面程序输出什么？
>    ```c
>    #define TWICE(x) x + x
>    printf("%d\n", 3 * TWICE(2));
>    ```
> 2. 把 `int g_count = 0;` 写进头文件 `util.h`，`util.c` 和 `main.c` 都 `#include "util.h"`。是编译阶段报错，还是链接阶段？大意是什么？
> 3. 头文件守卫（`#ifndef X_H` / `#define X_H` / `#endif`）防的是什么事？
> 4. `main.c` 调用了 `util.c` 里的函数，但 `CMakeLists.txt` 里的 `add_executable` 只列了 `src/main.c`。构建时看到 `undefined reference to ...`，是编译器还是链接器报的？
>
> > [!success]- 答案，以及跳过后要带走的东西
> > 1. **8**。展开成 `3 * 2 + 2`，先乘后加。宏要加括号：`#define TWICE(x) ((x) + (x))`。
> > 2. 链接阶段。两个 `.c` 各自编译都通过，链接时发现 `g_count` 有两份定义，报 `multiple definition of ...`。头文件里应该写 `extern int g_count;`，定义只放在一个 `.c` 里。
> > 3. 同一个头文件被直接或间接包含多次时，里面的类型、声明被重复贴进来，导致重复定义的错误。守卫让后面几次的内容整段被跳过。
> > 4. 链接器。编译器每次只看一个 `.c`，漏掉 `util.c` 是链接时才发现找不到定义。`add_executable` 的源文件列表，就是要编成 `.o` 并链接在一起的全部文件。
> >
> > **带走清单**：
> > - 头文件守卫模板：`#ifndef XXX_H` 开头、`#define XXX_H` 紧随其后、`#endif` 收尾，后面所有头文件（`cmd.h`、`log.h` 等）都这样写。
> > - 宏的写法规矩：参数和整体都加括号，参数里不放有副作用的表达式。
> > - `ARRAY_LEN(a)` 宏：`(sizeof(a) / sizeof((a)[0]))`，1.9 的 `main.c` 会再写一遍，只对真数组有效。
> > - 多文件项目的 CMake 写法：`projects/<名字>/CMakeLists.txt` 里 `add_executable(名字 源文件...)` 加 `target_include_directories(名字 PRIVATE include)`，顶层用 `add_subdirectory` 收进来。单片机工程里这件事由 `User/Src` 的自动收集完成（见 2.2）。
> > - 开关的写法：`option()` 加 `target_compile_definitions()` 给编译器传 `-DXXX`，源码里用 `#ifdef XXX`，3.1 的日志开关是同一个思路。
> > - 模块的写法：`.h` 就是对外的接口，只放类型和函数声明；模块内部用的函数和变量一律写 `static`。需要被外面用的东西，才进头文件。后面所有模块（日志、按键、串口命令行）都这样拆。
> > - 本节的 `util.h` / `util.c` / `main.c` 后面不再用，不用保留。

## 命令越写越多，先把要改的地方分开

1.7 的命令表已经能工作了。接下来再添几条命令时，命令的实现、查表过程和测试代码会一起增长。你只是想改一下 `echo`，却要在同一个文件里来回找；换一个小程序，又想复用同样的处理函数。

这时需要的不是先背一个新名词，而是把相关功能放到各自的位置，同时让工程仍然一键构建。下面先完成这件事，再从它引出的实际问题认识头文件、声明和宏。

## 动手做

### 第一步：把命令表拆成三个文件，让 CMake 编成一个程序

先把命令处理和程序入口分开。`main.c` 管命令表和执行流程，`util.c` 放各条命令的实现，`util.h` 列出两边共用的类型与函数。再给这个小项目写一份 `CMakeLists.txt`，告诉构建工具要把哪些文件放到一起。

这次的结果仍然是同一个命令表程序，改变的是文件组织。先按下面的位置放好文件，构建并运行，再回来看配置。

多文件项目放在 `c-lab/projects/` 下，每个项目一个子目录、一份自己的 `CMakeLists.txt`：

```
c-lab/
  CMakeLists.txt              顶层：末尾加一行 add_subdirectory(projects/cmdtab)
  projects/
    cmdtab/
      CMakeLists.txt          这个项目自己的构建说明
      include/util.h
      src/util.c
      src/main.c
```

下面的文件可以直接使用。`g_count` 用来统计执行过的命令，`TRACE` 是可开关的跟踪输出；先保留现状，后面的声明与条件编译步骤会用到它们。

`projects/cmdtab/include/util.h`：

```c
#ifndef UTIL_H
#define UTIL_H

#include <stddef.h>
#include <stdio.h>

/* 命令表的一行：名字、处理函数、一句话帮助 */
typedef struct {
    const char *name;
    int (*fn)(int argc, char *argv[]);   /* 返回 0 成功，非 0 失败 */
    const char *help;
} cmd_t;

/* 数组元素个数。只对真正的数组有效，对指针无效（1.5 讲过） */
#define ARRAY_LEN(a) (sizeof(a) / sizeof((a)[0]))

/* 编译时定义了 VERBOSE（第八步用 CMake 的开关传进来）才会打印跟踪信息，否则整句消失 */
#ifdef VERBOSE
#define TRACE(...) do { printf("[trace] "); printf(__VA_ARGS__); printf("\n"); } while (0)
#else
#define TRACE(...) ((void)0)
#endif

/* 已执行过的命令条数。这里只"声明"，定义在 util.c */
extern int g_count;

/* 三个命令处理函数 */
int cmd_hello(int argc, char *argv[]);
int cmd_add(int argc, char *argv[]);
int cmd_echo(int argc, char *argv[]);

/* 按名字查表并调用；找不到返回 -1 */
int dispatch(const cmd_t *table, size_t n, int argc, char *argv[]);

#endif /* UTIL_H */
```

`projects/cmdtab/src/util.c`：

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include "util.h"

/* 全局变量的"定义"只能出现在一个 .c 里 */
int g_count = 0;

int cmd_hello(int argc, char *argv[]) {
    (void)argc;
    (void)argv;
    printf("hello from the table\n");
    return 0;
}

int cmd_add(int argc, char *argv[]) {
    if (argc != 3) {
        printf("usage: add A B\n");
        return 1;
    }
    printf("%d\n", atoi(argv[1]) + atoi(argv[2]));
    return 0;
}

int cmd_echo(int argc, char *argv[]) {
    for (int i = 1; i < argc; i++) {
        printf("%s%s", argv[i], (i + 1 < argc) ? " " : "");
    }
    printf("\n");
    return 0;
}

int dispatch(const cmd_t *table, size_t n, int argc, char *argv[]) {
    TRACE("looking for '%s' among %lu commands", argv[0], (unsigned long)n);
    for (size_t i = 0; i < n; i++) {
        if (strcmp(table[i].name, argv[0]) == 0) {
            TRACE("found at index %lu", (unsigned long)i);
            g_count++;
            return table[i].fn(argc, argv);
        }
    }
    TRACE("not found");
    return -1;
}
```

`projects/cmdtab/src/main.c`：

```c
#include <stdio.h>
#include "util.h"

/* 命令表放在 main.c：想加命令，在这里加一行，再到 util.c 写函数、util.h 补声明 */
static const cmd_t g_cmds[] = {
    { "hello", cmd_hello, "say hello" },
    { "add",   cmd_add,   "add A B: print A+B" },
    { "echo",  cmd_echo,  "echo WORDS: print them back" },
};

/* 打印一次调用的结果，方便观察 */
static void run(int argc, char *argv[]) {
    printf("> %s\n", argv[0]);
    printf("  rc=%d\n", dispatch(g_cmds, ARRAY_LEN(g_cmds), argc, argv));
}

int main(void) {
    char *t1[] = { "hello" };
    char *t2[] = { "add", "3", "4" };
    char *t3[] = { "echo", "a", "b", "c" };
    char *t4[] = { "fly" };

    run(1, t1);
    run(3, t2);
    run(4, t3);
    run(1, t4);
    printf("g_count=%d\n", g_count);
    return 0;
}
```

`projects/cmdtab/CMakeLists.txt`（现在只有这几行，第八步还会加）：

```cmake
# 一个多文件项目：两个源文件，一个头文件目录
add_executable(cmdtab
    src/main.c
    src/util.c
)
target_include_directories(cmdtab PRIVATE include)
```

然后在 `c-lab/CMakeLists.txt` 的末尾加一行：

```cmake
add_subdirectory(projects/cmdtab)
```

保存全部文件，在 VS Code 里依次执行 `CMake: Configure`、`CMake: Build`，再用 `CMake: Set Launch/Debug Target` 选中 `cmdtab`，执行 `CMake: Run Without Debugging`。不需要重新创建整个 c-lab。

> [!tip]- 习惯终端时的等价操作
> 在 c-lab 根目录运行：
> ```powershell
> cmake -S . -B build -G Ninja
> cmake --build build --target cmdtab
> .\build\projects\cmdtab\cmdtab.exe
> ```
> Bash、Linux 或 macOS 的最后一行写成 `./build/projects/cmdtab/cmdtab`。

你应该看到：

```
> hello
hello from the table
  rc=0
> add
7
  rc=0
> echo
a b c
  rc=0
> fly
  rc=-1
g_count=3
```

程序跑通后，再读刚才的三个安排：

- `add_subdirectory(projects/cmdtab)`：让顶层工程进入这个子目录，读取它自己的构建说明。
- `add_executable(cmdtab ...)`：把列出的两个 `.c` 文件做成同一个 `cmdtab` 程序。清单漏掉一份实现，构建时就找不到那一份功能。
- `target_include_directories(cmdtab PRIVATE include)`：这个程序需要从 `include` 目录找头文件。`PRIVATE` 表示这条设置给 `cmdtab` 自己使用。

1.0 已经用过 CMake，只是每个例子只有一个源文件。这次它开始管理一个程序中的多个文件：你维护清单，构建时交给工具处理。

新增一条命令现在要动三处：`util.c` 里写函数，`util.h` 里补声明，`main.c` 的表里加一行。如果你新增的是一个**新的 `.c` 文件**，还要多做一件事：把它加进 `add_executable` 的列表。

若程序能构建，编辑器却把 `util.h` 或调用处标红，先检查它是否使用了 CMake 的配置，见 [[【拓展】让VSCode看懂CMake工程]]。不要为消除提示，把真实的构建清单和代码改乱。

CMake 还能按依赖决定哪些文件需要重新处理。先用下面这个小改动观察它，再决定要不要展开命令细节。

> [!info]- 选读：看真实构建命令和目标文件里的名字
> 想确认工具实际调用了什么，可以查看详细日志。这一段是选读，不要求先读过第 0 章。先清掉旧产物（否则已经是最新的，什么也不会重新做），再加上 `--verbose`（简写 `-v`）构建，它会打印每一条真正执行的命令：
>
> ```
> cmake --build build --target clean
> cmake --build build --target cmdtab --verbose
> ```
>
> 我这台机器上（MinGW gcc 6.3 加 Ninja），输出是下面三行。为了好读，我把绝对路径和依赖文件相关的选项做了省略，你的路径不同：
>
> ```
> [1/3] C:\MinGW\bin\gcc.exe  -I.../projects/cmdtab/include -std=c99 -Wall -Wextra ... -o projects/cmdtab/CMakeFiles/cmdtab.dir/src/main.c.obj -c .../projects/cmdtab/src/main.c
> [2/3] C:\MinGW\bin\gcc.exe  -I.../projects/cmdtab/include -std=c99 -Wall -Wextra ... -o projects/cmdtab/CMakeFiles/cmdtab.dir/src/util.c.obj -c .../projects/cmdtab/src/util.c
> [3/3] ... gcc.exe  projects/cmdtab/CMakeFiles/cmdtab.dir/src/main.c.obj projects/cmdtab/CMakeFiles/cmdtab.dir/src/util.c.obj -o projects\cmdtab\cmdtab.exe ... -lkernel32 -luser32 ...
> ```
>
> 前两行各编译一个 `.c`（选项里的 `-c` 就是"只编译不链接"），各自产出一个目标文件（MinGW 上后缀是 `.obj`，Linux 和 macOS 上是 `.o`）；第三行才是链接，把两个目标文件拼成 `cmdtab.exe`。注意 `-I` 就是 `target_include_directories` 给的，`-std=c99 -Wall -Wextra` 来自顶层的设置。这些命令由构建工具安排，不需要每加一个文件就手动重写一串命令。
>
> 看看那两个目标文件里各留下了什么：
>
> ```
> nm build/projects/cmdtab/CMakeFiles/cmdtab.dir/src/main.c.obj
> ```
>
> 在输出里找这几行（MinGW 下名字前多一条下划线，地址你的会不同）：
>
> ```
>          U _cmd_add
>          U _cmd_echo
>          U _cmd_hello
>          U _dispatch
> 00000060 r _g_cmds
>          U _g_count
> 00000079 T _main
> ```
>
> `U` 表示这个目标文件引用了一个尚未在本文件中定义的名字：`main.c` 只在头文件里见过 `dispatch` 和 `cmd_add` 的声明，真身不在这儿，等链接器去 `util.c.obj` 里找。`_main` 前面是 `T`，说明 `main.c.obj` 自己定义了它。
>
> 这种"每个 `.c` 各自编译成目标文件，最后再统一链接"的做法，叫**分别编译**。它还有个实惠的好处：

> [!example] 探针：只改一个文件
> 在 `util.c` 末尾随手加一行注释，再构建一次：
> ```
> cmake --build build --target cmdtab
> ```
> 我这台机器上的输出：
> ```
> [1/2] Building C object projects/cmdtab/CMakeFiles/cmdtab.dir/src/util.c.obj
> [2/2] Linking C executable projects\cmdtab\cmdtab.exe
> ```
> 只重新编译了 `util.c`，`main.c` 的目标文件原样拿来链接。再构建一次，什么也不会做（Ninja 会告诉你 `no work to do`）。文件一多，这就是省下的时间。

> [!example] 探针：漏掉一个文件
> 把 `projects/cmdtab/CMakeLists.txt` 里 `add_executable` 列表中的 `src/util.c` 一行删掉，再构建。
> 我这台机器上，CMake 先自动重新配置，编译 `main.c` 没有问题，到链接这一步报：
> ```
> projects/cmdtab/CMakeFiles/cmdtab.dir/src/main.c.obj:main.c:(.text+0x62): undefined reference to `dispatch'
> projects/cmdtab/CMakeFiles/cmdtab.dir/src/main.c.obj:main.c:(.text+0x120): undefined reference to `g_count'
> projects/cmdtab/CMakeFiles/cmdtab.dir/src/main.c.obj:main.c:(.rdata+0x64): undefined reference to `cmd_hello'
> ...
> collect2.exe: error: ld returned 1 exit status
> ninja: build stopped: subcommand failed.
> ```
> 这些名字都由漏掉的 `util.c` 提供，链接器找不到它们的实现。注意**这是链接器在报错，不是编译器**，`main.c` 本身没有任何毛病，毛病在 `add_executable` 的列表里少了一个文件。看完把那一行加回来。

先把刚才的拆分保存成一个可回看的版本：构建并运行确认行为未变，再看 `git diff`，只暂存这次涉及的源码和 CMake 清单，提交为“拆分命令表与实现”。不要把 `build` 加进去。后面实验删文件或改宏之前，都可以沿用这条小步习惯；具体操作见[Git 实践](/notes/git-workflow)。

### 第二步：头文件守卫

> [!question] 先猜一猜
> 把 `util.h` 里最上面的 `#ifndef UTIL_H`、`#define UTIL_H` 和最下面的 `#endif` 三行删掉，再在 `main.c` 里把 `#include "util.h"` 写两遍。能编译过吗？

> [!success]- 揭晓
> 过不了。

动手试：改完直接构建。错误出现在编译 `main.c` 这一步，还没走到链接。我这台机器上的第一条是：

```
.../projects/cmdtab/include/util.h:10:3: error: conflicting types for 'cmd_t'
 } cmd_t;
   ^~~~~
```

后面还会跟几条连带的错误，先看第一条就够了（路径是我省略过的）。

原因是秘书老实：`#include` 就是"把那个文件整个贴进来"，写两遍就贴两遍，`cmd_t` 被定义了两次。你不会故意写两遍，但很容易间接发生：`a.h` 包含了 `util.h`，`b.h` 也包含了 `util.h`，`main.c` 又同时包含 `a.h` 和 `b.h`。

恢复那三行，它们叫**头文件守卫**。第一次贴进来时，`UTIL_H` 还没定义，于是定义它并保留正文；第二次再贴，`#ifndef UTIL_H` 为假，整段被跳过。

### 第三步：头文件里只放声明

> [!question] 先猜一猜
> 把 `util.h` 里的 `extern int g_count;` 改成 `int g_count = 0;`，并删掉 `util.c` 里的同名定义，然后构建。三个步骤里（编译 `main.c`、编译 `util.c`、链接），哪几步会出问题？

> [!success]- 揭晓
> 两个 `.c` 各自的编译步骤都通过，只有最后的链接步骤失败。

我这台机器上，链接这一步的报错是：

```
projects/cmdtab/CMakeFiles/cmdtab.dir/src/util.c.obj:util.c:(.bss+0x0): multiple definition of `g_count'
projects/cmdtab/CMakeFiles/cmdtab.dir/src/main.c.obj:main.c:(.bss+0x0): first defined here
collect2.exe: error: ld returned 1 exit status
ninja: build stopped: subcommand failed.
```

这同样是**链接器**在报错，不是编译器。两个文件都包含了 `util.h`，于是每个目标文件里都生出一个 `g_count`。编译器每次只看一个文件，发现不了；链接器把两个目标文件拼到一起，才发现同一个名字有两个"真身"。到这里就能区分：每个源文件先分别检查和处理，再把需要的实现组合到一起。**编译和链接是两件事**，不必预先学过它们也能从这次报错看出分工。

正确做法是分工：头文件里用 `extern int g_count;` **声明**"这个变量存在，在别处"；恰好一个 `.c` 里写 `int g_count = 0;` **定义**它。`extern` 就是 `U` 便签的源头。

规矩：**头文件放声明，.c 文件放定义。**

### 第四步：头文件只露接口，内部都藏起来

回头看 `util.h`：它把 `g_count` 也 `extern` 出去了，任何文件都能读、都能改。那是为了演示 `extern` 才留的。写真正的模块时，要反过来想：头文件是这个模块**对外的接口**，只放使用者需要的类型和函数声明；模块内部用的函数和变量，一律写成 `static`，别的文件既看不见，也调不到。

这就是 1.4 里"封装"在多文件工程中的样子：对外只留名字、参数、返回值，其余藏起来。我们用 1.6 的对象写法做一个小模块：计数器。它也是 `c-lab` 里的一个多文件项目：

```
c-lab/projects/counter/
  CMakeLists.txt
  include/counter.h
  src/counter.c
  src/counter_main.c
  src/counter_bad.c      （等一下用）
```

`projects/counter/include/counter.h`：

```c
#ifndef COUNTER_H
#define COUNTER_H

/* 对外公开的只有：一个类型、三个函数。
 * 别人能用它做什么，看这一个文件就够了。 */
typedef struct {
    int value;
    int step;
} counter_t;

void counter_init(counter_t *c, int step);
void counter_inc(counter_t *c);
int  counter_get(const counter_t *c);

#endif /* COUNTER_H */
```

`projects/counter/src/counter.c`：

```c
#include "counter.h"

/* 内部函数：头文件里没有它，并且写成 static，
 * 别的文件既看不见，也调不到。 */
static int clamp_to_limit(int v) {
    return v > 100 ? 100 : v;      /* 计数最多到 100 */
}

void counter_init(counter_t *c, int step) {
    c->value = 0;
    c->step = step;
}

void counter_inc(counter_t *c) {
    c->value = clamp_to_limit(c->value + c->step);
}

int counter_get(const counter_t *c) {
    return c->value;
}
```

`projects/counter/src/counter_main.c`：

```c
#include <stdio.h>
#include "counter.h"

int main(void) {
    counter_t a, b;                 /* 两个计数器对象，各管各的 */
    counter_init(&a, 1);
    counter_init(&b, 60);

    for (int i = 0; i < 3; i++) {
        counter_inc(&a);
        counter_inc(&b);
    }
    printf("a = %d, b = %d\n", counter_get(&a), counter_get(&b));
    return 0;
}
```

`projects/counter/CMakeLists.txt`：

```cmake
add_executable(counter
    src/counter_main.c
    src/counter.c
)
target_include_directories(counter PRIVATE include)
```

顶层 `CMakeLists.txt` 末尾再加一行 `add_subdirectory(projects/counter)`。构建并运行 `./build/projects/counter/counter`，你应该看到：

```
a = 3, b = 100
```

`a` 每次加 1，`b` 每次加 60，到 100 封顶。两个计数器各管各的，互不干扰。`clamp_to_limit` 是内部细节，不在头文件里，使用者既不需要知道它，也不该依赖它。

正常版本跑通后，再新建一个坏版本 `projects/counter/src/counter_bad.c`，让 `main` 试着调用内部函数：

```c
#include <stdio.h>
#include "counter.h"

int main(void) {
    /* 偷用 counter.c 里的内部函数 */
    printf("%d\n", clamp_to_limit(150));
    return 0;
}
```

保存坏版本的文件后，在 `projects/counter/CMakeLists.txt` 末尾**追加**下面这个独立目标。先有文件，再把它列入清单，前面的正常版本不受影响：

```cmake
# 故意写错的版本：不放进默认构建，需要时用 --target counter_bad 单独构建
add_executable(counter_bad EXCLUDE_FROM_ALL
    src/counter_bad.c
    src/counter.c
)
target_include_directories(counter_bad PRIVATE include)
```

它不会参与默认构建。要观察这个故意错误的例子，执行 `cmake --build build --target counter_bad`。

### 第五步：用宏收拢重复写法，先看一次失误

前面的 `util.h` 已经用了 `ARRAY_LEN` 和 `TRACE`。有些反复出现的写法可以写成宏，但它和函数不完全一样。

可以把处理宏的工具想成一位只会剪刀加胶水的秘书。你说"把 `x * x` 贴到这里，x 换成 `1 + 2`"，他就一个字不差地贴上去。贴完通不通，他不管；算出来对不对，他更不管。

这项文本处理叫**预处理**。先用一个小例子看看它容易在哪儿出错：

```c
#include <stdio.h>

#define SQUARE(x) x * x

int main(void) {
    printf("%d\n", SQUARE(3));
    printf("%d\n", SQUARE(1 + 2));
    return 0;
}
```

> [!question] 先猜一猜
> 这个程序打印两行。第一行是 `SQUARE(3)`，第二行是 `SQUARE(1 + 2)`。它们各是多少？

> [!success]- 揭晓
> 第一行 9，第二行 **5**，不是 9。


存成 `src/macro1.c`，在 `c-lab/CMakeLists.txt` 末尾加一行 `add_demo(macro1)`，构建并运行 `./build/macro1`。

你应该看到：

```
9
5
```

没有报错，没有警告，答案就是错的。先别急着下结论，把可能的原因一个个检验。

> [!failure] 猜想 1：编译器算错了
> 不能只凭一个结果猜工具出错。下面直接查看宏替换后的表达式，再用已学过的运算优先级计算，比较代码实际要求了什么。

> [!failure] 猜想 2：`1 + 2` 先算成 3 再传进去，像函数调用那样
> 如果是这样，结果应该是 `3 * 3 = 9`。对不上。划掉。

宏会把参数原样替换进去：`SQUARE(1 + 2)` 展开成 `1 + 2 * 1 + 2`，乘法先算，所以结果是 5。

> [!info]- 选读：让工具显示替换后的代码
> 让秘书招供。`gcc -E` 只做预处理就停下，输出很长，看最后几行。这一步专门看预处理那一站，所以直接调 gcc（在 `c-lab` 目录里）：
>
> ```
> gcc -E -std=c99 src/macro1.c
> ```
>
> 我这台机器上，输出末尾是：
>
> ```
> int main(void) {
>     printf("%d\n", 3 * 3);
>     printf("%d\n", 1 + 2 * 1 + 2);
>     return 0;
> }
> ```

真相在这里：秘书把 `x` 原样换成了 `1 + 2`，没有加任何括号。乘法优先于加法，所以是 `1 + (2 * 1) + 2 = 5`。

现在可以起名字了：`#define` 定义出来的东西叫**宏**，把宏换成它的内容叫**宏展开**。普通宏展开操作的是预处理记号，不会替你按表达式优先级自动补括号或计算结果；但 `#if` 条件确实会求值允许的整数常量表达式，不能概括成预处理器完全不会算数。

### 第六步：加括号，加几层

存成 `src/macro1b.c`，末尾加 `add_demo(macro1b)`，里面放了两个版本：

```c
#include <stdio.h>

/* 只给参数加括号，没给整体加括号 */
#define SQUARE_A(x) (x) * (x)
/* 参数和整体都加括号 */
#define SQUARE(x) ((x) * (x))

int main(void) {
    printf("%d\n", SQUARE_A(1 + 2));
    printf("%d\n", 100 / SQUARE_A(5));
    printf("%d\n", SQUARE(1 + 2));
    printf("%d\n", 100 / SQUARE(5));
    return 0;
}
```

> [!question] 先猜一猜
> 四行输出各是多少？注意 `100 / SQUARE_A(5)`：它只给参数加了括号，没给整体加。

> [!success]- 揭晓
> ```
> 9
> 100
> 9
> 4
> ```
> `100 / SQUARE_A(5)` 展开成 `100 / (5) * (5)`。除和乘同级，从左往右算：先 `100 / 5 = 20`，再 `20 * 5 = 100`。想要的是 4。

规矩有两条：参数**每次出现**都加括号，整个表达式**再加一层**括号。

### 第七步：参数被算了两遍

宏的第二个坑更隐蔽。存成 `src/macro2.c`，末尾加 `add_demo(macro2)`：

```c
#include <stdio.h>

#define MAX(a, b) ((a) > (b) ? (a) : (b))

/* 每调用一次就报到一次，并返回一个递增的数 */
static int next(void) {
    static int n = 0;
    n++;
    printf("next() called, n=%d\n", n);
    return n;
}

int main(void) {
    int m = MAX(next(), 0);
    printf("m=%d\n", m);
    return 0;
}
```

> [!question] 先猜一猜
> `next()` 每调用一次，就打印一行并返回一个递增的数。打印几行 `next() called`？最后 `m` 是几？

> [!success]- 揭晓
> 打印**两**行，`m` 是 2，不是 1。

你应该看到：

```
next() called, n=1
next() called, n=2
m=2
```

用 `gcc -E` 看展开结果就明白了：`int m = ((next()) > (0) ? (next()) : (0));`。参数 `a` 在宏里出现了两次，`next()` 就被抄了两份，执行了两次。

修法是别用宏，改用函数。存成 `src/macro3.c`，末尾加 `add_demo(macro3)`：

```c
#include <stdio.h>

/* 用函数代替宏：参数只求值一次，还有类型检查 */
static inline int max_int(int a, int b) {
    return (a > b) ? a : b;
}

static int next(void) {
    static int n = 0;
    n++;
    printf("next() called, n=%d\n", n);
    return n;
}

int main(void) {
    int m = max_int(next(), 0);
    printf("m=%d\n", m);
    return 0;
}
```

输出：

```
next() called, n=1
m=1
```

函数调用时，每个实参表达式只求值一次，并按函数声明检查类型。这里的 `static` 把函数限制在当前源文件内；`inline` 是内联方面的提示，不保证实际展开，也不保证一定更快。这个例子真正需要的是函数的参数语义，不是某种优化承诺。

### 第八步：用 #ifdef 切换输出

`util.h` 里还有一段没解释的东西：

```c
#ifdef VERBOSE
#define TRACE(...) do { printf("[trace] "); printf(__VA_ARGS__); printf("\n"); } while (0)
#else
#define TRACE(...) ((void)0)
#endif
```

`#ifdef VERBOSE` 的意思是：如果定义过 `VERBOSE`，保留下面这段；否则保留 `#else` 后面那段。没被保留的那段，不会进入编译，也不会占用可执行文件的空间。

`VERBOSE` 从哪来？从编译命令来：编译器的 `-DVERBOSE` 选项，等于在每个源文件最前面写一行 `#define VERBOSE`。现在编译命令是 CMake 替你写的，所以开关也要交给 CMake。在 `projects/cmdtab/CMakeLists.txt` 末尾加这几行：

```cmake
# 打印跟踪信息的开关，默认关
option(CMDTAB_VERBOSE "print trace lines" OFF)
if(CMDTAB_VERBOSE)
    target_compile_definitions(cmdtab PRIVATE VERBOSE)
endif()
```

- `option(名字 "说明" 默认值)`：声明一个可以在配置时打开或关闭的开关，这里默认 `OFF`。
- `target_compile_definitions(cmdtab PRIVATE VERBOSE)`：让 CMake 编译 `cmdtab` 的每个 `.c` 时都加上 `-DVERBOSE`。

不打开开关，就是上面第一步的输出，没有任何跟踪信息。打开它，重新配置时加一个参数（注意：这个 `-D` 是给 CMake 设变量的，不是给编译器的），然后构建、运行：

```
cmake -S . -B build -DCMDTAB_VERBOSE=ON
cmake --build build --verbose
./build/projects/cmdtab/cmdtab
```

加了 `--verbose` 能亲眼看到，开关打开之后，编译命令里多了一个 `-DVERBOSE`（路径我做了省略）：

```
[1/3] C:\MinGW\bin\gcc.exe -DVERBOSE -I.../projects/cmdtab/include -std=c99 -Wall -Wextra ... -c .../projects/cmdtab/src/main.c
```

开关一变，两个源文件都要重新编译，因为编译命令变了。运行的输出应该是：

```
> hello
[trace] looking for 'hello' among 3 commands
[trace] found at index 0
hello from the table
  rc=0
> add
[trace] looking for 'add' among 3 commands
[trace] found at index 1
7
  rc=0
> echo
[trace] looking for 'echo' among 3 commands
[trace] found at index 2
a b c
  rc=0
> fly
[trace] looking for 'fly' among 3 commands
[trace] not found
  rc=-1
g_count=3
```

同一份源码，换一个 CMake 开关，就换了一套输出。这就是**条件编译**。关掉它用 `cmake -S . -B build -DCMDTAB_VERBOSE=OFF` 重新配置，再构建，就回到没有跟踪信息的版本。在 VS Code 里，可以把这个变量写进工作区设置的 `cmake.configureSettings` 里，不用每次敲命令行（待核对）。

`TRACE` 里的 `do { ... } while (0)` 先照写：它让一个含多条语句的宏，用起来像一条语句。为什么要这样，放在拓展里。

到了板子上，这套机制会天天见面：用它区分不同的芯片型号，也用它做日志开关，3.1 的 `LOG` 就是这个思路。

## 刚才发生了什么

开头的问题是：程序变长后，怎样只修改眼前这一块，而不用在一个大文件里找来找去。现在每个模块有自己的实现文件，头文件告诉使用者可以调用什么；CMake 的清单把这些文件组织成一个程序。

接着我们处理了拆文件带来的具体问题：同一份头文件被包含多次，需要守卫；变量不能重复定义；内部细节不应该被到处修改，所以对外留接口、对内用 `static`。到了重复写法和调试输出的开关，才继续用宏与条件编译，并看清它们的边界。

这套做法会直接延续到单片机：CubeMX 生成 CMake 工程，自己的模块放在 `User/Inc`、`User/Src`，文件如何加入构建见 [[2.2_开发环境与第一次点灯]]。想继续拆编译过程，再进入 [[第0章_工具与构建_自学选读]]，不用把那里的原理当成本节前置。

## 记住这几条

1. 宏的参数每次出现都加括号，整个表达式再加一层括号：`#define SQUARE(x) ((x) * (x))`。
2. 宏的参数里不要放有副作用的表达式（`i++`、函数调用）。能用函数或 `static inline` 就不用宏。
3. 头文件放声明，不放定义。全局变量在头文件里写 `extern`，定义只在一个 `.c` 里。
4. 每个头文件都加守卫，守卫名用文件名大写，例如 `UTIL_H`。
5. 怀疑宏展开错了，就用 `gcc -E` 看秘书到底贴了什么。
6. 用 `option()` 加 `target_compile_definitions()` 给编译器传 `-DXXX`，源码里用 `#ifdef XXX` 做开关，开关名一律大写，一眼能和普通变量区分。
7. **`add_executable` 里的源文件列表，就是要编成目标文件并链接的全部文件**。新增 `.c` 要加进列表，漏了就是 `undefined reference`；头文件目录用 `target_include_directories` 告诉编译器。
8. **头文件就是模块对外的接口**：只放类型和函数声明；模块内部用的函数和变量一律写 `static`。状态尽量放进对象（1.6），不要做成谁都能改的全局变量。
