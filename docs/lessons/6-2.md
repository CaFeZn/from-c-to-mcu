# 6.2 DMA与空闲中断

> **这一节你会做出**：把 6.1 的"每个字节进一次中断"换成"DMA 搬运 + 空闲中断通知"，让长度不定的一整段数据只在说完的时候叫你一声，一次发 100 行也不丢。上层的 shell、命令表一行都不用改。
> **前置**：[[6.1_串口命令行]]、[[5.4_中断与主循环共享数据]]　｜　**预计**：阅读 + 动手 60 分钟

> 先回答下面几个问题（写下来，别只在心里答）。**全部答对**就直接跳到 [[6.3_设计自己的协议]]；有一题拿不准，就从头读。
> 1. 115200、8N1 的串口，每秒最多能收多少个字节？6.1 的逐字节中断方式，这时每秒要进多少次中断？
> 2. 串口的"空闲中断"（IDLE）在什么时候触发？
> 3. 下面是一个收不定长数据的 DMA 缓冲回调（缓冲 128 字节，Circular 模式，半传输中断没有关）。对方一口气发来 100 个字节然后停下，这段代码总共会往队列里放多少个字节？
>    ```c
>    void HAL_UARTEx_RxEventCallback(UART_HandleTypeDef *huart, uint16_t Size)
>    {
>        for (uint16_t i = 0; i < Size; i++) {
>            ringbuf_put(&q, dma_buf[i]);
>        }
>    }
>    ```
> 4. 想把 6.1 的"逐字节中断"换成"DMA + 空闲"，shell 和命令表要改吗？为什么？
>
> > [!success]- 答案，以及跳过后要带走的东西
> > 1. 每字节 10 位（1 起始 + 8 数据 + 1 停止），115200 ÷ 10 = 11,520 字节每秒；逐字节中断就是每秒约 11,520 次。
> > 2. 线路上收到过数据之后，又安静了大约一个字符的时间（115200 下约 87 µs）。
> > 3. 164 个。先在半传输事件（缓冲写到一半，Size = 64）里放了 64 个，数据停下后的空闲事件（Size = 100）又从头放了 100 个，前 64 个被送了两遍。Size 是"缓冲里写到哪了"，不是"这次新来了几个"。
> > 4. 不用。它们只通过队列和接收器对象打交道，接收器内部换成什么，上层不知道。
> >
> > **带走清单**（代码在本节「第二步」，直接复制）：
> > - CubeMX：USART1_RX 开 DMA，模式选 **Circular**；USART1 与对应 DMA 流的中断优先级设成同一级。
> > - 用本节的 `uart_rx.h` / `uart_rx.c` **整体替换** `User/Inc/uart_rx.h` 和 `User/Src/uart_rx.c`（同名覆盖，不新增文件，不用重新配置；对外函数 `uart_rx_init` / `uart_rx_start` 不变）。6.3 会继续用它。
> > - 在 `User/Src/app_cli.c` 里加序号检查器和 `frame` 命令（第三步）。
> > - 回调里按"上次位置 → 这次位置"取数据的写法（`drain` 函数）。

## 先看一个怪现象

一家仓库，货车一趟趟来。经理的做法是：每来一箱货，都放下手里的事，跑到门口搬进货架，再回来接着干活。货一多，他就整天在门口和办公桌之间来回跑，什么也干不成。

6.1 的串口接收就是这样。每收到一个字节，CPU 都要放下手里的事，进一次中断。

> [!question] 先猜一猜
> 在 6.1 的方式下，收下面这个文件要进多少次中断？它有 100 行，每行形如 `frame 37\r\n`，一共 992 个字节。如果对方一直满速发送，每秒要进多少次？

> [!success]- 揭晓
> 992 次，每个字节一次。满速时每秒 11,520 次（见上面自测题 1）。对 168 MHz 的 CPU 来说不算致命，但每次进出中断都有固定开销，而且这些时间全是替"搬运工"的活付的。

我们换个办法：雇一个**搬运工**，专门把到的货一直搬进货架，不打扰经理。经理只在两种时候被叫一声：货架快满了，或者货车走了（线路安静下来了）。

这个搬运工的真名叫 **DMA**，货车走了的信号叫 **IDLE 空闲中断**。但先别急着认名字，有一件事要先想清楚。

> [!question] 先猜一猜
> 搬运工只会"搬 N 件货"。可是对方这次发多少个字节，我们事先并不知道。他怎么知道"货车走了"，该叫经理了？

> [!success]- 揭晓
> 看线路。串口收完一个字符之后，如果线路上接下来的一个字符时间里什么也没来，说明对方这一段话说完了。这个"安静了"的事件，就是空闲中断。115200 下一个字符时间约 87 µs。

## 动手做

### 第一步：在 CubeMX 里让 USART1_RX 用 DMA

1. 打开 USART1 → **DMA Settings** → Add，选 **USART1_RX**。
2. **Mode** 选 **Circular**（循环）。缓冲写满之后自动回到开头继续写，不会停下来等你。
3. Data Width 选 Byte 和 Byte，Increment Address 只勾内存那一侧。
4. NVIC Settings 里确认 **USART1 global interrupt** 和 USART1_RX 所用的那个 **DMA 流的中断**都已勾选，并且把这两个中断的**抢占优先级设成同一级**。

最后一条有来由：下面的回调会被两个中断调用，空闲事件从 USART1 中断来，半传输和传输完成事件从 DMA 中断来。优先级相同，它们就不会互相打断，回调里用的"处理到哪了"这个变量就不需要加保护。（[[【原理】中断与NVIC|中断与NVIC]]里讲了抢占是怎么回事。）

如果 3.1 的日志层已经给 USART1_TX 配了 DMA，保留它，不要动。

### 第二步：整体替换 uart_rx

把 6.1 放在 `User/Inc` 和 `User/Src` 里的 `uart_rx.h`、`uart_rx.c` 换成下面的版本（直接覆盖同名文件，CMake 不需要重新配置）。对外的两个函数 `uart_rx_init` 和 `uart_rx_start` 原样没变，所以 shell、命令表、`app_cli.c` 都不用动。

```c
#ifndef UART_RX_H
#define UART_RX_H

#include <stdint.h>
#include "usart.h"
#include "ringbuf.h"

#define UART_RX_DMA_SIZE  128u    /* DMA 接收缓冲的大小 */

/* 串口接收器：用 DMA + 空闲中断收，收到的字节放进指定的队列。
 * 对外的函数和 6.1 完全一样，只有内部的成员变了。 */
typedef struct {
    UART_HandleTypeDef *huart;     /* 管哪个串口 */
    ringbuf_t          *sink;      /* 收到的字节放到哪个队列 */
    volatile uint32_t   events;    /* 接收事件被回调的次数，观察用 */
    volatile uint32_t   bytes;     /* 一共收到多少字节，观察用 */
    uint16_t            old_pos;   /* 缓冲里已经处理到的位置 */
    uint8_t             dma_buf[UART_RX_DMA_SIZE];
} uart_rx_t;

void uart_rx_init(uart_rx_t *rx, UART_HandleTypeDef *huart, ringbuf_t *sink);
void uart_rx_start(uart_rx_t *rx);   /* 开始接收，要在 MX_USART1_UART_Init 之后调用 */

#endif /* UART_RX_H */
```

```c
#include <stddef.h>
#include "uart_rx.h"

/* 登记表：HAL 的回调只给 huart 指针，靠它找回对象（和 6.1 一样） */
#define UART_RX_MAX  2
static uart_rx_t *s_registry[UART_RX_MAX];

static uart_rx_t *find_rx(UART_HandleTypeDef *huart)
{
    for (int i = 0; i < UART_RX_MAX; i++) {
        if (s_registry[i] != NULL && s_registry[i]->huart == huart) {
            return s_registry[i];
        }
    }
    return NULL;
}

void uart_rx_init(uart_rx_t *rx, UART_HandleTypeDef *huart, ringbuf_t *sink)
{
    rx->huart = huart;
    rx->sink = sink;
    rx->events = 0;
    rx->bytes = 0;
    rx->old_pos = 0;
    for (int i = 0; i < UART_RX_MAX; i++) {
        if (s_registry[i] == rx) {
            return;
        }
    }
    for (int i = 0; i < UART_RX_MAX; i++) {
        if (s_registry[i] == NULL) {
            s_registry[i] = rx;
            return;
        }
    }
}

void uart_rx_start(uart_rx_t *rx)
{
    rx->old_pos = 0;
    /* DMA 在 CubeMX 里配成 Circular：缓冲写满后自动回到开头继续写 */
    HAL_UARTEx_ReceiveToIdle_DMA(rx->huart, rx->dma_buf, UART_RX_DMA_SIZE);
}

/* 把一个字节放进队列，并计数 */
static void push(uart_rx_t *rx, uint8_t b)
{
    rx->bytes++;
    (void)ringbuf_put(rx->sink, b);          /* 队列满了会丢掉并计数 */
}

/* 缓冲里从 old_pos 到 end 之间是新到的字节，搬进队列。
 * end 是"DMA 现在写到哪了"。半传输、传输完成、空闲三种事件都用同一套办法处理：
 * 只取"上次处理位置"到"现在位置"之间的字节，所以同一批字节永远不会被送两遍。 */
static void drain(uart_rx_t *rx, uint16_t end)
{
    if (end < rx->old_pos) {                   /* 绕过了缓冲末尾：先取到末尾 */
        for (uint16_t i = rx->old_pos; i < UART_RX_DMA_SIZE; i++) {
            push(rx, rx->dma_buf[i]);
        }
        rx->old_pos = 0;
    }
    for (uint16_t i = rx->old_pos; i < end; i++) {
        push(rx, rx->dma_buf[i]);
    }
    rx->old_pos = (end >= UART_RX_DMA_SIZE) ? 0 : end;
}

/* 半传输、传输完成、线路空闲，三种事件都会进这里（在中断里） */
void HAL_UARTEx_RxEventCallback(UART_HandleTypeDef *huart, uint16_t Size)
{
    uart_rx_t *rx = find_rx(huart);

    if (rx != NULL) {
        rx->events++;
        drain(rx, Size);
    }
}

/* 出错后接收可能已经停了：从头再来 */
void HAL_UART_ErrorCallback(UART_HandleTypeDef *huart)
{
    uart_rx_t *rx = find_rx(huart);

    if (rx != NULL) {
        __HAL_UART_CLEAR_OREFLAG(huart);
        uart_rx_start(rx);
    }
}
```

读代码时抓住三件事：

- `uart_rx_start` 里调用的是 `HAL_UARTEx_ReceiveToIdle_DMA`，名字就是"收到空闲为止，用 DMA"。
- 回调的名字是 `HAL_UARTEx_RxEventCallback`（注意是 `Ex` 和 `Event`，不是 6.1 的 `RxCplt`）。
- `drain` 里处理的是"从 `old_pos` 到 `end`"这一段，而不是"前 Size 个"。

> [!question] 先猜一猜
> 对方一口气发来 100 个字节然后停下，缓冲是 128 字节。回调会被调用几次？每次的 `Size` 是多少？

> [!success]- 揭晓
> 两次。缓冲写到一半（64 个字节）时触发**半传输事件**，`Size = 64`；数据停下、线路空闲后触发**空闲事件**，`Size = 100`。
> 注意第二次的 `Size` 是 100，不是 36。`Size` 永远是"缓冲里现在写到了第几个位置"。如果你把它当"这次新来的个数"，就会把前 64 个字节送两遍，一共 164 个。
> 我在电脑上写了个桩模拟 DMA（按硬件的规则触发半传输、传输完成、空闲三种事件，缓冲 128 字节，一共 12 次突发、1077 个字节），用上面的 `drain` 处理：收到 1077 个字节，一个不错，没有重复，回调一共 28 次。同样的 100 字节用错误写法，收到的是 164。

### 第三步：给 shell 加一个"验货员"

要验证"连续发 100 行不丢"，需要一个能数数的东西。在 `app_cli.c` 里加一个很小的对象：序号检查器，和一条 `frame N` 命令。

先在文件顶部加一行 `#include <stdlib.h>`（给 `strtoul` 用）。然后在 `s_shell` 之类的对象定义之后，加上这个对象：

```c
/* 序号检查器：检查收到的 "frame N" 是不是 1、2、3……连续的，用来验证有没有丢 */
typedef struct {
    uint32_t expect;    /* 下一个应该收到的序号 */
    uint32_t ok;        /* 连续的个数 */
    uint32_t bad;       /* 不连续的个数 */
} seq_check_t;

static void seq_check_init(seq_check_t *c)
{
    c->expect = 1;
    c->ok = 0;
    c->bad = 0;
}

static int seq_check_feed(seq_check_t *c, uint32_t n)   /* 连续返回 1，否则返回 0 */
{
    int good = (n == c->expect);

    if (good) {
        c->ok++;
    } else {
        c->bad++;
    }
    c->expect = n + 1u;
    return good;
}

static seq_check_t s_seq;
```

加命令函数，放在 `cmd_help` 之前：

```c
static int cmd_frame(int argc, char *argv[])
{
    uint32_t n;
    uint32_t want = s_seq.expect;

    if (argc != 2) {
        return 1;
    }
    n = (uint32_t)strtoul(argv[1], NULL, 10);
    if (!seq_check_feed(&s_seq, n)) {
        LOG(LOG_WARN, "frame: got %lu, expected %lu\r\n", (unsigned long)n, (unsigned long)want);
    }
    if (n == 100u) {                       /* 最后一帧：报告并重新开始 */
        LOG(LOG_INFO, "frames ok=%lu bad=%lu\r\n", (unsigned long)s_seq.ok, (unsigned long)s_seq.bad);
        seq_check_init(&s_seq);
    }
    return 0;
}
```

命令表里加一行，并补一句声明，声明和命令表现在是这样：

```c

static int cmd_echo(int argc, char *argv[]);

    { "led",  cmd_led,  "led on|off : turn the LED on or off" },
    { "echo", cmd_echo, "echo on|off : switch input echo" },

```

最后，在 `app_cli_init` 里初始化它：

    (void)ringbuf_init(&s_rxq, s_rxq_mem, sizeof s_rxq_mem);
    seq_check_init(&s_seq);

    shell_init(&s_shell, &s_rxq, s_line_mem, sizeof s_line_mem,

改完在 VS Code 里构建并下载。这个检查器同样是一个对象，状态（期望的序号、成功和失败的个数）都在 `seq_check_t` 里。

### 第四步：造一个测试文件，发送

在电脑上生成 `frames.txt`（Git Bash 或 Linux/macOS 终端）：

```
for i in $(seq 1 100); do printf 'frame %d\r\n' $i; done > frames.txt
wc -c frames.txt
```

我在电脑上跑了，`wc -c` 给出 992，和上面算的一致。

在串口助手里：

1. 先发 `echo off` 回车。原因：回显和提示符也是输出，要占日志缓冲。100 行的回显会白白占掉很多。
2. 用"发送文件"（名字随软件）把 `frames.txt` 发出去。
3. 发完后输入 `stat`。测完用 `echo on` 恢复回显。

你应该看到：

```
frames ok=100 bad=0
rx bytes=…, dropped=0, events=…
```

`frames ok=100 bad=0` 表示一百行一个不少，也没乱序。`stat` 里的 `bytes` 比 992 多一点（含你敲的 `echo off` 等命令），`dropped` 应当是 0。`events` 推演下来是十几次量级：连续满速发 992 个字节，每 64 个字节触发一次半传输或传输完成，加上最后的空闲，大约 16 次。这是按规则算的，板子上以你看到的为准。

对比 6.1：同样的文件，6.1 的 `events` 等于字节数，约 992，现在只有十几次。这就是搬运工的价值。

### 第五步：探针

**探针 1：错误的增量处理。** 只把原来的 `drain` 函数替换成下面的错误版本；保留已经初始化的对象、登记表、`push` 和 HAL 回调不变。不要再定义一个没有初始化的 `g_rx`。

```c
/* 错误示范：忽略 old_pos，每次把 [0, end) 都当成新数据。 */
static void drain(uart_rx_t *rx, uint16_t end)
{
    for (uint16_t i = 0; i < end; i++) {
        push(rx, rx->dma_buf[i]);
    }
}
```

> [!question] 先猜一猜
> 在串口助手里一次性发送恰好 100 个字节（比如 99 个字符加回车），不要分包。`stat` 里的 `bytes` 增加多少？

> [!success]- 揭晓
> 推演是增加 164，而不是 100。但这需要对方真的一口气发完，没有分包；有的串口助手会自己拆包，数字会不同。如果你的助手一口气发出，`bytes` 的异常增长就是半传输事件重复送货的证据。测完改回来。

**探针 2：关掉半传输中断。** 这里只关闭 HT，仍保留传输完成 TC 与串口空闲 IDLE 事件，不是“只剩空闲”：

```c
#include "uart_rx.h"
/* 变体 1：干脆关掉半传输中断 */
void uart_rx_start_no_ht(uart_rx_t *rx)
{
    rx->old_pos = 0;
    HAL_UARTEx_ReceiveToIdle_DMA(rx->huart, rx->dma_buf, UART_RX_DMA_SIZE);
    __HAL_DMA_DISABLE_IT(rx->huart->hdmarx, DMA_IT_HT);
}
/* 变体 2：回调里认出是哪种事件 */
void on_event(UART_HandleTypeDef *huart, uint16_t Size)
{
    (void)Size;
    if (HAL_UARTEx_GetRxEventType(huart) == HAL_UART_RXEVENT_HT) {
        return;   /* 半传输：先不理 */
    }
}
```

关掉之后，同样的 100 个字节只会触发一次空闲事件。注意代价：如果对方连续发送很长一段、中间没有空闲，你只有在缓冲写满时才会被叫一声，延迟变大。本节的 `drain` 不需要关它，因为它对重复事件天然免疫。

## 刚才发生了什么

字节从引脚到你的主循环，现在走的是这条路：

```
引脚 → USART 接收 → DMA 搬进 dma_buf（循环缓冲）
                      ↓ 半满 / 写满 / 线路空闲，三种事件之一
              HAL_UARTEx_RxEventCallback(Size)
                      ↓ drain：old_pos → Size 之间的新字节
                 ringbuf_t → 主循环 → shell → 命令
```

三种事件：

| 事件 | 什么时候触发 | Size 是多少 |
|---|---|---|
| 半传输（HT） | DMA 写到缓冲的一半 | 64（缓冲 128 时） |
| 传输完成（TC） | DMA 写满缓冲 | 128，写指针随后回到 0 继续写 |
| 线路空闲（IDLE） | 数据停下后线路安静了一个字符时间 | 当前写到的位置 |

DMA 的全名是直接存储器访问。它把"外设到内存"的搬运从 CPU 手里接走，细节放在[[【原理】DMA工作原理|DMA工作原理]]里。

为什么选 Circular 而不是普通模式？普通模式下，一次空闲事件之后 HAL 会结束这一轮接收，你必须重新启动，重启的间隙里到的字节没人接。Circular 模式下搬运工从不下班，没有这个空隙。

要不要处理半传输，有三种办法，任选其一：本节的位置差法（最稳，不依赖事件类型）、关掉 HT 中断、在回调里用 `HAL_UARTEx_GetRxEventType` 判断事件类型再决定。

你的代码需要满足一条时限：缓冲 128 字节时，最迟每 64 个字节（115200 下约 5.6 ms）会有一次事件，回调要在缓冲被写穿之前响应，否则数据会被覆盖。中断优先级别设得太低，被别的中断长时间压住，就有风险。

最后看对象的好处：这一节只换了一个对象（`uart_rx_t`）的内部，它的对外接口没变，所以 shell、行编辑器、命令表、组装文件全部原样。换实现不动上层，这就是把依赖收在接口后面的意义。结构体的成员变了，调用方要重新编译，但一行代码也不用改。想连结构体成员也藏起来，要用不透明指针，见[[【原理】C语言里的面向对象|C语言里的面向对象]]。

回到开头：992 个字节，现在只进十几次中断，经理有时间做别的事了。

## 记住这几条

1. 长度不定的接收，用 `HAL_UARTEx_ReceiveToIdle_DMA`：DMA 搬字节，空闲中断告诉你一段话说完了。
2. 回调里的 `Size` 是"缓冲里写到了哪个位置"，不是"这次新来多少个"。要处理"上次位置到这次位置"这一段。
3. 半传输、传输完成、空闲三种事件进的是同一个回调。用位置差法就不会重复送；也可以关掉 HT 中断，或用 `HAL_UARTEx_GetRxEventType` 区分。
4. 用 Circular 模式，别在回调里反复重启接收，重启的间隙会漏字节。
5. 回调所在的两个中断（USART1 与 DMA）优先级设成同一级，共用的状态变量才不需要保护。
6. 回调里仍然只做搬字节：放进队列，其余留给主循环。
7. 换实现不动上层：把变化收在一个对象的内部，对外的函数保持不变。
8. 批量测试前先 `echo off`：回显也是输出，也占日志缓冲。

## 练习

1. 按第四步发送 `frames.txt`，确认 `frames ok=100 bad=0`。再发一次，是否仍然正确？（复现）
2. 把 `UART_RX_DMA_SIZE` 改成 32，再测一次。结果还对吗？`events` 会怎样变？（改造）
3. 缓冲 128 字节，对方一口气发来 200 个字节然后停下。按本节的方式，回调依次会被调用几次？每次的 `Size` 是多少？总共往队列放多少字节？（预测）

> [!success]- 提示与答案方向
> 1. 序号检查器在第 100 条之后会自动重新开始，所以可以连续测。
> 2. 仍然不会丢，但事件更频繁：每 16 个字节有一次半传输或传输完成，`events` 大约变成原来的 4 倍。前提是中断仍然能及时响应：32 字节在 115200 下只有约 2.8 ms 的余量。
> 3. 四次：半传输 `Size = 64`；传输完成 `Size = 128`（写指针回到 0）；第二圈的半传输 `Size = 64`；最后的空闲 `Size = 72`（200 − 128）。总共放 64 + 64 + 64 + 8 = 200 个字节，一个不多。
