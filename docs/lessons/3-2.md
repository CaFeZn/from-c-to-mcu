# 3.2 调试与排错

> **这一节你会做出**：用调试器停住程序、看变量、看外设寄存器；掌握"时钟 → 引脚 → 模式 → 数据"四步排查；认出板子死在了 HardFault 还是 Error_Handler，并让它临死前留下一句话。
> **前置**：[[3.1_串口与日志]]　[[2.3_怎么读手册]]　｜　**预计**：阅读 + 动手 60 分钟

> [!tip] 跳读自测：这一节你可能不用读
> 先回答下面几个问题（写下来，别只在心里答）。**全部答对**就直接跳到 [[4.1_GPIO点灯按键蜂鸣器]]；有一题拿不准，就从头读。
> 1. LED 不亮，代码看起来没问题。四步排查法按什么顺序查哪四件事？
> 2. 下面的函数被 `sum_to(10)` 调用，期望得到 55。实际结果是多少？问题在哪一行？
>
>    ```c
>    static uint32_t sum_to(uint32_t n)
>    {
>        uint32_t sum = 0;
>        for (uint32_t i = 1; i < n; i++) {
>            sum += i;
>        }
>        return sum;
>    }
>    ```
>
> 3. 板子卡死了，调试器暂停后，程序停在 `HardFault_Handler` 的 `while (1)` 里。这和停在 `Error_Handler` 里，意思有什么不同？
> 4. CMake 的 Debug 和 Release 构建类型，编译选项各是什么？调试时为什么要用 Debug？
>
> > [!success]- 答案，以及跳过后要带走的东西
> > 1. 时钟 → 引脚 → 模式 → 数据。依次问：外设有时钟吗，系统时钟对吗；信号到该到的脚了吗；外设按你想的方式在工作吗（输入输出、中断和 DMA 开了没、定时器启动了没）；以上都对了，再看内容对不对。
> > 2. 结果是 45。`for` 的条件 `i < n` 少算了 `n` 本身，应该是 `i <= n`。
> > 3. 停在 `HardFault_Handler`：CPU 自己遇到了执行不了的事（空指针、野指针、栈溢出等）。停在 `Error_Handler`：HAL 或初始化代码返回了错误，调用栈里能看到是谁调的它。
> > 4. Debug 是 `-O0 -g3`，Release 是 `-Os -g0`。Debug 不优化、带完整调试信息，源码位置通常较容易跟踪，但不是逐行一一对应。Release 优化了代码，也没有调试信息，断点落不到源码行，变量也可能被优化掉。
> >
> > **带走清单**：
> > - CubeMX：SYS 里 Debug 选 Serial Wire。
> > - VS Code：使用关联单片机工程的 `STM32` Profile，确认 Cortex-Debug 已启用；工程 `.vscode/launch.json` 用本节「第一步」里的那份（改 `device` 和 `svdFile`）；构建类型选 Debug（`-O0 -g3`）。
> > - 方法：时钟 → 引脚 → 模式 → 数据 四步排查表（本节「第五步」）。
> > - 代码：在 `Error_Handler`（main.c）和 `HardFault_Handler`（stm32f4xx_it.c）里先 `LOG` 再 `log_flush()` 的两段，见本节「第七步」，需要 `#include "log.h"`。

## 先看一个怪现象

你写了一段看起来完全正确的代码，下载成功，LED 就是不亮。大多数人这时会做同一件事：把代码从头再读一遍，改一改，再下载。读了十遍还看不出错呢？

侦探不会这样办案。他先去现场看：通电了吗？门开着吗？开关拧对了吗？屋里的东西对不对？一样一样排除。这一节，我们给你一副侦探的工具箱。

> [!question] 先猜一猜
> LED 不亮，代码"看起来没问题"。你的第一步是：
> A. 把代码再读一遍　B. 重新下载一次　C. 先确认板子在不在跑、现象停在哪一层　D. 换一块板子试试
> 选一个，想想为什么。

> [!success]- 揭晓
> C。A 和 B 有一个隐含前提：错就藏在你读得出来的地方。可如果错在配置里（比如某个外设的时钟没打开），代码读一百遍也看不出来。先让现象告诉你"哪一层不对"，再到那一层去找。
> D 最贵，也最没用：板子多半是好的。

## 动手做

### 第一步：给自己装一双眼睛

先打开 2.2 的单片机工程，确认当前窗口使用 `STM32` Profile，Cortex-Debug 在这套配置中启用。若命令像是消失了，先按 [[2.2_开发环境与第一次点灯#先建立 STM32 Profile|2.2 的 Profile 设置]] 检查 Profile，不要把调试扩展装进 `C-PC` 来补救。下面的 `.vscode/launch.json` 仍属于当前工程，不会因为切换 Profile 而自动更换。

调试器要做的事，是让程序在你指定的地方停下来，让你看当时的变量和寄存器。我们在 VS Code 里用它，需要几样东西配合：

- **硬件**：一个 SWD 调试器（ST-Link、DAP-Link、J-Link 之类）。如果你的板子自带下载器，你在 2.2 下载程序时已经在用它了。SWD 需要的线是 SWDIO、SWCLK 和 GND，常见还会多接 NRST 和 3.3 V，以你的调试器和板子为准。
- **CubeMX**：SYS → Debug 选 Serial Wire。不要选 No Debug，那样 SWD 用的两个引脚会被当成普通引脚，之后可能连不上调试器（以你的 CubeMX 版本为准）。
- **软件**：VS Code 里的 Cortex-Debug 扩展，加上 STM32CubeCLT（2.2 装过）。后者带来三样东西：和 ST-Link 对话的 ST-LINK gdbserver、调试器本体 arm-none-eabi-gdb，以及描述各个外设寄存器的 SVD 文件。三者的分工是：gdb 负责"怎么调试"，gdbserver 负责"和芯片通话"，Cortex-Debug 把它们接到 VS Code 的调试界面上。
- **构建类型**：用 Debug 构建，它对应的编译选项是 `-O0 -g3`。第三步会解释这两个选项。在 VS Code 底部状态栏的 CMake Tools 里选 Debug 这个 preset（名字以你工程里 `CMakePresets.json` 为准，待核对），重新配置并构建。

**launch.json**：在工程的 `.vscode/` 目录下新建 `launch.json`，内容如下。这是从作者的参考工程精简泛化而来，字段含义见注释：

```jsonc
{
    "version": "0.2.0",
    "configurations": [
        {
            "name": "Debug STM32 (ST-LINK)",
            "type": "cortex-debug",
            "request": "launch",
            "cwd": "${workspaceFolder}",
            "servertype": "stlink",
            "interface": "swd",
            "device": "STM32F407IGHx",                 // 改成你的芯片，与 CubeMX 里选的型号一致
            "executable": "${command:cmake.launchTargetPath}",   // 用 CMake Tools 当前选中的目标生成的 .elf
            "runToEntryPoint": "main",                 // 下载后自动跑到 main 再停下
            "svdFile": "${config:STM32VSCodeExtension.cubeCLT.path}/STMicroelectronics_CMSIS_SVD/STM32F407.svd",   // 改成你的芯片对应的 .svd
            "serverpath": "${config:STM32VSCodeExtension.cubeCLT.path}/STLink-gdb-server/bin/ST-LINK_gdbserver",
            "stm32cubeprogrammer": "${config:STM32VSCodeExtension.cubeCLT.path}/STM32CubeProgrammer/bin",
            "armToolchainPath": "${config:STM32VSCodeExtension.cubeCLT.path}/GNU-tools-for-STM32/bin",
            "gdbPath": "${config:STM32VSCodeExtension.cubeCLT.path}/GNU-tools-for-STM32/bin/arm-none-eabi-gdb"
        }
    ]
}
```

其中 `device` 和 `svdFile` 两处要改成你自己的芯片。路径里的 `${config:STM32VSCodeExtension.cubeCLT.path}` 是 ST 官方 VS Code 扩展记录的 CubeCLT 安装目录，如果你没装这个扩展，就换成 CubeCLT 的实际路径。精简之后的字段没有在板子上逐个验证（待核对）。

**启动**：打开左侧"运行和调试"面板，选中这个配置，按 F5。程序下载进去后会自动停在 `main` 的开头，等你下命令。顶部的调试工具栏里，默认快捷键是：继续 F5，单步跳过 F10，单步进入 F11，单步跳出 Shift+F11。

调试信息和优化等级是工具链的两个开关，对调试体验影响很大，第三步会亲眼看到。

### 第二步：让 bug 现形

给你一个有 bug 的小函数。**main.c 的 USER CODE BEGIN 0 区**：

```c
/* USER CODE BEGIN 0 */
/* 想算 1+2+...+n，但这个版本藏了一个 bug */
static uint32_t sum_to(uint32_t n)
{
    uint32_t sum = 0;
    for (uint32_t i = 1; i < n; i++) {
        sum += i;
    }
    return sum;
}
/* USER CODE END 0 */
```

**main.c 的 USER CODE BEGIN Includes 区**：

```c
/* USER CODE BEGIN Includes */
#include "log.h"
/* USER CODE END Includes */
```

**main.c 的 USER CODE BEGIN 2 区和主循环**：

```c
  /* USER CODE BEGIN 2 */
  log_init(&huart1);
  uint32_t r = sum_to(10);                              /* 在这一行打断点 */
  LOG(LOG_INFO, "sum_to(10) = %lu\r\n", (unsigned long)r);
  /* USER CODE END 2 */

  while (1)
  {
    /* USER CODE END WHILE */

    /* USER CODE BEGIN 3 */
    HAL_GPIO_TogglePin(LED_GPIO_Port, LED_Pin);
    HAL_Delay(500);
  }
  /* USER CODE END 3 */
```

> [!question] 先猜一猜
> 读一遍代码，不运行。串口会打印出多少？你期望的是 55。如果不一样，你觉得错在哪？

先不看答案，用调试器来找：

1. **断点**：在 `uint32_t r = sum_to(10);` 这一行的行号左边点一下，出现红点。
2. **运行到断点**：点"继续"（Resume），程序在这一行停住。
3. **单步进入**：点"单步进入"（Step Into）进到 `sum_to` 里面。接着用"单步跳过"（Step Over）一行一行往下走。
4. **看变量**：打开变量窗口或 Watch 窗口，加入 `i` 和 `sum`，每走一圈循环看它们怎么变。

> [!success]- 揭晓
> 变量的变化是这样的：
>
> | 走完第几圈 | i | sum |
> |---|---|---|
> | 1 | 1 | 1 |
> | 2 | 2 | 3 |
> | 3 | 3 | 6 |
> | 4 | 4 | 10 |
> | 5 | 5 | 15 |
> | 6 | 6 | 21 |
> | 7 | 7 | 28 |
> | 8 | 8 | 36 |
> | 9 | 9 | 45 |
>
> 到 `i = 9` 就退出了，10 没有被加进去。串口打印 `sum_to(10) = 45`。条件应该是 `i <= n`。

这里有两个办案工具，各有分工：日志像**监控录像**，一路记下来，事后回放；调试器像**放大镜**，把时间定在这一刻，让你凑近看。前者是 `LOG`，后者就是调试器的断点、单步和观察窗。

**探针**：把 `i < n` 改成 `i <= n`，重新运行，应该打印 55。

### 第三步：构建类型决定了你能看到什么

CMake 工程有两种常用的构建类型：Debug 和 Release。它们对应的编译选项写在 CubeMX 生成的工具链文件 `cmake/gcc-arm-none-eabi.cmake` 里：

| 构建类型 | 选项 | 含义 |
|---|---|---|
| Debug | `-O0 -g3` | `-O0` 不优化，源码位置通常较容易跟踪，但不是逐行一一对应；`-g3` 带最完整的调试信息 |
| Release | `-Os -g0` | `-Os` 以代码体积为目标优化；`-g0` 不带调试信息 |

"调试信息"是编译时额外记在 `.elf` 里的一张对照表：第几行源码对应哪段机器码，变量叫什么名字、放在哪里。调试器靠它把机器码翻译回你的源码。

把构建类型切到 Release，重新配置并构建，再试一次第二步的断点和观察。

> [!question] 先猜一猜
> 在 `sum_to` 的循环里打断点，还能停下来吗？`sum` 和 `i` 还能看到吗？

> [!success]- 揭晓
> 多半不行，原因有两层。
> 1. Release 是 `-g0`，elf 里没有调试信息，调试器不知道源码第几行对应哪里，也不知道变量叫什么。断点落不到源码行上，变量窗口里也找不到 `sum`。
> 2. 就算你把 Release 的选项临时改成 `-Os -g3`（改 `CMAKE_C_FLAGS_RELEASE` 那一行，做完记得改回去），也还有第二层：`sum_to(10)` 的参数是常数，编译器在编译时就把结果算好了。作者用 CubeCLT 自带的 arm-none-eabi-gcc 12.3.1 编译这一段并看汇编，在 `-Os` 下循环已经不存在，只剩一条把 45 直接放进寄存器的指令。循环没了，断点自然没有可停的位置。别的版本和选项结果可能不一样。

调试器看的是你写的源码，CPU 跑的是被编译器改写过的机器码。优化越狠，两者差得越远。所以规矩是：**调试用 Debug，量最终的体积和速度用 Release**。想知道优化后的代码到底变成了什么，用 [[【拓展】看反汇编|看反汇编]]。优化为什么能这样改写代码，见 [[【原理】volatile与编译器优化|volatile 与编译器优化]]。

### 第四步：看外设，不只看变量

很多"没反应"的原因藏在外设里，而不是变量里。Cortex-Debug 会在调试侧边栏多出一个外设面板（叫 CORTEX PERIPHERALS，以你的扩展版本为准，待核对），内容来自 `launch.json` 里 `svdFile` 指向的 SVD 文件。里面能展开 GPIO、RCC、USART 等，直接看[[【原理】寄存器与内存映射|寄存器]]的值。

**探针**：运行到主循环里，展开你 LED 所在端口（`LED_GPIO_Port`）的 GPIO 寄存器，找到 ODR，随着 `HAL_GPIO_TogglePin` 的执行，对应那一位应该来回翻转。

再做一个破坏实验：把 `MX_GPIO_Init();` 这一行注释掉，重新构建并调试。LED 不会亮。这时候用调试器来查：先看 RCC 的 AHB1ENR，里面你 LED 所在端口对应的那一位是不是 1。多半是 0，因为端口的时钟没人打开。如果你的 LED 恰好和串口在同一个端口，时钟会被串口的初始化顺带打开，那就卡在下一步：看 GPIO 的 MODER，LED 那一对位应该是输出，现在是输入。两种情况都能查出来，只是卡在不同的关口。

有两条要小心：

- 个别寄存器**读一次就会清标志**，比如串口的数据寄存器，读一次会把收到的字节取走。别让调试器自动刷新这类窗口，否则你的观察本身会改变现象。
- 停在断点上时，时间并没有一起停：有些外设可能还在跑，所以断点前后的计时、超时都不能当真。

### 第五步：四步排查法

现在把侦探的做法写成表。排查的原则是**上游先于下游**：上游断了，后面全是白查。四个嫌疑人依次是：供电、门、开关、屋里的东西。它们的真名是：

| 步 | 嫌疑人 | 真名 | 要问的问题 | 怎么验证 | 典型症状 |
|---|---|---|---|---|---|
| 1 | 供电 | 时钟 | 这个外设有时钟吗？系统时钟对吗？ | 看 RCC 使能位；用 HAL_Delay(1000) 闪灯，对照秒表看快慢 | 写了寄存器没反应；串口乱码 |
| 2 | 门 | 引脚 | 信号到该到的脚了吗？ | 对照原理图；看复用配置；万用表、逻辑分析仪；检查接线 | 完全没动静 |
| 3 | 开关 | 模式 | 外设按你想的方式在工作吗？ | 输入还是输出；中断、DMA 开了没；定时器 Start 了没；看外设寄存器和句柄状态 | 动一次就不动了；只在某种条件下才动 |
| 4 | 屋里的东西 | 数据 | 通路都通了，内容对吗？ | 波特率、数值、缓冲区；用 LOG 或断点看 | 有输出但内容错 |

为什么时钟排第一？因为它最便宜：一眼就能看出来，而且它错了，后面三步的任何结论都不可信。

### 第六步：三个案子

三个案子都能用 3.1 的工程复现。每个案子先猜卡在四步中的哪一步。

**案子一：只说了一句话就哑了**

复现：回到 CubeMX，把 USART1 的 NVIC 里的 USART1 global interrupt 取消勾选，重新生成。现象：串口助手里只看到 `boot ok` 那一行，之后什么都没有，但 LED 还在闪。

> [!question] 先猜一猜
> 第一行能发出来，说明哪几步是对的？卡在哪一步？

> [!success]- 揭晓
> 第一行能发出，说明时钟、引脚、波特率都是对的，卡在**模式**：DMA 发送完成要靠串口的中断来通知，中断没开，`HAL_UART_TxCpltCallback` 永远不会被调用，日志层以为"上一段还没发完"，后面的内容就一直躺在缓冲里。
> 用调试器验证：暂停程序，在 Watch 窗口加入 `huart1.gState`。`huart1` 是 HAL 的串口对象，`gState` 是它的状态字段，调试器能直接展开对象看每个字段。它会停在 `0x21`（HAL_UART_STATE_BUSY_TX，表示还在发送），一直变不回 `0x20`（READY）。把中断勾回来就好了。

**案子二：一点声音都没有**

复现：把 TX 和 RX 的接线对调，或者故意选错 COM 号。现象：串口助手里什么都没有。

> [!question] 先猜一猜
> 先查哪一步？LED 在闪说明了什么？

> [!success]- 揭晓
> LED 在闪，说明板子在跑，系统时钟和 GPIO 的时钟都不会离谱。第一步通过，进入**引脚**。
> 用万用表量板子的 TX 脚对地：串口空闲时应该是高电平，接近 3.3 V。如果量到的是 0 V 不动，说明这个脚根本没配成串口，回头看 CubeMX 的引脚复用，以及板子上串口到底接在哪个脚（CubeMX 默认的 PA9 不一定是你板子接线的那个，以原理图为准）。如果高电平正常，就查接线是不是交叉、COM 号对不对。

**案子三：满屏乱码**

复现：把串口助手的波特率改成 9600，而板子这边仍然是 115200。现象：能看到字符，但全是乱码。

> [!question] 先猜一猜
> 这次是哪一步出的问题？如果两边都确认是 115200，乱码还在呢？

> [!success]- 揭晓
> 两边波特率不一致，属于**数据**这一步的约定没对上，改成一致就好。
> 如果两边设置都是 115200 仍然乱码，就要回到第一步：**时钟**。串口的波特率是用时钟频率算出来的，如果 CubeMX 里填的晶振频率和板子上实际焊的晶振不一致，整个系统时钟都是错的，波特率自然跟着错。验证方法：让 LED 用 `HAL_Delay(1000)` 闪，拿秒表数十次。明显偏快或偏慢，就是时钟参数错了。[[【原理】UART帧格式与波特率|波特率误差]]多大会乱码，见分支。

### 第七步：认出 HardFault

板子不再输出、LED 不闪时，先暂停调试器，看它停在什么地方，不要立刻追加更多日志。CubeMX 工程里常见两个停留点：

| 停留点 | 怎样到达 | 第一件要查的事 |
|---|---|---|
| `Error_Handler` | 代码发现失败后主动调用，例如 HAL 初始化返回错误 | 调用位置、返回值；外设和日志可能还没有初始化 |
| `HardFault_Handler` | Cortex-M 的硬件异常，或无法正常处理的可配置故障升级 | 异常状态寄存器、入栈现场；普通调用栈不一定能正确还原 |

空指针、越界、坏栈都可能与故障有关，但 C 的未定义行为不保证触发某个异常；也可能默默写坏内存。**不要靠调用 NULL 指针来验证固定的异常结果。**

这次用 Cortex-M4 明确定义的未定义指令陷阱做实验，而不是依赖 C 未定义行为。只在可重刷的实验工程里操作，先保存正常版本。下面写法针对本教程 GNU Arm 工具链，放在 `main` 初始化完成后的 USER CODE BEGIN 2 中：

```c
/* 临时故障实验：执行后不会进入正常主循环。 */
SCB->SHCSR &= ~SCB_SHCSR_USGFAULTENA_Msk; /* 使 UsageFault 升级到 HardFault */
__DSB();
__ISB();
__asm volatile ("udf #0");             /* Cortex-M4 的 UDF 指令 */
```

保留生成的 `HardFault_Handler` 死循环，不在其中调用普通日志库。给它下断点，下载后运行：预计会进入该处理函数。也可以先运行再暂停检查 PC。若没有停下，先核对实际下载的 ELF、断点和指令，再查异常状态，而不是假设芯片一定照着 C 源码执行。

> [!question] 先猜一猜
> 故障之前刚排队的串口日志，一定能完整发出去吗？进入 HardFault 后再调用 `LOG` 和 `log_flush()`，能保证补回来吗？

> [!success]- 揭晓
> 两个问题都不能保证。中断驱动的发送需要相关 IRQ 继续推进，HardFault 会阻止普通可配置中断抢占；故障还可能损坏堆栈、队列或外设状态。日志函数可能再次出错，等待基于 SysTick 的超时也可能永远等不到。即使某次成功输出，也不是可靠的异常处理协议。

在调试器的寄存器/内存视图检查 `SCB->CFSR` 和 `SCB->HFSR`：本实验应看到 `CFSR` 的 `UNDEFINSTR` 位（bit 16）与 `HFSR` 的 `FORCED` 位（bit 30）。检查相应位，不要求整个寄存器只含这一个位；旧故障标志也可能仍在。读取、保存异常入栈的 PC/LR 和辨认 MSP/PSP，放在[HardFault 现场分析](/notes/hardfault-analysis)继续。

恢复正常程序时，删除这段实验代码，重新构建、下载并复位。再次到达主循环，才算恢复成功。不要只让调试器“跳过”指令后继续使用未知状态。

`Error_Handler` 也不应无条件依赖串口：它可能在时钟或串口初始化之前被调用。本节先保留最小停留点；真正需要无人值守的故障记录时，按[故障记录与复位后回放](/notes/fault-persistence)设计有边界的采集、存储和复位策略。

本实验依据 Cortex-M4 的异常升级与故障状态规则，见 [PM0214](https://www.st.com/resource/en/programming_manual/pm0214-stm32-cortexm4-mcus-and-mpus-programming-manual-stmicroelectronics.pdf) 的 Exception model、Fault handling、UDF 部分。这里给出架构预期，不冒充已经上板测得的波形或串口输出。

## 刚才发生了什么

回到开头：LED 不亮，代码看起来没问题。现在你知道第一步不是读代码，而是让现象说话。

- 要看**此刻**的状态，用调试器：断点、单步、观察变量和外设寄存器。
- 要看**过程**，用 `LOG`。
- 要判断问题出在哪一层，用四步排查：时钟、引脚、模式、数据，上游先于下游。
- 板子卡死时，暂停看程序停在哪：`Error_Handler` 是 HAL 报错，`HardFault_Handler` 是 CPU 出事。
- 工具链也会影响你看到的东西：调试信息（`-g`）和优化等级（`-O0`、`-Os`）决定了调试器里的世界和你写的源码有多像，Debug 和 Release 就是两套不同的选择。

## 记住这几条

1. 没反应时先看现象，不先改代码。
2. 排查按时钟、引脚、模式、数据的顺序，上游先于下游。
3. 调试用 Debug 构建类型（`-O0 -g3`）；Release 是 `-Os -g0`，断点不停、变量看不到，先看是不是切成了 Release。
4. 调试器会影响现象：读个别寄存器会清标志，停在断点时外设可能还在跑。
5. 板子卡死，暂停后先看程序停在 `Error_Handler` 还是 `HardFault_Handler`。
6. 故障处理先保留最小现场，不无条件依赖普通日志库；日志基础设施本身可能尚未初始化或已经损坏。

## 练习

1. （复现）按第七步触发 UDF，记录实际停留的处理函数及 CFSR/HFSR 的相关位。删除实验代码后重新构建下载，确认能进入主循环。
2. （设计）某个业务回调可能为 NULL：如果它是允许缺省的可选动作，和“初始化后绝不能为空”的必需动作，错误处理应有什么不同？
3. （预测）把 `sum_to(10)` 改成 `sum_to(100000)`（仍然是 `i < n` 的版本），串口会打印多少？先在纸上算，再运行。

> [!success]- 提示与答案方向
> 1. 本实验预计进入 HardFault，CFSR.UNDEFINSTR 与 HFSR.FORCED 置位。普通日志是否发完不能用作唯一判据；恢复后应重新进入正常主循环。
> 2. 可选动作可以显式跳过；必需动作为空说明状态不合法，应在正常上下文报告并进入受控错误路径，不能静默吞掉。日志不是唯一手段，更不能把日志一定可用当作前提。
> 3. 1 到 99999 的和是 4999950000，超过 `uint32_t` 的最大值 4294967295，会回绕。作者用 gcc 实际算出的结果是 704982704。
