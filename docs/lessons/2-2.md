# 2.2 开发环境与第一次点灯

> **这一节你会做出**：在 VS Code 里搭好单片机开发环境，用 CubeMX 生成一个 STM32F407 的 CMake 工程，配置、构建、下载，让板上的 LED 每 500 ms 翻转一次；再给自己的代码建一个固定的"家"（`User/Inc` 和 `User/Src`）。后面所有章节都在这个工程上继续。
> **前置**：[[2.1_单片机里有什么]]；第 1 章里你已经用 CMake 构建过 PC 程序，这里是同一套办法　｜　**预计**：阅读 + 动手 90 分钟（软件安装与接线另算）

> [!tip] 跳读自测：这一节你可能不用读
> 先回答下面四个问题（写下来，别只在心里答）。**全部答对**就直接跳到 [[2.3_怎么读手册]]；有一题拿不准，就从头读。
> 1. 你在 `User/Src` 里新建了 `blink.c`，在 `User/Inc` 里新建了 `blink.h`，`main.c` 里调用了 `blink_step()`。顶层 `CMakeLists.txt` 的用户部分只写了下面两行，构建会报什么错？是编译器还是链接器报的？
>
>    ```cmake
>    file(GLOB_RECURSE USER_SOURCES CONFIGURE_DEPENDS ${CMAKE_SOURCE_DIR}/User/Src/*.c)
>    target_include_directories(${CMAKE_PROJECT_NAME} PRIVATE ${CMAKE_SOURCE_DIR}/User/Inc)
>    ```
>
> 2. CubeMX 生成的 `main.c` 里，每 500 ms 翻转一次 LED 的两行代码，放在 `USER CODE BEGIN 2`、`USER CODE BEGIN 3` 还是区外？为什么？
> 3. 编译器的名字 `arm-none-eabi-gcc`，`arm`、`none`、`eabi` 各表示什么？在电脑上编译、却给单片机跑的程序，这种做法叫什么？
> 4. `.elf`、`.bin`、`.hex` 三种文件，哪一种带符号和调试信息？"下载程序"在本质上是在做什么？
>
> > [!success]- 答案，以及跳过后要带走的东西
> > 1. 链接器报 `undefined reference to blink_step`。头文件找得到（include 目录那行有），所以编译能通过；但 `blink.c` 没有被加进可执行文件的源文件列表，根本没被编译，链接时就找不到函数定义。缺的是 `target_sources(${CMAKE_PROJECT_NAME} PRIVATE ${USER_SOURCES})` 这一行。
> > 2. `USER CODE BEGIN 3`。它在 `while (1)` 的大括号里，会反复执行。`BEGIN 2` 在循环之前，只跑一次；区外的代码，CubeMX 重新生成时会被抹掉。
> > 3. `arm` 是目标 CPU 的架构，`none` 是没有操作系统，`eabi` 是嵌入式应用二进制接口（一套调用约定）。这种做法叫**交叉编译**：编译所在的电脑叫 host，程序运行的单片机叫 target。
> > 4. `.elf` 带符号和调试信息；`.bin` 是纯字节。下载就是把这些字节**写进 Flash**（从 `0x0800 0000` 开始），没有别的魔法。
> >
> > **带走清单**：
> > - 一个能配置、构建、下载的 CubeMX CMake 工程，后面第 3 到 7 章都在它上面继续加东西。工程要点：芯片 STM32F407，HSE 经 PLL 到 168 MHz（APB1 42 MHz、APB2 84 MHz），Debug 选 Serial Wire，LED 引脚的用户标签命名为 `LED`，Toolchain / IDE 选 CMake。
> > - **用户代码的位置约定**：新建 `User/Inc` 和 `User/Src`，把 `.h` 放前者、`.c` 放后者；在顶层 `CMakeLists.txt` 里加下面三行，CMake 会自动收进来，新增文件后重新配置一次：
> >
> >   ```cmake
> >   # 用户代码：User/Src 下的 .c 自动加入；新增文件后重新配置即可
> >   file(GLOB_RECURSE USER_SOURCES CONFIGURE_DEPENDS ${CMAKE_SOURCE_DIR}/User/Src/*.c)
> >   target_sources(${CMAKE_PROJECT_NAME} PRIVATE ${USER_SOURCES})
> >   target_include_directories(${CMAKE_PROJECT_NAME} PRIVATE ${CMAKE_SOURCE_DIR}/User/Inc)
> >   ```
> >
> > - 环境：VS Code 的 `STM32` Profile 关联本工程，启用 CMake Tools、Cortex-Debug 等扩展；`C-PC` 留给 PC 练习。STM32CubeCLT（带 CMake、Ninja、arm-none-eabi-gcc、下载工具）；工程路径纯英文、无空格。
> > - 一个例子：`User/Inc/blink.h` 和 `User/Src/blink.c`（本节第八步），主循环里调用 `blink_step()`。

## 先看一个怪现象

在电脑上，程序员的第一声啼哭是 `hello, world`。单片机没有屏幕，也没有终端，它的第一声是一盏灯亮起来。

可从你敲下代码到那盏灯亮，中间要过三道手：**打包、送货、开箱**。哪一道出了问题，灯都不会亮，而且单片机不会告诉你是哪一道。这一节我们把三道手都走一遍，以后灯不亮，你知道先问谁。

> [!question] 先猜一猜
> 点亮第一盏灯，你自己要敲几行 C 代码（不算 CubeMX 替你生成的）？
> A. 0 行　B. 2 行　C. 20 行　D. 200 行
> 先选一个，做完再揭晓。

## 动手做

### 第一步：把环境装齐

继续使用 **VS Code + CMake**，但现在要把程序交给单片机运行。第 1 章的 `C-PC` Profile 留给电脑上的纯 C 练习，这里另建 `STM32`，把单片机用的扩展和设置放进去。两边写的都是 C，区别在运行目标和配套工具。

#### 先建立 STM32 Profile

1. 用“文件 → 新建窗口”（`Ctrl+Shift+N`）打开一个**空窗口**。不要在已经打开 `c-lab` 的窗口中直接切换，以免把那个文件夹重新关联到 STM32 配置。
2. 按 [[1.0_搭建环境#1. 安装 VS Code，建立 C-PC Profile|1.0 的方法]] 打开 Profiles 编辑器，点 **New Profile**，名称填 `STM32`；这次 **Copy from** 选已经配好的 `C-PC`。Settings 和 Extensions 从 `C-PC` 复制，不选持续共用 Default 的内容。
3. 点 **Create**，再用 **Use this Profile for Current Window** 或 `Profiles: Switch Profile` 让这个新窗口使用 `STM32`，确认 **In use** 标记。暂时不用勾选 **Use for New Windows**。

这样不用重新整理一遍通用编辑设置；复制的是一份起点，不是要求以后两套 Profile 始终同步。**它不会复制 c-lab 的工程文件**。如果你以前在 Profile 用户设置中写过 PC 专用编译器或绝对路径，先检查并移除不适合 STM32 的项；不要把 `c-lab/.vscode` 整个复制到单片机工程。

保持这个 `STM32` 窗口，继续把工具装齐：

| 装什么 | 它是干什么的 | 装完怎么确认 |
|---|---|---|
| **VS Code** | 编辑器，所有操作的入口 | 当前窗口使用 `STM32` Profile |
| **STM32CubeMX** | 图形化配置工具，生成工程。首次建 F4 工程时它会提示下载 STM32Cube 固件包，里面就是 HAL 库 | 能打开，能新建工程 |
| **STM32CubeCLT** | 命令行工具包。一个安装包里带着：CMake、Ninja、arm-none-eabi-gcc 一整套交叉编译工具、命令行下载工具 `STM32_Programmer_CLI`、ST-LINK 的 GDB 服务和各芯片的 SVD 文件 | 新开一个终端，下面四条命令都能打出版本号 |
| **VS Code 扩展** | 见下 | 扩展面板里能看到 |
| **下载器** | ST-LINK、DAP-Link、J-Link 都行，板载的也行。通过 SWD 两线口连到板子 | 插上后设备管理器里能看到 |

STM32CubeCLT 装好之后，新开一个终端，逐条执行：

```
arm-none-eabi-gcc --version
cmake --version
ninja --version
STM32_Programmer_CLI --help
```

四条都有输出，说明工具链就位。我本机的结果是：`arm-none-eabi-gcc` 12.3.1（GNU Tools for STM32 12.3.rel1）、CMake 3.28.1、Ninja 1.11.1。你的版本号会不同。如果提示找不到命令，是这几个工具的目录没在 `PATH` 里：把 CubeCLT 安装目录下的 `CMake/bin`、`Ninja/bin`、`GNU-tools-for-STM32/bin`、`STM32CubeProgrammer/bin` 加进 `PATH` 再重开终端。安装器是否会自动加，要看版本（待核对）。

在当前 **STM32 Profile** 里检查、安装这些扩展（在扩展面板搜名字，或搜括号里的标识）。从 `C-PC` 复制来的扩展不必重复安装，只确认在这套配置里启用；Cortex-Debug 等单片机扩展不需要放进 `C-PC`：

- **CMake Tools**（`ms-vscode.cmake-tools`）：在 VS Code 里完成配置、构建、选预设。必装。
- **C/C++**（`ms-vscode.cpptools`）：主线继续用它做代码提示和跳转。若你的 `C-PC` 已改用 **clangd**（`llvm-vs-code-extensions.vscode-clangd`），复制后重新检查分工，关闭 C/C++ 的 IntelliSense，避免两套分析同时给诊断；这里的编译数据库和工具链路径要换成 STM32 工程的。
- **Cortex-Debug**（`marus25.cortex-debug`）：连接调试器、下载、单步，3.2 会用。
- **STM32Cube for VS Code**（`stmicroelectronics.stm32-vscode-extension`）：ST 官方的扩展套件，能帮你管理 CubeCLT 的路径。可选，但装上更省事。

我本机装的是 CMake Tools 1.23.x、Cortex-Debug 1.12.1、ST 扩展 3.9.0，界面文字以你的版本为准。

Profile 不会自动隔离 Windows 的 `Path`，也不会替你安装 CubeCLT。扩展存在、命令能找到、工程选对工具链，是三件需要分别确认的事。

> [!warning] 最先要踩的坑：工程路径必须是纯英文、不带空格
> 我在 Windows 上试过：同一份工程放在含中文的路径里，CubeCLT 自带的 CMake 3.28.1 在配置阶段直接崩溃退出；放到纯英文路径，一切正常。所以工程放在比如 `D:\mcu\Led` 这样的位置，上层的文件夹名也别带中文和空格。

### 第二步：用 CubeMX 建工程

下面按 CubeMX 6.x 的界面写，菜单文字以你的版本为准。

1. **New Project**，在 Part Number 里搜你的芯片型号（比如 `STM32F407IGHx`），选中，Start Project。
2. **Pinout & Configuration → System Core → RCC**：High Speed Clock (HSE) 选 Crystal/Ceramic Resonator（有晶振的板子都选这个）。
3. **System Core → SYS**：Debug 选 **Serial Wire**；Timebase Source 保持 SysTick。
4. 在芯片图上点你的 **LED 引脚**，选 GPIO_Output。本教程的示例假设 LED 接在 PB13，**以你板子的资料为准**。怎么自己从原理图里找，2.3 会教。
5. 右键这个引脚，Enter User Label，输入 `LED`。
6. 在 System Core → GPIO 里确认这个引脚：Output push pull、No pull-up and no pull-down、Speed 为 Low。默认值就行。
7. 打开 **Clock Configuration** 选项卡：输入频率填你板子**实际的晶振频率**；PLL Source Mux 选 HSE；System Clock Mux 选 PLLCLK；在 HCLK 框里填 `168` 回车，让 CubeMX 自己求解。
8. **Project Manager**：Project Name 用英文（本节用 `Led`），Location 用纯英文路径；**Toolchain / IDE 选 `CMake`**；其余保持默认，点 **GENERATE CODE**。

> [!warning] 两个别踩的坑
> - **PA13、PA14 是 SWD 的 SWDIO 和 SWCLK。** 别把它们拿去当普通 IO，否则下载器很可能连不上板子。
> - **CubeMX 里的晶振频率必须和板子一致。** 这是 HAL_Delay 快慢的根，错了灯闪的速度就不对。

时钟树里 CubeMX 会自动填出 PLL 的参数。**以你 CubeMX 时钟树为准**，不要手改。参考一下：晶振 8 MHz 时，按公式 8 ÷ 4 × 168 ÷ 2 = 168，得到 `PLLM=4、PLLN=168、PLLP=2`；本教程作者的一块板子晶振是 12 MHz，生成的是 `6、168、2`。结果应该是：HCLK 168 MHz，APB1 外设 42 MHz、定时器 84 MHz，APB2 外设 84 MHz、定时器 168 MHz。这些数字后面第 5 章会反复用到，为什么是这样，放在[[【原理】时钟树|时钟树]]里讲。

### 第三步：读懂 CubeMX 生成的目录

在刚才准备的 VS Code 窗口里，用 **File → Open Folder** 打开生成的 `Led` 工程文件夹。打开后执行 `Profiles: Switch Profile`，选择 `STM32`，把它关联到这个工程；Profiles 编辑器的 **Folders & Workspaces** 中应能找到它。以后重新打开同一个工程，就会恢复这套 Profile。

从这里开始，两套环境这样区分：

| 要做什么 | 当前窗口的 Profile | 打开的工程 | 构建时确认什么 |
|---|---|---|---|
| 在电脑上练纯 C | `C-PC` | `C:/dev/c-lab` | CMake Kit 使用 PC 的 gcc |
| 构建、下载、调试单片机 | `STM32` | CubeMX 生成的 `Led` | CMake 配置预设使用 ARM 工具链 |

一个窗口使用一套 Profile。要同时看两边的代码，可以用 **File → New Window with Profile** 开另一个窗口，再打开对应文件夹；后续 PC 练习回 `C-PC`，本教程的板级工程继续用 `STM32`。如果误把 `c-lab` 关联到了 `STM32`，重新打开 `c-lab`，切回 `C-PC` 即可纠正关联。

**Profile 不是 CMake 的配置预设（Configure Preset）。** `STM32` 管编辑器环境，`debug`、`release` 这些预设管具体怎样构建；在同一个 STM32 Profile 下，也可以分别选择不同的构建预设。切换 Profile 不会自动改写 `.vscode/settings.json`、`CMakePresets.json`、工具链文件或已有的 `build` 缓存。最终要看 CMake 配置实际选中的编译器，不能只看 Profile 的名字。

接下来读工程目录。它大致是这样（CubeMX 版本不同，文件会略有出入）：

```
Led/
├─ CMakeLists.txt                 顶层：构建入口，CubeMX 只生成一次，之后归你改
├─ CMakePresets.json              预设：debug、release 等，记录用哪个工具链、构建到哪
├─ cmake/
│  ├─ gcc-arm-none-eabi.cmake     工具链文件：告诉 CMake 用哪个编译器、什么编译选项
│  └─ stm32cubemx/
│     └─ CMakeLists.txt           CubeMX 维护的源文件、头文件清单，重新生成时会被改写
├─ Core/
│  ├─ Inc/  main.h  stm32f4xx_hal_conf.h  stm32f4xx_it.h
│  └─ Src/  main.c  stm32f4xx_it.c  stm32f4xx_hal_msp.c  system_stm32f4xx.c
├─ Drivers/                       CMSIS 和 HAL 库
├─ startup_stm32f407xx.s          启动文件
├─ STM32F407XX_FLASH.ld           链接脚本
├─ Led.ioc                        CubeMX 工程文件，你的所有界面选择都存在这里
└─ build/                         构建之后才会出现
```

参考工程里还有一个 `cmake/starm-clang.cmake`，那是 ST 自己的 clang 工具链，本教程不用，用 GNU 的 `arm-none-eabi-gcc`。

几个文件各管一件事，按构建的先后顺序读：

- **`CMakePresets.json`** 是起点。你选一个预设（比如 `debug`），它就告诉 CMake：用 Ninja 生成构建清单，输出放在 `build/debug`，工具链文件是哪个，构建类型是 Debug。参考工程里它的"基础预设"长这样（我把工具链换成了 gcc 的）：

  ```json
  {
      "name": "default",
      "hidden": true,
      "generator": "Ninja",
      "binaryDir": "${sourceDir}/build/${presetName}",
      "toolchainFile": "${sourceDir}/cmake/gcc-arm-none-eabi.cmake",
      "cacheVariables": {
          "CMAKE_EXPORT_COMPILE_COMMANDS": "ON"
      }
  }
  ```

  预设的名字以你生成的为准，用 `cmake --list-presets` 查看；参考工程里是小写的 `debug`、`relWithDebInfo`、`release`、`minSizeRel`。另外，参考工程里的 `toolchainFile` 默认指向 `starm-clang.cmake`，你的 CubeMX 版本默认值是什么（待核对）。如果它指向的不是 `gcc-arm-none-eabi.cmake`，就像上面这样改成 gcc 的。
- **`cmake/gcc-arm-none-eabi.cmake`** 是工具链文件。它告诉 CMake 目标是什么机器、怎么编译。里面最关键的几行（原文摘录）：

  ```cmake
  set(CMAKE_SYSTEM_NAME               Generic)
  set(CMAKE_SYSTEM_PROCESSOR          arm)
  set(TOOLCHAIN_PREFIX                arm-none-eabi-)
  set(TARGET_FLAGS "-mcpu=cortex-m4 -mfpu=fpv4-sp-d16 -mfloat-abi=hard ")
  set(CMAKE_C_FLAGS_DEBUG "-O0 -g3")
  set(CMAKE_C_FLAGS_RELEASE "-Os -g0")
  set(CMAKE_EXE_LINKER_FLAGS "${CMAKE_EXE_LINKER_FLAGS} -T \"${CMAKE_SOURCE_DIR}/STM32F407XX_FLASH.ld\"")
  set(CMAKE_EXE_LINKER_FLAGS "${CMAKE_EXE_LINKER_FLAGS} --specs=nano.specs")
  set(CMAKE_EXE_LINKER_FLAGS "${CMAKE_EXE_LINKER_FLAGS} -Wl,--gc-sections")
  set(CMAKE_EXE_LINKER_FLAGS "${CMAKE_EXE_LINKER_FLAGS} -Wl,--print-memory-usage")
  ```

  逐行读：目标系统是 `Generic`（没有操作系统）、处理器是 ARM；编译器前缀 `arm-none-eabi-`；目标 CPU 是 Cortex-M4，带硬件浮点；Debug 构建不优化、带完整调试信息（`-O0 -g3`），Release 构建按体积优化、不带调试信息（`-Os -g0`）；链接时用 `-T` 指定链接脚本；构建完成后打印各存储区的用量（`--print-memory-usage`）。
- **顶层 `CMakeLists.txt`** 定义了工程名和可执行文件，再用 `add_subdirectory(cmake/stm32cubemx)` 把 CubeMX 维护的清单接进来。文件里有 `# Add user sources here` 这样的占位注释，就是留给你的。
- **`cmake/stm32cubemx/CMakeLists.txt`** 列出所有要编译的源文件（`main.c`、`stm32f4xx_it.c`、启动文件、HAL 的 `.c`）、头文件目录和宏（`USE_HAL_DRIVER`、`STM32F407xx`）。CubeMX 每次重新生成都会改写它，所以**不要手改它，也不要把自己的文件往 `Core/` 里加然后指望它被收进来**。第八步会给你的代码一个固定的家。

整条链是这样的：选预设 → CMake 读取预设、工具链文件、顶层 `CMakeLists.txt` → 汇总所有源文件 → 生成 Ninja 的构建清单 → Ninja 逐个调用 `arm-none-eabi-gcc` 编译，最后链接。启动文件和链接脚本怎么被带进来，2.4 会再细看。

### 第四步：写你的两行

在 `Core/Src/main.c` 里找到下面这一段，把两行代码放进 `USER CODE BEGIN 3` 与 `USER CODE END 3` 之间：

```c
  /* USER CODE BEGIN WHILE */
  while (1)
  {
    /* USER CODE END WHILE */

    /* USER CODE BEGIN 3 */
    HAL_GPIO_TogglePin(LED_GPIO_Port, LED_Pin);  /* 翻转 LED 引脚的电平 */
    HAL_Delay(500);                              /* 等 500 ms，期间 CPU 原地空转 */
  }
  /* USER CODE END 3 */
```

为什么是 `BEGIN 3` 而不是别处？`BEGIN 2` 在循环前面，只跑一次，灯只会翻转一下。区外的代码，重新生成时会被 CubeMX 抹掉（2.4 会让你亲眼看一次）。

完整的 `main.c` 放在下面，想对照整体结构时展开。

> [!example]- 完整的 main.c（CubeMX 生成 + 你的两行）
> 晶振 8 MHz 时的样子，PLL 参数按你的 CubeMX 为准。
>
> ```c
> /* USER CODE BEGIN Header */
> /**
>  ******************************************************************************
>  * @file           : main.c
>  * @brief          : Main program body

### 第五步：配置并构建

CMake 的"三步"里，前两步是**配置**（读各种 `CMakeLists.txt`，生成构建清单）和**构建**（真的去编译、链接）。你可以在 VS Code 里点，也可以在终端里敲，两种做法做的是同一件事。

**在 VS Code 里**：先确认这个工程关联的是 `STM32` Profile；执行 `CMake: Select Configure Preset`，选工程里实际存在的 `debug` 预设，再依次执行 `CMake: Configure` 和 `CMake: Build`。如果 CMake Tools 找不到 `cmake`，在**这个工程**的 `.vscode/settings.json` 中把 `cmake.cmakePath` 指向 CubeCLT 里实际的 CMake 可执行文件，不要把这项设置共享到所有 Profile。

**在终端里**（在工程根目录执行）：

```
cmake --list-presets
cmake --preset debug
cmake --build --preset debug
```

第一行列出有哪些预设，第二行配置，第三行构建。配置成功时会打印 `Build files have been written to: ...`；构建时你会看到每个 `.c` 被一个个编译，最后一行是链接。

> [!example] 我在电脑上构建同结构工程的结尾输出（Debug；你的数字会不同）
> ```
> Memory region         Used Size  Region Size  %age Used
>              RAM:        1584 B       128 KB      1.21%
>           CCMRAM:          0 GB        64 KB      0.00%
>            FLASH:        6000 B         1 MB      0.57%
>    text	   data	    bss	    dec	    hex	filename
>    5988	     12	   1572	   7572	   1d94	Led.elf
> ```

这几行就是上一小节里 `--print-memory-usage` 的成果，下面一行是 `arm-none-eabi-size` 的结果。它们告诉你程序占了多少 Flash、多少 RAM，2.4 会教你怎么读。

构建完成后，在 `build/debug` 里能找到这几个文件：

| 文件 | 里面是什么 | 大小（我的 Debug 构建） | 谁用它 |
|---|---|---|---|
| `Led.elf` | 机器码 + 地址信息 + 符号表 + 调试信息 | 964,352 字节 | 调试器和多数下载工具；你调试时看到的变量名、行号都来自它 |
| `Led.hex` | 文本格式的机器码，每行带地址 | 16,965 字节 | 下载工具，能直接知道写到哪 |
| `Led.bin` | 纯字节，没有地址、没有符号 | 6,000 字节 | 下载时你得另外告诉工具"写到 `0x0800 0000`" |
| `Led.map` | 链接器的"布局记录"：每个函数、变量放在了哪 | 333,964 字节 | 查"谁占了我的 Flash"时用 |

这四个文件里，只有 `.elf` 是链接器直接产出的，`.hex` 和 `.bin` 是后面用 `arm-none-eabi-objcopy` 从 `.elf` 转出来的。转换是顶层 `CMakeLists.txt` 里这几行安排的（作者的参考工程就是这么做的，函数的定义在后面的完整文件里；你的 CubeMX 版本是否已经自带，待核对）：

```cmake
create_hex_output(${PROJECT_NAME})    # 构建完成后用 objcopy 额外生成 .hex
create_bin_output(${PROJECT_NAME})    # 再生成 .bin
print_section_sizes(${PROJECT_NAME})  # 构建完成后打印 size 的结果
```

把预设换成 `release` 再构建一遍对比：Release 用 `-Os -g0`，不带调试信息。我这里同样的代码，Flash 用量从 6000 字节降到 3940 字节，`Led.elf` 从 964,352 字节降到 19,604 字节，而 `Led.bin` 是 3940 字节。三个文件里的机器码是同一份，`.elf` 大是因为 Debug 带了大量调试信息，真正要写进 Flash 的，只有那几 KB。

### 第六步：下载

下载就是把 `.elf`（或 `.bin`、`.hex`）里的字节写进芯片的 Flash。有两种做法：

**命令行**，用 STM32CubeProgrammer：

```
STM32_Programmer_CLI -c port=SWD -w build/debug/Led.elf -v -rst
```

`-c port=SWD` 表示通过 SWD 连接，`-w` 表示写入，`-v` 表示写完校验，`-rst` 表示写完复位运行。我没有接板子执行这一行，选项来自 `STM32_Programmer_CLI --help`（待核对）。

**在 VS Code 里**，用 Cortex-Debug 按 F5 下载并启动。在 `.vscode/launch.json` 里放一个最小配置（取自参考工程并泛化，`device` 改成你的芯片）：

```json
{
    "version": "0.2.0",
    "configurations": [
        {
            "name": "Debug STM32 - ST-Link",
            "cwd": "${workspaceFolder}",
            "type": "cortex-debug",
            "request": "launch",
            "servertype": "stlink",
            "executable": "${command:cmake.launchTargetPath}",
            "device": "STM32F407IGHx",
            "interface": "swd",
            "runToEntryPoint": "main",
            "svdFile": "${config:STM32VSCodeExtension.cubeCLT.path}/STMicroelectronics_CMSIS_SVD/STM32F407.svd",
            "serverpath": "${config:STM32VSCodeExtension.cubeCLT.path}/STLink-gdb-server/bin/ST-LINK_gdbserver",
            "stm32cubeprogrammer": "${config:STM32VSCodeExtension.cubeCLT.path}/STM32CubeProgrammer/bin",
            "armToolchainPath": "${config:STM32VSCodeExtension.cubeCLT.path}/GNU-tools-for-STM32/bin",
            "gdbPath": "${config:STM32VSCodeExtension.cubeCLT.path}/GNU-tools-for-STM32/bin/arm-none-eabi-gdb"
        }
    ]
}
```

`${config:STM32VSCodeExtension.cubeCLT.path}` 是 ST 扩展登记的 CubeCLT 路径。如果你没装 ST 扩展，这个设置不存在，请把它替换成 CubeCLT 的实际安装目录，比如 `D:/ST/STM32CubeCLT_1.16.0`。这份配置的细节和单步调试，3.2 再展开；这里你只要知道，F5 会下载并停在 `main` 的入口，再按继续就开始跑（我没有接板子验证，待核对）。

不管用哪种方式，板子上都要满足两个前提：**供电正常**，**BOOT0 引脚是低电平**（让芯片从自己的 Flash 启动）。多数开发板出厂就是这样，灯不亮时先检查它。

### 第七步：看灯，然后做两个探针

你应该看到：LED 每 0.5 秒亮灭一次，一个完整的闪烁周期是 1 秒。

> [!question] 先猜一猜
> 把 `HAL_Delay(500)` 改成 `HAL_Delay(5)`，重新构建下载。灯会怎么样？
> A. 闪得飞快，肉眼能数　B. 看起来常亮　C. 彻底熄灭

> [!success]- 揭晓
> 选 B 最接近。5 ms 翻转一次，一亮一灭是 10 ms，每秒 100 次，超过了眼睛能分辨的闪烁速度。亮和灭各占一半时间，所以看起来是常亮，只是比平时略暗（这是按时间推算的结果，你自己的灯怎么看，以眼睛为准）。

第二个探针，让你搞清楚自己板子上的 LED 是**高电平亮还是低电平亮**。把主循环里的两行换成：

```c
    HAL_GPIO_WritePin(LED_GPIO_Port, LED_Pin, GPIO_PIN_SET);   /* 输出高电平 */
```

重新下载。灯亮了，说明高电平点亮；灯灭了，说明低电平点亮。这件事不用试，读原理图就能知道，2.3 会教你。`TogglePin` 不关心极性，所以第一次点灯用它最省事。

### 灯不亮？按三道手排查

| 哪一道 | 问什么 | 怎么看 |
|---|---|---|
| 打包 | 配置和构建有没有 error？ | 配置阶段崩溃或报找不到编译器：先查路径是否纯英文、CubeCLT 是否在 `PATH`；构建输出里找 `error`；有就先别下载 |
| 送货 | 下载有没有成功、校验过没有？ | 下载器是否识别到芯片；下载工具有没有报 `verify` 失败；SWD 线是否接牢 |
| 开箱 | 复位之后程序真的在跑吗？ | 按一下复位键；BOOT0 是否为低；CubeMX 晶振频率是否填对（晶振起不来时，程序会卡在 `Error_Handler` 的死循环里） |

三道手都没毛病，再看灯本身：LED 极性、引脚是否选对。系统化的排错办法，3.2 会专门讲。

### 第八步：给自己的代码一个家

现在灯亮了，但两行代码直接写在 `main.c` 里。以后你要写串口日志、按键、定时器，几百上千行，不能都塞进去。CubeMX 的规矩是：**`Core/` 是它的地盘，你只在 `USER CODE` 区里写几行；自己的代码另建目录**。我们约定两个目录，整个教程都用：

- `User/Inc/`：放你自己的 `.h` 文件
- `User/Src/`：放你自己的 `.c` 文件

在工程根目录下新建这两个文件夹，然后把闪灯这件事封装成一个小模块。先写头文件 `User/Inc/blink.h`：

```c
#ifndef BLINK_H
#define BLINK_H

/* 翻转 LED 一次，然后等 500 ms。放进主循环里反复调用。 */
void blink_step(void);

#endif /* BLINK_H */
```

再写 `User/Src/blink.c`：

```c
#include "blink.h"
#include "main.h"   /* LED_Pin、LED_GPIO_Port 和 HAL 的声明都从这里来 */

void blink_step(void)
{
    HAL_GPIO_TogglePin(LED_GPIO_Port, LED_Pin);  /* 翻转 LED 引脚的电平 */
    HAL_Delay(500);                              /* 等 500 ms，期间 CPU 原地空转 */
}
```

回到 `main.c`，在 `USER CODE BEGIN Includes` 区加一行 `#include "blink.h"`，把主循环里的两行换成一行 `blink_step();`：

```c
/* USER CODE BEGIN Includes */
#include "blink.h"
/* USER CODE END Includes */
```

```c
    /* USER CODE BEGIN 3 */
    blink_step();
  }
  /* USER CODE END 3 */
```

现在最关键的一步：让 CMake 知道有这两个新目录。打开**顶层** `CMakeLists.txt`（它在 CubeMX 重新生成时不会被覆盖，文件头部写着"generated only once"），在 `add_executable` 之后的位置，加这三行：

```cmake
# 用户代码：User/Src 下的 .c 自动加入；新增文件后重新配置即可
file(GLOB_RECURSE USER_SOURCES CONFIGURE_DEPENDS ${CMAKE_SOURCE_DIR}/User/Src/*.c)
target_sources(${CMAKE_PROJECT_NAME} PRIVATE ${USER_SOURCES})
target_include_directories(${CMAKE_PROJECT_NAME} PRIVATE ${CMAKE_SOURCE_DIR}/User/Inc)
```

逐行读：

1. `file(GLOB_RECURSE ...)`：把 `User/Src` 下（包括子文件夹）所有的 `.c` 找出来，存进变量 `USER_SOURCES`。`CONFIGURE_DEPENDS` 让构建时重新检查一遍这个文件夹。
2. `target_sources(...)`：把这些 `.c` 加进可执行文件的源文件列表。**列表里有的才会被编译、链接。**
3. `target_include_directories(...)`：告诉编译器去 `User/Inc` 找头文件，`#include "blink.h"` 才找得到。

这样以后你每新建一个 `.c` 放进 `User/Src`，CMake 就自动把它收进来，不用再改 `CMakeLists.txt`。完整的顶层 `CMakeLists.txt` 放在下面，想对照时展开。

> - 删掉 `target_sources`：**链接器**报错，`main.c:91: undefined reference to blink_step`。头文件找得到，所以编译通过；但 `blink.c` 不在源文件列表里，没被编译，链接时找不到函数。这是 1.8 里你见过的 `undefined reference`，原因一模一样：**源文件列表就是"链接哪些 .o"**。
> - 删掉 `target_include_directories`：**编译器**报错，`fatal error: blink.h: No such file or directory`，`main.c` 和 `blink.c` 都报。

第三个探针：在 `User/Src` 里再新建一个 `.c` 文件，不改 `CMakeLists.txt`，直接构建。我在 Ninja 上试过，构建开头会出现 `Re-checking globbed directories`，新文件被自动收进并编译。保险起见，新增文件后仍然手动点一次 Configure：编辑器的代码提示靠配置阶段生成的 `compile_commands.json`，重新配置后才会认识新文件。

后面所有章节的"带走清单"里，文件位置一律写 `User/Inc/xxx.h` 和 `User/Src/xxx.c`，不再重复解释：**放进去，CMake 自动收，新增文件后重新配置一次。**

## 刚才发生了什么

先揭晓开头那道题：答案是 **B，2 行**。`main.c` 有两百多行，其余全是 CubeMX 生成的。我拿同样结构的工程构建，共有 19 个源文件参与（含启动文件和 HAL 库），其中你写的只有那 2 行。

再看这一路上的"三道手"，用寄快递来对应：

| 站 | 谁（真名） | 比喻 | 做的事 |
|---|---|---|---|
| ① | 你 + CubeMX | 写单子 | CubeMX 生成配置代码和 CMake 工程，你补两行 |
| ② | CMake + Ninja | 调度员 | CMake 读配置、生成构建清单；Ninja 照着清单安排活 |
| ③ | 交叉编译工具链（`arm-none-eabi-gcc` 等） | 打包工 | 在电脑上把 C 翻成 ARM 的机器码 |
| ④ | 链接器 + 链接脚本 | 仓库管理员 | 决定每段代码、每个变量放进 Flash 还是 RAM，产出 `.elf` |
| ⑤ | objcopy | 改装箱 | 从 `.elf` 转出 `.hex`、`.bin` |
| ⑥ | 下载器（ST-LINK）+ SWD | 快递员 | 把字节写进芯片的 Flash |
| ⑦ | 复位 | 收件人开箱 | CPU 从 Flash 起始处取出入口，开始执行 |

注意 CMake 本身并不编译任何东西，它是调度员，不是工人。第 1 章里的 `add_demo` 和这里的 `add_executable` 是同一种语言，只是这里多了一份工具链文件，告诉它"工人是交叉编译的那一套"。

**这里出现了一个新词：交叉编译。** 你在电脑（x86）上编译，程序却要在单片机（ARM）上跑，两种 CPU 的指令集不同，电脑自己的 `gcc` 编出来的东西，单片机看不懂。所以要用专门的编译器，它跑在电脑上，吐出来的却是 ARM 指令。编译的电脑叫 **host**，程序运行的单片机叫 **target**。这一整套工具合称[[【原理】交叉编译与工具链|工具链]]，工具链文件里的 `CMAKE_SYSTEM_NAME Generic`、`-mcpu=cortex-m4` 这些设置，就是在向 CMake 声明 target 是什么。

编译器的名字 `arm-none-eabi-gcc` 可以拆开读：`arm` 是目标 CPU 的架构；`none` 是没有操作系统；`eabi` 是嵌入式应用二进制接口，一套规定函数怎么传参、返回的约定，现在只要知道它是一套约定就够了；`gcc` 是编译器本体。同一套工具里还有 `arm-none-eabi-objcopy`（转格式）、`arm-none-eabi-size`（量大小，2.4 用）、`arm-none-eabi-gdb`（调试）等。

产物那张表你已经见过：`.elf` 带全部信息，`.hex` 带地址，`.bin` 只有字节。三个文件里的机器码是同一份，只是包装不同，这些格式的内部结构放在[[【原理】可执行文件格式|可执行文件格式]]里。

**下载就是把这些字节写进 Flash。** 下载器没有"运行程序"的魔法，它只负责把字节搬到 Flash 从 `0x0800 0000` 开始的位置（2.1 里核对过的地址）。Flash 断电不丢，所以下次上电，CPU 自己就从那里读出来跑，不需要电脑在场。

现在可以把"电脑上的程序"和"单片机上的程序"并排放一起看：

| | 电脑上的程序 | 单片机上的程序 |
|---|---|---|
| 在哪里编译 | 电脑上 | 电脑上（交叉编译） |
| 在哪里运行 | 同一台电脑 | 另一块芯片（target） |
| 编译器 | `gcc` | `arm-none-eabi-gcc` |
| 构建工具 | CMake + Ninja | CMake + Ninja（多一份工具链文件） |
| 有没有操作系统 | 有 | 没有（裸机） |
| 谁把程序装进内存 | 操作系统的加载器 | 没有人装：烧在 Flash 里，上电直接执行 |
| 产物 | `.exe` 或可执行文件 | `.elf`，再转成 `.bin` / `.hex` 下载 |
| 输出去哪 | 终端、屏幕（`printf`） | 引脚的电平（灯、串口 TX 脚等） |
| 出错了怎么看 | 终端报错 | 灯不亮就是没反应，要靠调试器或串口（第 3 章） |
| 内存大小 | GB 级 | KB 级 |

最后看你写的那几行。`HAL_GPIO_TogglePin(LED_GPIO_Port, LED_Pin)` 的参数是"哪个端口、哪个引脚"，函数本身并不认识具体哪盏灯，所以换引脚不用改代码。`HAL_Delay(500)` 靠[[【原理】SysTick与HAL时基|SysTick 定时器]]每 1 ms 计一次数，等够 500 次就返回。等待的时候 CPU 在原地空转，这叫忙等，现在点灯够用，后面我们会换更聪明的办法。

回到开头：三道手，你已经走了一遍。以后灯不亮，先问打包、送货、开箱，一个一个排除。

## 记住这几条

1. **自己的代码只写在 `USER CODE` 区之间，或者放进 `User/Inc`、`User/Src`。** 循环里反复执行的放 `BEGIN 3`，只执行一次的放 `BEGIN 2`。
2. **用户文件放 `User/`，靠顶层 `CMakeLists.txt` 里那三行自动收进来。** 新增文件后重新配置一次。漏了 `target_sources` 是链接错误，漏了 `target_include_directories` 是编译错误。
3. **引脚一律用 CubeMX 用户标签生成的宏**（`LED_Pin`、`LED_GPIO_Port`），不写死 `GPIOB` 和 `GPIO_PIN_13`。
4. **灯不亮，先问三道手**：构建过了吗？下载校验成功了吗？复位后真的在跑吗（BOOT0 为低）？
5. **CubeMX 里的晶振频率要和板子一致。** 不一致时 `HAL_Delay` 的快慢会不对，严重时程序卡死在 `Error_Handler`。
6. **SWD 占用 PA13、PA14，Debug 保持 Serial Wire。** 否则下载器可能再也连不上。
7. **工程路径用纯英文、不带空格。** 否则 CubeCLT 的 CMake 配置时可能崩溃。
8. **`HAL_Delay` 是忙等，只在主循环里用，中断里不许调用。**

## 练习

1. 完整走一遍本节，把灯点亮，并记下 Debug 和 Release 两个预设下构建输出里 Flash 和 RAM 的占用。（复现）
2. 让灯"亮 100 ms，灭 900 ms"，只能用 `HAL_GPIO_WritePin` 和 `HAL_Delay`，并且代码写在 `blink.c` 里。先用探针弄清自己的灯是高电平亮还是低电平亮。（改造）
3. 如果把 `HAL_GPIO_TogglePin` 和 `HAL_Delay` 这两行误放进 `USER CODE BEGIN 2`，灯会怎么样？先写下预测，再试。（预测）

> [!success]- 提示与答案方向
> 1. 数字以你自己的为准，把它记下来，2.4 要用。
> 2. 假设高电平亮，把 `blink_step` 改成：
>
>    ```c
>    void blink_step(void)
>    {
>        HAL_GPIO_WritePin(LED_GPIO_Port, LED_Pin, GPIO_PIN_SET);
>        HAL_Delay(100);
>        HAL_GPIO_WritePin(LED_GPIO_Port, LED_Pin, GPIO_PIN_RESET);
>        HAL_Delay(900);
>    }
>    ```
>
>    如果你的灯是低电平亮，把 `SET` 和 `RESET` 对调。
> 3. 只翻转一次：翻转完等 500 ms，然后进入一个空的 `while (1)`，什么也不再做。灯会停在翻转后的状态，不闪。
