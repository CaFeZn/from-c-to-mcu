# 补码与整型转换

串口收到一个字节 `0xFE`。协议说它表示 -2，你却打印出了 254；把它强制转换成 `int8_t`，电脑上看似修好了，另一个地方的 `-1 < 1u` 又变成假。问题不在串口，也不在比较器，而是你把三件事混在了一起：存下哪些位、表达式按哪种类型计算、最后怎样转换到目标类型。

这一篇接着 [1.3 整型与位运算](/lessons/1-3)，把主线中“格子”和“读法”的比喻落实为可以逐步推导的规则。先做实验，再给规则起名字。示例采用 C99，并要求实现提供 `uint8_t`、`uint16_t`、`uint32_t`；PC GCC 和本课 STM32F407 工具链满足这个条件。

## 先预测三个结果

在 [1.0 的 PC 工程](/lessons/1-0) 中增加一个演示目标，运行下面的完整程序。先猜：第一行是 `300 44` 还是 `44 44`？第二行的 -1 会留下什么值？

```c
#include <assert.h>
#include <stdint.h>
#include <stdio.h>

static int decode_twos8(uint8_t bits) {
    return bits < 128u ? (int)bits : (int)bits - 256;
}

int main(void) {
    uint8_t a = 200u, b = 100u;
    int sum = a + b;
    uint8_t small = (uint8_t)sum;
    uint8_t minus_one = (uint8_t)-1;

    assert(sum == 300 && small == 44u);
    assert(minus_one == 255u);
    assert(decode_twos8(0xFEu) == -2);
    printf("sum=%d stored=%u\n", sum, (unsigned)small);
    printf("minus_one=%u decoded=%d\n",
           (unsigned)minus_one, decode_twos8(0xFEu));
    return 0;
}
```

预期输出：

```text
sum=300 stored=44
minus_one=255 decoded=-2
```

`a + b` 并没有在 8 位里算。因为 `int` 至少能表示 -32767 到 32767，能覆盖 `uint8_t` 的全部 0 到 255，两边先提升成 `int`，所以结果是 300。随后存进 `uint8_t`，才把 300 转成 44。**表达式的类型由操作数决定，不是由接收结果的变量倒过来决定。**

## `1111 1110` 为什么能表示 -2

先暂时离开 C，把纸上八个比特当成一个协议字段。无符号的权重是 128、64、32、16、8、4、2、1。二进制补码的低七位权重不变，最高位的权重改为 -128。因此 `1111 1110` 的补码值为：

```text
-128 + 64 + 32 + 16 + 8 + 4 + 2 = -2
```

同样，`1000 0000` 是 -128，`0111 1111` 是 127。对一个宽度为 N 的补码字段，先把它读成无符号值 `u`：最高位为零时值就是 `u`，最高位为一时值就是 `u - 2^N`。上面的 `decode_twos8` 正是这条公式，减法在足够宽的 `int` 中进行，所有中间值都可表示。

这里的“补码”说明的是**表示**，不是允许一切 C 运算回绕。C99/C11 的普通有符号类型允许多种表示；但可选的精确宽度类型 `int8_t` 若存在，标准就要求它无填充位且使用补码。即便如此，C99/C11 中把 254 转成 `int8_t` 仍属于“目标有符号类型装不下”的转换，结果由实现定义，或产生实现定义的信号。GCC 明确规定按模缩减得到范围内的值，主线演示采用了它的规则。协议解码使用公式，可以把协议约定直接写进代码，不借这个实现选择。

## 按顺序走过三道关

### 第一关：小整数先提升

`char`、`signed char`、`unsigned char`、`short` 等低秩整数参与多数算术、比较及位运算前，先看 `int` 能否覆盖该类型的全部值。能则变为 `int`，否则变为 `unsigned int`。这叫**整数提升**。普通 `char` 是否有符号由实现选择，不应用它表达协议的有符号温度。

不能把“无符号小类型”简单等同于“按无符号计算”。例如在常见的 32 位 `int` 平台上，两个 `uint16_t` 先提升成 `int`，`60000 * 60000` 会超过 `INT_MAX`。下面先扩大一个操作数，才让乘法在能容纳结果的类型里发生：

```c
uint16_t width = 60000u, height = 60000u;
uint32_t area = (uint32_t)width * height; /* 3600000000 */
```

不要写成 `uint32_t area = width * height;` 后再期待左边替右边扩容，也不要把强制转换套在整个乘积外面。后两种写法都来不及挽救已经发生的有符号溢出。

### 第二关：双方选共同类型

提升之后，`+`、`-`、`*` 和比较等运算还要做**通常算术转换**。只看整数时，可以沿这条路线判断：

1. 类型相同，直接计算；同为有符号或同为无符号，把低转换等级的一方转换成高等级。
2. 一方有符号、一方无符号，若无符号类型等级不低，转换到该无符号类型。
3. 否则看较高等级的有符号类型能否表示另一方的全部值；能就用它，不能就用它对应的无符号类型。

等级不只是 `sizeof`：`long` 的等级高于 `int`，即使某个平台二者同宽。`int a = -1; unsigned b = 1;` 中二者等级相同，于是 -1 变为 `UINT_MAX`，`a < b` 为假。不是所有混合比较都变无符号，例如可覆盖 `unsigned int` 全范围的 `long long` 可以接住两边。

若有符号变量允许负值，而非负部分保证能放入对应的无符号类型，可以先处理负数：`a < 0 || (unsigned)a < b`。先理解范围，再写转换，不能只为消除警告盲目加一个 cast。数组长度涉及 `size_t` 时也应重新检查宽度，不能照搬 `unsigned`。

### 第三关：存入目标时再转换

目标能表示原值，值不变；目标为无符号且装不下，按“最大值加一”为模调整，所以 `(uint8_t)-1` 是 255、`(uint8_t)300` 是 44。目标为有符号且装不下，C99/C11 按前述实现定义规则处理。另一个完全不同的事件是 `int` 加法本身超范围，那属于未定义行为，见 [C 为什么不检查溢出](/notes/integer-overflow)。

## 回绕为什么有时正好有用

[5.2 的毫秒计时](/lessons/5-2) 用“现在减起点”，其依据是模运算，不需要把无符号值转成负数：

```c
uint32_t start = UINT32_MAX - 3u;
uint32_t now = 6u;
uint32_t elapsed = (uint32_t)(now - start);
/* elapsed == 10，计数跨过了零点 */
```

手算从 `UINT32_MAX - 3` 到最大值需要 3 步，到零再 1 步，到 6 再 6 步，共 10。转换回 `uint32_t` 把差约束到模 `2^32` 的范围。前提是你要测的真实经过时间少于一个完整计数周期，且没有因漏检查而丢失整圈信息。若已经过去一圈加 10，读数仍只告诉你 10。所谓“相减不怕回绕”，不等于“可以无限久不看时钟”。

## 再挡住两个常见误会

- 补码不意味着负数右移在 C99/C11 中必定补一，也不意味着负数左移安全。写掩码优先使用无符号操作数，并保证移位次数非负且小于提升后左操作数的位宽。`~small` 也先提升，并不会自动只翻转八位；需要八位结果时显式转回 `uint8_t`。
- `printf` 不会从参数里猜出类型。`uint8_t` 通常传参时提升为 `int`；本文先转为 `unsigned` 再用 `%u`。固定宽度的大整数可用 `inttypes.h` 的 `PRIu32`，或先转成确实能覆盖它的类型并使用匹配格式。

## 练习：拆开转换发生的位置

在上述类型存在的前提下，`(uint8_t)-129` 是多少？`uint8_t x = 255; int y = x + 1;` 中 `y` 是多少？如果再执行 `x = (uint8_t)y` 呢？最后解释为什么把 `60000 * 60000` 的接收变量改成 `uint64_t`，仍不能自动修复原表达式。

<details>
<summary>展开答案</summary>

`-129 + 256 = 127`，所以转换结果是 127。`x` 提升到 `int`，加一得到 256，`y` 因而是 256；转回 `uint8_t` 才得到 0。接收变量只参与赋值时的转换，不能改变已经求值的乘法。必须在乘法之前转换操作数，例如 `(uint64_t)width * height`。

</details>
