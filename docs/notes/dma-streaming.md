# DMA半传输与流式处理

ADC 连续采样，刚开机时均值正常。主循环偶尔打印一长行日志，曲线便出现一个不该有的尖峰。你给两个就绪标志都加了 `volatile`，尖峰仍在。

原因可能不在求平均的公式，而在平均期间的数组：**前半段曾经写完，不等于它现在仍属于 CPU；DMA 已经开始下一圈时，“昨天的就绪标志”保不住昨天的数据。**

本篇接着 [8.2 ADC 采集电压](/lessons/8-2) 和 [6.2 DMA 与空闲中断](/lessons/6-2)，把“回调置位、主循环处理”的适用前提补全。具体对象是 F407 循环 DMA 的双半区处理，不把顺序模型包装成线程安全驱动。

## 把八个格子画在纸上

设缓冲为 8 项，前半段是第 0～3 项，后半段是第 4～7 项。每次 ADC 结果搬入一项，输入依次为 1、2、3……16。先不要读缓冲，按四项一组填表：

| 刚搬完的输入 | 前半段 | 后半段 | 发生的通知 |
|---|---|---|---|
| 4 | 1、2、3、4 | 尚未填好 | HT |
| 8 | 1、2、3、4 | 5、6、7、8 | TC，随后回到开头 |
| 12 | 9、10、11、12 | 5、6、7、8 | HT |
| 16 | 9、10、11、12 | 13、14、15、16 | TC |

做两个预测：

1. 第一次 HT 后立即把前半段复制到另一块不交给 DMA 的数组，第二圈结束时这份复制是什么？
2. 一直不处理，只在两次 HT 中都执行 `half_ready = 1`，最后主循环能从这个标志知道发生过两次吗？

答案分别是“仍为 1～4”和“不能”。标志仍只为 1，而原缓冲已经是 9～12。配套 C99 顺序模型验证了这张表、独立快照和布尔通知合并；它没有模拟真实中断抢占，所以不声称证明了某段板级代码没有竞态。

## 半块能借给 CPU 多久

对一个偶数长度 N 的循环接收缓冲，单通道每秒搬入 Fs 个数据项，半块的时间预算为：

> T半块 = (N ÷ 2) ÷ Fs

从 HT 发生开始，DMA 填后一半；到下一次 TC，DMA 已经准备回到前一半。为了留出边界和服务延迟，不应压着第一次覆盖才结束，而应把下一次半区切换当作期限。

例如 N = 64、Fs = 2000 项/秒，半块是 32 项，预算为 16 ms。设计时必须满足：

> 最坏响应延迟 + 本次处理或复制耗时 + 安全余量 < 16 ms

若延迟 1 ms、计算 4 ms、余量 0.5 ms，总共 5.5 ms，可以进入后续实测；若计算需要 16 ms，总共 17.5 ms，应在设计阶段拒绝。不是“多数时候不到 16 ms”就算通过，还要把更高优先级中断、临界区、串口工作和总线争用纳入最坏情况。

下面的 C99 函数只验证预算算术。它不是实时调度器，也不能用一次测量出的平均耗时替代最坏耗时。

```c
#include <stdbool.h>
#include <stdint.h>

static bool block_fits_deadline(uint32_t latency_us, uint32_t work_us,
                                uint32_t guard_us, uint32_t half_period_us)
{
    return (uint64_t)latency_us + work_us + guard_us < half_period_us;
}
```

先提升到 64 位再相加，是为避免把大的 32 位耗时加成小数后误判通过。配套测试包含这一上限反例。

若 ADC 不经定时器限速，而以 21 MHz、56+12 周期连续转换，理论结果速率约为 308824 项/秒；64 项缓冲的半块预算只有约 104 µs。原本“很短”的主循环工作，在这个窗口里可能已经太长。改成受控触发率通常比盲目扩大数组更容易理解。

## 通知与所有权是两件事

HT/TC 是事件提示，不是互斥锁；DMA 硬件不读你的 `ready` 标志，也不会等主循环清掉它才继续。下面几种补丁各自只解决一小部分问题：

- **加 volatile：** 可以表达特定编译器下某些对象需要实际访问，但不延长缓冲有效期，不保证复合操作原子性，也不建立 C11 的线程同步关系。
- **把标志改成计数：** 可看见已服务回调之间的积压，却不会保存已被覆盖的数据。若关中断太久，硬件 HT/TC 标志本身会合并重复事件，回调计数也不是绝对不丢的采样圈数。
- **短暂关 CPU 中断：** 可用于保护 CPU 之间的共享索引，却不会暂停 DMA。把整个求均值包在关中断里，仍可能读到两圈混合的数据，还损害其它中断延迟。
- **读一次 NDTR：** 只能说明某一瞬间的位置；读完之后 DMA 仍在走。同一 NDTR 也可能来自下一圈。

因此，“置标志之后任意时刻读取”并不成立。要先选择数据交接策略，再决定回调里应该做多大工作。

## 三种可落地策略

### 方案一：直接处理，但证明能按期完成

低采样率、短计算、主循环最大间隔有界时，可以在下一次切换前完成刚结束半块的处理。把最坏延迟和处理时间测出来，检查上述不等式；检测到迟到就丢弃该块或停止采集，不能照常发布一个可疑均值。

为时间观测翻转诊断 GPIO，可以测量回调延迟与处理耗时，但那是软件执行时刻，不等于模拟采样时刻。断点单步通常会破坏时限，不能拿断点下的数组变化证明连续运行正确。

### 方案二：快速复制到真正属于消费者的块

在有严格上限的短处理路径中，将已完成半块复制到空闲软件块，随后把“块号、样本数、序号”交给主循环。复制也必须在 DMA 返回前完成；只排队一个原 DMA 缓冲指针并没有转移数据寿命。

队列必须说明：谁分配空闲块、谁发布、谁释放；满了是丢新块、丢旧块还是停采集，并记录计数。ISR 和主循环共享索引时，按目标编译器、CMSIS 和临界区约定实现同步；本篇不提供一段只靠 `volatile` 就宣称通用无锁的 C99 队列。

平均生产速率长期大于消费速率时，任何有限队列都会满。增加缓冲能吸收短时抖动，不能消除持续过载。

### 方案三：一次性采集，允许有间隙

测静态电压或低速批处理时，可以用普通 DMA 收满一批，并正确停止触发、确认 DMA 停止后再计算。计算结束重新准备下一批。这牺牲批次间的连续性，却能提供清楚的稳定快照；必须在时间戳上承认空洞，不能把各批拼接成等间隔连续数据。

## 两个半区不等于硬件双缓冲

一个 64 项循环数组，用 HT/TC 分成两半，是单缓冲双半区。F407 另有 DBM 硬件双缓冲：M0AR/M1AR 两个地址交替成为目标，CT 表示当前目标。它便于处理一块、填另一块，但同样有处理期限。修改地址时只能修改当前非活动目标，不能把正在被 DMA 使用的地址改掉。

多通道扫描还要保持“帧”的边界。三个通道按 A、B、C 顺序搬入时，半块长度最好是 3 的整数倍，否则下一半可能从 B 开始。此时 Fs 应使用**总数据项速率**，不是单通道采样率；两者混淆会把时间预算夸大三倍。

## 练习：64 项为什么装不下整齐的三通道半块

三个通道每秒各采 1000 次，现有 64 项循环缓冲。为什么半块不便处理？改成 96 项后，半块包含多少帧，时间预算是多少？一次 20 ms 的阻塞打印能接受吗？

<details>
<summary>展开答案</summary>

64 的一半是 32，不能被 3 整除，会把通道帧切开。96 的一半是 48 项，即 16 帧；总搬运速率为 3000 项/秒，预算是 48/3000 = 16 ms。一次 20 ms 阻塞已经超过预算，不算复制或计算就不合格。应改为非阻塞日志、降低采样率、采用有界复制及队列，或明确接受丢块/采集间隙。

</details>
