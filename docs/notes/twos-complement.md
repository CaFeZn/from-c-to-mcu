# 补码为什么成了标准

> **前置**：[1.3 整型与位运算](/lessons/1-3)。本篇先搭一个八位加法器模型，再回到 C 的类型规则。

## 五加负五，电路为什么不用先问正负

给一个只能保留八位结果的加法器输入 `0000 0101` 和 `1111 1011`，它会算出九位的 `1 0000 0000`。最高那一位没有地方存，留下的正好是零。

第二串位按无符号读是 251，按八位补码读却是 −5。同一个加法器，没有先比较谁正谁负，就完成了 `5 + (-5)`。这不是碰巧挑中了两个数：补码把整个负数区间安排到了能与普通二进制加法配合的位置。

先别背“取反加一”。试着回答：如果把负号单独放在最高位，−5 写成 `1000 0101`，直接与 5 相加还会得到零吗？

## 一、三种负号，三种账本

只讨论八个有效位、没有填充位的模型。正数 5 在三种方案里都是 `0000 0101`，区别从负数开始：

| 方案 | −5 的位模式 | 零的位模式 |
|---|---|---|
| 原码：符号加绝对值 | `1000 0101` | 正零与负零 |
| 反码：正数逐位取反 | `1111 1010` | 正零与负零 |
| 补码：取反后加一 | `1111 1011` | 只有全零 |

原码表达起来直观，却不能把符号当普通数位一起加。两个符号相反时，要判断绝对值、做减法、再决定结果符号。反码让许多操作更规整，但加法常要把最高位进位加回最低位，零也有两种编码。补码省掉了这些特殊处理：**先按普通二进制相加，只保留规定宽度；是否超出某种解释的范围，另行判断。**

“省掉特殊处理”不是说整颗 CPU 只剩一个加法器。比较、溢出检测、乘除等仍有自己的逻辑；它说明的是有符号和无符号加减法可以共享很大一部分数据通路。

## 二、为什么偏偏是取反再加一

八位共有 256 种状态。若希望 x 与“负 x 的编码”相加后低八位全零，就应选择 `256 - x`；当 x 为零时，仍保留零。八位逐位取反相当于 `255 - x`，再加一正好补齐。

这就是**模 256**：两数相差整整 256 的若干倍，在八位状态里落到同一处。一般 n 位则是模 2ⁿ。于是减法可以改写为加上模意义下的相反数：

`7 - 5` → `7 + 251` → 258 → 只留低八位得到 2。

但位模式还需要一本“读数说明书”。八位补码的读法是：0 到 127 原样读；128 到 255 减去 256 再读。因此 `0x80` 是 −128，`0xFF` 是 −1，范围不是对称的 −127 到 127。消除一个负零，恰好多出一个负数位置。

这个安排也让扩宽容易理解：−5 的八位编码 `0xFB` 扩成十六位，应该是 `0xFFFB`，都按相应宽度减去一圈后得到 −5。高位补 1 叫**符号扩展**；若补成 `0x00FB`，读到的就是正数 251。

## 三、用安全的 C 模型验证，不去制造溢出

下面的程序不把 128 强转成八位有符号数，也不让有符号表达式溢出。它用 `unsigned` 保存位模式，用普通 `int` 算出解码后的数学值。C99 保证它们足够容纳这里的中间结果，不依赖本机 `int` 恰好是 32 位。

先预测两行输出，再把整段作为独立 C99 程序编译运行：

```c
#include <assert.h>
#include <stdio.h>

static unsigned add8(unsigned a, unsigned b)
{
    assert(a <= 255u && b <= 255u);
    return (a + b) & 255u;
}

static int decode8(unsigned bits)
{
    assert(bits <= 255u);
    return bits < 128u ? (int)bits : (int)bits - 256;
}

int main(void)
{
    unsigned zero = add8(5u, 251u);
    unsigned edge = add8(127u, 1u);
    assert(zero == 0u);
    assert(edge == 128u);
    assert(decode8(edge) == -128);
    printf("bits=%02X value=%d\n", zero, decode8(zero));
    printf("bits=%02X value=%d\n", edge, decode8(edge));
    return 0;
}
```

预期输出：

```text
bits=00 value=0
bits=80 value=-128
```

第一行是正确的 `5 + (-5)`。第二行却不能解释为“有符号数学里 127 加一就是 −128”：数学结果是 128，超出了八位补码的正数范围；我们看到的是**截成八位后再解码**的结果。程序里的 `127u + 1u` 本身没有溢出，截断动作是显式的掩码。

## 四、硬件统一了，C 标准不是一直都统一

补码成为主流，既有共享加法通路、单一零编码、扩宽规整的工程优势，也有已经部署的大量机器和软件的惯性。WG14 的历史提案 N2218 列举了补码、反码、原码机器，并说明主流编译器的现实选择；它是理解标准为什么后来收拢的材料，不是“某一年所有机器同时改制”的证明。

读 C 代码时，还要分清两个时间点：

- **C99、C11**：一般有符号整数的表示允许原码、反码或补码，不能把现代 PC 的实验当成所有实现的要求。但可选的精确宽度类型 `int8_t`、`int16_t` 等若存在，已经要求无填充位的补码表示。不能反过来说所有 C99 平台都必须提供它们。
- **C23**：有符号整数表示统一要求补码。其公开草案 N3096 §6.2.6.2 第 2 段把符号位的权重规定为 −2ⁿ⁻¹，第 6 段明确称之为补码。但同一草案 §6.5 第 5 段仍保留越界表达式的规则：**普通有符号算术结果不可表示，行为仍未定义。** 表示规则与运算越界规则是两回事。

本课程以 C99 为基线。因此即使开发板确实使用补码，也先按可移植规则证明表达式安全，再研究生成的机器指令。

## 五、三个最容易混到一起的边界

**进位不等于有符号溢出。** `0xFF + 0x01` 有最高位进位，但按补码读是 −1 加一，结果零完全正常；`0x7F + 0x01` 没有最高位进位，却超出了有符号正数范围。它们是在回答不同的问题。

**补码不授权你执行 `INT_MAX + 1`。** 普通 `int` 的这个加法属于未定义行为，编译器不必保留你想象的低位结果。在补码范围下，对 `INT_MIN` 取负也无法用 `int` 表示。注意窄类型会先整型提升，不能把八位模型的边界直接套在每一个 C 表达式上。

**知道表示，不等于任意强制转换都有可移植结果。** 在 C99/C11 中，把 255 转成 `int8_t`，目标不能表示原值，结果是实现定义的，或引发实现定义的信号；并非语言保证“换一本说明书”。GCC 记录了自己的处理方式。上面的 `decode8` 则只做范围内转换和减法，明确表达我们需要的协议解码规则。

2. `0x7F + 0x02` 呢？哪一组有最高位进位，哪一组的有符号数学结果装不下？

第一组是 246 加 20，得到 266，低八位为 `0x0A`，读为 10。按补码解释输入是 −10 和 20，数学和为 10：有进位，但没有有符号溢出。

## 适用范围与继续阅读

八位模型适合解释数字电路、协议字段和固定宽度位模式；它不是任意 C 类型的对象表示探测器，也不讨论字节在内存中的排列顺序。只想让数到顶后停住，应选择另一种运算规则，而不是赌一次强制转换。
