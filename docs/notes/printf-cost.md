# printf 为什么慢又贵

你把一个计数值打印出来，灯还能闪；把打印移进每毫秒触发一次的中断，灯却几乎停了。再把整数改成小数，链接后的程序又突然变大。这里至少有三笔不同的账，不能一句“printf 很慢”就混在一起：**把值变成字符的计算、被链接进来的库代码、把字符送出设备的等待**。

本篇接着 [3.1 串口与日志](/lessons/3-1) 做两个不需要板子的实验。主机实验只验证格式化语义；交叉链接只比较产物体积。串口时长是计算值，不冒充真机测量。

## 先不碰 UART：8 个字节能放进 8 字节数组吗

下面是完整的 C99 程序。先预测两个返回值、两个数组的内容，再编译运行。输入固定为整数毫伏 `3300`。

~~~c
#include <assert.h>
#include <stdio.h>
#include <string.h>

int main(void)
{
    char full[16], small[8];
    int n = snprintf(full, sizeof full, "mv=%u\n", 3300u);
    int m = snprintf(small, sizeof small, "mv=%u\n", 3300u);

    assert(n == 8 && m == 8);
    assert(strcmp(full, "mv=3300\n") == 0);
    assert(strcmp(small, "mv=3300") == 0);
    printf("need=%d, stored=%u\n", m, (unsigned)strlen(small));
    return 0;
}
~~~

预期输出是 `need=8, stored=7`。完整文本占 8 字节，但 C 字符串还要存结尾的零，至少需要 9 字节。`snprintf` 的返回值是**若空间足够本来会生成的长度**，不含结尾零；它不是本次实际存进去的字节数。这里没有 UART，已经发生了截断，丢掉的恰好是换行。

因此，日志层必须先判负数，再判断是否达到容量：

~~~c
/* 集成片段：buf 是当前函数拥有的数组，n 是 snprintf 返回值。 */
if (n < 0) {
    /* 编码或格式化失败：记错误，不发送。 */
} else if ((size_t)n >= sizeof buf) {
    /* 截断：按约定整行丢弃，或者明确加截断标志。 */
} else {
    /* 只有此分支才能把 n 当作完整文本的字节数。 */
}
~~~

不要把过大的返回值直接交给发送函数，否则发送长度可能越过数组。也不要用 `sprintf` 替代检查：它没有容量参数，写出边界不是“输出乱一点”，而是未定义行为。

## 再算线上时间：DMA 不会改变这道除法

115200、8N1 的每个字符包含 1 起始位、8 数据位、1 停止位，合计 10 位。连续发送且没有流控暂停时：

~~~text
理论上限 = 115200 / 10 = 11520 字节/秒
64 字节占线时间 = 64 × 10 / 115200 ≈ 5.556 ms
1000 次/秒 × 每次 64 字节 = 64000 字节/秒
~~~

每毫秒产生 64 字节，平均产量是出口能力的五倍多，换 DMA 仍然发不完。DMA 解决的是 CPU 不必逐字等待，不是提高这根线的容量。缓冲只能接住有限的突发；若长期净增长约为每秒 52480 字节，一块最初为空的 1024 字节缓冲，在理想连续模型下约 19.5 ms 就会装满。实际开始时机、整行丢弃和发送批次会使观察值不同。

测量时也要区分“函数返回”和“最后一个停止位离开 TX”。异步发送的前者可能很快，后者仍受上述带宽约束。用 GPIO 包围格式化函数只能看 CPU 工作的区间；用逻辑分析仪观察 TX，才能看真正的占线时间。二者不是互相替代的探针。

## 第三笔账：一次调用拉进多少库代码

`printf` 要解释格式串，做整型或浮点转换，再经过流对象和底层输出接口。具体实现可能还使用重入状态、锁、缓冲和内存分配；不能断言每次调用都分配堆，也不能断言“线程安全库”就允许在中断里随便重入。

本组做了一个隔离的交叉链接实验：同一源文件用条件编译分别选择空 `main`、`printf("mv=%lu\n", mv)`、`printf("v=%.3f\n", v)`。为防编译器预先折叠数值，输入来自局部 `volatile` 变量。工具链为 GNU Tools for STM32 12.3.1，目标选项固定为：

~~~text
-std=c99 -mcpu=cortex-m4 -mthumb -mfloat-abi=soft -Os
-ffunction-sections -fdata-sections -Wl,--gc-sections
--specs=nano.specs --specs=nosys.specs
浮点组另加：-u _printf_float
~~~

实际 `arm-none-eabi-size` 输出摘要如下，单位为字节：

| 入口 | text | data | bss |
| --- | ---: | ---: | ---: |
| 空 main | 354 | 8 | 32 |
| 整数输出 | 4373 | 100 | 364 |
| 浮点输出且拉入支持 | 14498 | 464 | 364 |

这不是“任何 printf 固定占 4 KB”的结论。它只属于这些版本、ABI、优化和链接选项，实际工程里已经使用了哪些库函数，也会改变增量。`text` 通常还包含只读常量；`data` 通常既需要 RAM，也需要装载镜像；`bss` 不反映运行时栈峰值和堆峰值，不能把三列当作完整内存预算。

此实验使用默认链接环境和 `nosys` 桩，链接器确实警告 `_write` 等系统调用未实现。**这些 ELF 没有板级启动、正确的板级链接布局和串口重定向，不是可直接下载的固件，也没有执行过浮点输出。** 警告不影响本次链接体积比较，却说明“链接成功”不等于“输出通道已接好”。

## 为什么加了浮点选项才有小数

在这里使用的 Arm GNU newlib-nano 配置中，浮点格式化支持采用可选符号，链接时以 `-u _printf_float` 拉入。它不是 C 语言不支持 `%f`，也不是 Cortex-M4 有没有 FPU 的同一个问题。FPU 解决特定浮点运算，十进制格式化仍然需要库算法；可变参数中的 `float` 还会提升为 `double`。

课程主线故意选择整数日志。若数据本来就是毫伏，传递 `3300` 比先转成 `3.3` 再格式化更直接。若确实需要小数，先确认库配置、性能和空间预算，而不是盲目打开所有功能。不同编译器的底层接线可能不是 `_write`；这里的重定向说的是 newlib 工具链，不是 C 标准规定的函数名。

## 中断里最贵的可能不是格式化

阻塞串口发送会一直等状态标志或超时。某些超时依赖系统节拍，而当前中断的优先级可能不让节拍中断运行；若通道卡住，原本以为有限的等待就不再按预期前进。库锁也可能由被打断的主循环持有。反过来，即便换成非阻塞日志，格式化和整段复制仍然占用当前执行时间。

稳妥的分工是：中断记录事件编号、少量数值或计数，主循环把事件转成文本；日志出口只有一个所有者，队列满时明确丢新、丢旧或拒绝，并保留丢弃计数。调试崩溃现场可以另设有界的紧急输出路径，但不要让普通日志默认无限等待。

还要防两个与速度无关的坑：不可信文本应作为 `%s` 的数据，不能直接当格式串；格式符必须匹配提升后的实参类型，类型不匹配不是“显示不准确”，可能产生未定义行为。格式化后排队还涉及缓存生命周期，局部数组不能借给尚未结束的 DMA。

## 动手检查与练习

本组独立测试已经在 PC GCC 6.3.0 的 C99 Debug 与 `-O2` 下运行，覆盖上述截断和带宽整数演算。可在仓库根目录单独重跑，不需要构建网站：

~~~sh
cmake -S examples/notes/serial/core -B artifacts/course-completion/serial/core-build -G Ninja
cmake --build artifacts/course-completion/serial/core-build
ctest --test-dir artifacts/course-completion/serial/core-build --output-on-failure
~~~

练习：115200、8N1 下，每 2 ms 记录一行 40 字节文本，256 字节缓冲能否长期不丢？如果把 CPU 格式化时间优化为零，结论会改变吗？

<details><summary>展开答案</summary>

每秒产生 `500 × 40 = 20000` 字节，大于 `11520`。平均净积压约 `8480` 字节/秒，空缓冲按流体近似约 `256 / 8480 ≈ 30.2 ms` 装满；离散整行策略可能更早拒绝。优化格式化只省 CPU，不增加出口带宽。应降采样日志、缩短记录、改二进制编码或提高合法链路速率，并保留明确的拥塞策略。

</details>
