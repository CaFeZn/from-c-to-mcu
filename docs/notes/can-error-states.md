# CAN错误状态机

只接一块板和收发器，发送函数前三次都返回成功，第四次却说邮箱满；串口里没有“发送完成”，错误计数升到128附近后不再增加。把它解释成“HAL卡死”会走错方向：前三次成功通常只表示请求入邮箱，控制器仍在反复尝试没有得到ACK的帧。

本篇接着 [7.3 过滤器与错误处理](/lessons/7-3)，以F407 bxCAN的寄存器为具体观察入口，区分**请求、链路成功、错误状态与应用是否执行**。不需要故意短接总线才能学会状态机。

## 先预测三条轨迹

给定初始TEC=0、REC=0，并先忽略成功传输和错误计数规则中的其他事件。下面第一条轨迹刻意限定“每次都适用TEC加8规则”，不是所有发送失败的通用公式：

| 已发生的加8事件数 | TEC | 所处状态与提示 |
|---|---|---|
| 0 | 0 | 错误主动，无警告 |
| 12 | 96 | 仍错误主动，达到警告门槛 |
| 16 | 128 | 错误被动 |
| 31 | 248 | 仍错误被动 |
| 32 | 256 | Bus-Off |

第二条轨迹改成：只有一个节点，线路本身正常，只缺ACK。它可以因ACK错误进入错误被动；**进入被动后，若发送被动错误标志期间也没有检测到显性位，就适用TEC不增加的例外**。因此不能把“32次失败必定Bus-Off”套进这个场景。

第三条轨迹是TEC=0、REC=128。它是错误被动，但不是Bus-Off：**Bus-Off的门槛只由TEC达到256触发，不是任一计数达到256**。这些区别比背三个英文名称更重要。

## 三种状态，一条警告线

- **Error Active，错误主动**：TEC和REC都低于128。发现相应错误时，可发出主动错误标志；它包含6个连续显性位，会使当前传输不能被当作正常帧接受。
- **Error Passive，错误被动**：TEC或REC达到128。节点仍可参与通信，并非“只能收不能发”；检测错误时使用被动错误标志，而不是主动错误标志。刚完成发送的被动节点在正常帧间歇之外，还需遵守8位的Suspend Transmission等待规则；若别人先发送，它仍可接收。
- **Bus-Off，总线关闭**：TEC达到256。F407的bxCAN不再正常收发报文，也不能继续影响总线；还保留恢复所需的总线监测能力，不能把它理解成芯片断电。

硬件的错误警告在任一计数达到96时置位。它不是第四种与前三种并列的状态，也不是到96就禁止发送。警告常常比彻底掉线更值得记录：它给你排查间歇干扰、接地与位定时留下时间。

TEC和REC也不是“从上电累计错误次数”。成功发送通常使TEC减1，最低为0；成功接收在低计数区使REC减1，高计数区有恢复到较低范围的特殊规则。检测错误标志期间的位错误、连续显性等事件还可能引起加8。**不要自己在软件里按“收错加1、发错加8”重建一个声称完全等价的控制器。**

## 用一张寄存器快照练习诊断

F407的CAN_ESR中，REC在31:24，TEC字段在23:16，LEC在6:4，BOFF/EPVF/EWGF在2/1/0。关键细节：**TEC字段只是内部9位TEC的低8位**。发生Bus-Off后，看见该字段很小不表示恢复健康，必须看BOFF。

以下完整C99程序解码一个人为构造的快照，不访问芯片：

```c
#include <assert.h>
#include <stdint.h>
#include <stdio.h>

static const char *can_state(uint32_t esr)
{
    if ((esr & 4u) != 0u) return "bus-off";
    if ((esr & 2u) != 0u) return "error-passive";
    return "error-active";
}

int main(void)
{
    const uint32_t esr = UINT32_C(0x00800033);
    const unsigned tec_low = (unsigned)((esr >> 16) & 255u);
    const unsigned rec = (unsigned)((esr >> 24) & 255u);
    const unsigned lec = (unsigned)((esr >> 4) & 7u);
    assert(tec_low == 128u && rec == 0u && lec == 3u);
    printf("TEC-low=%u REC=%u LEC=%u %s\n",
           tec_low, rec, lec, can_state(esr));
    printf("BOFF snapshot: %s\n", can_state(4u));
    return 0;
}
```

预期第一行是`TEC-low=128 REC=0 LEC=3 error-passive`，第二行是`BOFF snapshot: bus-off`。后者只用于测试“BOFF判断优先”，不是声称真实芯片在某时刻一定恰好返回`0x00000004`。

LEC=3表示ACK错误；1是填充错误，2是格式错误，4/5分别是Bit recessive/Bit dominant错误，6是CRC错误，0表示无错误，7是软件设置的标记值。它是**最近一次错误状态**，不是累计分类表；后续成功传输可将它清为0。只每秒读一次，可能完全错过短暂错误。

## 怎样观察而不让日志制造新问题

在隔离于真实设备的双节点台架上，先让双方用已验证的正常配置稳定通信，并记录成功计数。随后停止另一节点的参与，观察剩余节点；不要用生产网络或执行器做故障注入。

给定输入为“Normal模式、自动重传开启、收发器使能、物理连接没有额外位错误、没有其他节点ACK”。预测是请求逐渐占满3个邮箱，成功发送计数不增长，LEC可能报告ACK错误，TEC进入被动后符合上述例外。若实际Bus-Off，说明实验前提可能不成立：还有位错误、额外显性、收发器模式或接线问题，不能用理论把实测抹掉。

程序应在错误中断/回调里保存事件标志与必要的ESR快照，主循环再格式化输出。主循环和中断共享数据需要按课程的临界区约定处理；单加`volatile`不等于多字段快照天然一致。别在高频错误回调里阻塞打印，打印造成的队列溢出会让诊断更混乱。

同时记四类量：请求数、成功完成数、接收/丢弃数、错误状态与时间戳。CAN接收FIFO溢出或软件队列满，是应用取走消息太慢的另一层问题，不应直接改叫“协议Bus-Off”。

## 恢复不是清一个布尔值

RM0090规定：自动恢复由MCR.ABOM控制；未开启时，软件通过进入并离开初始化模式发起恢复。两者都必须满足**观察到128次、每次11个连续隐性位**的恢复序列。初始化模式不监测CANRX，因此一直停在初始化模式里等BOFF清零不可行。

若总线持续隐性，128×11=1408位在500 kbit/s下对应2.816 ms；这是理想空闲情况下的协议等待量，不是“调用恢复函数后精确2.816 ms必定恢复”的墙钟保证。忙碌总线、持续故障、模式切换和软件调度会改变实际耗时。它也不要求整段1408位必须毫无间断地连续隐性，关键是规定的11位序列出现次数。

应用层恢复流程至少包括：保存原因和发生时间；把依赖通信的输出置于设计好的安全状态；限制恢复次数与重试频率；查清接线、时钟与收发器状态；发起恢复并等待硬件状态变化；重新建立对端在线与业务状态。自动恢复只完成控制器的那一段，不证明对端已经收到新指令。

还有一个常被遗漏的问题：恢复后的待发数据是否已经过期？例如两秒前的电机目标速度不应只因邮箱终于能发就继续执行。应用应按自己的时效、序号与取消策略处理积压消息，而不是无限重发旧请求。

## 练习：把三个判断分开

1. 快照REC=130、TEC-low=2、EPVF=1、BOFF=0，是什么状态？
2. TEC-low=0、BOFF=1，能否认为已恢复？
3. 单节点因缺ACK停在128，是否说明它永远不可能Bus-Off？

<details><summary>展开答案</summary>

1. 错误被动，因为接收错误计数已越过门槛；不是Bus-Off。
2. 不能。低8位不能表达内部256这个门槛，BOFF仍有效时必须按Bus-Off处理。
3. 不能。结论只适用于特定ACK错误例外；若出现其他使TEC增长的错误，仍可能进入Bus-Off。恢复后再次遇到同一根因，也可能很快再次掉线。
