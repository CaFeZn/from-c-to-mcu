# SWD 引脚被占用后的救援

刚下载的新程序把 PA13 配成了普通输出。LED 还在闪，下次连接却一直超时。换 USB 口、重装驱动都没用，你开始怀疑芯片被“锁死”。

先不要点击全片擦除。**应用启动后抢走引脚**，与读保护、供电不稳、探头失联，是几件不同的事。F407 复位时有默认调试引脚配置；在应用重配之前抢先建立连接，往往就有救援窗口。本篇只讨论自己有权维护的实验板，不提供绕过产品安全保护的方法。

## 第零步：让每次试验可比较

把当前错误文本、板子型号、探头型号、固件版本、接线和工具连接模式记下来。确认原固件和必要数据是否有备份，记录选项字节的可读信息。不要为了“试一下”顺手改变 RDP、WRP 或启动相关选项字节。

断开电机、继电器等可能运动或带来风险的负载，或者进入项目规定的安全状态。CPU 暂停时外设不一定暂停，重新启动也可能驱动输出。救援连接本身虽不擦 Flash，却会复位和改变运行状态，不能在设备忙于生产动作时直接进行。

先检查供电与共同地，确认 SWDIO 接 PA13、SWCLK 接 PA14。若探头要求 VTref，检查目标参考电压；VTref 不是自动给目标供电的保证。再核对 **NRST 真的连到 MCU 的复位网络**，不是接到 JTAG 的 nTRST，也不是只在 IDE 中选了“硬件复位”。

## 第一步：把“线路坏了”与“软件抢脚”分开

用同一套已经验证过的短线和探头，选择 SWD 接口，降低到工具支持的低速，例如候选 100 kHz，实际以探头支持列表为准。这里只连接、识别，不写入固件。

本轮的输入与预测如下：

| 操作 | 若应用启动后抢脚，可能看到什么 |
|---|---|
| 正常连接，应用一直运行 | 识别超时或连接立即掉线 |
| 复位下连接，先停在启动早期 | 能识别内核/设备，且保持连接 |
| 继续执行到错误 GPIO 初始化 | 接口再次失联 |

这三个现象一起出现，比一次“连接成功”更能支持软件重配置的假设。如果按住复位后连目标参考电压都没有，或者 SWCLK 根本没到目标脚，先修电气链路，不能用这张表推断 GPIO 代码有错。

不要为了复现实验，特意给一块没有 NRST、BOOT 接点的唯一工作板刷入抢脚程序。可以使用现有故障，或仅在有恢复手段的备用实验板上验证。

## 第二步：在复位下连接

常见工具把该模式叫 **Connect under reset**。F407 系统复位期间 SWJ 引脚回到调试用途；探头在复位窗口建立 SWD，设置复位捕获或相应的停止条件，释放复位后尽早停住内核，避免应用再次抢走引脚。

在本地 STM32CubeProgrammer CLI 帮助中，`mode=UR` 表示此模式，且该模式使用硬件复位。以下只请求连接，不附带擦除或下载选项：

```sh
STM32_Programmer_CLI -c port=SWD mode=UR reset=HWrst freq=100
```

100 的单位是 kHz。若工具报告不支持该频率，换成它列出的可用低频；不要假装所有探头接受相同档位。本篇实际核对的是已安装 CLI 的 `--help`，**没有执行这条连接命令，也没有实板连接结果**。

GUI 中采用对应的 SWD、Under Reset、Hardware Reset 设置，并确认复位线接通。手动按住复位再开始连接、按工具提示释放，有时可作为诊断手段，但它对时序敏感，不如探头控制 NRST 可重复。“一直按住复位却始终停不到 main”并不奇怪，处理器仍被保持在复位中。

连上后先观察而不是立刻继续：保存设备身份、保护状态和可读取的关键数据，确认停在错误应用初始化之前。之后用修复过的实验固件下载并校验。修复应真正移除 PA13/PA14 的错误配置，检查 CubeMX 生成代码和自己的 GPIO 初始化，而不只是把界面上的 Debug 选项改回去。

## 第三步：必要时改从系统存储器启动

如果当前应用一复位就进低功耗、重配引脚或高速崩溃，且板上可安全调整启动脚，可以让它暂时不执行那份 Flash 应用。**对 F407**，RM0090 给出的启动选择为：

| BOOT0 | BOOT1 | 复位后的启动存储器 |
|---|---|---|
| 0 | 任意 | 主 Flash |
| 1 | 0 | 系统存储器 |
| 1 | 1 | SRAM |

因此“把 BOOT0 拉高”还不完整，必须知道 BOOT1 的状态。按板图调整跳线或电平，避免与板上强驱动冲突，然后复位再尝试 SWD 连接。系统存储器里的 ROM bootloader 与 SWD 是不同入口；采用 ROM 的 UART/USB 下载，还要查具体芯片支持的接口和引脚，不能见到 USB 插座就认为支持 USB DFU。

启动模式的作用是避开出错的应用，不是解除安全保护。完成修复后恢复 BOOT0=0，再执行正常复位、脱离调试器冷启动，确认运行的是主 Flash 中的修复固件。忘记恢复跳线，会制造“下载成功但应用不运行”的新故障。

## 碰到保护状态必须停在正确边界

若可以识别器件，却访问 Flash 报保护错误，或工具明确报告 RDP，这不是同一个抢脚问题。F407 的 Level 1 回退到 Level 0 会触发主 Flash 和备份 SRAM 的擦除；不能把“解除保护”当作无损救援按钮。先确认授权、数据可丢弃性、可恢复固件与产品流程。

Level 2 不可逆，关闭相应调试与引导能力；普通 under-reset、改 BOOT 或慢速连接不能撤销它。本课程不让读者试烧 Level 2。若板子状态不明、资料不匹配，保留日志并核对器件手册和维护流程，不反复写随机选项字节。

还有三种边界容易被误诊：

- **低功耗**：应用进入某些低功耗状态后，调试链可能受影响；先用复位前连接验证，再检查低功耗和 DBGMCU 设置，不一上来全片擦除。
- **复位线被硬件拖住**：外部复位芯片、过大电容或线路短路会让复位波形不符合工具预期。软件设置无法修复一条没有接通的 NRST。
- **设备仍能跑不代表 SWD 正常**：CPU 执行 Flash 与外部探头连接经过不同路径，不能因为灯闪就排除调试口线路问题。

## 救回以后怎样证明真的修好了

把测试分为“连接恢复”和“应用恢复”两项：先用正常连接模式重复连接，确认无需每次 UR；再断开探头、按产品接线独立供电启动，检查应用行为。最后复核修复固件没有重新占用 PA13/PA14，板上是否留出了 GND、VTref、SWDIO、SWCLK、NRST 的可访问测试点。

延迟几秒再重配调试脚可以给开发救援留窗口，但不是量产安全策略，也不替代专用维护入口。安全保护和可维护性需要一起设计。

### 练习：BOOT0 高了仍没进 ROM

一块 F407 板 BOOT0=1、BOOT1=1。你以为它已经绕开应用进入 ROM，连接日志却不符合预期。第一步应改保护等级吗？还应补哪项测量？

<details><summary>答案</summary>

不应。该组合选择 SRAM，不是系统存储器。先按板图确认并设置 BOOT1=0，核对引脚实际电平与复位时序，再复位观察。还要测目标供电/VTref、检查 NRST 与 SWD 接线。保护等级变化既不能替代正确启动配置，也可能擦除数据或造成不可逆状态。
