# 文本协议与二进制协议

电脑端本来每次都能读到 `mv=3300`，某天却收到半行 `mv=3`，下一次才出现 `300`。你把发送端改成一个结构体直接发，换电脑后数值又变了。前一个故障是把一次读取当作一条消息，后一个是把本机内存布局当作线上格式。它们都不是“串口偶尔不稳定”。

这一篇不争论哪种协议高级。我们让同一个 3300 毫伏读数走两条路径，分别说明每个字节是什么意思、哪些输入应该拒绝，以及如何从连续字节中确认一条完整消息。主线接口仍回到 [6.1 串口命令行](/lessons/6-1) 和 [6.3 设计自己的协议](/lessons/6-3)。

## 先把文本规则写到能判错

约定一个刻意很小的协议：ASCII 文本，以 `mv=` 开头，后接一到五个十进制数字，再接单个 LF；数值范围 0 到 65535，允许前导零。不允许空格、负号、CR、尾随垃圾或内嵌零。单位固定为毫伏，不用浮点，也不依赖本地小数点设置。

固定输入 `mv=3300\n` 共 8 字节，成功后结果是整数 3300；`mv=65536\n` 必须失败，而不是回绕成零。下面是完整的解析函数，调用者保证 `p` 指向至少 `n` 字节，`out` 有效；函数处理的是一条已经拼完整的消息，不负责从 UART 收集一行。

~~~c
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>

static bool parse_mv(const uint8_t *p, size_t n, uint16_t *out)
{
    uint32_t v = 0;
    if (n < 5u || n > 9u || p[0] != 'm' || p[1] != 'v' ||
        p[2] != '=' || p[n - 1u] != '\n') return false;
    for (size_t i = 3u; i + 1u < n; ++i) {
        if (p[i] < '0' || p[i] > '9') return false;
        uint32_t d = (uint32_t)(p[i] - '0');
        if (v > (UINT32_C(65535) - d) / 10u) return false;
        v = v * 10u + d;
    }
    *out = (uint16_t)v;
    return true;
}
~~~

先检查下一步乘十加数字是否超过上限，再计算；不要让溢出先发生才回头补救。只在整条消息通过后赋给 `*out`，失败不会偷偷把原来的有效读数改成半成品。明确长度也意味着消息不需要尾随 C 字符串的零，`strlen` 不参与判断。

主机测试除正常输入外，还实际喂入空数字、65536、负数、混入字母、CRLF、换行后垃圾、六位数字和内嵌零，全部拒绝，并检查输出参数保持原值。用 `atoi` 替代会失去可靠的错误定位；采用 `strtoul` 等库函数时也必须检查终止位置、范围和错误状态，不能只看返回值非零。

## 接收端先拼行，再解析字段

发送一次 8 字节，不保证电脑一次读取 8 字节。`mv=3300\n` 可能分成 `m`、`v=33`、`00\n` 三批，也可能与下一行一起交上来。接收器应逐字节处理：遇到 LF 才提交当前行；容量用尽后进入丢弃状态，一直丢到 LF，不能把超长消息后半截当作新命令。

本例最多 9 字节含 LF。若行缓冲还需要 C 字符串结束零，应另留一个位置；缓冲容量是字节数，不是“能容纳多少汉字”。若将来允许 UTF-8 文本，一个字符可能占多个字节，分包还可能落在字符内部。协议层收齐字节后再交给合适的文本解码器。

换行也不是所有文本协议的天然边界。JSON 允许结构内部有空白和换行；只有双方另行约定“一行一个 JSON 值”并限制生成格式，才可以按单行分包。需要 JSON 时使用经过验证的解析库并限制深度、长度与数值范围，不把本例十几行代码扩充成临时的 JSON 解析器。

## 同一读数，换成明确的两个字节

现在只定义一个二进制**字段**：无符号 16 位整数，单位毫伏，低字节先传。3300 是 `0x0CE4`，所以字节顺序必须是 `E4 0C`。这不是一条完整协议，尚未解决消息边界、类型、校验或版本。

~~~c
#include <stdint.h>

static void put_u16_le(uint8_t p[2], uint16_t v)
{
    p[0] = (uint8_t)v;
    p[1] = (uint8_t)(v >> 8);
}

static uint16_t get_u16_le(const uint8_t p[2])
{
    return (uint16_t)((uint32_t)p[0] | ((uint32_t)p[1] << 8));
}
~~~

调用时保证两字节已齐全。逐字段移位组装，和 CPU 本机字节序无关，不要求接收缓冲地址满足 `uint16_t` 对齐，也不通过强制转换违反别名规则。本组测试枚举 0 到 65535 的所有值，编码再解码都还原原数，并核对 3300 的固定字节对。

直接发 `sizeof(struct)` 有四个隐含约定：成员间填充、各类型宽度、本机字节序、字段变化后的布局。`packed` 只能针对某个实现调整填充，还可能造成未对齐访问，不能一次解决剩余问题。连浮点也要约定格式、字节序、NaN 处理和单位；很多测量项目用固定单位整数更容易跨语言对接。

## 不能只比较2字节和8字节

若把两字节电压放入主线格式 `A5 | LEN | TYPE | SEQ | PAYLOAD | CRC低 | CRC高`，固定开销有 6 字节，那么这一帧同样是 8 字节，与最初的文本行一样长。不同功能的裸字段与完整消息直接比长度，会得出误导性的“二进制省四倍”。

假设每个采样点都要同时上报 32 位毫秒时间戳和 16 位毫伏值，且定义了独立消息类型，二进制负载为 6 字节、整帧 12 字节。文本 `ts=1000,mv=3300\n` 是 16 字节，数字位数变化后还会增长。在 115200、8N1 下每秒发 1000 点，二者分别需要 12000 和至少此例的 16000 字节/秒，都高于 11520 的理论上限。改二进制有帮助，但这组参数仍必须降采样、批量打包或升级链路。

对照还应包含开发和维护成本。人用串口助手敲命令、现场诊断时，文本很方便；连续采样、固定消息和资源紧张时，明确的二进制字段更节省解析与传输预算。JSON、CBOR 等成熟格式还能提供现成的工具生态，但它们不自动提供业务上的确认、重试或设备权限检查。

## 消息完整，不等于可以执行

一个可靠的解析流水线可以分成：确定边界，检查长度，验证校验，解码字段，再检查业务含义。CRC 通过只说明这段内容通过了所选检错规则，不证明来源可信，也不证明 `PWM=60000` 对这台设备合法。远程控制还要考虑认证和访问权限，CRC 不能代替消息认证码。

消息截断、错误长度和噪声都会影响重新同步。二进制帧头可能出现在负载内，不能见到一个 `A5` 就立刻重启；应结合长度、校验和超时策略。文本丢字节后也可能变成另一条语法合法的命令，不能笼统说“能看懂的文本就不需要校验”。

若把普通日志与二进制帧混在一根线上，日志只是额外噪声，不一定永远能被帧头识别可靠区分。正式设备最好分通道，或把日志也封装成一种消息类型；不要让任何模块绕过协议层直接输出任意字节。主线的混合观察适合教学探针，不应被当作无需约束的生产协议设计。

## 为下一版留出规则，不只留一个版本号

第一次发布就写清楚字段大小、单位、合法范围、字节序、CRC 覆盖范围、长度是否包含头尾、最大负载和未知类型如何处理。给新增字段安排显式长度或版本协商，旧接收端才能有界跳过不认识的消息。单纯在结构体尾部加成员却保持旧长度语义不变，会让接收端错误解释后续字节。

序号也不能只是打印好看。对带副作用的命令，ACK 丢失后重发应携带同一事务标识，接收端要定义去重窗口、重启后的行为和序号回绕策略。设置亮度为某个值通常比“亮度再加一”更容易做幂等，但仍不能代替明确的应答语义。

## 练习：两次读取，能否执行两次

接收 API 先返回 `mv=33`，再返回 `00\nmv=1\n`。应得到几条消息、什么数值？如果第一条超过上限，能否在看到前缀 `mv=6` 时先更新电压，再回滚？

<details><summary>展开答案</summary>

按 LF 拼接后是两条，值为 3300 和 1；不能按两次读取边界各调用一次字段解析。接收缓冲必须跨读取保留未完成内容。超范围的完整消息应整体拒绝，不应先执行前缀再回滚，因为执行可能触发硬件动作，回滚未必可逆。先验证完整消息，再把有效字段作为一次动作提交。

</details>

## 适用范围与依据

示例是 C99、八位字节平台上的受限 ASCII 文本与定宽无符号字段，不是通用序列化库。PC GCC Debug/优化版已真实运行范围拒绝、输出保持和全部 65536 个二字节值的往返测试；没有声称已验证串口驱动分包时序。

已核读 [RFC 8259](https://www.rfc-editor.org/rfc/rfc8259) 第 6 节数值限制、第 7 节字符串、第 8.1 节 UTF-8 和第 9 节解析器资源限制，以及 [RFC 8949](https://www.rfc-editor.org/rfc/rfc8949) 第 1.2 节术语与字节序、第 3.1 节 CBOR 主类型。CBOR 本身的多字节编码采用网络字节序，不等于本篇自定义的小端字段；选择标准格式后必须遵守标准，而不是混搭。
