# 动态内存与碎片

程序刚启动时能接收长命令，运行一段时间后却申请不到缓冲区；日志还说“有空闲内存”。先别急着增大堆。假如空闲的两段各有八字节，中间夹着仍在使用的数据，你需要的十二字节连续空间究竟放在哪里？

这里有两件必须分开的事：**谁负责保管和释放对象，以及空闲空间能否满足这一次请求。** 我们先验证第一件，再用一个完全可预测的模型观察第二件。不靠打印地址猜测某个分配器的内部布局。

## 一、先跑一次“失败后旧数据还在”的实验

前置是[数组与指针](/lessons/1-5)中的指针、数组长度和对象寿命。实验使用有标准库的 PC C99 环境，不需要开发板。在仓库根目录编译独立示例；不要定义会关闭断言的 `NDEBUG`：

```sh
gcc -std=c99 -Wall -Wextra -Wpedantic -Werror -O0 examples/notes/c-semantics/dynamic-memory.c -o dynamic-memory
./dynamic-memory
```

Windows 终端也可运行生成的 `dynamic-memory.exe`。程序不读键盘；输入过程已经写入测试：从空缓冲区申请三个整数，填入 `10, 20, 30`，拒绝一次扩容，再真正扩到六个，缩到两个，最后释放。先预测：失败会不会把第三个数弄丢？新增元素会不会自动成为零？

成功运行的固定输出是：

```text
failure: original allocation preserved
growth: kept=30 added=0
release: pointer=NULL count=0
model: free=16 largest=8 request=12 rejected
model: free=24 largest=24 request=12 fits
dynamic-memory: ok
```

第一行的失败是**主动注入**的：测试替身返回空指针而不释放原块，不是把电脑内存吃光。真正申请、扩容、缩容仍调用标准库；若这些步骤真失败，程序报告错误并非零退出，不会伪造上述成功输出。两条 `model` 输出来自占用模型，不是测量系统堆。

## 二、指针变量的寿命，不等于它管理的对象的寿命

普通自动局部指针变量的寿命随所在块结束，但成功申请的对象会一直存在到释放。反过来，指针变量还在，也不表示对象仍有效。可以把指针当成“保管凭证”，不能把凭证的存在当成房间仍归你使用的证明。

标准库的 `malloc` 按字节申请空间，失败返回空指针；新对象的值不确定，必须先初始化再读。`free` 使空间可用于后续分配，不是擦除数据，也不承诺让进程占用立刻下降。`calloc` 保证所有位清零，但不能把这个保证泛化成任意类型的空指针或浮点零表示。

本例把“唯一负责释放的指针”和“元素个数”放在一起维护。下面是示例使用的完整辅助接口，包含所需声明；`resize` 参数在正常路径传 `realloc`，在失败测试中传替身：

```c
#include <stdint.h>
#include <stdlib.h>

typedef void *(*resize_fn)(void *, size_t);

static int resize_ints(int **p, size_t *n,
                       size_t want, resize_fn resize)
{
    int *next;
    size_t i;

    if (want == 0) {
        free(*p);
        *p = NULL;
        *n = 0;
        return 1;
    }
    if (want > SIZE_MAX / sizeof **p) {
        return 0;
    }
    next = resize(*p, want * sizeof **p);
    if (next == NULL) {
        return 0;
    }
    for (i = *n; i < want; ++i) {
        next[i] = 0;
    }
    *p = next;
    *n = want;
    return 1;
}
```

调用约定不是装饰：`p`、`n` 要指向有效且独立的管理变量，初态为“空指针、零个元素”；之后的非空指针必须是本接口管理的分配块首地址，长度必须准确。不能把局部数组、块中间的地址或别的分配体系的对象塞进来。替身也必须遵守非零大小 `realloc` 的失败约定。

沿代码逐步检查：

1. 先处理零长度，把“清空”定义成显式释放，避免依赖零大小分配的实现定义行为。
2. 先做除法比较，再计算元素数乘元素大小。`size_t` 的无符号乘法回绕会把大请求变成小请求；得到非空指针也救不了后续越界。
3. 用临时指针接结果。非零大小的 `realloc` 失败时旧对象保持不变，管理变量也不更新。
4. 成功后保留新旧大小中较小部分的内容；新增长的区域由我们逐个赋零。输出中的 `added=0` 是这段循环的功劳，不是扩容函数自动初始化。

不要写 `p = realloc(p, bytes)` 后才发现失败：若没有其他可靠的所有权记录，旧地址会被空指针覆盖，留下无法释放的对象。这是**内存泄漏**，与碎片不是同一个问题。

## 三、空闲总量够，为什么仍放不下

把三十二个位置分成四块，每块八个位置，最初全部占用。只释放第一、第三块：

```text
位置  0..7      8..15     16..23    24..31
      空闲8     使用中8    空闲8     使用中8
```

现在总空闲量是十六，最大连续空闲段却只有八。对要求连续十二个位置的请求，答案是“放不下”。这就是**外部碎片**：空闲空间散在仍存活的对象之间，无法直接合成所需的一整块。

示例用字节数组记录“占用还是空闲”，逐格统计总空闲和最长连续段。它不返回对象指针，不处理对齐和分配器头部，也不把字符数组强转成任意类型；它只是上述图的可执行算术。

再释放中间第二块，前三块连成二十四，十二的位置便放得下了。这个模型允许把相邻空闲段视为整体，但真实分配器是否合并、何时合并，要查具体实现。C 标准没有规定连续两次申请必须相邻，更没有规定 `free` 之后下次一定拿回原地址。

**内部碎片**又不同：某个固定块池每块八字节，即使只请求五字节也占一整块，其余三字节不能交给别的对象。这是已经分出去的块内部有闲置，而不是外面有两段接不起来。还有分配器管理信息、对齐填充等成本，不能只用用户请求的字节数估算全部开销。

## 四、先定所有权，再选分配策略

对会跨函数使用的缓冲区，先在接口中写清：谁创建，谁拥有，谁只借用，在哪条成功或失败路径释放。函数返回一个动态对象可以成立；返回普通局部数组的地址不可以，二者不能只凭“都返回指针”类比。

至少守住下面三条边界：

- **释放一次，不是每个别名都释放一次。** `free(NULL)` 合法；重复释放同一对象、释放块内偏移地址属于未定义行为。把拥有者设为空指针不会自动清空其他借用者。
- **扩容成功后旧借用指针也必须作废。** 即使数值地址看起来没变，旧对象的寿命已经结束。不要用旧指针比较地址、继续解引用或释放；需要定位元素时，保存有效下标，并用新的首地址重新取得指针。
- **没有碎片，不等于不会失败或必定实时。** 容量耗尽、大小计算错误、管理开销都可能阻止申请；C 标准也不保证分配操作的最坏执行时间或中断可重入性。

小型 MCU 程序常能预先确定最大命令长度，此时固定数组最容易核对；对象数量有上限而寿命交错时，可考虑固定块池；一批对象一起生灭时，可考虑整批复位的区域分配。它们是不同的容量与生命周期设计，不是“动态内存永远不能用”。固定块池也会耗尽，也要定义失败动作。

若迁移到 STM32F407，必须另查所用 C 库如何取得可分配区域、链接配置的容量以及并发保护方式。PC 上通过并不证明板上容量足够，更不证明能在中断里调用。这里没有上板测试，也没有真实分配器的延迟、碎片率或长期压力数据。

## 自己算一次，再审一次接口

一块空间从低到高是“空闲八、占用四、空闲十二、占用八”。申请十六能否成功？如果释放占用四那块，在本篇的合并模型中会怎样？另有 `q = p + 1` 借用第二个元素，成功扩容后能否继续用 `q`？

初态总空闲二十，最大连续段十二，十六放不下。释放中间四后，前面三段连成二十四，模型中可以满足请求；这不是要求所有真实分配器都实现相同合并算法。

扩容成功后不再使用旧 `q`。如果新长度至少为二，用新的 `p + 1` 重新取得位置。扩容失败且请求大小非零时，旧对象和原有借用关系才仍有效。测试替身正是为了验证这个失败分支，而不让偶然可用的内存量决定答案。
