# SWD 口的安全与断点数量限制

前六个断点都能停，第七个却提示“无法插入硬件断点”。换到另一套工具后，第七个又似乎能用了。与此同时，有人问：既然 SWD 能读 RAM、改寄存器，产品外壳里的这几个焊盘是不是也能读走秘密？

这两个问题都来自同一件事：调试口是硬件能力的入口，不是无限、无权限的源码观察窗。先从一个明确限定的实验认识资源，再讨论何时应把这些能力交给维护人员。

## 七个函数，不等于七个无限免费的位置

配套板级探针包含 `bp1` 到 `bp7` 七个函数，每个都对 `volatile uint32_t breakpoint_visits` 加一个不同的小常量，再由 `breakpoint_round` 依次调用。GCC 的 `noinline` 和 `aligned(4)` 用于让实验中的入口彼此分离；使用 `-O0 -g`，不把优化合并后的地址数量误当成硬件容量。

探针核心如下，完整源文件位于本仓库的 debug 示例目录。它不带 `main`，需要由自己的板级工程调用；这里没有初始化外设或修改保护配置。

```c
#include <stdint.h>

volatile uint32_t breakpoint_visits;
#define POINT(n) \
    __attribute__((noinline, aligned(4))) void bp##n(void) \
    { breakpoint_visits += n; }

POINT(1)
POINT(2)
POINT(3)
POINT(4)
POINT(5)
POINT(6)
POINT(7)

void breakpoint_round(void)
{
    bp1(); bp2(); bp3(); bp4(); bp5(); bp6(); bp7();
}
```

在自己的普通 Flash 应用中集成探针，在主循环调用 `breakpoint_round()`。把函数放入工程源码列表，重新生成对应 ELF。这里是实验步骤，不是要求改课程工程或量产程序：

1. 删除已有用户断点，确认 IDE 的“运行到 main”临时断点已经移除。
2. 在 GDB 控制台依次请求硬件断点：

```text
hbreak bp1
hbreak bp2
hbreak bp3
hbreak bp4
hbreak bp5
hbreak bp6
hbreak bp7
info breakpoints
```

3. 必要时继续运行，让后端真正插入断点；有的后端到运行前才报资源不足。
4. 删除一个已启用断点，再尝试启用第七个，比较结果。

输入条件很重要：七个函数确实位于不同的 Flash 指令位置，要求的是**同时有效的硬件指令断点**，后端没有用软件补丁或其他机制替代。预期纯 FPB 资源不足以容纳第七个；资源还被内部功能占用时，甚至不到第七个就可能失败。UI 中七个红点都亮着，不自动证明七个硬件比较器已经存在。

本篇已经用 ARM GCC 把探针编译为 Cortex-M4 目标文件，并检查七个独立符号；没有上板执行断点插入实验。

## F407 里具体有什么

RM0090 对该实现列出：

| 模块 | 实现资源 | 本篇对应的用途 |
|---|---|---|
| FPB | 6 个指令比较器 | 在支持的代码地址匹配取指，触发硬件断点或重映射 |
| FPB | 2 个字面量比较器 | 针对代码空间字面量加载的补丁用途 |
| DWT | 4 个比较器 | 数据观察点或其他跟踪/触发用途 |

那两个字面量比较器不是“额外两个通用源码断点”，DWT 的四个也不是自动附赠四个 Flash 指令断点。一个模块有比较器，不意味着调试器会把所有硬件功能都暴露给你；单步、临时断点、跟踪或复杂观察条件还可能消费资源。

**断点**通常关心“执行到这个地址”；**数据观察点**关心“某处数据被读或写”。例如怀疑全局变量被意外改写，使用写观察点比在每个函数里下断点更直接。但是观察范围、对齐、读写类型受实现和后端支持限制，观察一个很大的结构体可能拆成多个资源，也可能直接不支持。

断点所在地址也有限制。F407 的 FPB 不是任意 32 位地址的通用比较器；别把可在内部 Flash 用的配置原封不动推广到所有 RAM 或外部映射区。其他 Cortex-M 或其他 STM32 的比较器数量也应重新查文档或实现寄存器，而不是记住“ARM 都是六个”。

## 为什么另一套工具能放更多断点

软件断点会修改目标指令，把某处替换成断点指令，执行到那里再恢复原指令或单步越过。在可写 RAM 中这比较容易；Flash 不是普通 RAM，修改涉及编程规则、擦写粒度和工具算法。某些工具提供 Flash 软件断点或补丁机制，所以界面上可用数量未必等于 FPB 数量。

但软件方案有代价：可能涉及 Flash 写入、执行与校验内容的变化、额外工具依赖和恢复步骤。调试器断开后若补丁没正确恢复，脱机行为可能变化。只想测硬件资源时，必须显式请求硬件断点，并记录后端实际采用的实现。

条件断点也不是零成本过滤器。后端可能先停住处理器，再在主机计算条件；即使最终没有让 UI 停下来，时序也已受影响。不能用它测量严格实时通信边界。

## 能调试的权限，到量产时要重新设计

开发时，开放 SWD 方便读内存、改 PC、装载代码。产品交付后，这些能力可能意味着提取固件、读取运行中的凭据或绕过应用逻辑。拆掉排针只增加接触难度，不等于实现身份认证；焊盘、走线和测试点仍可能存在。

F407 的读保护 RDP 有三个等级。下面是理解与评审用信息，**不是让你跟着烧写的实验表**：

- Level 0：RDP 字节为 `0xAA`，没有 RDP 读保护；其他保护仍需独立检查。
- Level 1：非 `0xAA`、非 `0xCC` 的值；在调试连接或从 RAM/系统存储器启动等条件下，对主 Flash 和备份 SRAM 的访问受限制；正常从用户 Flash 启动的用户程序仍有相应访问能力。
- Level 2：`0xCC`，更强的芯片/调试保护，相关调试和替代启动途径被关闭，选项字节不可再修改；**不可逆**。

Level 1 退回 Level 0 会触发主 Flash 和备份 SRAM 的整体擦除，不是“先关保护，再无损导出”。Level 2 也不存在普通调试器上的撤销按钮。课程不提供 Level 2 写入命令；不要在唯一开发板上试验不可逆配置。

RDP 不等于所有安全需求已经完成。固件更新认证、启动可信性、外部存储、串口维护命令、运行时漏洞和日志泄露仍需单独设计。读保护不是对每一类物理攻击的绝对保证，更不是给产品密钥管理省略评审的理由。

## 给量产留一道受控维护门

把开发、工厂、售后和最终用户状态区分开：谁可以用探头、什么时候接入、如何授权、哪些数据允许丢弃、如何确认恢复到正式配置。工厂测试可保留临时调试能力，但最终配置必须有可追溯的核验，不能依靠操作员记得点某个框。

如果售后需要故障证据，可以优先设计有限字段的诊断接口，而不是默认导出所有 SRAM。若故障记录包含构建标识和错误状态，很多问题不必把秘密与用户数据一起交出去。

在调试资源上也保留一份朴素清单：当前启用哪些断点、哪些是临时断点、哪个观察点占用 DWT、是否开启跟踪。资源不足时先删不需要的位置，而不是立刻改编译器或怀疑 MCU 坏了。

### 练习：第七个不行，就改 RDP？

F407 能稳定调试，前六个独立 Flash 硬件断点正常，第七个失败。有人建议降低读保护等级解决。另一个人建议用两个字面量比较器补上。两种建议为什么不成立？

<details><summary>答案</summary>

该现象首先符合 FPB 指令比较器数量限制，降低 RDP 不会增加比较器，而且保护变化可能擦除数据。两个字面量比较器不是通用指令断点资源。先检查后端真实断点类型和内部占用，移除不必要断点，必要时使用经过评估的软件断点或调整调试方法，而不是修改安全配置。

</details>

## 适用范围与依据

资源数字与 RDP 语义针对 STM32F407/RM0090，不能直接迁移到所有 STM32。ARM 编译仅验证探针代码与独立函数生成；没有验证探头行为，更没有写入任何保护配置。
