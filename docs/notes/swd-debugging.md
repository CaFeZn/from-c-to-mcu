# SWD 调试原理

同一块板子，串口还能不断输出，调试器却提示“无法连接目标”。另一回，下载成功、单步也能停住，变量窗口却全是问号。这两个故障看起来都叫“调试坏了”，实际上发生在不同位置。

先沿 [3.2 调试与排错](/lessons/3-2) 的工程走一遍：确认板子能独立运行，接上探头，读一个不会影响外设的变量，再暂停和继续。你会发现 **SWD 搬运的是调试事务，源码名字来自另一份信息**。

## 第一轮：先检查五根线各管什么

STM32F407 用 PA13 作 SWDIO、PA14 作 SWCLK。两根是信号线，不意味着只接两根就能可靠工作。按板子和探头的引脚说明逐项核对，不能套用另一款排针的物理针号。

| 信号 | 本轮需要确认的事 |
|---|---|
| GND | 探头与目标有共同参考地 |
| SWDIO | 双向数据接 PA13，没有接反或被外设强驱动 |
| SWCLK | 探头输出的时钟接 PA14 |
| VTref | 若探头要求，接目标 I/O 电源作为电平参考 |
| NRST | 接目标复位，便于硬件复位和 under-reset 连接 |

VTref 通常是输入参考，不是“给板子供电的 3.3 V 输出”。有的探头另有供电输出，有的低成本模块把端子叫法混在一起，必须查本机说明。目标已独立供电时，不要把两个未经确认的电源输出直接并联；电压不确定时先停下。SWD 接口也不天然具有电气隔离，连接带危险电位的系统需要相应隔离与安全条件。

本轮输入是“同一块已供电 F407、短线、已核对的探头引脚”。预期探头能报告有效目标参考电压，随后识别调试接口和设备。若连参考电压都没有，先查供电与接线，不要改 ELF 路径。若电压正确而识别超时，再查信号、线长、接口选择和连接时序。降低到探头支持的较低 SWD 频率是有用的对照实验，但不能代替修复接地或电平问题。

## 第二轮：读一个由你拥有的普通变量

在自己的实验工程全局区加入下列板级片段，在已经有 1 ms HAL 时基的主循环中调用一次自增。不要把它混入中断与多任务并发写入中。

```c
#include <stdint.h>

volatile uint32_t debug_counter;

/* 放在已有主循环内；HAL_Init 和时钟初始化已完成。 */
/* debug_counter++;
   HAL_Delay(100); */
```

注释中的两行是集成位置提示，不是一个独立可运行程序。`volatile` 的目的，是让这个观察用对象的访问保留在生成代码中，不是给计数器提供并发原子性。

把变量加入观察窗，做三个动作并记录结果：

1. **运行约一秒后暂停**：计数器应比开始大约多 10；实际受启动时点和循环耗时影响，不要求精确等于 10。
2. **暂停后再读两次**：只由主循环修改的变量不再变化；此时 CPU 不在执行自增。
3. **继续后再次暂停**：值继续增长。若工具支持运行中读内存，也可开启这一项对照，但不要假设每个 IDE 都默认允许。

该实验预测的是模型行为，本文未连接实板执行。若读回数值不变，先确认下载的是本次构建、变量地址对应当前 ELF、程序是否真的经过自增，再怀疑总线访问。

## 两根线怎样走到变量的地址

可把一次变量读取拆成这条路径：

```text
IDE / GDB
→ 探头对应的调试服务器
→ USB 探头
→ SWDIO + SWCLK
→ SW-DP
→ AHB-AP
→ 目标存储器
```

SW-DP 是串行线调试端口，负责接收请求、返回应答和数据；访问端口 AHB-AP 把调试操作转换成系统总线访问。它能在一定条件下独立于处理器运行状态访问系统，所以“CPU 停了”不等于“调试器完全无法读 RAM”。反过来，目标掉电、受保护、总线不可用或内存区域不可达，也不是探头可以凭两根线解决的。

“debug_counter 在哪个地址、有多宽”来自 ELF 的符号和调试信息。SWD 上不会传输 C 变量名来让 MCU 搜索。没有源码符号时，仍可能按地址读内存、查看寄存器或运行机器码；但编辑器不知道怎样把它们可靠地对应回源码。

暂停、继续、单步则通过内核调试设施实现。硬件指令断点由 FPB 等资源支持；数据观察点使用 DWT。暂停时处理器保存的是执行状态，不是给整块板子按了时间暂停键。DMA、定时器、外部设备和看门狗是否继续工作，各有条件和配置。

## 下载不是“把字节直接写给 Flash 就行”

下载固件时，工具需要识别器件、处理访问权限，再按该芯片的 Flash 控制器协议擦除、编程和校验。常见实现会把一小段 Flash 算法装入目标 RAM，让目标执行；不同工具与存储介质的实现也可能不同。

这解释了为什么“能读设备 ID”不保证“能擦写 Flash”：前者只验证访问链的一部分，后者还需要写保护状态、算法、RAM、时钟或电源条件正确。“校验通过”同样只说明指定范围字节与预期一致，不保证复位入口、向量表、外设时钟和板级接线都正确。

遇到下载失败，保留工具完整错误信息和实际命令：失败在连接、擦除、编程还是校验？不要把几次不同阶段的错误都归为“驱动问题”。

## 观察可能会改变被观察对象

普通 RAM 计数器适合入门，外设寄存器并不总适合自动刷新。UART 数据寄存器、FIFO、读清标志等入口，读一次可能取走数据或参与清标志序列。调试器经 AHB-AP 发出的读取，同样可能产生这些硬件副作用。读寄存器前要看手册的访问规则，而不是因为界面叫“观察”就以为无害。

另一个边界是多字段一致性。CPU 正在更新一个结构体，调试器分多次读取，可能拼出新旧混杂的画面。这不一定是 C 程序真的产生了那一组状态。要验证不变量，先暂停所有相关写入者，或让固件在明确边界生成快照；单纯加大刷新频率不能制造原子快照。

还有两个常见误区：

- **SWD 不是 SWO。** SWDIO 是双向调试数据，SWO 是独立的跟踪输出信号；F407 的 PB3 可用于 TRACESWO，缺这根线不会妨碍基本 SWD 下载，但会影响相应的追踪输出。
- **连接探头不等于系统行为不变。** 暂停、断点、调试冻结配置和内存读取都会改变时序。排查通信超时时应同时保留脱离调试器的运行对照。

### 练习：能读地址，却看不到名字

工具能读取目标 RAM、暂停内核，机器码也正常运行，但编辑器里 `debug_counter` 显示找不到符号。此时优先换 SWD 线还是检查构建产物？应核对哪三件事？

<details><summary>答案</summary>

先查构建产物。已经能稳定读内存并暂停，说明基本调试链可用。核对当前调试会话载入的 ELF 是否对应实际下载版本；编译是否带所需调试信息；源文件与符号路径能否匹配，以及变量是否被优化或根本没链接进来。仍需保留通信稳定性的证据，但“名字不存在”主要不是 SWD 接线问题。

</details>

## 适用范围与依据

路径模型以 F407 的 SW-DP/AHB-AP 为具体例子，接线必须服从自己的板图和探头说明。本文验证了官方资料，未进行探头连接、下载或运行中内存读取实测。
