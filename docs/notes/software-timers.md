# 软件定时器与简易调度器

一盏灯每 500 ms 翻转，一次按键扫描每 10 ms 执行，日志每秒打印。三个任务各加一个 `HAL_Delay`，按键马上变得迟钝；全改成“到点就做”以后，平常看起来正常，偶尔一段耗时日志却让灯连续闪了几下。这次不是定时器算错，而是程序没有回答：**错过的那些周期，到底要不要补？**

本篇接着 [5.2 定时器与节拍](/lessons/5-2)，把主线的 `soft_due` 扩展为有明确迟到策略的协作式调度。先用人工输入的时间戳演算，最后再接 `g_ms` 或 `HAL_GetTick()`，不需要拿板子等 49 天。

## 先让任务故意迟到

设任务周期 100 ms，启动时把基准 `phase` 设为 0。主循环上次检查后被其他工作占住，直到 350 ms 才重新调度。先预测下面三种处理会发生什么。

| 策略 | 350 ms 这次做什么 | 后续名义到期点 |
|---|---|---|
| 从实际执行时刻重新起算 | 做一次，基准改为 350 | 450 ms |
| 保持相位，逐次补做 | 补 100、200、300 三次 | 400 ms |
| 保持相位，只做最新一次 | 做一次，记录跳过两次 | 400 ms |

它们没有哪一种永远正确。界面刷新通常只需要最新状态；定量累计可以一次处理“过去了三个周期”；过去没采到的传感器数据，不能用现在连续采三次冒充。电机控制若已经错过时限，应进入设计好的故障策略，而不是无限补算。

主线的 `*last += period` 保持的是时间格子，不是让执行自动发生在格子上。若一次只加一个周期，主循环下一轮仍会认为任务到期，积欠会变成连续调用。这里选第三种策略，让一次轮询最多调用一次任务。

## 一个可直接验证的核心

下面是完整的 C99 小程序；只处理调用者传入的时间，和 HAL 无关。约定 `period` 为 1 到 `INT32_MAX`，且真实的“现在减基准”始终小于一个 32 位毫秒计数周期。参数错误不是正常业务分支，开发时用断言发现。

```c
#include <assert.h>
#include <stdint.h>
#include <stdio.h>

static uint32_t take_due(uint32_t now, uint32_t *phase,
                         uint32_t period)
{
    assert(period > 0u && period <= INT32_MAX);
    uint32_t elapsed = (uint32_t)(now - *phase);
    uint32_t n = elapsed / period;
    if (n != 0u) {
        *phase += elapsed - elapsed % period;
    }
    return n;
}

int main(void)
{
    uint32_t phase = 0u;
    assert(take_due(99u, &phase, 100u) == 0u);
    assert(take_due(350u, &phase, 100u) == 3u);
    assert(phase == 300u);
    assert(take_due(399u, &phase, 100u) == 0u);
    assert(take_due(400u, &phase, 100u) == 1u);

    phase = UINT32_MAX - 15u;
    assert(take_due(4u, &phase, 10u) == 2u);
    assert(phase == 4u);
    puts("scheduler: late=3, phase=300; wrap=2");
    return 0;
}
```

350 除以 100 得到三个完整周期，余数 50。基准前进 300，而不是改成 350，因而保留了原来的节奏。回绕例从 `0xfffffff0` 到 4，实际经过 20 ms，无符号差也是 20，不是一个巨大的负数。代码没有把超出范围的无符号值强转成有符号值。

把函数接到板上时，每轮先取一次 `now`。每个任务各有一份 `phase` 和非零周期；启动时全部初始化为当前时刻。遍历任务表，若返回 `n > 0`，只调用一次回调，把 `n - 1` 加到漏期统计。回调应是“推进一步后立刻返回”的状态机，不可以在里面等待串口发完、等按键松开或睡 500 ms。任务表和基准只由主循环拥有，中断只提供节拍或事件。

## 时间戳回绕不是无限时间机器

对于本目标的 `uint32_t`，减法按模 2³² 计算。设真实间隔为 `d`，只要 `0 <= d < 2^32`，无符号差就是 `d`。可要是主循环停了整整 2³² ms 再回来，两个时间戳可能完全一样，程序无法知道中间丢了一整圈。49.7 天是可表示的圈长，不是任何定时写法都能无条件运行的保证。

“比较两个任意时间点谁先谁后”通常另用半圈约束；本篇是“已知基准后流逝了多久”，不要把二者混成同一条规则。工程上限制周期不超过半圈，并保证最长停顿、任务暂停和相位滞后之和远低于一圈，会更容易审计。若需要几个月的截止日期，用更宽时间源或 RTC 日历，而不是强行解释一个 32 位差。

还要区分 C 算术和 MCU 并发：`volatile` 不会把任意共享结构变成原子的。F407 上对齐的 32 位节拍读取可由合适的单次字访问完成；这不是通用 C 多线程的同步保证。如果中断维护 64 位计数，主循环直接读取两半可能得到拼接时间，要用保存并恢复中断屏蔽状态的临界区或其他经过证明的快照方案。

## 从三个 if 到简易调度器

调度器的骨架其实仍是主线那几个 `if`：取时间、遍历表、判断到期、调用回调。使用函数指针只是把重复代码收在一起，不会产生并行线程。一个 20 ms 的回调仍能阻止后面那个 1 ms 任务运行。

验证时至少记录三项：每个任务的最长执行时间、最坏调度迟到量、累计漏期数。所有任务平均 CPU 利用率小于 100% 只是必要的容量检查，不是及时性的充分证明；同一轮很多任务同时到期、长临界区和高优先级中断都可能形成尖峰。可以用 GPIO 包围一次任务让逻辑分析仪量执行窗口，但量到的是包含抢占影响的墙上时间，要说明测量口径。

若回调会改变任务表，先明确修改什么时候生效。例如把增删请求排队，在这一轮遍历结束后统一处理；不要一边遍历一边释放当前对象。低功耗也不是随手在循环末尾调用一次休眠：要处理“刚判断没事，中断就送来事”的竞争，并确认所选节拍在该低功耗模式中继续走。

## 这些写法特别容易出错

- `now >= phase + period` 跨回绕可能提前到期；比较流逝差值，而不是两个裸大小。
- 周期为 0 会破坏含义，本例还会导致除零；输入必须在创建任务时验证。
- 用无限 `while (due)` 补做可能永远追不上，饿死其他任务；补做型设计必须给每轮预算和积欠上限。
- `HAL_SuspendTick`、长时间关中断或停钟后，“软件过了多少拍”未必等于真实经过时间。需要跨深睡眠计时就另设计 RTC 补偿。

## 适用范围与依据
