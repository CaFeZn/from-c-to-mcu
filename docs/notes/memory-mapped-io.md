## 同一个数，写到不同地方

把数值 `0x00000020` 写到一块已经分配给变量的 SRAM，那里就保存了这个数。可是在 F407 上，把同一个数写到 `0x40020018`，它会成为对 GPIOA 的一次置位请求。

差别不在于数值突然有了特殊能力，而在于：**这个地址选中了什么硬件，以及那块硬件把写入解释成什么动作。**

> [!warning] 地址属于目标芯片，不属于你的电脑进程
> 本篇裸地址只用于解释 STM32F407，不要把它们放进 PC 的 C 练习程序里执行。网页中的变化是教学模型，不会访问真实芯片。上板实验应沿用 [[2.2_开发环境与第一次点灯]] 的已确认接线与初始化，不要随意改变不知用途的引脚。

图中只展开 F407 的少量映射，不按容量比例绘制。完整地址空间还有别名、CCM、其他外设、系统控制区域和未使用的空洞。32 位地址能表达 4 GiB 地址空间，**不代表芯片安装了 4 GiB 物理内存**。

CPU 发出读写请求时，芯片的**地址译码**电路选择相应模块。让外设的控制和状态入口也占据这张地址表，叫**内存映射 I/O**，常简写为 MMIO。

“内存映射”说的是访问方式，不是把外设变成一段普通 RAM。总线把请求送到 GPIO 后，接手的是 GPIO 的寄存器与逻辑电路。有关这些接口怎样连接，可回看 [[【原理】单片机内部结构|单片机内部结构]]。

## 二、基址加偏移，找到一个具体入口

先只看 GPIOA。F407 给这组寄存器安排的基址是 `0x40020000`，组内每个成员再有自己的偏移。

| 名称 | 偏移 | 实际地址 | 本篇关心的作用 |
|---|---|---|---|
| GPIOA_MODER | `0x00` | `0x40020000` | 每个引脚用两位选择模式 |
| GPIOA_OTYPER | `0x04` | `0x40020004` | 输出类型，如推挽、开漏 |
| GPIOA_OSPEEDR | `0x08` | `0x40020008` | 输出速度等级，不是 LED 的闪烁频率 |
| GPIOA_PUPDR | `0x0C` | `0x4002000C` | 上拉、下拉等配置 |
| GPIOA_IDR | `0x10` | `0x40020010` | 读取引脚输入采样 |
| GPIOA_ODR | `0x14` | `0x40020014` | 输出数据锁存 |
| GPIOA_BSRR | `0x18` | `0x40020018` | 发出输出位置位、复位请求 |

因此，`0x40020000 + 0x18 = 0x40020018`。这里的偏移单位是**字节**，`0x18` 是十进制 24，不是“第 18 号寄存器”。

同样的办法也能定位时钟使能：

| 项目 | F407 中的值 |
|---|---|
| RCC 基址 | `0x40023800` |
| AHB1ENR 的偏移 | `0x30` |
| RCC_AHB1ENR 的地址 | `0x40023830` |
| 其中 GPIOAEN 的位号 | bit 0 |

**地址选寄存器，位或位域再选其中的功能。** 例如 PA5 的 MODER 字段占 bit 11:10，而不是“第 5 位”；PA5 的 ODR 状态才对应 ODR5 这一位。一个字段可能占多位，不能把每个寄存器都理解成 32 个互不关联的单独开关。

## 三、指针没有魔法，结构体也没有创建一份 GPIO

你会在 STM32 的设备头文件中看到类似这样的定义：

```c
#define GPIOA_BASE  0x40020000UL
#define GPIOA       ((GPIO_TypeDef *) GPIOA_BASE)
```

上面是为解释概念而展开的等价值；正式工程使用设备头文件的原定义，不要重复定义这些宏。

`GPIO_TypeDef` 按手册顺序描述 GPIO 寄存器布局：MODER、OTYPER、OSPEEDR、PUPDR、IDR、ODR、BSRR 等。编译器知道每个成员的类型、大小和偏移，所以：

```c
GPIOA->BSRR = 0x00000020u;
```

可以理解为：在 GPIOA 基址上加上 BSRR 的成员偏移，向得到的目标发起一次写入。在本目标、这次访问的意义上，它对应：

```c
*(volatile uint32_t *)0x40020018u = 0x00000020u;
```

类型转换没有申请新的 RAM，没有初始化一个软件 GPIO 对象，也不是通过字符串查找硬件。**地址定位硬件，类型告诉编译器怎样访问该地址。**

不要自己随意修改外设结构体的字段顺序、成员宽度或填充。少一个字段、偏移错四个字节，就可能把本来要写 BSRR 的数交给另一个入口。实际工程优先使用对应芯片的 CMSIS 设备头文件。

### 两种结构体，不是同一件东西

| 名称 | 通常在哪里 | 用来做什么 |
|---|---|---|
| `GPIO_InitTypeDef` | 普通程序数据，例如栈或 SRAM | 把引脚、模式、上下拉等配置交给 HAL |
| `GPIO_TypeDef` | 作为外设寄存器布局的类型描述 | 使 GPIOA 等指针的成员访问对应硬件地址 |

给 `GPIO_InitStruct.Mode` 赋值，首先只是修改你的配置数据。调用 HAL 初始化函数后，驱动才根据这些数据写入相应硬件寄存器。

### 不是每次都把数原样存下来

BSRR 的 32 位分成两个命令半区：

| 写入的位置 | 写 1 表示什么 | 写 0 表示什么 |
|---|---|---|
| bit 0..15，即 BS0..BS15 | 把对应 ODR 位设置为 1 | 不改变该位 |
| bit 16..31，即 BR0..BR15 | 把对应 ODR 位复位为 0 | 不改变该位 |

例如，对 PA5：

```c
GPIOA->BSRR = 1u << 5;         /* 请求 ODR5 = 1 */
GPIOA->BSRR = 1u << (5 + 16);  /* 请求 ODR5 = 0 */
```

第一行的数据是 `0x00000020`，第二行是 `0x00200000`。两次写的是同一个地址，但命令位置不同。

若原来的 ODR5 为 0，推演第一行：

1. CPU 发起写请求：地址 `0x40020018`，数据 `0x00000020`。
2. 地址译码选中 GPIOA 的 BSRR 入口。
3. GPIO 逻辑识别低 16 位中的 BS5 请求。
4. ODR5 锁存位被置为 1，未被请求的其他位保持。
5. 在本例已确认的推挽输出等条件下，输出驱动按照锁存值改变引脚逻辑。

**不是 BSRR 变成了一个永远保存 `0x20` 的普通变量，再由软件慢慢检查它。** 它是命令入口。其命令位读回为 0，不能用读 BSRR 的办法获取当前输出状态。

### ODR 与 IDR 也要分开

- **ODR** 表示输出锁存：硬件被要求输出什么。
- **IDR** 表示引脚输入采样：输入电路实际采到什么。
- 两者不保证在所有模式和外部条件下都相等。例如开漏输出释放线路后，其他器件仍可能把线拉低。

本动画不模拟负载、电流、开漏上拉和所有引脚模式，也不测量实际电压。它展示的是所选条件下的逻辑关系，不能代替真实接线检查。

> [!question] 再猜一次
> 向 BSRR 写入 0，是不是把所有输出都清零？

> [!success]- 揭晓
> 不是。两个命令半区里的 0 都表示“不操作”。要清某个位，应向对应 BR 位写 1。

> [!info]- 同一位同时置位、复位怎么办
> F407 的 RM0090 明确规定：同一位的 BSx、BRx 同时写 1 时，BSx 优先，即置位优先。例如 `0x00200020` 对 PA5 的结果是置 1。
> 这是应纳入模型测试的边界规则，不是鼓励日常代码发出含糊的双重请求。不同寄存器的冲突规则仍需查各自手册。

## 五、为什么不能给所有寄存器套用同一种写法

普通 RAM 变量通常可以直接保存新数值。硬件寄存器则可能是读写配置、只读状态、写命令，或者具有写 1 清除、读后变化等副作用。

因此，在手册里要看三件事：**访问类型、各位含义、读写的副作用**。还要保留手册要求保留的位。

### 配置一个位域，要保留无关配置

以 PA5 的 MODER 两位为例，字段起始位置是 `2 * 5 = 10`：

```c
uint32_t shift = 2u * 5u;
GPIOA->MODER = (GPIOA->MODER & ~(3u << shift))
             | (1u << shift);
```

这是“先清这个两位字段，再写入输出模式 01”的读改写。它只解释位域操作，**不是完整 GPIO 初始化流程**；实际工程应优先按已有 HAL/CubeMX 配置完成时钟、初始输出值、输出类型、速度等级和上下拉等设置。

也不能直接把整个 MODER 写成只含 PA5 的值：其他引脚可能承担调试或通信功能。F407 的 GPIOA、GPIOB 的 MODER 复位值也并非全零，不要把空白示意图当成真实复位状态。

### BSRR 则直接写本次命令

对 BSRR，使用 `GPIOA->BSRR = mask` 表达本次请求，不需要先读取它再做 `|=`。读取命令入口并不能拿到你想保护的当前 ODR 状态。

直接对 ODR 做 `|=` 是读出、计算、写回的过程。如果中间另一个执行上下文改变了 ODR，旧快照写回可能覆盖对方的改动。BSRR 用一次总线写对指定输出位操作，避免这个特定的读改写窗口；它不保证由多次写组成的整个程序片段都原子。更多并发问题可继续到 [[5.4_中断与主循环共享数据]]。

## 六、volatile 管的是访问，不是全部硬件条件

CMSIS 头文件里的 `__IO` 展开涉及 volatile。对于这类硬件对象，编译器不能简单把相关访问当作普通变量的可省略读写；例如，外设状态可能在没有普通 C 赋值的情况下改变。

但 volatile 不会替你：

- 打开 GPIO 时钟、设置输出模式或连接实际电路。
- 让一个错误或未实现的地址自动变得有效。
- 把 `reg |= mask` 的读改写变成不可分割的操作。
- 提供所有需要的内存顺序、屏障或外设等待时间。

所以，“加了 volatile 仍然没反应”不矛盾。地址、位定义、访问方式和硬件条件仍然要逐项确认。

## 七、回到调试器：到底该看什么

当 GPIO 没有按预期工作，先在初始化完成的位置暂停，沿这条链检查：

1. **RCC_AHB1ENR.GPIOAEN**：GPIOA 时钟是否已使能并生效？ST 的 HAL 使能宏在置位后还回读 RCC，用于覆盖使能生效延迟。
2. **GPIOA_MODER**：PA5 的两位字段是否为本例需要的输出模式？输出类型、上下拉等是否对应实际电路？
3. **GPIOA_ODR**：输出锁存位是否按预期变化？有无后续代码又改回去？
4. **GPIOA_IDR 与实际引脚**：采样和物理电平如何？它们是否符合当前模式、负载和接线？

外设面板里的名称与位解释通常来自 SVD，值则来自目标设备访问或调试工具显示的缓存。SVD 是帮助阅读的描述，不是芯片控制硬件时必需的软件。

还要留意某些寄存器读取具有副作用，外设也可能在 CPU 暂停时继续运行。调试器刷新并非对所有外设都完全没有影响，单个截图也不等于完整时序记录。具体使用见 [[3.2_调试与排错]]，排查顺序见 [[8.1_故障排查]]。

## 自己推演一次

> [!question] 四个检查点
> 1. 已知 GPIOA 基址，怎样算出 ODR 和 BSRR 的地址？
> 2. 原来 ODR0、ODR5 都为 1，向 BSRR 写 `0x00200000` 后分别是什么？
> 3. 为什么 MODER 配 PA5 时要处理两位，而 BSRR 对 PA5 置位只写一个命令位？
> 4. `GPIOA->BSRR` 与 `GPIO_InitStruct.Mode` 都用了结构体语法，为什么一个写硬件、另一个通常只是改配置数据？

> [!success]- 对照答案
> 1. 分别加 `0x14`、`0x18`，得到 `0x40020014`、`0x40020018`。
> 2. BR5 请求只清 ODR5；ODR0 仍为 1，ODR5 变成 0。
> 3. 两种寄存器定义了不同的字段和写入语义，不能由“都是32位”推断用法相同。
> 4. 前者的基址与成员偏移定位到外设入口；后者通常定位到普通 RAM 中的配置对象。语法相似不代表地址背后的目标相同。
