# 序号锁与双缓冲

中断刚把时间从“7 秒 999 毫秒”推进到“8 秒 0 毫秒”，主循环却显示“7 秒 0 毫秒”。每个 32 位字段都读对了，却拼出了从未发布过的一份快照。

[5.4 共享数据](/lessons/5-4)已经给出短临界区。若数据较大，或不希望每次读取都关中断，可以换个问题：不是保证读取期间没人写，而是**读完后判断这份副本是否来自同一版**。另一个方向则是给读写双方各自的空间，避免他们同时接触正在处理的那一份。

## 先在纸上制造半新半旧

初始 `(sec, ms)=(7,999)`。读者先读 sec=7；写者完整更新为 (8,0)；读者再读 ms=0，于是得到 (7,0)。两个字段单次访问都没有被撕裂，组合仍然错误。这也是“所有字段都 volatile”不足以保证一致快照的原因。

给数据附加一个无符号序号，约定偶数表示稳定，奇数表示写入中。写者开始前加一，完成后再加一；读者在复制前后各读取一次序号。

| 动作 | seq | 数据 |
|---|---|---|
| 已发布旧版 | 10 | (7,999) |
| 读者保存起始序号 | 10 | 先读到 sec=7 |
| 写者开始 | 11 | 正在更新 |
| 写者完成 | 12 | (8,0) |
| 读者读 ms 并复查 | 12 | 发现 10 不等于 12，丢弃副本 |
| 重新完整读取 | 12 到 12 | 接受 (8,0) |

接受条件是“起始序号为偶数，并且结束序号与起始相同”。仅仅看到两个序号相同不够：同为奇数意味着复制发生在写入中。

这种原始计数机制更精确地叫 sequence counter。完整的 seqlock 往往还含有写者互斥机制；以下只有单写者，不要从标题里的“锁”推断两个写者可以同时进入。

## 一次尝试，不在高优先级里死等

这是 STM32F407、GCC/CMSIS 下的受限板级版本。唯一写者是一个 ISR，读者只在主循环；没有 DMA 写入，没有更高优先级读者抢占写者，没有第二个写者。共享对象自然对齐地放在普通 SRAM，全部初始化完成后才开放中断。


```c
#include "stm32f407xx.h"

typedef struct {
    volatile uint32_t seq;
    volatile uint32_t sec;
    volatile uint32_t ms;
} shared_stamp_t;

typedef struct { uint32_t sec, ms; } stamp_t;

void stamp_publish_isr(shared_stamp_t *s, uint32_t sec, uint32_t ms)
{
    ++s->seq;
    __DMB();
    s->sec = sec;
    s->ms = ms;
    __DMB();
    ++s->seq;
}

int stamp_try_read(const shared_stamp_t *s, stamp_t *out)
{
    uint32_t first = s->seq;
    if ((first & 1u) != 0u) { return 0; }
    __DMB();
    uint32_t sec = s->sec;
    uint32_t ms = s->ms;
    __DMB();
    if (first != s->seq) { return 0; }
    out->sec = sec;
    out->ms = ms;
    return 1;
}
```

初始化可用 `shared_stamp_t s = {0u, 7u, 999u};`。主循环调用成功时才使用输出；失败则本轮保留上一份有效显示，稍后再试。生产者必须保证 ms 的业务范围，例如 0–999；序号机制验证版本一致，不验证业务内容本身正确。

这段代码刻意不在函数里无限重试。假如换成主循环写、ISR 读，ISR 恰在写者把 seq 改为奇数后进入，并一直等待偶数，写者永远没有机会继续，系统会卡住。即使当前方向没有这种死等，写入太频繁也可能让读者长期失败，所以应用仍需设定可接受的数据年龄和失败策略。

## 序号只能验证版本，不能撤销错误访问

边界一：两个写者必须先串行化。写者 A 把 seq 从 0 加到 1，写者 B 再加到 2，读者会误以为稳定。单写者假设一旦变化，要重新设计临界区或锁，不能只增加序号位数。

边界二：无符号序号会回绕。本例每次完整发布加二；一次读取期间若恰好经历 `2^31` 次完整发布，32 位序号可能回到原值。工程上通常可以建立远小于此的读取时长上界，但应写成假设，而不是说“序号永远不同”。

边界三：复制过程中只能做安全的值读取，失败后才能丢弃。若字段是一个可能失效的指针，你先解引用它、再发现序号变化，之前的非法访问已经发生，重试无法挽救。序号也不能自动保证外部对象的生命周期。

边界四：这不是可直接搬到 C11 多线程的普通数据实现。C11 线程中，对非原子字段的并发冲突访问可以构成未定义行为，最后检查序号不会把它变合法；volatile 和 DMB 也不自动提供语言层同步。需要相应平台经过证明的原子/锁实现。这里严格使用嵌入式单核 ISR 场景与工具链约定。

## 双缓冲：第二块内存不是自动安全

假设生产者准备一屏数据，消费者需要很久才能发完。用 A、B 两块缓冲：生产者写完 B 后把“当前指针”切到 B，消费者继续处理 A。看上去读写分开了，但下一次生产者又写 A 时，消费者可能还没处理完。

所以双缓冲至少有两个约束：发布时，内容已经准备好；复用时，上一位使用者已经交还所有权。仅仅把索引改为 `index ^= 1u`，只满足不了第二个条件。

先用状态表跟做一个两槽 FIFO 协议。每槽只有空闲、待消费、消费中三种状态；消费完成前绝不回到空闲。

| 步骤 | A | B | 允许的动作 |
|---|---|---|---|
| 初始 | 空闲 | 空闲 | 写者填 A |
| 发布第1份 | 待消费 | 空闲 | 读者领取 A，写者填 B |
| 发布第2份 | 消费中 | 待消费 | 两槽都不可覆盖 |
| 第3份到来 | 消费中 | 待消费 | 返回忙或按约定丢弃新份 |
| 读者释放 A | 空闲 | 待消费 | 写者才可再次写 A |

给定第1份为 (7,999)、第2份为 (8,0)，先领取 A 却不释放，再尝试生产第3份：正确的结果是报告忙，A 内容仍是 (7,999)。释放 A 后第三份才可成功，B 的第二份也不能被悄悄跳过。配套主机测试显式检查了“持有期间不能覆盖”。

这是一种保留顺序的两槽队列，不是“只保留最新显示”的邮箱。屏幕刷新可以选择丢弃尚未消费的旧版，但绝不能覆盖正在读的版本；选择最新值、全部样本或丢新数据，必须先给业务语义，再设计状态转移。

## 把所有权落到工程里

在单核中断模型中，可以用短临界区完成索引/状态的领取和释放，把大块内容处理放在区外。关键是状态一旦表明“消费者持有”，生产者就必须尊重它；否则即使交换指针原子，数组内容仍会被覆盖。

如果由 DMA 读写缓冲区，完成事件才是重要的交还依据，CPU 的 PRIMASK 不能暂停 DMA。双缓冲传输连续切换时，还必须保证消费者在硬件再次覆盖之前处理完；两块缓冲只能增加有限的处理窗口，不能修复平均消费速度长期不足。

小数据、低更新率时，几条指令的临界区往往最容易审核；只要一致快照而允许重试时，可以考虑序号；大块数据且双方都有明确使用周期时，再设计双缓冲。选法取决于延迟预算、数据大小、丢弃策略和所有权，而不是哪种名字听起来更高级。

## 练习：把生产者加速十倍

现有双缓冲消费者每份用 5 ms，生产者每 1 ms 生成一份。增加到三块缓冲能否保证永久不丢数据？若改用序号锁，消费者就能读到每一份吗？

<details><summary>展开答案</summary>

不能。平均产生速度大于消费速度，有限缓冲只会推迟溢出。必须降低产生速率、加速消费、批量处理、背压或明确丢弃策略。序号锁解决“某次接受的副本一致”，不是历史队列，重试成功时可能已经跳过很多版本；要求逐份不丢时，需要队列容量与吞吐分析。

</details>

## 依据与验证范围

C99 主机模型检查了半新半旧被拒绝、奇数序号被拒绝、稳定副本被接受以及两槽持有期拒绝覆盖；F407 的尝试读取函数经过 ARM 编译。未做真实 ISR 高频压力测试，不承诺无饥饿或固定完成时间。

- [Linux v6.12 序号计数文档](https://github.com/torvalds/linux/blob/v6.12/Documentation/locking/seqlock.rst)：Introduction、seqcount_t、latch sequence counters；核对写者串行化、不能被读侧抢占和指针生命周期风险。Linux API 依靠自己的同步规则，不是此 MCU 代码的直接替代品。
- [C11 委员会草案 N1570](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf)：§5.1.2.4 第25段 的线程数据竞争规则；此处用于说明不能把 MCU 中断协议直接当成标准线程同步。
- [PM0214 Rev10](https://www.st.com/resource/en/programming_manual/dm00046982-stm32-cortexm4-mcus-and-mpus-programming-manual-stmicroelectronics.pdf)：§2.2.4 屏障，§2.3 异常抢占。
- [CMSIS GCC 屏障实现](https://github.com/STMicroelectronics/STM32CubeF4/blob/60c8abe0ae88a23bbd1c925358330031e36dd20f/Drivers/CMSIS/Include/cmsis_gcc.h)：DMB 与编译器内存约束。
