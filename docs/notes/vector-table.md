# 中断向量表的由来

你写好了 `EXTI0_IRQHandler`，没有任何 C 函数调用它，按键到来后它却执行了。把名字少写一个字母，工程仍然能编译，按钮又失灵了。真正决定入口的不是“函数名里有没有 IRQ”，而是一张由启动文件和链接器共同放好的地址表。

[2.4 程序是怎么跑起来的](/lessons/2-4)解释了启动代码的工作。本篇先把这张表当成可以手工解码的数据，之后再看硬件为什么需要它。

## 先读四个字，不急着读汇编

假设调试器在 Flash 起点看到如下内容。地址与函数值是教学样例，必须用自己 ELF 与链接映射中的实际值核对，不能复制到任意工程。

| 表项地址 | 32 位内容 | 解释 |
|---|---|---|
| 0x08000000 | 0x20020000 | 初始 MSP |
| 0x08000004 | 0x08000101 | Reset_Handler 的 Thumb 入口值 |
| 0x08000008 | 0x08000141 | NMI_Handler 的入口值 |
| 0x0800000C | 0x08000145 | HardFault_Handler 的入口值 |

先预测两件事：CPU 会从地址 4 开始执行指令吗？第一项也是函数指针吗？

都不是。复位时内核从地址零读取初始 MSP，从地址 4 读取复位入口值。后者是一次“先读地址，再去地址所指位置执行”的过程，不是把地址 4 当代码开头。表的第一项用于建立栈，并非异常处理函数。

F407 从主 Flash 启动时，启动映射把 Flash 内容映射到地址零附近，所以这里的前两个字可通过启动别名被读到；Flash 本来的 `0x08000000` 地址仍然可用。别名不是把整个 Flash 复制到 RAM，也不是任何启动都先经过 ROM 引导程序。选用系统存储器或 SRAM 启动时，地址零背后的存储对象会变化。

`0x20020000` 是 F407 128 KiB 普通 SRAM 末尾的上一界。满递减栈先减 SP 再存储，因此栈顶可指向已分配空间的末端之后；这不声称该地址本身是一个可读写 RAM 字节。栈区还必须满足链接分配、对齐及实际芯片容量要求。

## 为什么函数入口看起来是奇数

Cortex-M4 只执行 Thumb 指令。异常向量的 bit 0 用于表示 Thumb 状态，所以样例值 `0x08000101` 对应指令地址 `0x08000100`，而不是从奇数字节地址取指。若入口状态位错误，可能导致故障或锁死，不能把清零 bit 0 当作“帮 CPU 对齐”。

这个规则针对可执行处理函数的入口值，不针对初始 MSP，也不要求保留表项非零。汇编器、链接器及编译器通常依据函数符号生成正确的 Thumb 地址；在源代码里给每个函数地址再盲目加 1，并不是普遍正确的修复。

## 从 IRQ 编号算到表项

设备头文件把 EXTI0_IRQn 定义为 6。完整表先有 16 个内核位置，外部 IRQ0 从第 16 项开始，因此：


```text
异常编号 = IRQn + 16 = 22
表项字节偏移 = 22 * 4 = 88 = 0x58
VTOR = 0x08004000 时，EXTI0 表项地址 = 0x08004058
该地址保存的数值才是 EXTI0_IRQHandler 的入口值
```

不能混淆三个数：6 是设备 IRQ 编号；22 是异常编号；`0x58` 是表项相对基址的字节偏移。把表迁到 `0x08004000` 不会自动给每一个处理函数地址也加 `0x4000`；表项中的函数地址由程序实际链接布局决定。

可在 PC 上单独运行这个 C99 计算，不涉及访问 MCU 地址：


```c
#include <assert.h>
#include <stdint.h>
#include <stdio.h>

int main(void)
{
    uint32_t base = UINT32_C(0x08004000);
    uint32_t irqn = 6u;
    uint32_t slot = base + 4u * (irqn + 16u);
    assert(slot == UINT32_C(0x08004058));
    printf("EXTI0 slot=0x%08lX\n", (unsigned long)slot);
    return 0;
}
```

这部分也被收入 `examples/notes/core/test.c`。计算正确只证明下标规则，不证明表中真的装有有效函数地址。

## 这张表解决了什么问题

硬件能报告一个中断编号，但 C 函数在 Flash 的最终地址要等链接之后才知道。向量表给二者提供稳定接口：硬件按编号索引；链接器把实际符号地址填进对应位置。这样业务函数可以换位置，设备中断编号不用跟着改。

F407 官方 GCC 启动文件把表放在 `.isr_vector` 节里：第一项是链接符号 `_estack`，第二项是 `Reset_Handler`，再往后按芯片约定列出异常与外设处理函数。链接脚本负责节的位置、保留与对齐。只给一个 C 数组取名“vectors”，却没有正确节属性和链接布局，并不能使 CPU 自动认出它。

未被应用覆盖的处理函数常通过弱别名落到默认死循环。名字拼错时，你定义的是另一个普通函数，真正的表项还指向默认入口。排查时要看最终映像中的表项和符号，而不只是“源码里有这个名字”。

## VTOR 让表可以换住址，但不会搬程序

VTOR 是向量表基址寄存器。启动别名决定复位最初从哪里取前两个字，VTOR 则影响之后异常向量的查找；它与 SYSCFG 的存储器重映射不是一回事。

F407 的完整表包含 16 个内核位置和 IRQ0–81，共 98 个字、392 字节。使用 512 字节对齐的表空间，符合 PM0214 对此设备的表基址要求。不要只看到通用描述里的 `0x80` 就认为 F407 完整表只需 128 字节对齐。

若真的需要把表搬到 SRAM，先在独立工程的早期初始化中按以下顺序检查，不要直接在运行中的电机或通信程序里试：

1. 链接器在 CPU 可读的普通 SRAM 保留一块静态、512 字节对齐的空间，生命周期覆盖整个运行期。
2. 从当前正确表复制全部 98 项，保留保留项的位置，不压缩空洞；确认初始栈项及全部可能触发的异常入口有效。
3. 在相关中断源尚未启用、系统状态可控时完成复制；需要时保存/屏蔽/恢复可配置中断，不能假装这样也屏蔽了 NMI。
4. 在公布新表之前按架构要求完成可见性顺序，更新 VTOR 后使用适当的 DSB/ISB 同步，再开放相应请求。
5. 在调试器里读回 VTOR，按上面的偏移公式核对一两个表项，最后用已知安全的请求验证入口。

复制后只改 VTOR，不会搬移处理函数、不初始化新程序的数据段，也不会替引导程序设置栈和外设状态。“跳进另一个固件”还涉及链接地址、栈、挂起请求、时钟及运行库，远多于更换一张表。

## 练习：一次错误的搬家

有人分配了 98 字的局部数组，复制完向量后把 VTOR 指向它；函数返回后继续运行。他还把 EXTI0 的入口放到数组下标 6。请指出至少三个问题。

<details><summary>展开答案</summary>

局部数组退出作用域后生命周期结束，其栈空间会复用；普通局部数组也不保证 512 字节对齐；EXTI0 应放在下标 22，而下标 6 原来属于 UsageFault。还必须核对完整表项、链接位置、公布顺序与切换时的中断状态。正确做法是静态保留并正确对齐整个表，按真实芯片表顺序复制和核验，而不是只修一个索引。

</details>
