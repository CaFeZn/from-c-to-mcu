# HardFault 现场 dump 与复位后回放

你终于在串口上等到了故障，结果屏幕只显示半个单词，板子就被看门狗复位了。重连调试器时，PC 已经回到正常主循环。再发生一次也许要等一夜。

问题不只是“日志来不及发”。故障时栈、DMA、锁或日志缓冲可能正是损坏源。这时继续格式化一整段文本，反而可能再次异常。本篇把事情分成两段：**出事时只留下小记录；下次启动、运行环境恢复后再解释和输出。** 先读 [HardFault 现场分析](/notes/hardfault-analysis)，这里不重新推导异常帧。

## 先用十二个字模拟一次“复位”

不接板子，先定义一条固定布局的教学记录。每个元素都是 `uint32_t`，共 12 个字、48 字节；不把带填充的 C 结构体直接当跨版本协议。

| 索引 | 含义 |
|---|---|
| 0 | 最后写入的提交标记 MAGIC |
| 1–4 | 格式版本、字数、构建标识、记录序号 |
| 5–7 | EXC_RETURN、CFSR、HFSR |
| 8–10 | PC、xPSR、字段有效性 FLAGS |
| 11 | 32 位加和校验的补数 |

教学输入是版本 1、字数 12、构建标识 `0x20261025`、序号 7，CFSR=`0x00010000`，HFSR=`0x40000000`，PC=`0x08001234`。FLAGS=1 表示这个演示中的基本帧字段有效。实际产品通常还要存原始 SP、LR、BFAR/MMFAR 及各自有效标志、启动计数；这里刻意不转储整块栈。

先预测三种结果：写完记录但没写 MAGIC、全部写完、写完后改坏一个字。然后在仓库根目录运行：

```sh
cmake -S examples/notes/debug -B artifacts/course-completion/debug/build -G Ninja
cmake --build artifacts/course-completion/debug/build
./artifacts/course-completion/debug/build/debug_models.exe
```

其中一行预期为：

```text
record: valid pc=08001234, torn/corrupt/version rejected
```

实验先逐步复制尚未提交的记录，模拟在各次写入后突然中断，验证都被拒绝；再提交完整记录；最后逐字翻转一位、改变格式版本，检查读取端不盲信数据。**这是 PC 内存数组模型，不是真机断电试验。**

## 提交标记必须最后到达

故障入口的写入顺序应该是一个小事务，而不是“先放一个魔数，再慢慢填内容”：

1. 先令旧 MAGIC 无效，防止旧的有效标记搭配新的半截内容。
2. 写固定版本、固定长度、构建标识和已验证字段。读不出的现场填占位数，但相应有效位必须为 0。
3. 计算校验。这个模型让索引 1 到 11 的无符号 32 位和等于零。
4. 确认前面的写入完成之后，最后发布 MAGIC，再请求受控复位。

为什么不只检查 MAGIC？因为发生故障时并不保证“记录区完整”。老记录、随机 RAM、写一半的记录都可能带有看似正确的开头。为什么不只检查校验？因为版本不匹配时，解析器可能把新格式某字段错认成旧版长度。

本模型的加和校验只为演示验证流程；两处相反改动能相互抵消，它**不是 CRC，也不是密码学认证**。产品可换经过验证的 CRC 来提高随机错误检测能力，但 CRC 仍挡不住主动伪造。对外发送记录，应另行设计鉴权与完整性保护。

真实 Cortex-M4 实现还要明确编译器和硬件顺序。仅把 MAGIC 声明为 `volatile`，不等于普通字段会按你想的次序对其他观察者可见。故障写入端可使用明确的易失访问约定、编译器屏障及适当的 `__DSB()`；发布标记和请求复位前必须核对生成代码。F407 没有 D-cache，本篇不添加凭空出现的“清 D-cache”步骤。换到带缓存芯片时则需要重新设计一致性和持久性协议。

## 记录为什么能躲过启动代码

普通静态变量一般落入 .bss，复位后的 C 启动代码会把该区清零。给变量起名为 crash 或 noinit，并不会改变这个事实。

在 GCC 加 GNU ld 的 F407 工程中，可以为单独的记录区使用类似下面的**集成片段**：

```c
#include <stdint.h>

__attribute__((section(".noinit.crash"), used, aligned(4)))
volatile uint32_t crash_words[12];  /* 不添加 C 初始化器 */
```

在链接脚本的 SECTIONS 内、合适的 RAM 分配位置放入：

```text
.noinit.crash (NOLOAD) :
{
    . = ALIGN(4);
    KEEP(*(.noinit.crash))
    . = ALIGN(4);
} > RAM
```

这不是完整链接脚本。必须同时检查四件事：

- 该区落在真实可用 SRAM 内，没有与堆、栈、其他保留区重叠。
- 启动代码的清零区间不包含它；例如 ST GCC 模板只清 `[_sbss, _ebss)`，记录区应在该区间之外。
- 下载器、引导程序和内存自检没有另行清空它。
- 预期的复位方式与供电条件确实保留这段内存。

`NOLOAD` 是链接器输出段属性，不是硬件“永不丢失”的开关。一次 ELF 下载也不能证明下次上电仍保留数据。普通 SRAM 的 no-init 路线只讨论**供电保持、经验证的暖复位路径**；掉电、Standby、欠压后的内容不得依赖。

若要求 VDD 消失后仍保留，F407 还有 4 KiB 备份 SRAM，但它需要正确的访问时钟、PWR 访问配置、备份稳压器和 VBAT 供电。不能把“焊了电池”当作全链路已经生效。Flash 又有擦写粒度、耗时、寿命和掉电一致性问题，通常不适合在未知故障状态下临时擦一扇区。

## 重启后先读证据，后清标志

启动后先保存 RCC_CSR 的复位标志，再按工程流程清除。F407 的 SFTRSTF、IWDGRSTF 等能帮助判断软件复位、看门狗复位，但它们可能累积，不能当作互斥枚举。含 BOR/POR 等不可信电源历史时，普通 SRAM 记录应按保守策略丢弃。

读取端流程可以写成：

```text
保存复位原因
→ 检查保留条件
→ 检查 MAGIC、固定版本和固定长度
→ 检查校验及字段有效位
→ 复制到普通 RAM 快照
→ 使保留记录失效，或按明确的确认协议标记已消费
→ 日志层初始化完成后输出
```

不要用记录里的任意长度直接循环读内存。先确认格式版本与期望长度，才能进入固定范围的校验。重复复位时，单槽会覆盖前一条记录；要保留“第一次出错”，可选择有效记录未消费时不覆盖。要保留最近几次，则需带序号的多个槽，而不只是把数组开大。

一条完整记录应能关联到**原下载固件的 ELF、映射文件、编译器版本和选项**。本例短构建号只是标签，不保证全球唯一；产品应使用可追溯且足够唯一的发布标识。收到旧版本 dump，不能拿新固件地址表硬解释。

## 不要为了留证把故障处理变成第二套系统

故障路径不应依赖堆分配、操作系统锁、UART 中断、复杂 printf 或很深的函数调用；最好不使用浮点，避免触发额外现场保存。即使已经换到紧急栈，也不代表原栈和内存总线恢复正常。写不了记录本身就是可能的结果，复位策略仍要有界。

还要注意保密：原始栈可能含口令、密钥、会话数据。完整转储虽然方便，却把秘密复制到了更容易读取的地方。默认采用字段白名单；必要的完整 dump 只能在受控开发模式收集，不能悄悄带进量产固件。

### 练习：旧标记、新内容

旧记录的 MAGIC 仍有效。写新记录时先更新 PC，再写校验，最后重写同一个 MAGIC。若在更新 PC 后复位，能否保证读端拒绝它？怎样修改顺序？

<details><summary>答案</summary>

不能把安全性寄托在校验“碰巧不匹配”上，尤其旧字段与新字段可能形成碰撞。应先使 MAGIC 无效，再更新所有固定字段和校验；在写入完成后最后提交。读端仍需检查版本、长度和校验。若要连旧完整记录也保留，应使用两个独立槽及序号/提交规则，而不是原地覆盖一个槽。

</details>
