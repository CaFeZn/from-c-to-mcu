# CRC校验

串口助手发出一条亮灯命令，协议正文是 `LEN TYPE SEQ PAYLOAD`，即 `01 01 07 01`。你故意把中间两个字节改成 `02 06`，接收端的累加和检查却仍然通过：两组字节相加都是 `0A`。消息类型和序号已经变了，“和没变”显然不能证明“消息没变”。

这次不接板子，先在电脑上重现这个漏洞，再让主线使用的 CRC-16/CCITT-FALSE 来检查同样的数据。目标不是让 CRC 承包整个协议，而是弄清楚：它到底检查了什么，双方怎样才能算出同一个数。

## 先复现这两个错误

配套独立工程位于下面命令指定的目录。需要能在终端找到 C99 编译器、CMake 和 Ninja；命令从仓库根目录执行，不构建网站。

```bash
cmake -S examples/notes/serial/crc -B artifacts/course-completion/serial/crc/build -G Ninja -DCMAKE_BUILD_TYPE=Debug
cmake --build artifacts/course-completion/serial/crc/build
ctest --test-dir artifacts/course-completion/serial/crc/build -V
```

测试先使用九个 ASCII 字节 `31 32 33 34 35 36 37 38 39`，也就是 `"123456789"`，**不含字符串结束的零字节**。再测试正文和两种损坏，预期得到：

| 输入字节 | 含义 | CRC16 |
|---|---|---|
| `"123456789"` 的九个 ASCII 字节 | 参数检查向量 | `29B1` |
| 无字节 | 空输入 | `FFFF` |
| `01 01 07 01` | 原正文 | `4CF2` |
| `01 01 07 00` | payload 翻一位 | `5CD3` |
| `01 02 06 01` | 累加和不变的修改 | `2693` |

原帧在线上是 `A5 01 01 07 01 F2 4C`。接收端计算中间四字节得到 `4CF2`，再把最后两字节按协议组合成 `4CF2`，二者相等才通过。若只把 payload 改为零却保留 `F2 4C`，重新计算会得到 `5CD3`，应拒绝这一帧。

先预测，再运行：若把 CRC 字段交换成 `4C F2`，会不会通过？不会，接收方按低字节在前解码得到的是 `F24C`。此时正文和算法都正确，错在字段编码，不该先去改多项式。

## “CRC16”还不足以构成约定

本篇沿用主线算法；CRC RevEng 参数目录把它称为 CRC-16/IBM-3740，CCITT-FALSE 是别名。只写“CCITT”容易与其他参数组合混淆，协议里应写全以下约定。

| 参数 | 本篇值 | 作用 |
|---|---|---|
| width | 16 | 状态宽度 |
| poly | `0x1021` | 常规表示，省略最高的 `x^16` 项 |
| init | `0xFFFF` | 每条新消息的初始状态 |
| refin / refout | false / false | 输入及输出不作反射 |
| xorout | `0x0000` | 最终结果不再异或非零常量 |

还要另写两件事：CRC 覆盖 `LEN、TYPE、SEQ、PAYLOAD`，不含 `A5` 帧头和 CRC 字段；校验字段先发低字节。这些是**帧协议的约定**，不属于多项式本身。

反射、字节序和串口发送位序是三个层次。UART 硬件可以先发送一个字符的最低位，软件拿到完整字节后仍按本篇的最高位优先算法更新；CRC 字段低字节先发，也不意味着 `refin=true`。切勿为了“匹配小端”就把移位方向改掉。

## 余数为什么能检查一串位

CRC 把位串看成二元多项式的系数。系数只有零和一，加减都等于异或，没有进位和借位。`0x1021` 表示的低位部分是 `x^12+x^5+1`，加上隐含的最高项，生成多项式就是 `x^16+x^12+x^5+1`。

先缩小成一个三位 CRC 的手算模型：消息 `1101`，除数 `1011`，初值为零且没有反射、输出异或。在消息后补三个零，再做异或长除法：

```text
1101000 XOR 1011000 = 0110000
0110000 XOR 0101100 = 0011100
0011100 XOR 0010110 = 0001010
0001010 XOR 0001011 = 0000001
```

余式为 `001`，把它接到原消息后得到 `1101001`，这个码字能被 `1011` 整除。若传输中改变了一些位，接收串相当于原码字再异或一个“错误多项式”；除法余式不为零就能发现变化。这只是解释数学关系的小模型，不是把真实 CRC16 的初值改成零。

软件不必保存整个长除法过程。一个宽度固定的寄存器保存当前余式，逐位移入消息；最高位将被移出时，用生成多项式消去它。下面是配套实现的核心，完整工程还提供整帧函数与测试入口：

```c
#include <stddef.h>
#include <stdint.h>

uint16_t crc16_ccitt_false_update(uint16_t state,
                                 const uint8_t *data, size_t length)
{
    uint32_t crc = state;
    for (size_t i = 0u; i < length; ++i) {
        crc ^= (uint32_t)data[i] << 8;
        for (unsigned bit = 0u; bit < 8u; ++bit) {
            crc = (crc & UINT32_C(0x8000)) != 0u
                ? (crc << 1) ^ UINT32_C(0x1021) : crc << 1;
            crc &= UINT32_C(0xFFFF);
        }
    }
    return (uint16_t)crc;
}
```

这里用无符号的 32 位临时量计算，再限制为 16 位状态。`data` 必须指向至少 `length` 个可读字节；长度为零时允许传空指针。调用者在第一块前传 `0xFFFF`，之后把返回状态传给下一块；最后直接得到本算法的 CRC。循环已经实现所需的 CRC 更新，不要照着前面的手算模型，再额外喂两个零字节。

## 检出能力有条件，不是“永不出错”

对于这里具有非零常数项的 16 次生成多项式，在码字边界正确、按多项式约定的码字位序把错误表示成位翻转的模型下，跨度不超过 16 位的非零突发错误都能检出。“跨度”从第一个错误位算到最后一个错误位，包含中间没有变化的位，不是只数翻转了几位。

这个界限说的是上述码字位序。主线将 CRC 低字节先发，UART 又有自己的位序，不能未经映射就把它等同于线路上任意 16 个时钟周期；丢字节、插字节和帧边界变化也不能直接套用这个位翻转模型。

原因可以从长除法看出来：去掉前面的移位因子后，这样的错误多项式次数小于 16，不可能是生成多项式的非零倍数。更长的错误模式则可能恰好整除，出现漏检。对具有适当随机分布的长错误模式，常用 `2^-16` 估计漏检概率；这不是对任意错误、任意帧长或故意篡改的保证。

CRC 也不负责判断命令是否合法。攻击者可以重算 CRC，坏掉的长度字段仍可能诱导程序越界，重复的好帧也会有正确 CRC。因此解析器必须先限制长度、处理超时，再检查 CRC，最后验证消息类型、数值范围和序号；需要防伪时使用认证机制，不能把 CRC 当作密码学签名。

## 两个很容易漏掉的边界

**空 payload 不等于空 CRC 输入。** 主线中即使 `LEN=0`，还要计算长度、类型和序号三个字节。表里的空输入 `FFFF` 只是算法测试，不是所有无载荷帧的校验值。二进制消息中出现 `00` 也不能提前停下，长度应由协议或调用参数给定，不用 `strlen`。

**“把整帧再算一遍，看是否为零”不能无条件套用。** 上面的简化长除法有零余数性质，但真实参数、初值以及 CRC 的附加顺序会影响检查方式。本算法把 CRC 高字节在前接到正文后可得到零；主线实际选择低字节在前，不能套这个判据。配套测试专门检查了两种顺序。协议现有实现采用“排除 CRC 字段重新计算，再与收到的值比较”，更容易核对。

分块接收时还要保留状态。收到前半段后重新初始化，会把后半段误当作一条新消息。CRC 能连续更新，是因为当前状态概括了之前的计算；它没有替你记住帧头、长度或解析器正处在哪一步。

## 留一道分块题

把 `"123456789"` 分成 `"1234"` 和 `"56789"`。应该怎样调用更新函数？再把九字节数组误写成包含结尾零字节的十字节长度，是否仍应该期待 `29B1`？

<details>
<summary>展开答案</summary>

第一块使用 `state=0xFFFF`，第二块使用第一块返回的状态，且不重新初始化；结束结果应为 `29B1`。配套测试遍历了这个九字节输入的全部十个切分位置，包括第一块或第二块为空。

多算结尾零字节就是换了输入，不再属于该检查向量。也不能把两段独立算出的 CRC 直接异或，来代替连续更新；初值和位移传播都参与了结果。

</details>
