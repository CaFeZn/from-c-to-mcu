# 用 Markdown 写清楚工程

把能运行的 `c-lab` 发给同学，对方问：“打开哪个文件？点哪个按钮？出现什么才算成功？”你回答“和我电脑上一样”，但对方没有你的记忆，也不知道你最后运行的是 `hello` 还是 `greet`。

先不背语法表。这次只做一件事：**在工程根目录写一份 README，让第一次打开工程的人能够复现一次结果。** 它跟源码一起保存，不依赖聊天截图，也不是一篇开发日记。

> **前置**：完成 [1.0 环境与 hello](/lessons/1-0)，至少已经看到过一次 `hello, world`。本篇不增加开始写 C 的必修步骤，也不替换原有的 VS Code 操作路线。

## 一、现在就给工程加一份说明

在 VS Code 打开自己的 `c-lab`，在 `CMakeLists.txt` 同一层新建 `README.md`。注意不是 `README.md.txt`，文件编码使用 UTF-8。把下面框内的内容写进去，保留内部三个反引号；外层更长的围栏只是本教程用来展示 Markdown 源文的。

````markdown
# c-lab

电脑上的 C99 问候语练习，不连接单片机。

## 环境

- Windows 64 位，gcc、CMake 3.20 或更高、Ninja 已可在终端调用。
- 下列运行命令使用 PowerShell。
- 在本工程根目录执行，目录里应有 CMakeLists.txt。

## 构建与运行

```powershell
cmake -S . -B build -G Ninja
cmake --build build --target hello
.\build\hello.exe
```

输入：不需要键盘输入，也不读取文件。

预期标准输出：

```text
hello, world
```

成功时程序退出码为 0。仅看到构建完成，不等于已经运行程序。

## 文件入口

- [问候语源码](src/hello.c)
- [构建清单](CMakeLists.txt)

## 已知限制

这里只验证 PC 上的标准输出，不涉及串口、下载器或板上 LED。
````

保存后，在命令面板执行 `Markdown: Open Preview to the Side`。Windows 默认也可以先按 `Ctrl+K`，松开后再按 `V`。VS Code 内置预览足够做这次练习，不需要先安装文档插件。

先预测：预览里应有一个工程标题、四个小节、一个命令块、一个输出块和两个可点击的文件入口。`#` 不应显示成正文开头的字符，命令的反斜杠和换行也不应丢失。点击“问候语源码”，确认打开的是本工程的 `src/hello.c`，不是其他目录里同名的文件。

然后真正照 README 运行一遍。终端停在工程根目录，逐条执行；每一步成功再做下一步。有错误时不要继续运行昨天留下的可执行文件。这个例子的输入是“无”，标准输出是一行 `hello, world`，程序正常退出。它验证的是 PC 程序，不是串口消息。

如果你已在 Git 练习中把问候语改成 `hello, c-lab`，这份 README 就暂时过期了：按真实代码修正预期结果再验证，或者用独立的起步工程跟做，不要为了匹配模板偷偷覆盖自己的进展。

## 二、每一种写法都解决一个具体问题

刚才的源文件是普通文字。Markdown 解析器把标题、段落、列表、代码块和链接识别为不同结构，预览再把结构显示出来。后缀不会让命令自动执行，写上 `c` 也不会调用编译器。

### 用标题回答读者的问题

`# c-lab` 是一级标题；`## 环境` 和 `## 构建与运行` 是同级章节；只有确实属于某一章的内容才继续使用 `###`。`#` 后面留一个空格，标题前后留空行，源文与预览都容易读。

标题不只是“加大字体”。“准备什么、怎样运行、看到什么、哪里不能用”形成可扫描的顺序，编辑器目录也能据此导航。不要把每一句话都升级成标题，也不用为了好看从一级直接跳到四级。

### 用代码格式保留该照抄的字符

正文里提到短命令或文件名，用一对反引号，例如 `hello`、`src/hello.c`。多行命令放在围栏代码块里：首尾至少三个反引号，开始一行可以写 `powershell`、`bash`、`c` 或 `text`。

语言标签给渲染器提供高亮信息，不改变程序语义，更不保证命令能在那种终端运行。上面的 `.\build\hello.exe` 明确是 Windows PowerShell 写法；Linux、macOS 通常运行 `./build/hello`。不要把两套写法混进一个未标环境的复制框。

命令里不加提示符 `PS C:\dev\c-lab>` 或 `$`，免得读者一起复制。输出放到另一个 `text` 块：`hello, world` 是结果，不是一条待执行命令。需要粘贴的内容不要只放截图。

如果你写完一个命令块，后面的所有标题也变成了代码，先检查末尾围栏是否遗漏。围栏没有闭合时，后续内容可能一直被当成代码。需要展示“内部含三个反引号”的 Markdown 时，像第一节那样用四个反引号包住整个例子。

### 用列表说明条件，不用空格排版

环境要求适合无序列表；必须先后执行的步骤适合有序列表。普通段落间留一个空行。**仅在源文按一次回车，通常只产生软换行，不保证预览中另起一段。** 想分段就留空行，不要靠许多空格把文字推到下一行。

短表格可以比较“目标”和“预期输出”：

```markdown
| 目标 | 预期输出 |
|---|---|
| hello | hello, world |
| greet | hi, c-lab |
```

表格属于 GitHub Flavored Markdown 的扩展，并非所有 Markdown 处理器都支持。表头后面的分隔行不能漏；不要把完整构建日志、长命令或多段说明塞进单元格，窄屏上难读，代码块通常更合适。

## 三、让文件入口跟工程一起搬家

模板里的 `[问候语源码](src/hello.c)` 有两部分：方括号里是读者看到的名字，圆括号里是目标。对仓库文档来说，优先使用从当前 Markdown 文件位置出发的相对路径，且路径写 `/`。README 放在根目录时，`src/hello.c` 指向根目录下的源码。

若以后把这份文档移到 `docs/usage.md`，同一个源码入口就要写成 `../src/hello.c`。**文档移动、文件改名或大小写改变，都可能让链接失效。** 在 Windows 本地能打开，不代表部署到大小写敏感的环境仍能打开。

不要把个人绝对路径写成共享入口，例如 `C:\Users\某人\Desktop\c-lab\src\hello.c`。这种地址把别人的机器假设成你的机器，也可能暴露私人目录。图片同样应保存在工程约定的资源目录，用相对路径链接，并写有意义的替代文字；没有图片时不要留下假的图片链接。

外部资料则写有名称的链接，读者应知道点过去是什么。站点的章节锚点生成规则可能随平台变化，标题改名后要重新点验。本课程正文使用课程路由，个人工程 README 使用仓库相对路径，两种发布场景不要混抄。

VS Code 可以在设置里启用 `markdown.validate.enabled` 检查本地链接。它不能代替外部网站可访问性检查，也不能证明命令运行成功；链接没有波浪线，不等于说明已经正确。

## 四、补充一个新目标，说明也跟着变

现在保持 `hello` 的说明不动，再给 1.0 已建立的 `greet` 增加一段“运行 greet”。如果还没做过，先回到 1.0 新建 `src/greet.c`、登记 `add_demo(greet)` 并运行它，不在 README 里描述一个不存在的目标。

新增段落至少包含以下命令：

```powershell
cmake --build build --target greet
.\build\greet.exe
```

其前提是已经按前面的步骤配置了工程，预期输出应单独写成：

```text
hi, c-lab
```

再增加 `[greet 源码](src/greet.c)` 入口。合上旧聊天与教程，只看自己的 README，能否从根目录准确运行这两个目标？检查自己有没有遗漏“先配置”、终端种类或运行目标。

接下来做一次有意的故障：只把 README 链接中的 `src/greet.c` 临时改成 `src/greet-missing.c`，不移动实际源码。预览文字看起来几乎没变，但点击会失败或被本地校验报告。改回后再点一次。这个实验说明，排版正常和内容正确是两回事。

## 五、把复现条件写清，而不是写“已测试”

一个有用的验证记录至少告诉别人：用了什么环境，执行了哪条命令，输入是什么，预期是什么，实际观察到什么。记下实际版本，例如从 `gcc --version`、`cmake --version` 读取；不要把教程里的版本号直接当成自己的测试记录。

改问候语时，源码与预期输出应一起更新；修复构建方式时，命令与工作目录应一起更新。多人协作时让说明跟相关代码进入同一次小提交，参见 [用 Git 保存进展](/notes/git-workflow)。不要为了交差写“全部正常”，也不用把每次编译的几百行重复日志都粘进首页。保留关键输入、输出和第一条错误更容易定位问题。

两处边界尤其值得留意：

- **语法方言不同。** 表格、任务列表、双中括号链接、提示框和站点组件并非同一套通用语法。README 先用标题、列表、普通链接和代码块；若用扩展，必须在真实发布平台预览。
- **预览不是可信执行环境。** 文档里原始 HTML、外部图片和链接可能具有隐私或安全影响。不要为显示来路不明的文件随意关闭预览安全限制；不要公开日志里的令牌、密码或私人路径。

以后转到单片机工程，README 还要补充芯片完整型号、板卡版本、接线、供电、下载接口和如何观察结果。这里只跑过 PC 程序，就明确写 PC；“编译通过”不能写成“LED 已实测”。

## 自己改一份说明

某份工程说明只有这三句：

```text
打开终端。
运行 build/hello。
能打印就是对的。
```

把它改到另一位 Windows 学习者可以复现：补齐执行目录、工具前提、配置与构建、实际运行命令、输入和完整预期输出。再说明把 README 从根目录移动到 `docs/` 后，原来的 `src/hello.c` 链接为什么需要修改。

从已保存的 C99 工程根目录开始，先确认 gcc、CMake 3.20 或更高和 Ninja 可调用。在 PowerShell 中执行：

```powershell
cmake -S . -B build -G Ninja

```

每步成功再继续。输入为空，标准输出应为 `hello, world` 加换行，正常退出码为 0；这与“随便打印了一句”不同。需要诊断运行结果时，在 PowerShell 直接运行程序后查看 `$LASTEXITCODE`。

相对链接从文档的位置解析。根目录 README 中的 `src/hello.c` 可用；移到 `docs/` 后应改为 `../src/hello.c`。修改后重新预览并点击，不能只靠肉眼检查字符串。

## 适用范围与技术参考

正文使用 CommonMark 的基础结构，表格单独标明 GFM 扩展。示例以 1.0 的 Windows、Ninja 单配置构建为准；Visual Studio 等多配置生成器的程序路径可能不同，不能只改后缀就声称跨平台适用。配套问候语工程与 Markdown 结构可独立核验；本轮未在 GitHub 发布，也未在每一种编辑器上验收。

- [CommonMark 0.31.2](https://spec.commonmark.org/0.31.2/)：§4.2 标题、§4.5 围栏代码块、§6.3 链接、§6.7–6.8 硬换行与软换行，版本日期为 2024-01-28。
- [GFM 规范](https://github.github.com/gfm/)：§4.10 表格与 §5.3 任务列表都是扩展，不能由“Markdown”这个名称推断所有平台行为相同。
- [VS Code Markdown 文档](https://code.visualstudio.com/docs/languages/markdown)：Markdown preview、Path completions、Link validation，核对内置预览、相对链接与本地链接校验的范围。
