# DMA工作原理

你在调试器里看见 ADC 数据寄存器一直变化，数组却始终是零。给主循环加十个打印也没有用：CPU 根本不负责把这批结果逐个存进数组。换一种错误配置，数组只有第一个位置不断变化，其余仍为零。

这两种现象都能从一张“搬运清单”解释。**DMA 不会因为你创建了数组，就猜出应该往哪里搬；外设也不会因为 DMA 已使能，就自动产生转换结果。**

本篇把 [8.2 ADC 采集电压](/lessons/8-2) 的结果搬运拆开看，也为 [6.2 DMA 与空闲中断](/lessons/6-2) 提供底层背景。具体硬件为 STM32F407 的 DMA1/DMA2，不是新型号的 DMAMUX、BDMA 或 GPDMA。

## 先手工搬八个数

约定 ADC1 已经正确完成八次转换，结果依次是 100、200、300、400、500、600、700、800。

目的地是八个 `uint16_t` 元素组成的数组。我们选普通模式、外设到内存、双方半字宽度、外设地址固定、内存地址递增，并把传输数量设为 8。下面先忽略总线仲裁延迟，追踪每次请求被服务之后的状态。

| 已搬数量 | 本次写入 | 剩余数量 NDTR | 新事件 |
|---|---|---|---|
| 0 | 尚未写入 | 8 | 无 |
| 1 | 第 0 项 = 100 | 7 | 无 |
| 4 | 第 3 项 = 400 | 4 | HT |
| 8 | 第 7 项 = 800 | 0 | TC，普通模式结束 |

每次都从同一个 ADC 数据寄存器读取；写入的内存地址则每次前进 2 字节。若数组首地址记为 B，目的地址依次是 B、B+2、B+4……B+14。B 是程序真正分配的地址，不是随便挑的一块 RAM。

现在先猜：只把内存递增关掉，会得到什么？

<details>
<summary>展开预测结果</summary>

八次都写第 0 项，最后第 0 项为 800，其余项保持原值。NDTR 仍会减到零，TC 仍会发生。**“收到了完成中断”只说明搬运按配置结束，不证明地址配置正确。**

</details>

配套 C99 模型实际验证了这两种配置，也验证普通模式完成后第九次请求不会再改数组。它模拟的是地址和计数规则，不是 F407 总线时序或模拟输入。

## 把清单对应到寄存器

F407 的一个 DMA 流可以按下表理解。示例使用 ADC1 的一个合法组合：DMA2、Stream 0、Channel 0；RM0090 表 44 还列有 ADC1 的其它合法组合。不是任意 DMA、流和通道都能搭配。

| 清单项 | F407 中的对应位置 |
|---|---|
| 谁发来请求 | 流的 CHSEL 选择与芯片请求映射表 |
| 从哪个外设入口取 | PAR 指向 ADC1 数据寄存器 |
| 搬到哪里 | M0AR 指向数组首地址 |
| 搬多少项 | NDTR = 8 |
| 往哪个方向 | DIR = 外设到内存 |
| 每项多宽 | PSIZE、MSIZE 均为半字 |
| 哪边地址递增 | PINC = 0，MINC = 1 |
| 搬完是否重来 | CIRC = 0，普通模式 |

“流”是有独立地址、计数和状态的一套搬运资源；这里的“通道”是这个流选择哪条请求线路，**不是 ADC 的模拟通道号，也不是八个能同时干活的子流**。两个外设若争用同一个流，不能靠填不同通道号让它们同时拥有这套寄存器。

本例的 NDTR 是 8 个数据项，不是 8 字节；总目标容量为 16 字节。如果把 `sizeof(array)` 的结果 16 当成半字项数填进去，DMA 会尝试写 32 字节，可能破坏紧邻变量。只改数组 C 类型、不改 DMA 宽度，也不构成正确配置。

## 一次请求的真实路径

ADC 完成一次规则转换后，把结果放进数据寄存器；当 ADC 的 DMA 请求已启用时，它提出请求。DMA 控制器依据请求选择和优先级获取总线，读外设入口，再把数据写到目标内存，并更新计数。

CPU 在最初配置资源、启动采集，在完成或异常时处理通知。中间的每个数不需要先绕进 CPU 通用寄存器再由 C 赋值写入，所以中断次数可以显著减少。但 DMA 仍然消耗总线带宽；多个主设备访问同一存储器时会发生仲裁。把 DMA 优先级调到最高，不会使内存无限快，也不是把 CPU 中断优先级一起调高。

对 ADC1，DMA 流与 ADC 请求端必须同时配好：流能工作是一回事，ADC 的 `DMA` 位允许发请求是另一回事。循环收集还要核对 ADC 的 `DDS` 与 DMA 的 `CIRC`，它们分别控制持续请求与缓冲重装载，不能只开其中一边就宣布“永远采集”。

## 按顺序启停，比反复重试可靠

在 CubeMX/HAL 工程里，应让生成代码建立 ADC 与 DMA 句柄关联、外设时钟和中断入口，再调用相应启动函数；不要在 HAL 管理同一流期间额外随意写寄存器。排查时可按这个顺序看状态：

1. 先停止触发来源，确认没有新数据不断涌入。
2. 需要重新配置流时，清 EN 后**等读回为 0**，不能认为写零立即生效。
3. 清理该流的旧状态，核对 PAR、M0AR、NDTR、请求映射、宽度和方向。
4. 先让目标缓冲与 DMA 就绪，再开放外设请求和触发来源。
5. 检查错误标志，再解释 HT/TC；别把错误结束当正常数据包。

F407 的流标志通过 LIFCR/HIFCR 相应位写 1 清除。不要对“写 1 清除”寄存器机械套用普通变量的读改写操作。若 ADC 因数据未及时搬走而设置 OVR，RM0090 §13.8.1 要求重新同步 DMA 与 ADC 的状态、地址和计数；只清一次标志可能留下通道与数组位置错位。

## 三个“完成”不是同一个承诺

**半传输 HT** 表示本次目标数据的一半已到达；**传输完成 TC** 表示这次配置的数据搬运结束。循环模式下 TC 不表示 DMA 停下来等你，它会重装 NDTR 并返回缓冲开头。处理前半段的有效窗口见 [DMA 半传输与流式处理](/notes/dma-streaming)。

对串口发送还要多问一步：DMA 完成表示最后一个数据已交给外设入口，不一定已经从 TX 引脚发完。USART 的发送完成状态描述的是另一个阶段；驱动回调的语义应按相应 HAL 实现核对。不要用 ADC 的接收完成含义解释所有外设。

## 缓冲区必须活着，而且 DMA 必须够得着

- **地址可达。** F407 的普通 SRAM1/SRAM2 可供 DMA 使用，CCM 数据 RAM 不接在 DMA 可访问的总线路径上。CPU 能读写某个数组，不证明 DMA 也能访问它；应查链接后的地址，而不是只查变量名。
- **生存期。** 发起异步传输后立刻返回的函数，不能把即将失效的局部数组交给 DMA。发送期间也不能提前复用这块内容；接收期间更不能边覆盖边假装取到了完整快照。
- **缓存与可见性。** F407 没有 D-cache；换成带 D-cache 的芯片，需要另外设计缓存维护和对齐。即使在 F407，给变量加 `volatile` 也不会让 DMA 停下、不替代所有权协议，也不是 C 语言的线程同步原语。
- **队列不是硬件自动提供的。** NDTR 只有当前位置的信息。轮询过慢、DMA 已经绕过一整圈时，相同 NDTR 可能对应不同圈，不能凭一次读数恢复丢失数据。

## 练习：为何完成了，却毁了旁边的变量

接收目标为 64 项 `uint16_t`，宽度仍是半字，你却把传输长度填为 128。DMA 最多会写多少字节？若改成循环模式，前一次的 TC 能保护后面的变量吗？

<details>
<summary>展开答案</summary>

128 项 × 2 字节 = 256 字节，而数组只占 128 字节，后半段越过数组边界。TC 只描述这次被配置的 128 项已经搬完，不知道 C 数组的边界；循环模式还会重复这种错误。正确做法是容量、数据宽度、元素数一起核对，长度应为 64，并保证数组地址可达、对齐与生存期都正确。

</details>
