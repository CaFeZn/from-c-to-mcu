# 从协作式到抢占式调度

LED 单独运行时很准，加入一次较长的屏幕刷新后，按键响应突然慢了。1 ms 定时中断仍在计数，程序也没有死循环；只是主循环要先等刷新函数返回，才能检查按键。

这是[5.2 软件定时器](/lessons/5-2)和[5.5 定时精度](/lessons/5-5)之后常遇到的瓶颈：知道“到点了”，不等于“现在就有机会运行”。调度讨论的是谁获得 CPU，以及当前代码在什么条件下交还 CPU。

## 用同一份输入比较三种做法

给定两个任务，先忽略中断与切换开销，用整数毫秒作为模型时间：

- L：低紧急度的批量处理，时刻 0 就绪，需要 8 ms CPU。
- H：高紧急度的按键响应，时刻 2 就绪，需要 1 ms CPU，要求不晚于时刻 5 完成。

**一次跑到底的协作式调用**：L 从 0 跑到 8；主循环随后发现 H，H 从 8 跑到 9。H 的响应等待为 6 ms，完成时已经超过截止时间。定时中断即使在时刻 2 准确地置了标志，也不能迫使主循环立即从普通函数跳出来。

**拆成小步的协作式调度**：每次只让 L 做 1 ms 的工作，返回调度循环，优先检查 H。这个给定输入里，H 可以从 2 跑到 3。改善来自 L 主动交还控制权，不是 CPU 自动知道哪个任务更紧急。若 H 在一个小步刚开始后到达，仍需等该小步结束。

**抢占式调度**：H 在时刻 2 就绪后，调度器暂停 L，让 H 从 2 跑到 3，再恢复 L 的剩余 6 ms。L 到时刻 9 完成。H 更及时了，L 并没有凭空少做一毫秒工作。


```text
时间区间        0 1 2 3 4 5 6 7 8
整段协作式      L L L L L L L L H
固定优先级抢占  L L H L L L L L L
```

配套 `examples/notes/core/test.c` 用顺序 C99 模拟两条时间线，断言 H 在协作式模型中于 9 完成，在抢占式模型中于 3 完成；它不是 RTOS，也不启动宿主线程，因而不会把操作系统的偶然时序当成证明。

## 先把函数改成愿意返回的样子

引入 RTOS 之前，先检查能否把工作拆成明确的状态。串口命令处理不要“进函数后一直等完整命令”，而是每次处理已有的少量字符，状态保存在对象里，然后返回。刷新屏幕可按行或小块推进，而不是用一次调用长期占住主循环。

这种运行到完成的小步模式，可以只用 C99 函数指针和对象状态实现：


```c
typedef void (*step_fn)(void *context);
typedef struct { step_fn step; void *context; } task_t;

void run_one_round(task_t tasks[], unsigned count)
{
    for (unsigned i = 0; i < count; ++i) {
        tasks[i].step(tasks[i].context);
    }
}
```

这个接口的契约比代码更重要：每个 step 都必须在有上界的短时间内返回，不能等待一个依赖“后面的 step”才能满足的条件。数组先后只是调用顺序，不是能够打断当前函数的优先级。

还要给本轮总耗时记账。若一轮包含很多小步，一个刚检查完的任务仍可能等到下一轮；有上界的小步不自动等于整个轮转满足截止期。可按紧急度分层检查，但必须知道最坏阻塞来自哪个不可中断区段。

协作式并不等于“系统没有中断”。ISR 仍会打断这些函数；协作说的是任务之间交还 CPU 的方式。因此主循环和 ISR 的共享数据问题仍然存在，只是两个普通任务之间的交错点相对明确。

## 抢占式调度多保存了什么

普通函数返回前，局部变量和调用链还在同一条执行流上。抢占式任务被暂停时，却可能正位于深层调用中，调度器必须保留它的栈、寄存器及恢复位置，之后像没被打断一样继续。这些保存的信息叫任务上下文。

Cortex-M4 的异常入口硬件会保存基本栈帧，但并没有替 RTOS 保存全部任务上下文。以核对过的 FreeRTOS V11.1.0 GCC ARM_CM4F 移植为例，PendSV 处理代码还保存 R4–R11、相应的异常返回信息，并在需要时处理额外浮点寄存器，再切换任务控制块里的栈指针。任务使用 PSP，异常处理使用 MSP；具体约定属于移植层，而不是任意 C 函数自动具备的能力。

PendSV 常被配置成很低的异常优先级，用于在合适的异常边界完成切换；SysTick 可推进内核节拍并请求 PendSV。系统也可以由其他定时器提供 RTOS tick。不要把“抢占”误解为“每个 tick 轮流执行一个函数”：高优先级任务因事件从阻塞变就绪，也可能请求调度，不必只等下一次时间片。

因此，在定时器 ISR 里轮流调用几个普通任务函数，并不是构造了完整的抢占式线程系统。它只是把大量业务移进中断；没有独立栈、阻塞语义和正确保存恢复，反而更容易造成中断风暴。

## 优先级不是 CPU 百分比

在固定优先级抢占策略下，运行的是最高优先级的就绪任务。高优先级任务如果永远就绪、又不阻塞等待，低优先级任务就可能永远得不到运行。一个“不断检查是否有数据”的高优先级忙等任务，常比一个会阻塞等待通知的任务更危险。

要把三种状态分开：正在运行；可以运行但尚未轮到；等待时间或事件因而暂时不可运行。延时或等待队列通常把任务置为阻塞，让别的任务使用 CPU；在 while 循环里反复检查一个标志则可能仍处于就绪状态。

同优先级的时间片轮转是否开启、时片多长、任务主动让出后的行为，都取决于内核配置。本篇的时间线只假定固定优先级和两个任务，不把某个 RTOS 默认配置当作所有系统的规则。

MCU 的 NVIC 优先级与 RTOS 任务优先级也不是一张表。IRQ 先由 NVIC 处理，任务由内核选择。内核通常限制哪些中断优先级可以调用其 ISR 版本 API；应查当前移植的最大系统调用中断优先级与相关配置，不能只把名字改为 FromISR 就从任意紧急中断中调用。

## 及时性换来了新的共享资源责任

协作式下，A 的某段普通代码可能因没有显式返回而不会与 B 交错；换成抢占式后，这个隐含假设消失了。格式化缓冲、链表、驱动句柄甚至“先检查空闲再占用”的两行代码都要重新审核。

互斥量可以保护任务共享资源，但不是让 ISR 去等待它。持锁任务被更高优先级任务抢占，而后者又等待同一锁时，必须依靠正确的阻塞和调度协议，不是忙等；优先级继承可缓解某类优先级反转，却不能让任意长临界区没有代价。

每个任务还需要栈空间。函数最深调用、局部数组、库函数和浮点上下文都会影响栈预算；“单独任务运行过一次”不是并发压力下不溢出的证据。切换、节拍与同步也有时间成本，抢占式并不会增加 CPU 总算力。

## 练习：平均占用低，为何仍超时

L 每 100 ms 运行一次，整段耗时 8 ms；H 每 20 ms 运行一次，耗时 1 ms。总平均 CPU 占用仅约 13%。为什么整段协作式下，H 仍可能无法在到达后 3 ms 内完成？拆步时应优先量什么？

<details><summary>展开答案</summary>

平均利用率并没有限制一次连续阻塞的长度。H 若恰好在 L 开始后到达，可能要等待接近 8 ms，再做自己的 1 ms。拆步首先量最长不可让出的区段和主循环一轮的最坏耗时，再把其他中断、临界区与 H 自身执行时间计入响应预算。提高时钟或增加缓冲可以帮助某些负载，但不是对该调度上界的直接证明。
