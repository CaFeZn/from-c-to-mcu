# PWM与预装载

一盏灯原本以 25% 占空比发光，你把比较值改成 750，想让下一周期亮到 75%。示波器却可能在当前周期后半段又看到一次上升沿。平均亮度看起来没错，单个脉冲却已经变形。问题不在计算除法，而在于：**新值什么时候交给正在工作的比较器？**

以下固定为 STM32F407 的 TIM3_CH1，内部时钟、向上计数、边沿对齐、PWM 模式 1、高电平有效。通道和 GPIO 复用已正确启用，不使用外部清除信号。换模式、极性或高级定时器后，不能直接沿用全部结论。

## 先把一圈数出来

输入为定时器时钟 84 MHz、`PSC=83`、`ARR=999`、`CCR1=250`。计数时钟是 1 MHz，每格 1 us；CNT 依次经历 0 到 999，共 1000 格。PWM 模式 1 的内部参考信号在 `CNT < CCR1` 时有效，因此预期周期 1 ms、高电平 250 us、占空比 25%。

在纸上列出 `CNT=0、249、250、999` 四个位置，输出应分别为高、高、低、低。这里比较的是当前生效值，不一定是调试器刚读回的写入值。频率与占空比为：

```text
fPWM = fTIM / ((PSC + 1) * (ARR + 1))
D = CCR1 / (ARR + 1)  [0 <= CCR1 <= ARR + 1]
```

现在等 CNT 到 600，把 CCR1 从 250 改成 750，暂时假设写入立即生效。原来 250 到 599 已经是低电平；新比较值生效后，600 又小于 750，输出重新变高，到 750 才变低。同一圈出现两段高电平，不能称为“完整的 75% 周期”。实际寄存器总线写入相对计数边沿的位置会有偏差，这个整数时刻例子只负责展示机制。

## 两份数值，一次交接

解决办法是把“软件准备的下一份配置”和“本周期正在使用的配置”分开。前者叫预装载寄存器，后者常称影子寄存器或有效寄存器。它们不是需要你自行分配的两个 C 变量，而是定时器内部的缓冲机制。

| 对象 | 缓冲控制 | 何时交给计数或比较逻辑 |
|---|---|---|
| PSC | 固有缓冲 | 更新事件时 |
| ARR | `CR1.ARPE` | 开启缓冲后，在更新事件时 |
| CCR1 | `CCMR1.OC1PE` | 开启缓冲后，在更新事件时 |

开启 `OC1PE` 后，仍在 CNT=600 写 750。预期本周期维持原来的 250 格高电平；到自然回绕的更新事件，750 才进入有效寄存器，下一周期高电平才变成 750 格。软件读取 CCR1 可能已经读到 750，所以仅凭寄存器面板的新值不能判断引脚已经切换。

可跟做的验证分两层：先按上面的四个位置和改写时刻手算，再在已有 PWM 工程里保持 ARR 不变，启用输出比较预装载，用示波器观察一次 250 到 750 的切换。预期看见一个完整的 25% 周期接一个完整的 75% 周期。关闭预装载的情形只是解释风险的对照，不是本文建议的连续 PWM 配置；手册要求按 PWM 配置启用相应预装载。没有示波器时，LED 亮度不足以验证有没有短脉冲。

## 改频率还需要成组提交

假设当前 `ARR=999、CCR1=500`，目标是 `ARR=499、CCR1=250`，让频率从 1 kHz 变成 2 kHz 而保持 50%。同时开启 ARPE 和 OC1PE 很必要，但不意味着两次 CPU 写入成为一次事务：

| 顺序 | 发生的事 | 已生效的 ARR / CCR1 |
|---|---|---|
| 1 | 写 ARR 预装载为 499 | 999 / 500 |
| 2 | 恰好发生自然更新 | 499 / 500 |
| 3 | 写 CCR1 预装载为 250 | 499 / 500 |
| 4 | 再发生一次更新 | 499 / 250 |

中间那圈的 CNT 只有 0 到 499，却始终小于 500，于是出现一个 100% 周期。预装载保证各值在更新边界切换，**不保证更新边界一定在你写完全部值之后**。即使关掉 CPU 中断，定时器也会继续计数，问题仍可能发生。

对于独占 TIM3 的简单输出，可以在写两个预装载值之前设置 `CR1.UDIS=1`，写完再恢复为 0，让下一次自然更新统一接收。需要先确认原本允许更新，并确保中断、DMA、其他通道管理代码不会并发改这组配置。UDIS 阶段计数仍按旧参数循环，但更新事件被禁止，相应更新请求也会缺失；若同一定时器还承担系统节拍或触发其他设备，这种方案就有副作用。

另一种方案是停止输出和计数后统一重配，再开始新周期，但它明确接受输出中断。需要严格连续且高速成组更新时，应另行设计 DMA、同步与截止时刻，不能把“写得够快”当证明。本文模型只演示 UDIS 阻止交接的情况，不提供可任意嵌入现有固件的驱动。

## 启动前的更新与运行中的更新不同

预装载值不会凭空变成有效值。初始化通常在计数器停止时配置 PSC、ARR、CCR，然后通过 `EGR.UG` 触发一次更新，使首个周期使用正确参数。使用 HAL/CubeMX 时应检查生成的初始化顺序，不要不分场合再追加一遍。

运行中写 UG 不只是“立刻提交”：它还会重新初始化 CNT 和预分频计数器，当前周期可能被截短。根据 URS、UDIS 等设置，还可能置 UIF 并产生请求。要保证完整周期，一般等待自然更新；不要在每次设置亮度后无条件写 UG。URS 选择哪些来源产生更新请求，不等于关闭预装载传输。

## 三个容易越界的地方

**满占空比受寄存器宽度限制。** 对本模式，CCR1=0 是恒低，CCR1 大于 ARR 是恒高。ARR=999 时写 1000 没问题；但 TIM3 是 16 位通道，ARR=65535 时，数学上的 ARR+1=65536 无法装入 CCR1。把 C 变量改为 32 位也不会增加硬件位数，不应写入保留高位。可限制 ARR 不超过 65534，或为恒有效输出设计单独的模式切换路径。简单把值限制到 65535 只会得到接近 100%，并非恒高。

**频率和分辨率要一起看。** 计数时钟固定为 1 MHz 时，周期从 1000 格减到 100 格，占空比步长就从 0.1% 变成 1%。提高频率不会白送更细亮度等级，整数除法还会让目标频率发生量化误差。

**内部参考信号不等于任意引脚电压。** 极性、通道使能、GPIO 复用和外部接线都影响实际输出。低电平点亮的 LED 看起来会反向；TIM1/TIM8 还涉及主输出、互补输出和死区，不能套用 TIM3 的接线结论。中心对齐模式的计数轨迹也不同，不能直接套用本篇周期公式。

## 练习：预装载到底保住了什么

当前 ARR=999、CCR1=200，ARPE 和 OC1PE 均开启。CNT=800 时写 CCR1=600，但不写 UG。当前圈和下一圈高电平各有多少格？若同时把 ARR 改成 399，并把目标占空比改为 50%，应怎样配置才能避免出现混合值？

<details><summary>展开答案</summary>

只改 CCR1 时，当前圈仍是 200 格，下一圈才是 600 格。目标 ARR=399 表示一圈 400 格，50% 对应 CCR1=200，而不是沿用 600。先确定这组寄存器由一个上下文管理，在允许短暂禁止更新且不会破坏其他用途的前提下，用 UDIS 包住两次预装载写入，恢复后等待自然更新。若当前已有待提交的 600，也必须在受保护阶段覆盖它。直接依次写两个值、仅关闭 CPU 中断或强行写 UG，都不能同时保证成组提交和当前周期完整。
