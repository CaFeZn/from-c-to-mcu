# 汇编如何读写寄存器

调试器里执行了 `movs r1, #32`，R1 的确变成了 32，PA5 却没有变化。再执行一条 `str r1, [r0, #24]`，才可能改变输出。两条指令都在“写寄存器”，为什么效果差这么远？因为 R1 是 CPU 内部暂存数据的寄存器，而 GPIO 的 BSRR 是通过地址总线访问的外设寄存器。两者同名，不在同一个位置，也不靠同一种指令操作。

本篇用 F407 的 PA5 做地址演算，不假定开发板恰好把 LED 接在 PA5。已有示例可以在没有板子的电脑上交叉汇编，但真正改变引脚还要求 GPIOA 时钟已开启、启用延迟已满足、PA5 配成合适的输出模式，并且没有其他执行者同时控制该引脚。以下函数不负责这些初始化工作。

## 一条写操作之前发生了什么

GNU 汇编文件的核心片段如下。完整文件还包含 Thumb 函数标记、符号导出和函数大小声明，见[配套示例](https://github.com/CaFeZn/from-c-to-mcu/tree/main/examples/notes/platform)。这是独立汇编函数，不是可以原样粘进 C 函数的内联汇编字符串。

```asm
.syntax unified
.cpu cortex-m4
.thumb

pa5_high_asm:
    movw r0, #0
    movt r0, #0x4002
    movs r1, #32
    str r1, [r0, #24]
    bx lr
```

先盖住最后两行，逐步记录数值：`movw` 将 16 位立即数放入 R0 的低半部，并把高半部清零；`movt` 只改高 16 位，保留低半部。所以 R0 最终是 `0x40020000`，不是 `0x00004002`。R1 则等于 `0x00000020`，即第 5 位为一。到这里还没有发出 GPIO 写请求。

方括号表示一次内存寻址。`str` 的有效地址为：

```text
R0 + 24 = 0x40020000 + 0x18 = 0x40020018
写入值  = R1 = 0x00000020
```

`str` 在这里发出一个 32 位写访问；它不会把 R0 改为加完偏移的地址。手册规定 `0x40020018` 是 GPIOA 的 BSRR，低 16 位中的一请求设置对应 ODR 位，高 16 位中的一请求复位对应 ODR 位。因此这次请求设置 PA5 的输出锁存位。最终管脚电压还受模式、输出类型、外部负载和供电影响，不能只靠 R1 的数值判断。

`bx lr` 返回调用者。这里使用 R0、R1 作为临时寄存器符合普通 Arm C 调用接口的用法；没有改写需要被调用者保存的 R4 等寄存器。若自己加入嵌套调用，就必须重新处理返回地址和栈对齐，不能以为末尾永远加一条 `bx lr` 就够了。

## 读地址，和读地址指向的内容

读取输入的函数使用另一种常见写法：

```asm
pa5_input_asm:
    ldr r1, =0x40020000
    ldr r0, [r1, #16]
    lsrs r0, r0, #5
    and r0, r0, #1
    bx lr
```

两行 `ldr` 不要混为一谈。带等号的第一行是汇编器伪指令，要求把常量地址放进 R1；工具可能使用立即数指令，也可能从代码附近的常量池读取它。本组工具实际生成了 PC 相对的 `ldr`，常量池里存着 `0x40020000`。这次访问的对象是常量池，不是 GPIOA。

第二行才按 R1 加 `0x10` 访问 GPIOA 的 IDR。如果给定一次采样得到 `IDR = 0x000000A0`，右移 5 位得到 5，再与 1 相与，返回值为 1；若采样值为 `0x00000080`，返回值为 0。R0 作为整数返回值交给 C 调用者。`lsrs` 还会更新部分状态标志，但本函数没有依据它们跳转。

这里读到的是那一次访问的输入状态，不是永久稳定的按键值。硬件同步和机械抖动仍然存在；不要用 CPU 运算速度很快推导出“只读一次就消抖”。同样，把 IDR 换成有读清除行为的状态寄存器时，重复读本身就可能改变外设状态。

## 不上板也能验证到哪一层

在已经配置 ARM 工具链的终端中，从仓库根目录执行：

```sh
arm-none-eabi-gcc -mcpu=cortex-m4 -mthumb -c \
  examples/notes/platform/register_access.s \
  -o artifacts/course-completion/platform/register_access.o
arm-none-eabi-objdump -dr \
  artifacts/course-completion/platform/register_access.o
```

本次实际交叉汇编成功。输出包含 `movw r0, #0`、`movt r0, #16386` 和 `str r1, [r0, #24]`。其中十进制 16386 就是 `0x4002`，不是工具改错了常量。读取函数也保留了偏移为 16 的 `ldr`。这些结果证明工具接受指令，并按照目标架构编码了访问；没有证明 RCC 已开启、线路接对或 LED 已点亮。

配套 PC 测试进一步把 BSRR 规则写成普通整数模型。给定 ODR 为 `0x0002`，写请求 `0x00000020` 后预期为 `0x0022`；再请求 `0x00200000` 后回到 `0x0002`。这说明复位 PA5 的一必须在第 21 位，而不是给低半部写零。模型解释协议，不能代替物理 GPIO。

## 为什么不能随手改成读改写

若用 ODR 完成置位，通常需要 `ldr` 读原值、`orr` 修改 CPU 中的副本、`str` 写回。假设主循环读到 `0x0002` 后被中断，中断把 PA7 设为一，ODR 变成 `0x0082`；主循环恢复后仍把旧副本加上 PA5，写回 `0x0022`，便覆盖了 PA7 的更新。单条 32 位写指令不等于前面整个读改写过程不可分割。

对 BSRR 直接写 `0x20` 只请求 PA5 置位，不把其他引脚旧状态带回来。但这不代表所有并发问题都消失：两个执行者若都控制 PA5，最后状态仍取决于请求顺序；两个相关外设的操作也不会自动合成事务。不要对这种命令寄存器使用 `|=` 来“保留原值”。

访问宽度也要查手册。F407 的 BSRR 支持手册列出的字、半字和字节访问，但不能据此推广到所有外设。某些寄存器要求指定宽度和对齐，错误的 `strb`、`strh` 或未对齐 `str` 可能不生效或产生总线错误。

另外，CPU 执行完存储指令、总线事务完成、引脚达到外部所需电平，是三个不同观察点。汇编没有 C 的 `volatile` 问题，却仍然受总线、器件时序和内存属性约束。需要屏障时按架构与芯片手册使用，不把随手插入的空操作当作通用修复。

## 练习：一次请求改变两个引脚

初始 ODR 为 `0x0082`。要求 PA5 置位、PA7 复位，同时保留 PA1，应该给 BSRR 写多少？如果把同一个请求写到 ODR，又会怎样？

<details><summary>展开演算与答案</summary>

PA5 置位请求是 `1u << 5`，PA7 复位请求是 `1u << (16 + 7)`，合起来是 `0x00800020`。按 BSRR 语义，最终 ODR 为 `0x0022`。若把该数写到 ODR，低 16 位只有 `0x0020`，PA1 也会被写成零；高半部不再代表复位命令，并且不能依赖向保留位写一的行为。相同数值写到不同地址，是不同的硬件协议，不能只检查值而不检查目标寄存器。

</details>
