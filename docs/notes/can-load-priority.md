# 总线负载与优先级设计

系统平均总线负载只有几个百分点，一条要求300 μs内发完的控制命令却偶尔超时。把位率再提高一档之前，先问：命令到来那一刻，总线上是不是已经有一帧开始了？CAN优先级能决定下一轮谁先发送，**不能把正在发送的低优先级帧切成两半**。

本篇从 [7.2 CAN仲裁与帧](/lessons/7-2) 的负载估算继续。范围是经典CAN正常数据帧，默认节点错误主动、无错误重传，计入正常3位Intermission。工程中的错误、过载、软件排队和被动节点额外等待要另列，不能藏在平均值里。

## 先确定“占用时间”包含什么

只算8字节数据有64位，却漏掉ID、控制字段、CRC、ACK、帧结束和填充。标准数据帧从SOF到EOF，不计位填充为`44 + 8d`位；再计3位帧间歇，得到`47 + 8d`。其中d为0–8字节。

从SOF到CRC序列结束的`34 + 8d`个原始位参加经典CAN位填充：连续5个相同位后插入相反位。插入位也影响后续连续位计数，所以不能简单地把原始位数除5。一个便于预算的保守界为：

```text
标准数据帧：
L = 34 + 8d                         可填充区原始位数
B = 47 + 8d + floor((L - 1) / 4)   含帧间歇的保守位数
C = B / bitrate                    保守总线占用秒数
```

这个界不尝试利用ID、DLC和CRC之间的约束证明某种位型必定达到上界。称它为**保守预算**比称每帧都恰好这么长更准确。扩展数据帧的基础开销多20位，对应`67 + 8d + floor((54 + 8d - 1)/4)`。不要把经典CAN公式套到CAN FD，其速率阶段、CRC和填充机制不同。

## 运行一个小计算器

下面是完整C99例子，固定比较0、4、8字节的标准与扩展数据帧；无外部输入，不做总线模拟：

```c
#include <assert.h>
#include <stdio.h>

static unsigned frame_bound(unsigned d, int extended)
{
    const unsigned extra = extended ? 20u : 0u;
    assert(d <= 8u);
    return 47u + extra + 8u * d
         + (34u + extra + 8u * d - 1u) / 4u;
}

int main(void)
{
    for (unsigned d = 0u; d <= 8u; d += 4u) {
        printf("d=%u std=%u ext=%u\n", d,
               frame_bound(d, 0), frame_bound(d, 1));
    }
    assert(frame_bound(8u, 0) == 135u);
    assert(frame_bound(8u, 1) == 160u);
    return 0;
}
```

预期三行分别为`d=0 std=55 ext=80`、`d=4 std=95 ext=120`、`d=8 std=135 ext=160`。500 kbit/s下每位2 μs，所以标准8字节帧按270 μs、扩展8字节帧按320 μs预算。

本文的断言用于固定有效输入。若把函数暴露给网络配置工具，必须在运行时拒绝d大于8，不能依赖可能被`NDEBUG`禁用的断言。远程帧没有数据字段，不能拿它的DLC直接代入本数据帧公式。

## 先算长期平均量，再检查最坏时刻

设计三种标准数据帧：

| 消息 | ID | 字节 | 周期 | 保守占用 |
|---|---|---|---|---|
| 控制cmd | `0x080` | 3 | 10 ms | 85位，170 μs |
| 状态state | `0x180` | 8 | 20 ms | 135位，270 μs |
| 诊断diag | `0x600` | 8 | 100 ms | 135位，270 μs |

周期流的估算负载为`U = Σ(Ci / Ti)`。本例：

```text
cmd   : 170 / 10000  = 1.70%
state : 270 / 20000  = 1.35%
diag  : 270 / 100000 = 0.27%
合计                    3.32%
```

这是正常周期通信的保守平均占用，不含事件突发与错误重发。现在制造一个合法但不走运的时刻：diag刚开始发送，cmd紧接着产生请求；state也在等待。没有其他帧到达，队列容量足够。

```text
最坏预算时间轴：
0                270            440                 710 μs
| diag已在发送    | cmd           | state              |
                  下一轮cmd以较小ID先赢
```

用一整帧270 μs作为cmd可能遭遇的低优先级阻塞上界，再加自身170 μs，得到约440 μs的释放到传输完成预算。哪怕平均负载只有3.32%，也无法凭此保证cmd的300 μs截止时间。真实阻塞会少一点，因为cmd在diag开始后才到达；预算仍应按不利相位留足余量。

注意：这条时间线只验证**给定一次到达序列**。如果等待期间还有更高优先级帧反复到达，需累计它们的干扰；若有释放抖动、同一流积压多帧或重传，则需要更完整的最坏响应时间分析。把`U < 100%`当成所有截止时间都满足，是两个不同问题混为一谈。

## ID是消息优先级，不是越小越“高级”

设计先列消息的最小到达间隔、允许延迟、抖动、有效期和失效后果，再分配优先级。短截止时间的控制量通常比日志更急，但“故障消息”若能高频无界触发，也会把其他控制量饿死，必须规定合并、限速和重复策略。

同格式下较小ID在同轮竞争中获胜；混合标准/扩展时须按线上仲裁位比较。某协议已固定COB-ID或功能码时，不能为抢优先级随意改掉。也不能让两个独立生产者为了优先级共用一个ID发送不同内容。

对本例的300 μs目标，可以考虑降低允许的最长低优先级帧占用、调整满足电气条件的位率、重新定义截止时间，或用有计划的释放/调度机制降低阻塞。仅把cmd从`0x080`改成`0x001`没有帮助：它已经比diag优先，但仍不能抢占已开始的帧。

## 总线优先级前面还有软件和邮箱

bxCAN有三个发送邮箱。F407的MCR.TXFP=0时，待发送邮箱通常按标识符优先级选择；TXFP=1时按请求先后选择。**这是节点内部选择规则，不改变全网仲裁规则。** 若应用把紧急帧压在软件FIFO的一长串日志之后，或三个邮箱都被低优先级帧占着，它可能尚未进入硬件候选集。

不要把“发送API返回成功”当作时延终点。测量至少区分业务产生、软件入队、硬件受理、发送完成、对端应用确认。记录队列峰值、超期丢弃、邮箱忙次数和帧完成时间，比每秒只打印一个负载百分比有用。

对周期状态，常见策略是只保留最新值，避免恢复通信后逐个发送过期状态；对必须逐次执行的命令，则可能需要序号、确认和有限重试。两者不能都用一个“队列满就永远重试”的策略。ACK不负责这些业务保证。

## 不能省略的容量边界

- **接收过滤不降总线负载。** 它减少本节点CPU需要处理的消息，线上的传输时间已经发生。
- **不能靠100%利用率规划可靠系统。** 需要给突发、重传、时间偏差和诊断留余量；但“固定低于某百分比就安全”也不是普遍定理。余量要由需求和故障假设说明。
- **流量越界要有处理。** 日志洪水应限流，事件应定义最小间隔或合并窗口；必要时分网。低优先级无限等待是协议允许的现象，不是编译优化问题。

## 练习：低负载为何仍可能来不及

将cmd周期从10 ms改成5 ms，其他不变。新的估算负载多少？给定的diag阻塞场景下，cmd完成上界会自动减半吗？如果低优先级最长帧改成0字节标准数据帧，阻塞加本帧约多少？

<details><summary>展开答案</summary>

cmd变成3.40%，合计`3.40 + 1.35 + 0.27 = 5.02%`。周期改变不自动缩短一帧已经开始后的阻塞，单次给定场景仍按约440 μs估算。0字节标准数据帧预算55位，即110 μs；本例无其他干扰时，110+170=280 μs。但实际系统还需计入软件延迟、更多到达与误差，280 μs不应直接宣告整机满足300 μs。
