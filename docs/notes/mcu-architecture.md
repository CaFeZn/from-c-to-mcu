# 【原理】单片机内部结构

> **类型**：二级分支（建议读）　｜　**前置**：[[2.1_单片机里有什么]]
> **读完你能回答**：一次取指或数据读写怎样到达目标？Flash 为什么不必先整体搬到 RAM？复位后，谁把程序带到 main？
> 回到 [[00_教程导览]] ｜ 全部分支见 [[分支总表]]

## 先看一个不靠电脑也会发生的过程

把固件写进主 Flash 后，单片机不需要 VS Code 一直给它发送下一条指令。在供电、启动配置正确的前提下，复位后它能自己重新运行程序。

可是，Flash 只是存储器。它不认识 C 语言，也不会替你做加法。真正的问题是：**内核怎样拿到 Flash 里的指令，又怎样让另一块硬件发生变化？**

本篇以 STM32F407 为对象。动画只跟随几条选定的访问和启动动作，不是周期精确的芯片仿真；没有开发板也能先观察。仲裁、流水线重叠、缓存细节和完整时钟树会被省略，不要把“一步动画”理解成“一个时钟周期”。

GPIO 示例预先假定端口时钟已经开启、PA5 是推挽输出，且没有外部电路强行拉住它。**不是说复位后的任意引脚都已经这样配置好了**，也没有假定 PA5 一定连接你的板载 LED。

> [!question] 先猜一猜
> 指令执行后，一个位于 SRAM 的变量从 7 变成 8，Flash 中保存的变量初值也必须改成 8 吗？

> [!success]- 揭晓
> 不必。内核可以从 Flash 取指，再对 SRAM 发起数据读写。指令存放的位置、变量运行时所在的位置，不必是同一块存储器。

### 把图里的名字认清

| 部分 | 负责什么 | 容易误会的地方 |
|---|---|---|
| 内核 | 取指、解码、执行，使用 ALU 和内核寄存器工作 | Cortex-M4 是内核，不是整颗 STM32 芯片 |
| Flash | 保存断电后还要保留的机器指令、只读数据和一些初值 | 它提供内容，执行内容的是内核 |
| SRAM | 保存运行时数据，例如可写变量、栈和缓冲区 | 上电后的原始内容不能当作已经初始化的 C 变量 |
| 外设 | GPIO、定时器、串口等专门的电路 | CPU 不必逐条指令模拟它们的全部工作 |
| 总线与桥 | 传递地址、读写方向、数据和响应，连接不同模块 | 不是所有模块都能同时占用同一条通路 |
| 时钟与复位控制 | 提供模块所需时序，控制复位和使能 | 写对地址，不代表工作条件已经具备 |

图中的 R0、PC 属于**内核寄存器**；GPIOA 的 ODR、BSRR 属于**外设寄存器**。名字里都有“寄存器”，位置和职责不同。下一篇专门展开后者。

## 二、一张地址表，不等于只有一条总线

“地址空间”回答的是：**这个地址表示访问哪里？** “总线连接”回答的是：**请求通过哪些接口到达那里？**

Cortex-M4 区分了 I-Code、D-Code 和 System 等接口。在本篇涉及的典型访问中：

- **I-Code**：访问代码区域的指令，例如从主 Flash 取指。
- **D-Code**：访问代码区域中的数据，例如读取放在 Flash 里的常量。
- **System**：访问 SRAM、外设等；在允许的存储区域中也可承担取指，不能简单理解为“永远只读变量”。

这些接口接到 STM32 的片上互连、存储器接口和外设接口。F407 有多层 AHB 总线矩阵和 AHB/APB 桥。动画中的 I-Code 和 System 两列表示经同一矩阵的不同访问通路，不是两块不同的矩阵，也没有完整画出全部主设备与从设备端口；GPIO 位于 **AHB1**，许多定时器、串口等位于 APB。不要把所有外设都画成经过同一个 APB 桥，也不要把另一款 STM32 的框图直接当作 F407。

实际芯片还有 DMA 等其他访问发起者。DMA 可以按配置搬运数据，不必让 CPU 对每个字逐个执行复制指令；但它能访问什么、怎样竞争总线，仍由具体芯片连接决定。动画只展开 CPU 发起的几条请求。

### 请求不是喊出一个地址就结束

一次访问涉及地址、读写方向、数据和目标响应。硬件用**地址译码**选择对应模块；忙不过来时还会有等待和仲裁。

从源代码的一行到引脚变化，中间存在真实的传输和时序。动画把过程慢放、拆开，真正的内核可能在流水线中重叠处理多件事。

## 三、Flash 为什么能直接执行

先把这句话补完整：**内核可以从映射到地址空间中的 Flash 读取机器指令，然后在内核里执行。**

例如，PC 指向 Flash 中的一段代码：

1. 内核发出取指请求。
2. 芯片根据地址把请求送到相应的 Flash 接口。
3. Flash 接口把机器指令提供给内核。
4. 内核解码、执行；下一条指令的位置可能顺序推进，也可能因跳转改变。

图中用汇编文字帮助辨认指令，Flash 实际保存的是机器指令编码，不是需要逐句解释的 C 源文件。

**这里没有“必须先把全部代码复制到 SRAM”这一步。** 代码留在原存储位置供内核取指，通常称为就地执行（XIP）。它说的是取指方式，不是说 Flash 自己会计算。

> [!tip] 能直接取指，不等于没有等待
> Flash 的访问速度并不总能跟上内核的每一次需求。F407 的 Flash 接口、ART 加速、预取等机制用于改善访问；等待周期还与频率、电压和配置有关。本篇不把它简化成“Flash 与 SRAM 一样快”。

也不能推断所有带 Flash 字样的器件都能这样执行。普通 SPI Flash 需要相应控制器读数据，不会仅因接在 SPI 引脚上，就自动变成内核可直接取指的区域。是否支持映射取指，要看控制器和内存属性。

动画使用选定的教学布局。实际函数地址、变量地址和栈顶由启动文件、链接脚本决定，不要把动画地址直接复制进自己的工程。

### 硬件先读向量，不是立即调用 main

在本例启动映射下，低地址 `0x00000000` 对应主 Flash 开头 `0x08000000`。内核从向量表开头取得必要信息：

| 向量表位置 | 本例内容 | 用途 |
|---|---|---|
| 开头第一个字 | 初始 MSP `0x20020000` | 建立主栈指针；本例选在普通 128 KiB SRAM 的顶端 |
| 接下来一个字 | 复位入口值 `0x08000201` | 进入 Reset_Handler；最低位用于表示 Thumb 状态 |

本例实际指令入口是 `0x08000200`，不是从奇地址 `0x08000201` 随意读取指令。向量中的最低位与指令状态有关，不要为了“地址对齐”把它清掉。

Reset_Handler 也不自动等于 main。它先运行启动代码，建立后面 C 程序需要的条件。启动之后，软件还可以按规则用 VTOR 指定异常向量表的位置；这不等于 PC 每次取指都去读向量表。

### 初值复制与取指，是两件事

用两个全局变量作为观察对象：

```c
#include <stdint.h>

volatile uint32_t counter = 7;
volatile uint32_t events;

int main(void)
{
    counter++;
    for (;;) {
        (void)events;
    }
}
```

这里用 volatile 保留对演示变量的访问，便于观察；它不让代码变成“多线程安全”。这段代码只说明初始化与访问，不包含完整板级启动工程。

在常见的这类链接布局中，可以把内容分为三类：

| 内容 | 断电后保存什么 | 运行时怎样使用 |
|---|---|---|
| 机器指令，通常归入 `.text` | Flash 中的指令编码 | 内核从 Flash 取指 |
| `counter` 的初值，通常是 `.data` 的加载内容 | Flash 中的初值 7 | 启动代码复制到 SRAM，变量随后在 SRAM 中改变 |
| 未显式赋初值的静态存储期变量 `events`，通常归入 `.bss` | 无需为每个零都保存一份初值数据 | 启动代码把对应 SRAM 区域清零 |

动画中的初值放在 Flash 示例位置 `0x08000800`，运行时 `counter` 在 SRAM 示例位置 `0x20000000`，`events` 在 `0x20000004`，main 的示例取指位置为 `0x08000400`。这些布局数值用于区分位置，不表示编译器总会这样分配。

请观察最后的区别：**RAM 中的 counter 从 7 变成 8，Flash 中供下次启动使用的初值仍是 7，代码也仍在 Flash 中。**

`.bss` 清零不是“SRAM 天生就是零”。函数里的普通局部变量如果没有初始化，也不能套用这里的规则。若绕过正常启动过程直接跳进 C 函数，就不能假定这些条件已经建立。

> [!info]- 完整启动顺序，以工程为准
> 除了复制 `.data` 和清零 `.bss`，还有系统初始化和 C 运行库初始化等工作。ST 的 GCC F407 启动模板先调用 SystemInit，再完成这两项数据初始化，然后调用运行库初始化并进入 main；不同工具链和工程模板需要分别核对。
> 动画只展开本篇需要区分的动作，不把简化轨迹当作完整启动模板。继续到 [[2.4_程序是怎么跑起来的]]，对照自己的启动文件和链接脚本。

## 五、为什么图上不能只写一个“RAM”

F407 的 RAM 不是把总容量排成一整段，就能从任意接口随便访问。

- 普通 SRAM1、SRAM2 可以供相应的系统访问，支持内核执行代码与 DMA 访问，但仍有具体通路和配置条件。
- F407 的 **64 KiB CCM 数据 RAM** 位于 `0x10000000`，走内核的数据通路，不在普通总线矩阵上，不能用来取指，也不能假定 DMA 能访问它。
- 因此，看到某个型号标称 192 KiB RAM，不能把从 `0x20000000` 开始的一整段 192 KiB 都当成连续、用途相同的普通 SRAM。

代码确实可以按需要放到允许执行的 SRAM 区域，但要安排正确的链接地址、复制过程与跳转。这是另一种布局选择，不是所有程序从 Flash 启动时自动发生的必需步骤。

## 六、把两条看似矛盾的话放在一起

“代码直接从 Flash 执行”和“启动时从 Flash 向 RAM 复制数据”，可以同时成立：

1. 第一条说的是**指令在哪里被读取**。
2. 第二条说的是**某些可写变量怎样得到初值**。
3. 加法、判断、跳转由内核执行；Flash、SRAM、外设分别响应与自己相关的请求。

还剩一个问题：为什么地址落到 GPIO 上，写入就会成为控制动作，而不是只多存一个数字？继续读 [[【原理】寄存器与内存映射|寄存器与内存映射]]。

## 自己推演一次

> [!question] 三个检查点
> 1. counter 已经变成 8。重新走正常启动流程后，为什么又从 7 开始？
> 2. 同一块 Flash 里有指令也有常量，CPU 是否永远用同一种访问读取它们？
> 3. 把需要 DMA 读写的缓冲区随便搬进 F407 的 CCM，为什么可能不工作？

> [!success]- 对照答案
> 1. 运行时副本在 SRAM；正常启动重新使用 Flash 中保留的初值。要保存跨掉电的新值，需要另行设计非易失存储方案。
> 2. 不是。取指与读常量是不同目的的访问，Cortex-M4 提供不同接口，具体连接还取决于芯片集成。
> 3. 容量不等于可达性。F407 的 CCM 是内核数据通路上的存储，不能假定 DMA 和 CPU 有相同的访问能力。
