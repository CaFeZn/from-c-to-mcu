# 环形缓冲区

主循环去处理一次耗时任务，回来时串口已经漏了几个字符。把中断改成收到字符就立即执行命令，又让更紧急的中断延迟了。需要的不是让两边互相等待，而是给“字节到达”和“字节被处理”之间放一个有明确容量的队列。

[6.1 串口命令行](/lessons/6-1) 中的接收器正这样工作：中断交字节，主循环取字节。本篇先在单线程里证明队列不会把旧数据覆盖掉，再讨论移入中断时额外需要什么。**数组下标算对和并发安全是两个不同的问题。**

## 八个格子，先手推一圈

用一个容量为 8 的数组。`head` 记录累计放入的个数，`tail` 记录累计取出的个数，二者都是无符号 32 位数。存储下标使用 `计数器 & 7`，计数器本身不在数组边界处清零。

先执行这组固定操作，预测最后读到的顺序：放入 0 到 7；再尝试放入 99；取出三个；放入 8、9、10；一直取到空。

| 时刻 | head | tail | 待取数量 |
| --- | ---: | ---: | ---: |
| 初始化 | 0 | 0 | 0 |
| 放入 0 到 7 | 8 | 0 | 8，满 |
| 拒绝 99 后 | 8 | 0 | 8，未改旧数据 |
| 取出 0、1、2 | 8 | 3 | 5 |
| 放入 8、9、10 | 11 | 3 | 8 |
| 全部取完 | 11 | 11 | 0，空 |

最后一轮必须得到 `3 4 5 6 7 8 9 10`。此时数组物理位置可能是 `8 9 10 3 4 5 6 7`，但读取顺序由 `tail` 决定，不能从数组下标零直接向后打印。

## 把手算写成可验证的 C99

下面是算法核心，调用者保证对象和输出指针有效；初始化应发生在队列投入使用之前。本段**只用于顺序执行或已经受外部同步保护的调用**，没有声称可直接放入任意两个线程。

~~~c
#include <stdbool.h>
#include <stdint.h>

#define CAP 8u
typedef struct {
    uint8_t data[CAP];
    uint32_t head, tail;
} ring_t;

static bool ring_put(ring_t *r, uint8_t b)
{
    if ((uint32_t)(r->head - r->tail) == CAP) return false;
    r->data[r->head & (CAP - 1u)] = b;
    ++r->head;
    return true;
}

static bool ring_get(ring_t *r, uint8_t *out)
{
    if (r->head == r->tail) return false;
    *out = r->data[r->tail & (CAP - 1u)];
    ++r->tail;
    return true;
}
~~~

创建对象用 `ring_t r = {0};`。满时函数返回 `false`，调用者记录丢弃或稍后再试；空时也立即返回，不能在中断中循环等待主循环腾位置。这里用相等判断满，依赖“不允许占用量越过容量”的不变量；实际驱动若还要容错，可以对异常状态单独报错，但不能把损坏的索引当作正常拥塞继续写。

完整断言程序已收进本组独立例子，除了上述输入，还连续运行一万字节的不同生产、消费节奏。仓库根目录可运行：

~~~sh
cmake -S examples/notes/serial/core -B artifacts/course-completion/serial/core-build -G Ninja
cmake --build artifacts/course-completion/serial/core-build
ctest --test-dir artifacts/course-completion/serial/core-build --output-on-failure
~~~

预期测试全通过；直接运行测试程序会出现 `ring: empty/full/order/uint32-wrap/10000-byte schedule OK`。这些是顺序模型测试，不是硬件并发压力测试。

## 满和空为什么不会混淆

若只保存已经取模的下标，`head == tail` 既可能代表空，也可能代表转了一圈的满。这类实现通常留一个槽，容量 8 实际只能存 7，或另存满标志/计数。它们并不错误，但要让公式和容量说明保持同一套约定。

本例保留累计计数：空时差为 0，满时差为 8，因此八个槽都能用。始终保持三条约束：生产者只有成功写入才前进；消费者只有成功取出才前进；尚未消费的数据总量不超过 8。队列并不保存“绝对运行了多少字节”的历史，计数器只是用来区别当前这段有限距离。

无符号计数器最终会自然回绕。把初始 `head`、`tail` 同设为 `UINT32_MAX - 2u`，放入八字节后，`head` 变成 5，而转换回 `uint32_t` 的差仍为 8。不能换成有符号数指望溢出同样回绕，那会引入未定义行为。

两种回绕也别混淆：数组每八步回一次，计数器每 2^32 步回一次。容量取 2 的幂，使掩码取下标正确，而且容量整除计数器模数；距离正确还必须依赖未消费量始终有界。不是写了一个 `&` 就自动得到不会溢出的队列。若要任意容量，重新设计下标回绕或更宽的计数方案，不能只把 8 改成 10 而保留掩码。

## 从顺序模型到中断，需要补哪份约定

单生产者、单消费者常简称 SPSC。接收中断独占写 `head`，主循环独占写 `tail`，减少了多个执行者争抢同一索引的问题，但还有发布顺序：

~~~text
生产者：确认有空间 -> 写 data 槽 -> 发布新 head
消费者：确认有数据 -> 读 data 槽 -> 发布新 tail
~~~

若 `head` 先被另一方看到，而槽内容还没写好，就会读到上一圈的数据。若 `tail` 提前发布，生产者可能覆盖消费者还没拿走的内容。`volatile` 不能把普通数组访问与索引访问自动排成跨执行上下文的顺序；GCC 官方文档明确说它不是普通内存访问的屏障。

[5.4 中断与主循环共享数据](/lessons/5-4) 的板级示例使用 CMSIS 编译器屏障，其适用条件必须一起保留：单核 Cortex-M4、已确认的编译器实现、对齐的索引、唯一生产者与消费者，且初始化不与收发同时发生。不要把它的 `volatile` 字段单独抄走，就称为通用无锁库。

不熟悉发布/获取语义时，本课更保守的移植办法是让主循环和可屏蔽中断对上述顺序核心的每次操作都经过很短的、保存并恢复 PRIMASK 的临界区，并使用有编译器屏障语义的 CMSIS 实现。NMI/HardFault 不参与这个队列，DMA 也不会被关中断暂停。不能在区间内格式化、等 UART 或处理整条命令。

若目标是 C11 多线程，可使用原子索引与 release/acquire 建立数据发布关系；这属于 C11 扩展，不是本篇 C99 模型天然拥有的能力。RTOS、多核和缓存系统还要按各自内存模型验证，不能凭“32 位读写是单条指令”推断整个队列线程安全。

## DMA 发出去了，槽就可以重用吗

不可以。把 `tail` 开始的一段内存借给 DMA 后，该段仍由发送方占用，直到约定的传输完成条件满足。提前推进 `tail` 会让生产者改写 DMA 还没读完的数据。主线日志层把 `inflight` 和已完成的 `tail` 分开，正是为了管理这个生命周期。

环尾也可能把数据切成两段。例如 `tail=6`、待发 5 字节，第一次可发下标 6、7 的 2 字节，第二次再发下标 0、1、2。连续 DMA 不能把数组末尾后面的内存自动理解为环首。F407 发送缓冲应位于 DMA 可达的 SRAM，不能放进 CCM；本器件没有 D-cache，换到有数据缓存的器件还要另查一致性要求。

## 队列满了，别只藏起错误

容量是延迟预算，不是无限保险。115200、8N1 连续收字节时，256 字节只够承受约 `256 / 11520 = 22.22 ms` 的完全停止消费，实际要扣掉已有积压和服务抖动。长期处理速度低于到达速度，再大缓冲也会满。

字节协议里丢一个字节会破坏当前帧。除增加溢出计数，还应让解析器知道流发生了缺口，丢弃未完成消息并按协议重新同步。日志则可选择整条记录拒绝，避免输出半截数字误导排错。若采用丢旧策略，生产者去改消费者的 `tail` 就破坏了本例单写者条件，必须重做同步设计。

## 练习：这是满了还是空了

容量 8，`head=2`、`tail=UINT32_MAX-3u`。尚有几字节？再成功放两字节后能否放第三个？若现在 DMA 正在读其中四字节，能不能在启动 DMA 时直接把 tail 加四？

<details><summary>展开答案</summary>

按 32 位无符号距离计算得到 6。放两字节后距离为 8，第三个必须拒绝。DMA 启动不等于已经读完，不能提前释放四个槽；应保存本次在途长度，在正常完成路径里再推进 tail，并对取消或错误明确处理。数组下标仍通过各计数器的低三位得到。

</details>

## 适用范围与技术依据

本篇实际通过 PC GCC 6.3.0 C99 Debug 和 `-O2 -Werror -Wconversion` 的断言测试，包括空、满、顺序、计数回绕和一万字节调度模型。没有进行 ISR 并发或 DMA 真机验证。

- 标准语义核对 [WG14 N1570（C11 委员会草案）](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf) 第 6.2.5 段 9 的无符号模运算，以及第 5.1.2.4 段 25 的 C11 数据竞争规则。前者用于本篇 C99 算法；后者只用于说明多线程扩展边界，不给裸机 ISR 虚构标准线程语义。
- 已核读 [GCC：When is a Volatile Object Accessed?](https://gcc.gnu.org/onlinedocs/gcc/Volatiles.html)，尤其普通内存不与 volatile 自动有序的说明。
- 已核读 [ST PM0214 Rev 10](https://www.st.com/resource/en/programming_manual/dm00046982-stm32-cortexm4-mcus-and-mpus-programming-manual-stmicroelectronics.pdf) 的内存顺序/屏障章节，以及 [RM0090 Rev 22](https://www.st.com/resource/en/reference_manual/dm00031020-stm32f405415-stm32f407417-stm32f427437-and-stm32f429439-advanced-armbased-32bit-mcus-stmicroelectronics.pdf) 的系统架构与 CCM 可达性。屏障、互斥和 DMA 生命周期分别解决不同问题。
