# 量产固件的日志策略与日志泄露

开发板运行得好好的，接上现场设备后却每秒报告几千次通信错误。串口满了，日志缓冲满了，CPU 忙着把同一个错误转成文字。售后导出的记录里，还夹着客户输入的完整口令。

这不是一个“把 DEBUG 改成 INFO”就能收尾的问题。日志同时占用时间、存储和信息权限。一个量产方案应回答：记录什么、谁能看、最多花多少资源、出口坏了怎么办、保留多久。先继承 [3.1 串口与日志](/lessons/3-1) 的非阻塞与丢弃计数，再为产品增加策略，而不是换个更快的串口就结束。

## 先算资源账，不要先加缓冲

假设每条错误日志为 80 字节，一秒产生 2000 条：

```text
生产：80 × 2000 = 160000 字节/秒
UART 115200、8N1：每字节 10 位
理想有效输出上限：115200 / 10 = 11520 字节/秒
```

生产约为理想消费的 13.9 倍。4 KiB 缓冲只能吸收短暂突发，无法让长期入不敷出消失；格式化和中断开销还没算进去。若后台出口完全断开，连续生产更会迅速填满。

本轮实验不用板子：把输入设为“同一毫秒产生十次同类错误”，允许每个一秒窗口只输出三条，其余计入抑制计数。预期前三次被接纳，后七次被抑制；到 999 ms 仍不开放新预算，到 1000 ms 第一条重新被接纳。

## 把限流放在格式化之前

下面是配套 C99 主机实验中的核心策略。状态只由主循环使用，不宣称可被多个中断或线程无锁并发修改。

```c
#include <stdint.h>

typedef struct {
    uint32_t start;
    uint32_t sent;
    uint32_t suppressed;
} log_budget_t;

static int log_admit(log_budget_t *b, uint32_t now)
{
    if ((uint32_t)(now - b->start) >= 1000u) {
        b->start = now;
        b->sent = 0u;
    }
    if (b->sent == 3u) {
        if (b->suppressed != UINT32_MAX) ++b->suppressed;
        return 0;
    }
    ++b->sent;
    return 1;
}
```

让 `log_admit` 返回真之后才拼字符串，而不是先格式化 2000 次再丢弃 1997 次。由 `uint32_t` 差值比较经过时间，可以处理一次时基回绕；调用间隔不能跨越整整一圈还期待模型知道真实经过了多久。1 ms 的 32 位时基一圈约 49.7 天，应明确系统调度和长时间停机后的重置策略。

这里是简单的窗口预算，不是平滑的令牌桶。在窗口末尾和新窗口开头，短时间内可能连续通过两批消息；它也不保证每条消息同等延迟。若控制任务对突发更敏感，可按更小时间粒度、令牌补充或固定事件队列设计。日志抑制的计数应使用饱和或有明确回绕语义，不能无声变成“零次错误”。

仓库根目录运行：

```sh
cmake -S examples/notes/debug -B artifacts/course-completion/debug/build -G Ninja
cmake --build artifacts/course-completion/debug/build
./artifacts/course-completion/debug/build/debug_models.exe
```

其中预期包含：

```text
budget: burst=3 suppressed=7, boundary/wrap/saturation passed
```

这是已执行的主机断言测试，覆盖 999/1000 ms、无符号回绕和计数饱和；没有测量板上格式化耗时。

## 内容白名单比“出了事再打码”可靠

为每类事件规定字段，不默认接受“把整个对象输出”的接口。例如通信失败记录事件编号、接口编号、有限错误码、累计次数、固件版本，而不是整包原始业务数据。

| 内容 | 默认策略 |
|---|---|
| 私钥、密码、认证令牌、解锁材料 | 不进入日志缓冲，不依赖导出时再删除 |
| 原始用户数据、定位信息、设备唯一标识 | 按实际诊断必要性和授权最小化 |
| 事件编号、错误码、重试次数、版本 | 在经过字段审查后保留 |
| 原始栈、完整内存转储 | 开发期受控采集，量产默认不用 |

“只打印令牌前八位”也可能泄露可关联信息；“做一个不加密的哈希”也不自动匿名，低熵数据可以被枚举。最好的字段常常不是脱敏后的秘密，而是根本不需要那个秘密的事件描述。

完整 dump 可能包含之前留在栈上的凭据。它被复制到备份 RAM、外部 Flash 或售后文件后，原先的访问控制不一定还在。记录数量少不代表敏感度低。

## 外部文本有两类不同危险

第一类是把外部输入当格式串。不要写 `LOG(LOG_WARN, received_text)` 这样的调用。安全方向是固定格式串，参数作为数据；同时保证字符串有边界、合法终止，并符合日志层的支持范围。课程主线接口不应被悄悄假定支持所有格式扩展。

第二类即使用了固定 `"%s"` 也存在：外部字符串可能含换行、终端控制序列或分隔符，伪造出一条“系统认证成功”的日志。需要按出口编码转义或过滤控制字符，并限制长度。若诊断只需要“收到无效命令，长度 17”，就不要把原文重新输出。

两类问题分别对应格式串注入与日志内容注入，不要以为加了 `"%s"` 就完成了整个安全设计。任何字符串示例都应在输入验证之后使用，不把未验证内存当可靠字符串遍历。

## 级别、抑制与丢弃要各自计数

至少区分三件事：

1. **过滤**：因级别策略而不生成，例如正常产品不输出逐字节 DEBUG。
2. **抑制**：相同事件太频繁，被前置限流拒绝。本例的 suppressed 属于这一类。
3. **丢弃**：策略允许，但出口缓冲已满；这是主线 `log_dropped()` 所关心的资源问题。

每秒可发送一次汇总：“接口 1 本窗口超时 2000 次，抑制 1997 次”。汇总本身也要有预算，不能因为丢了一条日志再递归打印“又丢了一条”。关键错误可以有独立保留槽或小队列，避免被低级别噪声挤掉；但不能把每条错误都升成“必须无限等待”的特权。

若为了裁掉发布日志使用编译期开关，还要审计参数是否包含副作用。把必要动作写进 `LOG(..., read_sensor())`，可能让开发版正常、发布版因宏展开成空而不采样。应先完成业务动作，再记录结果。运行时关闭级别也不保证调用参数完全不求值。

## 日志出口坏了，业务还要继续

验收至少覆盖：接收器断开、串口长期忙、存储满、连续重复错误、输入含控制字符、系统反复复位。对每种情况规定最大 RAM、最大调用时间、持久化写入量和降级行为。

Flash 中长期日志要考虑擦写寿命与掉电一致性，采用有边界的轮转或配额；不要每个错误都立即擦写同一扇区。保留时长、导出权限、删除机制和工厂维护接口同样属于设计。日志通过 UART/RTT 暴露时，也不能因为没有联网就当成私密通道。

在 HardFault 中更不应依赖正常日志系统完成最后一次大输出。故障路径只保存经过验证的最小记录，恢复启动后再做有权限、有预算的回放。详见 [故障记录与回放](/notes/fault-persistence)。

### 练习：错误越多，系统越慢

一个模块每次认证失败打印完整输入和一条“日志已满”，随后阻塞等待缓冲空位。有人建议把缓冲从 1 KiB 改成 8 KiB。请给出至少四项比单纯扩容更重要的修改。

<details><summary>答案</summary>

不记录口令或完整认证输入，改为审查过的事件码与有限上下文；在格式化之前限流并汇总重复失败；缓冲满时有界失败且只累计丢弃，不递归记录“日志已满”；禁止业务关键路径等待接收者；设置读取授权与保留期限；测试无接收器和恶意控制字符。扩容只能延后满载，不能解决泄密、持续吞吐不足和无限等待。

## 适用范围与依据

本篇提供的是可验证的基础策略，不是完整的安全认证方案。C99 限流模型为单线程；实际 RTOS、ISR 和持久化后端需要各自的同步与时序验证。未进行实板时延、功耗或寿命测试。

- [WG14 N1256（C99 合并草案）](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1256.pdf)：6.2.5 第 9 段，无符号运算的模运算语义。
- [MITRE CWE-532](https://cwe.mitre.org/data/definitions/532.html)：敏感信息进入日志造成的泄露，Common Consequences 和 Potential Mitigations。
- [MITRE CWE-117](https://cwe.mitre.org/data/definitions/117.html)：日志注入、输出编码与输入验证。
- [MITRE CWE-134](https://cwe.mitre.org/data/definitions/134.html)：外部可控格式串与固定格式串的缓解措施。
