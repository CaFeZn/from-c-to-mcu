# 按键抖动与消抖

一次按键，计数器从 10 跳到 13；给程序加一句“延时 20 ms”，计数好像正常了，却又漏掉蜂鸣器响声期间的下一次按压。两次修改其实解决了不同问题：前者是触点与输入信号的多次变化，后者是程序长时间不再观察输入。

[4.1 主线](/lessons/4-1) 已经做过四状态按键对象。本篇不再复制整套 HAL 驱动，而是把“时间”和“这次采到的电平”作为函数参数，在电脑上重放相同输入，先证明算法做了什么，再去板子上验证输入是否符合假设。

## 把一次按压写成证据

假设按键按下接地、松开由上拉拉高。先把电平转换成逻辑量：低电平对应 down=1，高电平对应 down=0。下面不是测得的真实按键，而是人为规定的测试输入：

| 时刻 / ms | down | 情况 |
|---|---|---|
| 0 | 0 | 初始松开 |
| 1、3、6、10 | 1、0、1、0 | 按下期间反复变化 |
| 12 | 1 | 最后一次变为按下 |
| 31、32 | 1、1 | 检查确认边界 |
| 100、103、107 | 0、1、0 | 松开期间反复变化 |
| 126、127 | 0、0 | 检查松开确认边界 |

先预测：如果规则是“候选状态至少保持 20 ms 才替换已确认状态”，按下事件应出现在 **32 ms**，不是 21 ms；释放应出现在 **127 ms**，不是 120 ms。31 和 126 都还差 1 ms。把最后一次变化作为起点，才能重新开始确认。

真正的板上采样应规律地持续进行，例如目标约每 1 ms 一次。这里列出关键时间点是为了测试状态迁移，并不表示只在表里这些时刻看两眼，就能证明中间一直稳定。

## 一个可以独立编译的状态机核心

下面使用 C99，状态只属于对象；函数不读 GPIO，不调用延时，也不私自读取全局时钟。它报告按下与释放两种事件，调用者当场处理返回值。

~~~c
#include <stdint.h>

typedef enum {
    KEY_NONE = 0, KEY_PRESS = 1, KEY_RELEASE = 2
} key_event;

typedef struct {
    uint8_t stable_down;     /* 已确认状态 */
    uint8_t candidate_down;  /* 正在等待确认的状态 */
    uint32_t since_ms;       /* 候选状态首次被采到的时刻 */
} debounce;

static key_event debounce_step(debounce *d, uint8_t down,
                               uint32_t now_ms)
{
    down = down != 0u;
    if (down != d->candidate_down) {
        d->candidate_down = down;
        d->since_ms = now_ms;
    }
    if (d->candidate_down != d->stable_down &&
        (uint32_t)(now_ms - d->since_ms) >= UINT32_C(20)) {
        d->stable_down = d->candidate_down;
        return d->stable_down ? KEY_PRESS : KEY_RELEASE;
    }
    return KEY_NONE;
}
~~~

初始化使用 `debounce d = {0u, 0u, 0u};`，约定系统起始的已确认状态为松开。若开机时已经按住，第一次采到按下后，经过确认时间会产生一次按下事件。若产品要求“开机按住不算，先松开再允许触发”，就要显式增加启动等待释放状态，不能默默改变初值而不说明交互行为。

可跟做的最小断言如下；把它接在前面的核心后面即可作为完整主机程序。仓库的 `examples/notes/gpio/test.c` 还覆盖完整抖动时间线、双对象、释放抖动和计数回绕。

~~~c
#include <assert.h>
#include <stdio.h>

int main(void)
{
    debounce d = {0u, 0u, 0u};
    assert(debounce_step(&d, 1u, 12u) == KEY_NONE);
    assert(debounce_step(&d, 1u, 31u) == KEY_NONE);
    assert(debounce_step(&d, 1u, 32u) == KEY_PRESS);
    assert(debounce_step(&d, 1u, 90u) == KEY_NONE);
    assert(debounce_step(&d, 0u, 100u) == KEY_NONE);
    assert(debounce_step(&d, 1u, 103u) == KEY_NONE);
    assert(debounce_step(&d, 0u, 107u) == KEY_NONE);
    assert(debounce_step(&d, 0u, 127u) == KEY_RELEASE);
    puts("press=32 ms, release=127 ms: OK");
    return 0;
}
~~~

32 ms 之后持续按住不会再报告，因为候选状态和已确认状态已经相同。松开也必须确认：否则释放抖动中的一次短暂高电平会重新“武装”计数器，随后的低电平又被误算成下一次按下。

在 F407 工程中，主循环读一次 `HAL_GPIO_ReadPin(KEY_GPIO_Port, KEY_Pin)`，把是否等于 `GPIO_PIN_RESET` 转成 down，再把 `HAL_GetTick()` 传入函数。只在返回 KEY_PRESS 时翻转 LED；不要同时保留主线旧驱动和本篇驱动，让同一个按键被两套算法计数。

## “等 20 ms”到底保证了什么

这里的 20 ms 是教学参数，不是所有机械开关的上界。实际需要覆盖器件抖动、容差、老化、环境噪声，又不能长到把合法的快速点按过滤掉。TI 的设计说明也要求按开关的抖动特性选时间常数，而不是把一个数当成器件规格。

软件确认的严格含义是：**最近一段时间里，没有采到与候选状态相反的样本**。两次采样之间仍可能发生短脉冲。若主循环先忙了 50 ms，算法没有时间机器，不能恢复这段时间的所有按压。按键服务的最大间隔，应与希望识别的最短有效按压一起设计；日志、Flash 操作、阻塞通信都要算进去。

同理，第一次读到低以后延时 20 ms，再读低，只能证明两个时刻是低，并不证明中间连续为低。它可能对某块板“看起来能用”，但不是本文采用的稳定时间判据。

另一种常用方案是在固定周期采样，连续 N 个相同样本才确认。实现简单，N 和周期共同决定延迟；注意 N 个样本的首尾时间跨度是 (N−1) 个周期。积分计数方案能抵抗零星毛刺，但历史样本会影响阈值，语义又不同。选方案前先写清“什么算有效输入”，不要只比较代码行数。

## 回绕与对象边界

无符号差值按模 2 的 32 次方计算：起点为 0xFFFFFFF0，now 为 4，差是 20，所以这次跨零点确认仍正确。前提是关注的真实间隔没有跨越完整的 32 位周期，时钟单调按毫秒前进，服务不会停摆到丢失一整圈计数。休眠中停止的时基也不是现实时间。

同一个对象应由一个执行上下文更新。不要在中断和主循环里同时调用它；volatile 不能解决状态更新交错。若使用 EXTI 唤醒，可在短中断里记录线索，让周期任务完成确认；中断边沿只是原始输入变化，不是已经消抖的“用户按了一次”。主线 pending 单标志还能合并尚未取走的事件，而本篇返回事件若不立即处理就会丢失，需要积压时应设计计数或队列。

## 硬件 RC 能帮什么忙

若输入来自长线，软件不该承担全部抗干扰责任。可先用限流电阻、电容与具有明确阈值的施密特输入滤波，再由软件判断按下/长按。一个便于计算的松开充电模型是：100 kΩ 上拉、100 nF 对地电容，时间常数 RC=10 ms。

从 0 V 向 VDD 充电有 `V(t)=VDD×(1−exp(−t/RC))`。若仅为演算，假设上阈值为 0.7VDD，则达到它约需 1.20RC，即 12 ms。**这个 0.7 不是宣布所有施密特门都用相同阈值**；实际必须代入选定器件的最坏阈值、R/C 容差和漏电流。

按键直接短接电容会有瞬时放电电流，可以在开关支路加串联电阻并重新计算低电平残值及放电时间。慢斜坡应接到适合慢输入的施密特器件，普通 CMOS 输入可能在阈值区耗电或反复翻转。加了电容也不等于 ESD、过压和长线浪涌保护都已完成。

## 练习：按了两下，为什么只报一下

已确认按下后，按键从 100 ms 松开到 110 ms，随后再次按住；确认窗口仍为 20 ms，采样足够密。第二次按下会产生新的 KEY_PRESS 吗？如果需求要求识别这种快速双击，应只把按下确认时间改短吗？

<details>
<summary>展开答案</summary>

不会。释放候选只保持了 10 ms，没有被确认，stable_down 始终为 1；再次按住只是回到已确认状态。若要识别，应一起审查允许的最短按压、最短释放、真实抖动与采样间隔。按下和松开可以采用不同确认窗口，但缩短释放窗口也会更容易把释放抖动当成一次真正松开。不能只改按下时间并期待双击自动恢复。
