# CRC32与查表实现

PC 工具对 `"123456789"` 报出 `CBF43926`，你把同样九个字节交给 F407 的 CRC 外设，却对不上。为了凑够最后一个 32 位字，又补了三个零，结果仍然不对。这种故障不一定是算错了除法，更常见的是双方没有在计算同一种 CRC，甚至没有计算同一串字节。

本篇先在电脑上让逐位实现与查表实现一致，再明确 F407 硬件的适配条件。CRC32 用在哪里、覆盖什么字段，仍由协议决定；它不是给现有 CRC16 函数换一个返回类型就完成升级。

## 用一个向量固定目标

选定 **CRC-32/ISO-HDLC**，也就是 gzip 使用的那组常见 CRC32 参数：

| 参数 | 值 |
|---|---|
| width / poly | `32 / 0x04C11DB7` |
| init | `0xFFFFFFFF` |
| refin / refout | `true / true` |
| xorout | `0xFFFFFFFF` |
| 九个 ASCII 字节 `"123456789"` | `0xCBF43926` |
| 空输入 | `0x00000000` |

检查向量不包含字符串终止字节，也不是把字符当十六进制数 `12 34 56 78 09`。名字只写“CRC32”仍然不够；例如 CRC-32/MPEG-2 使用相同的常规多项式，却不反射、没有最终异或，九字节检查值是 `0376E6E7`。

独立例子同时提供逐位更新、查表更新和 F407 适配的软件模型。准备好 C99 编译器、CMake、Ninja 后，从仓库根目录运行：

```bash
cmake -S examples/notes/serial/crc -B artifacts/course-completion/serial/crc/build -G Ninja -DCMAKE_BUILD_TYPE=Debug
cmake --build artifacts/course-completion/serial/crc/build
ctest --test-dir artifacts/course-completion/serial/crc/build -V
```

其中几行预期输出如下；这里的 `software model` 很重要，它不意味着运行过真实外设。

```text
CRC32 bitwise=CBF43926 table=CBF43926 empty=00000000
F407 software model word 31323334: raw=A695C4AA
F407 adapted software model: CBF43926 (9 bytes, no padding)
PASS: 258 lengths, 33411 splits, 1024 byte/state pairs, 104 bit flips
```

只有一个检查向量通过还不够。测试还比较长度零到 257 的确定性字节序列、全部切分位置以及所有 256 个单字节与四种初始状态的组合；短输入、整字边界和尾部残留都参与比较。逐位版保留作容易审查的参照，不因为查表版能运行就删掉它。

## 先认清右移的那一个状态

`0x04C11DB7` 是常规、最高位优先表示，省略了 `x^32` 项。对本篇反射算法，采用最低位优先、右移的等价实现时，使用它的 32 位反转表示 `0xEDB88320`。它们描述相应方向的同一个 CRC 生成多项式，不是随手可互换的两个常数。

每个输入字节先异或到状态的低八位，再连续执行八次：最低位为一就右移并异或 `0xEDB88320`，否则只右移。用 `uint32_t` 保存状态，右移补零。这里从一开始就用反射方向维护状态，最终**不要再反转一次结果**；处理完所有数据后仅执行 `state ^ 0xFFFFFFFF`。

`init` 是新消息开始前的状态，`xorout` 是结束处理，两者即使数值相同也不是同一件事。配套的两个 `update` 函数都收取并返回尚未最终异或的原始状态：

```c
uint32_t state = CRC32_ISO_INIT;
state = crc32_iso_update_table(state, first, first_len, table);
state = crc32_iso_update_table(state, second, second_len, table);
uint32_t result = crc32_iso_finish(state);
```

此片段放在已包含示例头文件的函数内，两个缓冲区及长度由调用者提供，表必须先初始化。它演示的是接口约定，不是独立程序。

RFC 1952 附录的接口采用另一种便利约定：每次调用内部先将上次输出与 `FFFFFFFF` 异或，还原为内部状态，结束时再异或一次；调用者最初传零。这是按位取反，不是把最高位与最低位交换的位序反转。两种接口都能正确分块，但不能把 RFC 接口的“初值零”直接搬进本例的原始状态接口，也不能在每块之间直接传已经最终异或的值。

## 查表到底省去了什么

八步右移中，低八位决定哪些位置需要异或多项式。把这 256 种可能的八步结果提前存好，就能将每字节的更新写成一次索引和一次异或：

```c
unsigned index = (unsigned)((state ^ byte) & UINT32_C(0xFF));
state = (state >> 8) ^ table[index];
```

表不是“某个字节单独算出的最终 CRC”。生成第 `i` 项时，从 `i` 开始做八次右移更新，不套用整条消息的初值和最终异或：

```c
for (unsigned i = 0u; i < 256u; ++i) {
    uint32_t value = (uint32_t)i;
    for (unsigned bit = 0u; bit < 8u; ++bit) {
        value = (value & UINT32_C(1)) != 0u
              ? (value >> 1) ^ UINT32_C(0xEDB88320) : value >> 1;
    }
    table[i] = value;
}
```

于是 `table[0]=0`、`table[1]=0x77073096`。高 24 位右移八位，低八位引发的多项式作用则由表补上。这种分解成立的原因是 CRC 位运算对异或具有线性关系，而不是“CRC 值可以相加”。

表占 256×4，即 1024 字节。例子让调用者拥有并初始化表，没有在中断和主循环中共享一个未保护的懒初始化标志。板上可把核对过的表生成为只读常量，或在启动阶段生成一次；放在局部数组时也要计入栈预算。查表减少了逐位分支，但实际速度还受存储位置、Flash 等待和编译优化影响，本篇没有给出板上性能倍数。

## F407的CRC外设为什么不能直接替换

本轮读取了 RM0090 Rev 22 第四章。对这里讨论的 STM32F407，固定多项式确实是 `0x04C11DB7`，但还有这些约束：

- `CRC_DR` 每次处理整个 32 位字，不是自动识别字节数组；寄存器要求 32 位访问。
- `CRC_CR.RESET` 将状态复位为 `FFFFFFFF`。向 `CRC_DR` 写普通数值会继续计算，不是任意设置初值。
- `CRC_CR` 只有 RESET 控制位，其余位保留；没有较新 STM32 CRC 单元上的输入、输出反射配置。
- 读回的是硬件计算状态，不会替本篇 ISO-HDLC 算法完成末尾的 `xorout`。

因此“用了 Ethernet 多项式”不等于“直接给出 gzip CRC32”。按最高位优先、左移处理的整字软件模型，向初始状态喂入数值 `31323334` 得到 `A695C4AA`；这里明确说的是一个 32 位**数值**及其原始结果，不是对九字节字符串计算出的最终 CRC。

配套的适配模型按以下顺序把两套状态对应起来：

1. 对四个顺序字节 `b0 b1 b2 b3`，显式组成 `w=b0|(b1<<8)|(b2<<16)|(b3<<24)`，各字节先转换为 `uint32_t`。将 `reverse32(w)` 喂给最高位优先的整字模型。
2. 全部完整四字节组处理完后，把模型状态反转成软件右移版所用的原始状态。
3. 剩余零到三个字节由逐位软件更新接着处理，最后统一异或 `FFFFFFFF`。

例如 `31 32 33 34` 先组成 `34333231`，再反转成 `8C4CCC2C`。不能把“每字节反转”和“整个字反转”混用，也不要直接将任意字节指针强转成 `uint32_t *`：那会额外引入对齐、对象访问和主机字节序问题。

九字节测试用两个完整字组加一个软件尾字节，不补零。补零会改变消息，只有协议明确把填充纳入覆盖范围时才可以这样做。空输入则直接按软件参数得到零。该模型只验证算法映射；真正驱动还必须处理 CRC 时钟、外设独占、复位时机及整字寄存器访问，再上板与软件结果对照。不同 STM32 系列要重新查手册，不能照搬这些限制或适配代码。

## 升级协议前做两项检查

第一，CRC32 不提供身份认证，也不替代长度、序号和重传策略。将两个校验字节改成四个，会改变帧总长、CRC 字段位置和解析器状态，发送接收两端必须一起修改。短帧是否值得增加开销，应根据实际错误模型、帧长及检错要求决定。

第二，缓存必须在整个计算期间保持一致。DMA 正在改写输入时，即使 CRC 算法完全正确，也可能得到一个不存在于任意完整帧中的混合结果。同理，两个调用者交替复位、喂数给同一个硬件 CRC 外设，也不能各自得到独立结果。外设不是普通局部变量，须保护整段事务。

## 练习：九字节怎样喂

把输入分成前四字节和后五字节。查表实现要初始化几次、最终异或几次？若改用 F407 硬件加软件尾部，最后一个字节可以填三个零再写寄存器吗？

<details>
<summary>展开答案</summary>

按本例原始状态接口，只在第一块前初始化一次，跨两块保留状态，结束时最终异或一次，结果为 `CBF43926`。分块位置不能改变消息的 CRC。

硬件适配应处理两个完整四字节组，再把硬件状态转成软件反射状态，继续处理剩下一个字节。不能为满足访问宽度而擅自补零；补零后的输入有十二字节，已经是另一条消息。若不准备维护可靠的适配层，全部使用已核对的软件实现更容易验证。

## 核对依据与验证边界

适用范围是 C99、八位字节与固定宽度整数的 CRC-32/ISO-HDLC 软件实现，以及 STM32F407 整字计算的教学模型。PC 已真实运行断言测试，核心和测试源码通过 ARM GCC 的 Cortex-M4 编译；未链接板级固件、未操作真实 CRC 寄存器，也未测量执行时间。

- [RFC 1952](https://www.rfc-editor.org/rfc/rfc1952.txt)，May 1996，§2.3.1 的 CRC32 字段及 §8 示例代码：已读取反射表生成、更新公式与调用约定。
- [CRC RevEng：CRC-32/ISO-HDLC](https://reveng.sourceforge.io/crc-catalogue/17plus.htm#crc.cat.crc-32-iso-hdlc) 及同页 MPEG-2 条目：已读取完整参数与检查向量，用于区分同多项式的不同算法；不将目录转引的标准算作本轮已读资料。
- [ST RM0090](https://www.st.com/resource/en/reference_manual/dm00031020-stm32f405415-stm32f407417-stm32f427437-and-stm32f429439-advanced-armbased-32bit-mcus-stmicroelectronics.pdf)，Rev 22，§4.1–4.4，印刷页 113–115：通过仓库的可信文本缓存核对固定多项式、整字访问、状态复位和控制位。
