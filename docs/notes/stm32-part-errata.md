# STM32 型号命名与勘误表

两块板子都印着“STM32F407”，为什么一个工程能放进 Flash，另一个却在链接或下载时越界？为什么同样的初始化逻辑，换一批芯片后还要重新检查勘误？第一件事是把三个信息分开：开发板商品名、芯片完整订货号、芯片的硅修订版本。它们回答不同问题，不能用其中一个替代另外两个。

本篇拿完整订货号 `STM32F407VGT6` 做查表练习，再检查一个很容易被删掉的代码动作：打开 GPIO 时钟后，为什么还要读一次 RCC 寄存器。这里没有读取真实板子的 ID，所有 ID 数值都明确作为手工演算输入。

## 按该系列的数据手册拆型号

先打开 DS8626 的 Ordering information，而不是凭网上一张“STM32 通用命名图”推断所有系列。在本篇核对的 Rev 12 中，可以把示例拆成：

| 字段 | 本例 | 在这份手册中的含义 |
|---|---|---|
| 器件家族 | STM32 | Arm 32 位微控制器 |
| 产品类型 | F | 通用产品类型标识 |
| 子系列 | 407 | 该子系列，带相应连接、摄像头、以太网能力 |
| 引脚数 | V | 100 引脚 |
| Flash 容量 | G | 1024 Kbytes |
| 封装 | T | LQFP |
| 温度等级 | 6 | 工业温度范围，负 40 至正 85 摄氏度 |

所以它不是“V 表示电压、G 表示速度”。同一份表中 E 表示 512 Kbytes，Z 表示 144 引脚；后缀 TR 表示卷带包装，不能把它看成一个新的 CPU 型号。不同系列的代码映射可能不同，应回到对应数据手册，不能把本例的每一列当作跨所有 STM32 的永恒规则。

再做一遍数量检查：1024 KiB 等于 `0x100000` 字节。如果本例的 1 MiB 主 Flash 从 `0x08000000` 开始，连续容量区间的最后一个字节就是 `0x080FFFFF`。若实际使用 E 容量版本，却仍拿 G 版本的 Flash 长度配置链接脚本，就可能让链接器允许使用芯片实际没有的后半段。能生成 ELF，并不表示实际器件能存下它。

另一方面，容量不等于可直接把整块空间交给应用。启动加载程序、配置参数、升级镜像和擦除扇区布局都可能占用部分空间。正确做法是先确认器件总容量，再按工程分区分配，而不是看到“一兆”就把应用长度硬填成一兆。

## 型号没有告诉你的事情

完整型号能缩小候选范围，但仍不能替代引脚表、电气规格和原理图。100 引脚封装没有自动拥有其他封装引出的全部信号；同一个管脚也可能被晶振、调试口或其他外设占用。外设模块存在，不等于你的板子已经引出并连接它，更不等于无需外部器件就能使用。

温度等级也不是电源电压或最高结温的替代品。最高频率要结合供电、稳压模式、Flash 等待周期等条件核对；“5 V tolerant”必须逐引脚、逐模式查条件，不能推广到模拟输入、所有 GPIO 或掉电状态。手册首页的最高指标是检索入口，不是所有工作条件下的统一保证。

还要把 RAM 数量拆开。F407 常见的 192 KiB 包含 128 KiB 普通 SRAM 和 64 KiB CCM 数据 RAM，不能据此给 DMA 分配任意 192 KiB 连续缓冲区；另有备份 SRAM，也有自己的供电与访问条件。这个边界会直接影响链接脚本和外设数据传输。

## 用实际修订号进入勘误表

订货号中的末尾 `6` 是温度等级，不是芯片修订号。F407 的调试识别寄存器 `DBGMCU_IDCODE` 位于 `0xE0042000`；RM0090 规定只能按 32 位读取，低 12 位是 DEV_ID，高 16 位是 REV_ID，中间有保留位。板级固件可通过匹配器件的官方头文件读取：

```c
#include <stdint.h>
#include "stm32f407xx.h"

void read_chip_identity(uint32_t *device, uint32_t *revision)
{
    uint32_t id = DBGMCU->IDCODE;
    *device = id & UINT32_C(0x0fff);
    *revision = (id >> 16) & UINT32_C(0xffff);
}
```

这是集成片段：调用者必须传入两个有效可写地址，在目标 MCU 上执行；不要拿 PC 编译后的程序解引用这个设备地址。给定一次假设读取值 `0x10000413`，演算结果是 DEV_ID `0x413`、REV_ID `0x1000`。后者在本篇核对的适用器件表中对应修订 A。

这里仍有两个不能跳过的步骤。DEV_ID `0x413` 对应的是一组器件，不会唯一告诉你封装、Flash 容量和完整订单号；某些 REV_ID 还可能覆盖多个封装标记修订。应合并芯片丝印、采购资料与调试读取结果，再核对 ES0182 的适用型号和修订列。如果证据不足，就记录“不确定”并采用覆盖相关修订的保守处理，不要猜一个最方便的版本。

## 一个会影响第一条外设写入的勘误

假设程序紧接着执行：设置 RCC 的 GPIOA 时钟使能位，然后访问 GPIOA。ES0182 的“Delay after an RCC peripheral clock enabling”指出，写入时钟使能位与外设实际可用之间可能存在延迟。对 AHB 外设，描述为最多涉及两个 AHB 周期的延迟；APB 情况又与分频有关。

这解释了为什么 ST HAL 的 `__HAL_RCC_GPIOA_CLK_ENABLE()` 不只有一条置位操作，还紧接着读回对应 RCC 使能位。读回用于该器件已规定的使能延迟处理，不是为了获得一个应用业务结果。手写初始化时，同样应采用手册给出的有效规避方案，而不是为了让代码看起来短就删掉它。

下面是便于审查的等价意图片段，假设这里没有其他执行者同时修改 RCC：

```c
RCC->AHB1ENR |= RCC_AHB1ENR_GPIOAEN;
(void)RCC->AHB1ENR;
/* Only now configure GPIOA registers. */
```

预期检查不是“延时后灯一定亮”，而是生成代码中保留了时钟使能访问及随后读回，且第一次 GPIO 配置发生在其后。灯能否亮还取决于模式、引脚和接线。本组核对的是官方 HAL 实现与勘误要求，没有上板复现首次写入丢失的故障。

不要把此例变成“所有外设初始化前随便插两条 NOP”。不同总线的等待条件不同，另一个芯片也可能有不同规避办法。更不能把本例的读回方法直接推广到读清除状态寄存器，后者的读操作可能有副作用。勘误的触发条件、受影响修订、规避办法必须成套阅读。

## 把核查结果写成可追溯记录

一条实用记录应包含：完整型号和封装、REV_ID 原始值、资料编号及修订版、使用到的外设、触发条件是否可能出现、采用哪项规避办法、代码位置和回归测试。未使用某个外设，可以说明本次不适用；没有复现某故障，却不能自动判定“不受影响”。

数据手册说明器件配置和电气边界，参考手册解释寄存器及工作机制，编程手册说明内核，勘误则补充实际限制和文档错误。更新 HAL、换芯片批次、改变时钟或启用低功耗，都可能改变此前“不触发”的条件，应重新审查对应条目，而不是只在买板时读一遍。

## 练习：两个“6”是不是一回事

某板完整型号为 `STM32F407VGT6`，调试读取 `DBGMCU_IDCODE = 0x10000413`。同事说“型号最后是 6，所以只看 Revision 6 列”。请指出错误，并说明此时能确认与不能确认的信息。

<details><summary>展开核对答案</summary>

型号末尾 6 对应本系列温度等级，不是硅修订号。给定读取值的高 16 位是 `0x1000`，按适用器件表应核对修订 A；低 12 位 `0x413` 只能识别相应器件组。完整型号支持确认 100 引脚 LQFP 和 G 容量等订货信息，但 IDCODE 本身不能独立证明全部信息。还需要核对真实丝印与采购记录，并保存使用的 ES0182 版本和实际适用条目。
